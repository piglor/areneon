## Commands

Clone with `--recurse-submodules`. Toolchain: Node 24 + pnpm 10, uv (Python 3.12). GNU Make ≥ 3.82.

```bash

make ts             # pnpm lint && pnpm typecheck && pnpm test (vitest, coverage) + check-rules.ts
make python         # ruff check, ruff format --check, mypy, pytest (coverage)
make contracts      # contract schemas fit their ADR-008 profile; generated TS types and pydantic models have no drift
make contracts-update  # regenerate the TS types and pydantic models after a schema change (commit the result)
make guards         # team guards (PokePaste text, JSON data_class) + production licence allowlist
make db-up db-test  # rules store on a fresh local Postgres 18 (127.0.0.1:55432): roles, migrations, tests
make db-down        # remove that container
make db-bootstrap-test  # bootstrap.sql on its own throwaway Postgres: refuses missing/blank passwords, sends none outside its CREATE ROLE
make importer-e2e   # build the importer image, import the recorded releases into a fresh db-up DB twice (commit, then no-op); db-up again before db-test
RULES_DB_PORT=55433 RULES_DB_COMPOSE_PROJECT=areneon-e2e make importer-e2e  # the same beside the default DB (db-up/db-test/db-down honour both too)
```

Single tests. The coverage thresholds apply per file and fail on a subset, so run without coverage:

```bash
pnpm exec vitest run packages/showdown-bridge/test/runner.test.ts        # one file
pnpm exec vitest run packages/showdown-bridge/test/request.test.ts -t "forced switch"
uv run pytest tests/scripts/test_check_licenses.py --no-cov               # add ::test_name for one
```

Re-capture golden fixtures and team verdicts (only after a deliberate Showdown pin bump or engine-facing change; review the diff):

```bash
node packages/showdown-bridge/scripts/capture-golden.ts
node packages/showdown-bridge/scripts/capture-choices.ts   # golden choice corpus; also after an enumerator change
node packages/showdown-bridge/scripts/capture-samples.ts   # shared contract sample corpus; also after a contract change
```

TypeScript runs directly under Node's type stripping (`.ts` imports, `erasableSyntaxOnly`): no build step, no parameter properties, enums or namespaces.

## Architecture

**Polyglot monorepo** (ADR-002): TypeScript in `packages/*` (pnpm workspace), Python in `scripts/` and `tests/` today plus the generated-contracts package `packages/schema/python` (a uv workspace member next to its schemas; `services/`, `ml/` later), Rust in `crates/` once the first crate lands. `packages/schema` holds the JSON Schema contracts: the rules records (`rules/`, ADR-007) and the cross-language contracts (`contracts/v<N>/`, ADR-008), from which the TS types in `generated/ts/` and the pydantic models in `python/areneon_contracts/models/` (the `areneon-contracts` uv workspace package, `scripts/contract_models.py`) are generated and checked in; serde follows with the first crate. On Python, `areneon_contracts.contracts` validates with python-jsonschema, then parses into the model (`parse`), and hashes with RFC 8785 (`jcs`, `request_hash`). `fixtures/contracts/` is the shared sample corpus (valid and invalid instances of every contract, plus `reader-invalid/` ones that pass the schema and that a TS reader such as `readEpisode` refuses, plus their JCS digests in `hashes.json`): Ajv and python-jsonschema must classify it identically and every language must reproduce the digests. A contract's `$id` (`urn:areneon:schema:<contracts|engine>:v<N>:<name>`) declares its profile, and `src/profile.ts` enforces it as a keyword whitelist: closed objects, bounded integers, local `$ref`s, `kind`-tagged `oneOf`; `engine` schemas, which copy the pinned engine's wire shapes, also allow scalar type unions and get their own Ajv instance (`src/ajv.ts`). `Provenance` gained the optional `collection` as a minor change within v1 (ADR-008 §3): a reader older than it rejects such an Episode, so the generated types and models ship with the schema change. `make contracts` fails on a profile violation or on generated types that differ from a fresh run.

**The reference engine is upstream Showdown, unmodified** (ADR-003). `vendor/pokemon-showdown` is a git submodule pinned to an exact SHA and built with `make showdown`. Areneon never decides legality itself: it asks the engine (`TeamValidator`, `side.choose`) and stops on unknowns. `docs/showdown-champions-gaps.md` lists what the engine does for Champions and what is unverified. It is generated from the gap ledger records in `rules/gaps/` by `scripts/gaps-doc.ts`; edit the records, never the doc (a test compares them). Gap edits move `rules_snapshot_hash` but never `format_rules_hash`.

**`packages/showdown-bridge`** is the only code that talks to the engine:
- `engine.ts`: `loadEngine()` loads `dist/sim` via `createRequire` behind narrow local interfaces (`ShowdownSim`). It refuses a missing build or a checkout whose HEAD is not `PINNED_SHOWDOWN_COMMIT`. A test checks that constant against the submodule gitlink, so a pin bump changes both.
- `rules.ts` / `rules-load.ts` (ADR-007): Areneon's own rules are JSON records in `rules/`, never code constants. That covers which formats it runs and the forbidden engine rules (e.g. `forceopenteamsheets`, because CTS needs Bo1 with sheets declined). They are validated by `packages/schema/rules/v1` (Ajv) and fail closed. `jcs()` (RFC 8785) gives `rules_snapshot_hash` (provenance) and `format_rules_hash` (replay identity). `packages/showdown-bridge/scripts/rules-hash.ts` and everything it pulls in (`rules.ts`, `request-identity.ts`, `canonical-json.ts`, `engine.ts`) import only Node built-ins, because CI reruns old commits' copy of it from bare archives. `canonical-json.ts` (`canonicalJson`, `jcs`) imports nothing at all, so the engine-free observation builder can use it too (ADR-008 §5); a test enforces that.
- `formats.ts`: `resolveFormat` checks a format against the rules snapshot and the pinned engine. It returns the version manifest `{showdown_commit, format_id, regulation, ruleset_hash, format_rules_hash}` plus the embedded format rules record that every fixture (and, later, every episode) carries.
- `scripts/check-rules.ts` (in `make ts` and CI; policy in `rules-channel.ts` / `rules-history.ts`): validates every record and checks `rules/channels/`, which must hold exactly one file per channel in the channel schema's enum. Each channel must name a snapshot built for the current pin, and `seq` rises by 1 per change. A pin bump must also move the channel (CONTRIBUTING).
- `request.ts` / `request-identity.ts`: decode one `|request|` into a phase (`preview`/`move`/`forceSwitch`/`wait`). The body is first validated against the closed engine-mirror schema `packages/schema/contracts/v1/engine-request.schema.json` (the pinned `sim/side.ts` request types, minus fields no supported format has), so only an engine-shaped request is hashed; a pin bump that changes the shape edits that schema. Request identity is `request_seq` + `request_hash`, a SHA-256 of canonical JSON that excludes `rqid`. `rqid` exists only on the Showdown server path, never on the in-process sim.
- `runner.ts`: `runBattle` runs a seeded in-process BattleStream battle (runtime A1) on copies of the teams (the caller's sets stay as brought) and records `team_hashes` (each seat's set array as brought). Teams are validated first. Each `Actor` sees only its own player's requests. Each request carries its `legal` choice set, judged by a `CloneJudge` on the stream's own battle. The CloneJudge's verdicts on pending candidates go to `hidden_verdicts`, never to an actor. If the actor submits a pending candidate and the engine refuses it as `[Unavailable choice]`, the updated request that follows is a new request (`request_seq` + 1). Any other engine `|error|` aborts; nothing is retried. `|t:|` wall-clock lines are dropped so the same commit, seed and choices reproduce `omniscient_log`. That log holds both sides' hidden information: an evaluation artifact, never actor input. `replayActor` replays recorded choices. The optional `players` option sets each seat's `name` and `avatar` on the `|player|` lines (default `p1`/`p2`, no avatar) so a recorded server battle can be reproduced; `validatePlayers` refuses unsafe names (blank, edge whitespace, no letter or digit, over 18 UTF-16 units, `|` `,` `[` `]`, control characters, double spaces, or two names alike) and avatars that are not 1-32 letters, digits or `-`.
- `teams.ts`: `importPaste` / `exportPaste` wrap the engine's `Teams.import` / `Teams.export`. Showdown silently skips unknown lines (an `SPs:` line zeroes the Stat Points; they belong in `EVs:`), so `importPaste` rejects a paste unless each Pokémon's lines all reappear in that Pokémon's re-export: only the engine's canonical form passes. `validateTeam` returns the pinned `TeamValidator`'s messages verbatim.
- `choices.ts` / `choice-judge.ts` (ADR-006): `enumerateCandidates` turns the player's own request into every engine-distinct joint choice, in a fixed canonical order. It is pure and fails closed on any request field it does not know. Candidates whose legality depends on `maybeTrapped` / `maybeDisabled` / `maybeLocked` are `pending`. `legalChoiceSet` (its `LegalChoiceSet` type is generated from `packages/schema/contracts/v1/legal-choice-set.schema.json`, imported as `@areneon/schema/types/v1/…`) has a `ChoiceJudge` check every non-pending one; it never asks about pending ones, so no hidden-information verdict reaches a policy. `CloneJudge` judges on `Battle.fromJSON(battle.toJSON())`, never on the live battle, and refuses unless the battle is at the request's `request_hash`. `runBattle` builds one per request (A1); the corpus and tests use it too. `Battle.fromJSON` rebuilds `activeRequest` from the Pokémon, so the clone carries the live request over: after an `[Unavailable choice]` the live one was edited in place. `judgeSubmission` (the SubmissionJudge) classifies the engine's `|error|` after a submission. If the engine refuses a non-pending candidate, that is an `EnumeratorDefectError`. On A2 (`judge: null`), the engine judges only at submission.
- `observation.ts` (ADR-008 §5): `buildObservation` is the only constructor of a `PreviewObservation` / `BattleObservation`. Its battle input is a branded `PlayerChannel` (one player's own stream up to the request being answered), plus that player's own `PrivateTeamSpec`, the version manifest and an optional `DecisionContext`; the omniscient log is a distinct `OmniscientLog` type and cannot be passed. The module imports no engine, runner or Node built-in (a test enforces it), so it runs wherever WebCrypto does; it hashes through an injected `Sha256` port (`nodeSha256` in `player-channel.ts`, `webSha256` on WebCrypto) to exactly `decodeRequest`'s `request_hash`. `player-channel.ts` is the A1 adapter: `playerChannel` validates a `PlayerChannelLog` and every `|request|` in it before branding, and `recordedChannel` cuts a runner record's channel at a `request_seq`. `test/observation.test.ts` holds the ADR-008 privacy tests: golden parsing, the canary test (no opponent secret line or request stats in any observation, with a negative control), schema probes and the type test.
- `episode.ts` / `episode-io.ts` (ADR-008 §3, §5): an `Episode` is one player's recorded battle: their own channel (stored once), their own team, their decisions (a `deadline` record required on A2, absent on A1), provenance, `data_class` and matching `rights`. `episodeFromRecord` writes one from an A1 record, given both teams: it classifies by BOTH (`private` if either is; `rightsFor` follows), checks each team's `teamHash` (JCS of the set array, so it ignores the label) against `record.team_hashes`, and refuses a `synthetic` label whose hash is not in the given `known_synthetic` set; `readEpisode` reads a copy back by its `schema_version` (an unknown version is refused), checks the channel is the player's own and its ending matches `result`, rebuilds the Team Preview observation and every decision's (so the team must be the player's own, in request order), and on A2 requires each decision's deadline record; every refusal is an `EpisodeError`. `playerChannel` refuses `|split|` lines and the opponent's exact HP, the SECRET halves a player never sees. `episodeFromRecord` also takes an optional `collection` record, which must carry the battle's own `record.seed`. An Episode's optional `provenance.collection` (ADR-009 §4: `league`, `evaluation` or `sparring`, a `kind`-tagged `oneOf`) names the run, the seed (`sodium,<hex>`, null on A2), the evaluation `sealed` flag or the opponent policy; `readEpisode` also refuses a seed on A2 or none on A1, which the schema cannot say. `episodeHash` is SHA-256 of the JCS bytes through the `Sha256` port. `answersRequest` is the stale-invalidation check for a `Recommendation`. A `league` or `evaluation` `provenance.collection` carries a required `opponent_team_data_class`, which `episodeFromRecord` sets from the opponent's `StampedTeam` (never the caller's); `readEpisode` requires the Episode's `data_class` to equal the higher of the own team's class and that field (so a stored Episode relabelled synthetic is refused), and a `sparring` Episode to be `private`.
- `training-loader.ts` (ADR-009 §4): `loadTrainingSet` is the one way an Episode becomes training data, and it fails closed. Each Episode goes through `readEpisode` (with `known_synthetic`), then only a `synthetic`, `cc0-synthetic` Episode of collection kind `league` is accepted: a missing collection record, `evaluation`, `sparring` and private data are refused, as is any Episode whose `episodeHash` an `EvaluationRunManifest` lists, and a repeated Episode or manifest. Every refusal is a `TrainingLoaderError`; none is skipped. It writes a stream of `TrainingExample` lines (`episode_hash`, `observation`, `choice`; no provenance, so no seed or opponent id) in Episode-hash order, and a `TrainingSet` (the Episode hashes, the checked manifests' JCS hashes, `data_class`, line count, `stream_sha256`). `readEvaluationRunManifest` / `readTrainingSet` enforce the sorted-and-unique hash lists the profile cannot (corpus samples under `reader-invalid/`). A relabelled copy of an evaluation Episode has another hash, so only the storage partition catches it. `evaluationRunManifest` is the evaluation job's writer (hash-only, sorted and unique); `decisionObservations` (`episode-io.ts`) rebuilds each decision's observation for the examples. On the Python side `areneon_contracts.training.read_stream` reads a stream only with a manifest that matches its digest, line count, Episode hashes and class, validating every line.
- `server-lines.ts` (ADR-005 §5): the A2 server-path filter, an allowlist of the sim's line kinds. `serverOnlyLine` is the stateless check: `>room` headers, plain-text notices and `||text`, `|request|null`, nameless `|player|<slot>|`, and the known server kinds (joins/leaves/renames, chat and PMs, `|raw|`/`|html|`/`|uhtml|`, timer and timestamp lines, room and session state, `|sentchoice|`). `stripServerLines(stream)` returns `{ lines, dropped }`: it keeps sim kinds (`|error|` included), places the engine's `otsrequest` prompt and clear and the sim's `|player|` lines by their position relative to `|gametype|` and `|start`, drops the server's auto-tie `|-hint|` and its inactivity and forfeit `|-message|` lines by exact text, and reports lines of unknown kind in `dropped`. The adapter filters the stream from its first line every time, never a suffix. The channel equals the A1 one up to server-layer `|error|` refusals, which only A2 produces; `|player|` equality is left to the A1/A2 equality test. It imports nothing (a test enforces it), and the golden channels pass through unchanged.
- `choice-corpus.ts`: the golden choice corpus (ADR-006 rule 7). Each case is a seeded battle log that reaches one situation (`CASE_KINDS`: preview, target types, Mega, forced switches, trapping, Imprison, a fainted active, a locked move), plus every candidate with the engine's verdict. Verdicts on pending candidates are hidden state, kept for evaluation. CI replays each log (it never re-runs the search in `scripts/capture-choices.ts`) and compares the result. `missedActions` is the brute-force oracle: it judges every syntactic choice string and fails on any engine-accepted action the enumerator did not offer.
- `team-class.ts` (#817): a class is proven by source, never by a caller's label. `teamHash`, `classOfSets` / `stampTeam` (`synthetic` only for a hash in the known synthetic set, `private` otherwise, `private-data/` teams included), `higherClass`, and `battleClass`, whose branded result is the only value `recordedChannel` takes as a channel's `data_class` (`syntheticFixtureHashes` in `golden.ts` is today's set: the committed fixtures' teams). The set is trusted caller input and the brand is compile-time only; a loader reading the committed synthetic-team manifest or generator output is to replace it behind the same `SyntheticTeamHashes` type. `stampTeam` returns a compile-time-branded `StampedTeam`, the only team type `episodeFromRecord` accepts (`runBattle` still takes plain sets: a battle is not an Episode, and `team_hashes` binds the teams to the record). `readEpisode` checks its own team against the required `known_synthetic` and the opponent's class through `collection.opponent_team_data_class`; an Episode without a collection record has no opponent class to check. An A2 stream has no opponent team to hash, so its `data_class` is the caller's label and defaults to `private`.
- `engine-data.ts` (ADR-010 §3): `exportEngineData` reads the species, move, item, ability, type (with the engine's own type chart), status, weather and terrain vocabularies and their numeric attributes from the pinned engine's data for the format's mod, each list sorted by id (the position is the vocabulary index), into the `EngineData` contract (`packages/schema/contracts/v1/engine-data.schema.json`). It refuses any value of a shape it does not know; a standard species' nonstandard base species or ability is kept so no reference dangles. `readEngineData` adds what the profile cannot say (sorted unique ids, references that resolve). `engineDataHash` is SHA-256 of the JCS bytes: the engine-data hash of the encoder version, so a pin bump yields a new one. The golden table and `engine-data.summary.json` (hash, counts) sit in `fixtures/showdown/<format>/`; a test re-exports and compares them. `scripts/export-engine-data.ts` rewrites them.
- `actor-rule.ts`: `actorRule`, the shared A1/A2 actor rule (ADR-005 §1). It plays the first non-pending candidate in canonical order, else the first pending one, and refuses only an empty set (`NoCandidateError`). It is pure and imports only types, so the A2 bot client reuses it.
- `random-legal.ts`: the random-legal baseline (evaluation protocol pool B). `randomLegal(legal, state)` picks uniformly among the non-pending candidates, else among the pending ones (the `actorRule` order of preference), refuses an empty set with `NoCandidateError`, and returns the next state of its explicit Mulberry32 PRNG (a uint32 seed; integer-only, so stable across Node versions; never `Math.random`). `randomLegalActor(seed)` is an A1 `Actor` (it checks the seed at construction); the A2 choice step would thread `randomLegal`'s state through its own battle state, since `session.ts` calls `actorRule` with no per-seat state. Protocol D9 seeding: the caller reduces the HMAC for the seat and policy label to a uint32 (`parseInt(h.slice(0, 8), 16)`; never `Number()` or `>>> 0` on a raw 128-bit value); about 10^5 streams collide in the 32-bit space, every stream is the same 2^32 cycle at another offset, and the label must carry seat and policy id.
- `team-inventory.ts` (#775): the owner-team feature inventory, run as `scripts/team-inventory.ts`. It reads `private-data/teams/*.txt`, runs `importPaste` and `validateTeam`, lists species, items, abilities, moves and Mega use, and flags features that a gap record names (advisory name matches; the report also lists every gap as `format_wide_gaps`). It writes only `private-data/reports/team-inventory.json` and prints counts and the path, never team content; it refuses any path without a `private-data` segment. See `packages/showdown-bridge/README.md`.
- `golden.ts`: the golden battle (each side plays `firstLegal`, which applies `actorRule` to the request's legal choice set), team-fixture and verdict builders shared by the tests and the capture script.

**Fixtures** live only under `fixtures/` (CC0, synthetic or sanitized, with provenance). `fixtures/showdown/<format>/` holds the golden request fixtures plus `battle.summary.json` (the log hash and choices), `channels/p1.json` and `p2.json` (each player's own stream of the golden battle as a `PlayerChannelLog`, the only battle input an observation may be built from), and `choices/` the choice corpus. `fixtures/teams/<format>/` holds synthetic PokePaste teams, a `manifest.json` (provenance, expected verdict and reason) and `verdicts.json` (the validator's log). CI re-captures and compares the request fixtures, summary and verdicts, so engine behaviour drift fails the build. Pastes keep Showdown's trailing spaces (`.editorconfig`, `.gitattributes`).

**Repo guards** (`scripts/`, Python): `check_no_pokepaste.py` rejects PokePaste-shaped files outside `fixtures/` (exact-path exemptions in `.pokepaste-guard-allow`). `check_data_class.py` (ADR-008) rejects committed JSON/JSONL with `"data_class": "private"` anywhere, and, outside `fixtures/`, any team-shaped object (`species` + `moves` + `evs`) without `"data_class": "synthetic"` at the document root; and (ADR-009 rule T2) any sealed evaluation Episode (an object with `"kind": "evaluation"` and `"sealed": true`) everywhere, `fixtures/` included, except the exact paths in `SEALED_MARKERS` (the shared corpus's synthetic markers: `valid/evaluation-sealed.json`, and the negative sample `invalid/collection-evaluation-no-seed.json`, under `fixtures/contracts/v1/episode/`) whose root says `"data_class": "synthetic"`; a new marker is an edit to that constant, under code-owner review. The guard checks structure and path, not content: a real Episode relabelled synthetic and placed at an allowlisted path is caught only by review and the O13 hash scan (evaluation-protocol §7), and stringified JSON inside a string is not inspected. A marker added by another PR means rebasing onto this constant (the pinning test fails until `SEALED_MARKERS` is edited); both run in `make team-guard`. `check_licenses.py` fails closed on any production dependency licence outside the allowlist, for pnpm and, through `python_licences.py`, for the shipped Python packages' whole lockfile closure (an SPDX `License-Expression`, else an explicitly mapped trove classifier, else refused). `licences-selftest.sh` (`make licences-selftest`, CI only: it needs network) injects an AGPL dependency into a scratch copy, once for pnpm and once for Python, and requires `make licences` there to fail each time. `.github/CODEOWNERS` puts the gates under code-owner review.

**Rules store** (ADR-007, #704): published rules snapshots and channel history live in PostgreSQL 18, append-only. `db/bootstrap.sql` (a superuser, once; role passwords from the environment) creates `rules_owner` (NOLOGIN, owns the tables), `rules_migrator` (runs dbmate), `importer` (INSERT/SELECT) and `areneon_reader` (SELECT) and the `rules` schema. `db/migrations/` (dbmate, pinned image) defines `rules_snapshot` and `rules_release` with named CHECKs (hash = sha256(body), columns agree with the payload, the channel enum equals `channel.schema.json`'s) and triggers that refuse UPDATE, DELETE and TRUNCATE. Publishing (ADR-007 §6): `.github/workflows/rules-publish.yml` runs on main after a rules change in two jobs. `plan` (read-only, no environment) re-runs the channel check on the merged commit, builds the artifacts not yet released (`src/rules-publish.ts`: the commit's snapshot `rules-snapshot-<hash>.json`, and each channel's current file as `rules-channel-<channel>-<commit that last changed it>.json`, validated by `packages/schema/rules/v1/channel-artifact.schema.json`) with a sha256 manifest as a workflow artifact, and outputs `publish=true` only if there are any, so a push with nothing new ends without asking for approval. `publish` (protected environment `rules-dev`) then checks the downloaded files against the manifest and against the plan made again (`verifyPlan`), writes the release set to `verified/` (skipping entries released meanwhile), and attests (build provenance) and releases only that verified set, exactly those bytes, snapshots first. A Release counts only if it is published and carries its file; runs are grouped per commit, so none is dropped. A channel must name this commit's snapshot or a released one; an older snapshot that was never released (before this workflow, or a cancelled run) is refused: re-run that commit's workflow, or revert the records in a PR. `packages/rules-store` tests it against a real Postgres, so the root `pnpm test` skips it: `make db-up db-test` locally, the `database` job in CI. `make db-bootstrap-test` (also in that job) runs `db/bootstrap.sql` against its own throwaway Postgres that logs every statement: it refuses missing and blank (empty or whitespace-only) passwords, which psql checks on the client, and requires each password in the server log only in its own `CREATE ROLE`. Never point these at the Coolify database.

**Rules importer** (`packages/rules-importer`, ADR-007 §6, #768), the last step of the rules pipeline (publish, then import): `GitHubReleaseSource` lists the non-draft `rules-snapshot-*` / `rules-channel-*` Releases through `gh` (an injected `CommandRunner` whose children see only an env allowlist), resolves each tag to its commit, downloads each asset into a private temp dir and keeps only the bytes `GhAttestationVerifier` returns. It skips a snapshot asset whose hash (in its name) is already stored; `planImport` then plans a snapshot a channel names by reference (`stored-snapshot`), and `applyImport` refuses the plan unless that row is stored with hash = sha256(body) (summary status `referenced`). A skipped asset is never used, so tampering with the Release of a stored snapshot is caught only by GitHub's reported digest; the stored row stays authoritative. `runImportCommand` (entry `src/cli.ts`) reads `DATABASE_URL` (never logged; a URL that sets a timeout or `options` is refused) and `RULES_IMPORT_{STATEMENT,LOCK,IDLE_IN_TRANSACTION}_TIMEOUT_MS`, requires the `importer` role, then `planImport` and `applyImport`, and prints one JSON line `{ok, stale, steps}`; exit 0 ok, 1 refused (the whole plan rolled back), 2 configuration. A `stale` channel step (seq at or below the stored maximum, no stored row at that seq) is skipped, never written, reported and counted in `stale`, and does not fail the run; a stored row at that seq with another hash or source commit is a fork and is refused. The planner stays fail-closed on a channel naming a snapshot that is neither released nor stored. `gh` needs `GH_TOKEN`. Its Dockerfile's default target is the production image (node, gh, CA bundle, `/app`); the `e2e` target alone adds a stand-in `gh` replaying `fixtures/rules-releases/`, and `FakeAttestationVerifier` lives only in the `./testing` export.

**CI** (`.github/workflows/ci.yml`) runs `python`, `typescript` (submodule checkout + `make showdown`), `database` (rules store on Postgres 18), `importer-image` (`make importer-e2e`), `team-guard`, `licences`, `gitleaks`, `osv` and `dco`. The aggregate `ci` job is the required check on `main`, together with CodeQL.

A2 (ADR-005) is a bot client on a local Showdown server, for local human sparring against the bot; `packages/bot-client/README.md` is the sparring guide (start, connect, challenge, stop). In `packages/bot-client`, `ProtocolReader` (`src/protocol.ts`) numbers each room's requests per channel: a room's `|init|battle` (sent on every join, before the replayed log, which holds no requests) resets its `request_seq`, open request and re-send identity, so the request re-sent after a rejoin is request 1 of the new channel, as `buildObservation` numbers it.
