## Commands

Clone with `--recurse-submodules`. Toolchain: Node 24 + pnpm 10, uv (Python 3.12). GNU Make ≥ 3.82.

```bash
make setup          # build pinned Showdown, uv sync, pnpm install, pre-commit install
make check          # every offline CI gate: python + ts + guards
make showdown       # rebuild vendor/pokemon-showdown (needed before any TS test)
make ts             # pnpm lint && pnpm typecheck && pnpm test (vitest, coverage) + check-rules.ts
make python         # ruff check, ruff format --check, mypy, pytest (coverage)
make contracts      # contract schemas fit their ADR-008 profile; generated TS types and pydantic models have no drift
make contracts-update  # regenerate the TS types and pydantic models after a schema change (commit the result)
make guards         # team guards (PokePaste text, JSON data_class) + production licence allowlist
make db-up db-test  # rules store on a fresh local Postgres 18 (127.0.0.1:55432): roles, migrations, tests
make db-down        # remove that container
scripts/check-evaluation-store.sh --store DIR --owner USER  # owner only: read-only isolation checks of the evaluation store (docs/runbooks/evaluation-store.md)
make db-bootstrap-test  # bootstrap.sql on its own throwaway Postgres: refuses missing/blank passwords, sends none outside its CREATE ROLE
make importer-e2e   # build the importer image, import the recorded releases into a fresh db-up DB twice (commit, then no-op); db-up again before db-test
RULES_DB_PORT=55433 RULES_DB_COMPOSE_PROJECT=areneon-e2e make importer-e2e  # the same beside the default DB (db-up/db-test/db-down honour both too)
```

Single tests. The coverage thresholds apply per file and fail on a subset, so run without coverage:

```bash
pnpm exec vitest run packages/showdown-bridge/test/runner.test.ts        # one file
pnpm exec vitest run packages/showdown-bridge/test/request.test.ts -t "forced switch"
uv run pytest tests/scripts/test_check_licenses.py --no-cov               # add ::test_name for one
```

Re-capture golden fixtures and team verdicts (only after a deliberate Showdown pin bump or engine-facing change; review the diff):

```bash
node packages/showdown-bridge/scripts/capture-golden.ts
node packages/showdown-bridge/scripts/capture-choices.ts   # golden choice corpus; also after an enumerator change
node packages/showdown-bridge/scripts/capture-samples.ts   # shared contract sample corpus; also after a contract change
node packages/showdown-bridge/scripts/export-team-vocabulary.ts   # golden team vocabulary (about 10 s); also after a vocabulary-export change; run before capture-samples.ts, which reads it

```

TypeScript runs directly under Node's type stripping (`.ts` imports, `erasableSyntaxOnly`): no build step, no parameter properties, enums or namespaces.

## Architecture

**Polyglot monorepo** (ADR-002): TypeScript in `packages/*` (pnpm workspace), Python in `scripts/` and `tests/` today plus the generated-contracts package `packages/schema/python` (a uv workspace member next to its schemas; `ml/` for the policy worker in `ml/areneon_ml/worker` (the networks follow), `services/` later), Rust in `crates/` once the first crate lands. `packages/schema` holds the JSON Schema contracts: the rules records (`rules/`, ADR-007) and the cross-language contracts (`contracts/v<N>/`, ADR-008), from which the TS types in `generated/ts/` and the pydantic models in `python/areneon_contracts/models/` (the `areneon-contracts` uv workspace package, `scripts/contract_models.py`) are generated and checked in; serde follows with the first crate. On Python, `areneon_contracts.contracts` validates with python-jsonschema, then parses into the model (`parse`), and hashes with RFC 8785 (`jcs`, `request_hash`). `fixtures/contracts/` is the shared sample corpus (valid and invalid instances of every contract, plus `reader-invalid/` ones that pass the schema and that a TS reader such as `readEpisode` refuses, plus their JCS digests in `hashes.json`): Ajv and python-jsonschema must classify it identically and every language must reproduce the digests. A contract's `$id` (`urn:areneon:schema:<contracts|engine>:v<N>:<name>`) declares its profile, and `src/profile.ts` enforces it as a keyword whitelist: closed objects, bounded integers, local `$ref`s, `kind`-tagged `oneOf`; `engine` schemas, which copy the pinned engine's wire shapes, also allow scalar type unions and get their own Ajv instance (`src/ajv.ts`). `Provenance` gained the optional `collection` as a minor change within v1 (ADR-008 §3): a reader older than it rejects such an Episode, so the generated types and models ship with the schema change. `make contracts` fails on a profile violation or on generated types that differ from a fresh run.

**The reference engine is upstream Showdown, unmodified** (ADR-003). `vendor/pokemon-showdown` is a git submodule pinned to an exact SHA and built with `make showdown`. Areneon never decides legality itself: it asks the engine (`TeamValidator`, `side.choose`) and stops on unknowns. `docs/showdown-champions-gaps.md` lists what the engine does for Champions and what is unverified. It is generated from the gap ledger records in `rules/gaps/` by `scripts/gaps-doc.ts`; edit the records, never the doc (a test compares them). Gap edits move `rules_snapshot_hash` but never `format_rules_hash`.

**`packages/showdown-bridge`** is the only code that talks to the engine:
- `engine.ts`: `loadEngine()` loads `dist/sim` via `createRequire` behind narrow local interfaces (`ShowdownSim`). It refuses a missing build or a checkout whose HEAD is not `PINNED_SHOWDOWN_COMMIT`. A test checks that constant against the submodule gitlink, so a pin bump changes both.
- `rules.ts` / `rules-load.ts` (ADR-007): Areneon's own rules are JSON records in `rules/`, never code constants. That covers which formats it runs and the forbidden engine rules (e.g. `forceopenteamsheets`, because CTS needs Bo1 with sheets declined). They are validated by `packages/schema/rules/v1` (Ajv) and fail closed. `jcs()` (RFC 8785) gives `rules_snapshot_hash` (provenance) and `format_rules_hash` (replay identity). `packages/showdown-bridge/scripts/rules-hash.ts` and everything it pulls in (`rules.ts`, `request-identity.ts`, `canonical-json.ts`, `engine.ts`) import only Node built-ins, because CI reruns old commits' copy of it from bare archives. `canonical-json.ts` (`canonicalJson`, `jcs`) imports nothing at all, so the engine-free observation builder can use it too (ADR-008 §5); a test enforces that.
- `formats.ts`: `resolveFormat` checks a format against the rules snapshot and the pinned engine. It returns the version manifest `{showdown_commit, format_id, regulation, ruleset_hash, format_rules_hash}` plus the embedded format rules record that every fixture (and, later, every episode) carries.
- `scripts/check-rules.ts` (in `make ts` and CI; policy in `rules-channel.ts` / `rules-history.ts`): validates every record and checks `rules/channels/`, which must hold exactly one file per channel in the channel schema's enum. Each channel must name a snapshot built for the current pin, and `seq` rises by 1 per change. A pin bump must also move the channel (CONTRIBUTING).
- `request.ts` / `request-identity.ts`: decode one `|request|` into a phase (`preview`/`move`/`forceSwitch`/`wait`). The body is first validated against the closed engine-mirror schema `packages/schema/contracts/v1/engine-request.schema.json` (the pinned `sim/side.ts` request types, minus fields no supported format has), so only an engine-shaped request is hashed; a pin bump that changes the shape edits that schema. Request identity is `request_seq` + `request_hash`, a SHA-256 of canonical JSON that excludes `rqid`. `rqid` exists only on the Showdown server path, never on the in-process sim.
- `runner.ts`: `runBattle` runs a seeded in-process BattleStream battle (runtime A1) on copies of the teams (the caller's sets stay as brought) and records `team_hashes` (each seat's set array as brought). Teams are validated first. Each `Actor` sees only its own player's requests. Each request carries its `legal` choice set, judged by a `CloneJudge` on the stream's own battle. The CloneJudge's verdicts on pending candidates go to `hidden_verdicts`, never to an actor. If the actor submits a pending candidate and the engine refuses it as `[Unavailable choice]`, the updated request that follows is a new request (`request_seq` + 1). Any other engine `|error|` aborts; nothing is retried. `|t:|` wall-clock lines are dropped so the same commit, seed and choices reproduce `omniscient_log`. That log holds both sides' hidden information: an evaluation artifact, never actor input. `replayActor` replays recorded choices. The optional `players` option sets each seat's `name` and `avatar` on the `|player|` lines (default `p1`/`p2`, no avatar) so a recorded server battle can be reproduced; `validatePlayers` refuses unsafe names (blank, edge whitespace, no letter or digit, over 18 UTF-16 units, `|` `,` `[` `]`, control characters, double spaces, or two names alike) and avatars that are not 1-32 letters, digits or `-`.
- `teams.ts`: `importPaste` / `exportPaste` wrap the engine's `Teams.import` / `Teams.export`. Showdown silently skips unknown lines (an `SPs:` line zeroes the Stat Points; they belong in `EVs:`), so `importPaste` rejects a paste unless each Pokémon's lines all reappear in that Pokémon's re-export: only the engine's canonical form passes. `validateTeam` returns the pinned `TeamValidator`'s messages verbatim.
- `choices.ts` / `choice-judge.ts` (ADR-006): `enumerateCandidates` turns the player's own request into every engine-distinct joint choice, in a fixed canonical order. It is pure and fails closed on any request field it does not know. Candidates whose legality depends on `maybeTrapped` / `maybeDisabled` / `maybeLocked` are `pending`. `legalChoiceSet` (its `LegalChoiceSet` type is generated from `packages/schema/contracts/v1/legal-choice-set.schema.json`, imported as `@areneon/schema/types/v1/…`) has a `ChoiceJudge` check every non-pending one; it never asks about pending ones, so no hidden-information verdict reaches a policy. `CloneJudge` judges on `Battle.fromJSON(battle.toJSON())`, never on the live battle, and refuses unless the battle is at the request's `request_hash`. `runBattle` builds one per request (A1); the corpus and tests use it too. `Battle.fromJSON` rebuilds `activeRequest` from the Pokémon, so the clone carries the live request over: after an `[Unavailable choice]` the live one was edited in place. `judgeSubmission` (the SubmissionJudge) classifies the engine's `|error|` after a submission. If the engine refuses a non-pending candidate, that is an `EnumeratorDefectError`. On A2 (`judge: null`), the engine judges only at submission.
- `observation.ts` (ADR-008 §5): `buildObservation` is the only constructor of a `PreviewObservation` / `BattleObservation`. Its battle input is a branded `PlayerChannel` (one player's own stream up to the request being answered), plus that player's own `PrivateTeamSpec`, the version manifest and an optional `DecisionContext`; the omniscient log is a distinct `OmniscientLog` type and cannot be passed. The module imports no engine, runner or Node built-in (a test enforces it), so it runs wherever WebCrypto does; it hashes through an injected `Sha256` port (`nodeSha256` in `player-channel.ts`, `webSha256` on WebCrypto) to exactly `decodeRequest`'s `request_hash`. `player-channel.ts` is the A1 adapter: `playerChannel` validates a `PlayerChannelLog` and every `|request|` in it before branding, and `recordedChannel` cuts a runner record's channel at a `request_seq`. `test/observation.test.ts` holds the ADR-008 privacy tests: golden parsing, the canary test (no opponent secret line or request stats in any observation, with a negative control), schema probes and the type test.
- `episode.ts` / `episode-io.ts` (ADR-008 §3, §5): an `Episode` is one player's recorded battle: their own channel (stored once), their own team, their decisions (a `deadline` record required on A2, absent on A1), provenance, `data_class` and matching `rights`. `episodeFromRecord` writes one from an A1 record, given both teams: it classifies by BOTH (`private` if either is; `rightsFor` follows), checks each team's `teamHash` (JCS of the set array, so it ignores the label) against `record.team_hashes`, and refuses a `synthetic` label whose hash is not in the given `known_synthetic` set; `readEpisode` reads a copy back by its `schema_version` (an unknown version is refused), checks the channel is the player's own and its ending matches `result`, rebuilds the Team Preview observation and every decision's (so the team must be the player's own, in request order), and on A2 requires each decision's deadline record; every refusal is an `EpisodeError`. `playerChannel` refuses `|split|` lines and the opponent's exact HP, the SECRET halves a player never sees. `episodeFromRecord` also takes an optional `collection` record, which must carry the battle's own `record.seed`. An Episode's optional `provenance.collection` (ADR-009 §4: `league`, `evaluation` or `sparring`, a `kind`-tagged `oneOf`) names the run, the seed (`sodium,<hex>`, null on A2), the evaluation `sealed` flag or the opponent policy; `readEpisode` also refuses a seed on A2 or none on A1, which the schema cannot say. `episodeHash` is SHA-256 of the JCS bytes through the `Sha256` port. `answersRequest` is the stale-invalidation check for a `Recommendation`. A `league` or `evaluation` `provenance.collection` carries a required `opponent_team_data_class`, which `episodeFromRecord` sets from the opponent's `StampedTeam` (never the caller's); `readEpisode` requires the Episode's `data_class` to equal the higher of the own team's class and that field (so a stored Episode relabelled synthetic is refused), and a `sparring` Episode to be `private`.
- `training-loader.ts` (ADR-009 §4): `loadTrainingSet` is the one way an Episode becomes training data, and it fails closed. Each Episode goes through `readEpisode` (with `known_synthetic`), then only a `synthetic`, `cc0-synthetic` Episode of collection kind `league` is accepted: a missing collection record, `evaluation`, `sparring` and private data are refused, as is any Episode whose `episodeHash` an `EvaluationRunManifest` lists, and a repeated Episode or manifest. Every refusal is a `TrainingLoaderError`; none is skipped. It writes a stream of `TrainingExample` lines (`episode_hash`, `observation`, `choice`; no provenance, so no seed or opponent id) in Episode-hash order, and a `TrainingSet` (the Episode hashes, the checked manifests' JCS hashes, `data_class`, line count, `stream_sha256`). `readEvaluationRunManifest` / `readTrainingSet` enforce the sorted-and-unique hash lists the profile cannot (corpus samples under `reader-invalid/`). A relabelled copy of an evaluation Episode has another hash, so only the storage partition catches it. `evaluationRunManifest` is the evaluation job's writer (hash-only, sorted and unique); `decisionObservations` (`episode-io.ts`) rebuilds each decision's observation for the examples. On the Python side `areneon_contracts.training.read_stream` reads a stream only with a manifest that matches its digest, line count, Episode hashes and class, validating every line.
- `server-lines.ts` (ADR-005 §5): the A2 server-path filter, an allowlist of the sim's line kinds. `serverOnlyLine` is the stateless check: `>room` headers, plain-text notices and `||text`, `|request|null`, nameless `|player|<slot>|`, and the known server kinds (joins/leaves/renames, chat and PMs, `|raw|`/`|html|`/`|uhtml|`, timer and timestamp lines, room and session state, `|sentchoice|`). `stripServerLines(stream)` returns `{ lines, dropped }`: it keeps sim kinds (`|error|` included), places the engine's `otsrequest` prompt and clear and the sim's `|player|` lines by their position relative to `|gametype|` and `|start`, drops the server's auto-tie `|-hint|` and its inactivity and forfeit `|-message|` lines by exact text, and reports lines of unknown kind in `dropped`. The adapter filters the stream from its first line every time, never a suffix. The channel equals the A1 one up to server-layer `|error|` refusals, which only A2 produces; `|player|` equality is left to the A1/A2 equality test. It imports nothing (a test enforces it), and the golden channels pass through unchanged.
- `choice-corpus.ts`: the golden choice corpus (ADR-006 rule 7). Each case is a seeded battle log that reaches one situation (`CASE_KINDS`: preview, target types, Mega, forced switches, trapping, Imprison, a fainted active, a locked move), plus every candidate with the engine's verdict. Verdicts on pending candidates are hidden state, kept for evaluation. CI replays each log (it never re-runs the search in `scripts/capture-choices.ts`) and compares the result. `missedActions` is the brute-force oracle: it judges every syntactic choice string and fails on any engine-accepted action the enumerator did not offer.
- `team-class.ts` (#817): a class is proven by source, never by a caller's label. `teamHash`, `classOfSets` / `stampTeam` (`synthetic` only for a hash in the known synthetic set, `private` otherwise, `private-data/` teams included), `higherClass`, and `battleClass`, whose branded result is the only value `recordedChannel` takes as a channel's `data_class` (`syntheticFixtureHashes` in `golden.ts` is today's set: the committed fixtures' teams). The set is trusted caller input and the brand is compile-time only; a loader reading the committed synthetic-team manifest or generator output is to replace it behind the same `SyntheticTeamHashes` type. `stampTeam` returns a compile-time-branded `StampedTeam`, the only team type `episodeFromRecord` accepts (`runBattle` still takes plain sets: a battle is not an Episode, and `team_hashes` binds the teams to the record). `readEpisode` checks its own team against the required `known_synthetic` and the opponent's class through `collection.opponent_team_data_class`; an Episode without a collection record has no opponent class to check. An A2 stream has no opponent team to hash, so its `data_class` is the caller's label and defaults to `private`.
- `engine-data.ts` (ADR-010 §3): `exportEngineData` reads the species, move, item, ability, type (with the engine's own type chart), status, weather and terrain vocabularies and their numeric attributes from the pinned engine's data for the format's mod, each list sorted by id (the position is the vocabulary index), into the `EngineData` contract (`packages/schema/contracts/v1/engine-data.schema.json`). It refuses any value of a shape it does not know; the vocabularies hold the engine's standard entries plus, so no reference dangles, every base species a standard forme names and every ability a standard species lists even if the engine marks them nonstandard (eight at this pin: cramorant, eiscue, floette, meloetta, minior, ogerpon, terapagos, Aura Guard). Out of v1 scope (a change needs schema_version 2, the contract being closed): natures, volatile conditions, learnsets, evos, requiredItem, move effects, species height and gender. The table is derived from the pinned Showdown data files (MIT, not CC0; `NOTICE-engine-data.txt` beside it keeps the upstream notice). `readEngineData` adds what the profile cannot say (sorted unique ids, references that resolve). `engineDataHash` is SHA-256 of the JCS bytes: the engine-data hash of the encoder version, so a pin bump yields a new one. The golden table and `engine-data.summary.json` (hash, counts) sit in `fixtures/showdown/<format>/`; a test re-exports and compares them. `scripts/export-engine-data.ts` rewrites them.
- `team-vocabulary.ts` (ADR-013 §2, #859): `exportTeamVocabulary(engine, format, table?)` is what the team generator may draw from, read from the pinned engine and built on the `exportEngineData` table (it names that table by `engine_data_hash` and its ids resolve in it). It adds the roster the validator accepts, each roster species' abilities and move pool, the natures, the items the format does not ban, and the rule-table values (`adjustLevel`, `evLimit`, Item Clause, team sizes, from the resolved rule table; an unset one is refused, never defaulted). No game rule is written by hand: a species, ability, move, nature or item is in the vocabulary exactly when the pinned `TeamValidator` takes a probe set with it (one Stat Point and a neutral nature, so the "0 Stat Points" check stays quiet) or `checkItem` does not ban it. IVs, the per-stat draw maximum and item weights are `TeamGeneratorConfig` fields, not here. `teamVocabularyHash` (SHA-256 of the JCS bytes) is the `vocabulary_hash` the team manifests carry; `readTeamVocabulary` adds sorted-and-unique ids and, given the table, that every id resolves. The golden `team-vocabulary.json` and `.summary.json` sit beside the engine-data table (MIT-derived, same `NOTICE`); a test re-exports and compares byte for byte (about 10 s), `scripts/export-team-vocabulary.ts` rewrites them.
- `team-records.ts` (ADR-013 §4, #859): the identities and readers of the team records (`packages/schema/contracts/v1/team-{vocabulary,record,label-set,generator-config,dataset-manifest,snapshot-manifest}.schema.json`; all integers-only, no `number`). `canonicalTeamHash(sets)` is SHA-256 of the JCS bytes of the sets sorted by species id (ties by each set's JCS bytes): the same for every permutation, equal to the positional `teamHash` only for the canonical order. `recordHash`, `shardLogicalHash`, `logicalSnapshotHash` (writer-independent) and `snapshotHash` (one physical publication) follow ADR-013 §4. `readTeamRecord(engine, value, labelSet?)` adds the engine round trip (the paste must be the engine's own export of its sets), both team hashes recomputed and the labels' order; `readTeamLabelSet`, `readTeamGeneratorConfig`, `readTeamDatasetManifest` and `readTeamSnapshotManifest` add what the profile cannot say (sorted and unique lists, sums, tiling cell ranges, the recomputed logical hash). A `data_class` of `synthetic` is a constant of every record and manifest. The generator and the Parquet shard reader are later slices (#816, ADR-013 d1).
- `actor-rule.ts`: `actorRule`, the shared A1/A2 actor rule (ADR-005 §1). It plays the first non-pending candidate in canonical order, else the first pending one, and refuses only an empty set (`NoCandidateError`). It is pure and imports only types, so the A2 bot client reuses it.
- `random-legal.ts`: the random-legal baseline (evaluation protocol pool B). `randomLegal(legal, state)` picks uniformly among the non-pending candidates, else among the pending ones (the `actorRule` order of preference), refuses an empty set with `NoCandidateError`, and returns the next state of its explicit Mulberry32 PRNG (a uint32 seed; integer-only, so stable across Node versions; never `Math.random`). `randomLegalActor(seed)` is an A1 `Actor` (it checks the seed at construction); the A2 choice step would thread `randomLegal`'s state through its own battle state, since `session.ts` calls `actorRule` with no per-seat state. Protocol D9 seeding: the caller reduces the HMAC for the seat and policy label to a uint32 (`parseInt(h.slice(0, 8), 16)`; never `Number()` or `>>> 0` on a raw 128-bit value); about 10^5 streams collide in the 32-bit space, every stream is the same 2^32 cycle at another offset, and the label must carry seat and policy id.
- `private-team-source.ts` / `team-inventory.ts` (#775, ADR-014 section 11): the owner-team feature inventory, run as `scripts/team-inventory.ts`. Teams come through the `PrivateTeamSource` port (an async iterable of `{name, paste}`; no file system, network or crypto assumed). `PasteDirectorySource` is the one adapter here: it reads `private-data/teams/*.txt` and refuses any path without a `private-data` segment. The inventory runs `importPaste` and `validateTeam`, lists species, items, abilities, moves and Mega use, and flags features that a gap record names (advisory name matches; the detail also lists every gap as `format_wide_gaps`). It writes no file. It refuses unless stdin, stdout and stderr are terminals (and `CLAUDECODE` / `AI_AGENT` are unset; accident prevention, ADR-014 X6) and `/dev/tty` opens, before reading any team; stdout gets counts and per-gap match counts only, and the detail goes to `/dev/tty`. An encrypted reader is not in this package. See `packages/showdown-bridge/README.md`.
- `policy-protocol.ts` / `policy-worker.ts` / `policy-actor.ts` (ADR-010 §2): the policy worker's TS side. `policy-protocol.ts` holds the three worker contracts' validators and reader rules (`readPolicyQuery`: `identity` equals `observation.identity`, no candidate twice; `readHandshake`: contracts sorted by name, checkpoints by role), `contractVersions()` (name, `schema_version` and the SHA-256 of the schema's JCS bytes, for the handshake) and `encodeFrame` (JCS plus `\n`, bounded by the run's maximum line length). `PolicyWorkerClient` spawns the worker with stdio only and an explicit environment, opens the session with the handshake (a different contract set, `encoder_version`, engine-data hash or checkpoint ids is a `PolicyHandshakeError` before any battle), allows one outstanding query per battle and at most `n_parallel` at once, and re-checks every reply (`answersRequest`, the policy id, the `choice` among the query's candidates). Reply lines must be the JCS bytes of their value. Failures are classified for `guardActor`: a dead worker is a `PolicyWorkerError` (its detail names only the class of the last stderr line), an invalid reply a `PolicyReplyError` (the actor turns it into a forfeit `invalid_reply`), `unsupported_candidate` an `UnsupportedCandidateError` and a query the harness cannot send or a worker that refuses it a `PolicyProtocolError` (incidents `unsupported_candidate` and `policy_protocol`). Nothing is retried. A query that overran its budget stays outstanding (`guardActor` cannot cancel it): call `client.beginGame()` before each game, while no game runs on the client, and it restarts the worker if a query was abandoned or the session failed. `policyActor` is the A1 online observation adapter (the player's own stream from the `ActorContext`, the observation through `observe`, the candidates from `enumerateCandidates`, never a `CloneJudge` verdict or the seed) and `sampleU` the hash-based sampler (first 53 bits of SHA-256 over the JCS of `{seed, game, player, policy_id, request_seq}`). `policyGame` takes the battle seed once and uses it for both the engine and the sampler: use it rather than `policyActor` directly. `test/policy-worker.python.test.ts` drives the real Python worker and is skipped where `.venv` does not exist.
- `ActorContext`: `runBattle` calls an `Actor` as `actor(request, { player, channel })`, where `channel` is a copy of that player's own stream up to and including the request (no `|t:|` lines, never the omniscient log). The second argument is optional in the type, so actors that ignore it are unchanged; `guardActor` forwards it.
- `ml/areneon_ml/worker` (ADR-010 §2, Python): the policy worker, `python -m areneon_ml.worker --run-dir … --preview <id> --battle <id> --engine-data … --max-line-bytes …`. One JCS line per frame, strict (duplicate keys, floats and non-canonical lines refused); first frame the hello, answered with `ready` (and the session ends if the contracts differ); then one `PolicyReply` per `PolicyQuery`, in order, one query per pass. A malformed frame ends the process (exit 2); a query that breaks a contract or reader rule gets an `invalid_query` reply, one with a candidate shape `candidates.py` does not know an `unsupported_candidate` reply. Checkpoints are read only as `<run dir>/checkpoints/<id>.safetensors`, must hash to their id, must hold the network of the role they were named for, and must have been made for the worker's engine-data table and encoder version (`ready` carries the encoder version, the engine-data hash and the checkpoint ids). A reducer or encoder refusal of a query's observation is an `invalid_query` reply (no log line echoed), a candidate the encoder cannot back with the request an `unsupported_candidate` reply. CPU inference is made deterministic (`configure_cpu_inference`) before the first query. `view.py` is what an encoder may read of a query (no `decision_context`, no `rqid` even inside the log's `|request|` lines, no sampling or policy fields), `sampler.py` picks from the probabilities (float32 values summed in float64, first candidate whose sum exceeds `u / 2^53`), and the scorer is `model/scorer.py`'s `NetworkScorer` (below). No module of `ml/areneon_ml` (worker, model, checkpoint, reducer) imports a network module (an AST test scans them; third-party code such as torch is not scanned, and a session test runs with sockets disabled). `PolicyQuery`, `PolicyReply` and `PolicyHandshake` (`packages/schema/contracts/v1`) are the worker's contracts. `PolicyReply`, `PolicyHandshake` and the `query_id` field (correlating replies when a worker serves several battles) go beyond the ADR-010 §5 table and are to be listed in its next erratum.
- `golden.ts`: the golden battle (each side plays `firstLegal`, which applies `actorRule` to the request's legal choice set), team-fixture and verdict builders shared by the tests and the capture script.

**Log-to-state reducer** (`ml/areneon_ml/reducer/`, ADR-010 §3, R10, #838), Python and clean-room (grammar from the repo fixtures, `sim/SIM-PROTOCOL.md` and ADR-006/008; no Showdown client parser): `reduce_channel(player, lines, team, vocab)` turns ONE player's own channel plus that player's own team into a `BattleState` (`own` / `opponent` halves: HP as the player sees it, status, boosts, volatiles, revealed moves/items/abilities, Mega, active slots, weather, terrain, field and side conditions, turn, winner; own exact values come from the player's own requests). Ids are checked against a `Vocabulary` built from the hashed engine-data export, never against lists of its own. It fails closed with typed `ReducerError`s (`UnknownLineError`, `UnknownFieldError`, `MalformedLineError`, `VocabularyError`, `OpponentSecretError`): an unknown line type, tag, positional field or request key raises, a `|split|`, an opponent HP not out of 100 or a request for the other player is an `OpponentSecretError`. A `[from] item:`/`ability:` counts only without `[of]`, and a move is revealed only when chosen (not when called by another effect). Limits, known and deliberate: volatile ids (`-start`/`-end`) are kept as opaque public strings after a shape check, because the engine-data export has no volatile or condition table (a volatile/condition vocabulary, engine-data schema_version 2, is a follow-up the encoder will need); a field or side condition must still be a move or an ability of the vocabulary. `|replace|` (Illusion ending) is a named refusal: the reducer binds a Pokemon to the disguise it was shown, so it is not reduced past that line. After Mimic, Sketch or Transform `moves_revealed` can list more than four moves, and Trace (or Role Play) records the copied ability on both the tracer and the `[of]` target (the tracer's original ability is not tracked). `-activate` of Skill Swap clears both abilities (unknown), as the per-Pokemon result is not stated. Channel lines of the A2 server path (`|t:|`, `|c|`, `|inactive|`) raise here and belong to the A2 adapter slice, which strips them first. The HP colour class the champions mod appends at exactly 50% and 20% (`50/100g`, `20/100y`) is accepted and dropped.

Tests (`tests/ml/reducer/`): a unit test per line type, the refusals, the canary with negative controls, a drift test of the request key sets against `engine-request.schema.json`, a corpus test over `fixtures/showdown/<format>/random/` (seeded random-legal vs random-legal battles on random synthetic teams, `random-corpus.ts`; CI re-plays each from its committed seed, teams and actor seeds) that requires zero refusals except at the one named unsupported line type `replace` (Illusion ending; handling it is follow-up #851), in at most a quarter of the channels, with the canary at every request point, and golden snapshots `fixtures/showdown/<format>/reduced/p1.json` / `p2.json` for every committed channel (rewrite deliberately with `ARENEON_UPDATE_GOLDEN=1 uv run pytest tests/ml/reducer/test_golden.py --no-cov` and review the diff).

**Encoder, candidate parser, networks, checkpoints and the C1/C6 checker** (`ml/areneon_ml/model/`, `ml/areneon_ml/checkpoint/`, ADR-010 §3, §5, #839). `GameData.from_table(engine_data)` indexes the hashed engine-data export: one `IdVocab` per vocabulary (species, moves, items, abilities, statuses, weathers, terrains, types; index 0 is none, 1 unknown, the engine's ids follow in the export's order) and the numeric attribute tables (types, base stats, weight; move power, accuracy, priority, PP, target and flag one-hots; item flags), each column scaled by the largest value in the data. No list of game content is written in model code, so a vocabulary grows with the table. `Encoder(game, EncoderConfig).encode(query)` reads only `query["observation"]` (`player`, `kind`, `log`, `team.team`) and `query["candidates"]` (`choice`, `pending`): the log goes through `reduce_channel`, the player's last `|request|` gives the Pokémon order (`switch N` / `team NNNN` name the Pokémon at that request position) and the move ids, and it returns tensors without a batch dimension (`EncodedQuery`: one token row per own then opponent Pokémon, the field features, per-candidate slot parts, the picked team tokens and the `pending` flag). It ignores `decision_context`, `identity` (so `rqid`), the `rqid` inside `|request|` lines and every verdict field, so the A1 and A2 forms of a decision give equal tensors (tests over every request of the `fixtures/a2/` recordings and the `policy-query` samples). Volatiles and field/side conditions are engine-owned ids with no vocabulary yet, so they are SHA-256 bucketed into `volatile_buckets` / `condition_buckets`. `encoder_version` is `enc<format>:` + SHA-256 of the engine-data hash, the attribute tables as built, the config (scales included), the feature layout and the index constants (genders, request kinds, events, target codes, slot letters, the bucket hash), so a pin bump or any such change is a new version, never a silent remap. A change in how a value is computed from the state, with the same names and constants, is not visible to the hash: bump `ENCODER_FORMAT`; a golden test pins one version string and the tensor digests of fixed queries and fails on such a change. The A1/A2 equality is also tested on `fixtures/showdown/<format>/a2-pairs.json` (the A1 replay's observations and the A2 frames' observations of the ADR-005 fixtures with candidates from the real `enumerateCandidates`; rewrite with `node packages/bot-client/scripts/capture-encoder-pairs.ts`, a bot-client test compares it with a fresh capture). The encoder raises (fails closed) when an observation's kind does not match its request or candidates, or a Pokémon shows more moves than `max_moves`. `parse_choice` (`model/candidates.py`, re-exported by the worker) splits a canonical candidate into `SlotAction`s (pass, move with optional target and event, switch) or a Team Preview order and refuses any other shape with `UnsupportedCandidate`; `ParsedChoice.format()` is its exact inverse, and `tests/ml/model/test_candidates.py` round-trips every candidate of every `fixtures/showdown/**/choices/*.json`. `CheckpointRecord` (`packages/schema/contracts/v1/checkpoint-record.schema.json`, generated TS and pydantic types, corpus samples in `fixtures/contracts/v1/checkpoint-record/`) is the content-addressed provenance record of one frozen checkpoint; `checkpoint/record.py` reads it (sorted and unique hash arrays, no id referring to the record itself). Part 2 (networks and checkpoints, #839). `PolicyNetwork(role, game, ModelConfig)` (`model/network.py`) is one architecture per role, built and stored separately: a transformer over the entity tokens plus a field token and an aggregation token (attention written out as matmul and softmax, no fused kernel), a candidate head (a `battle` candidate embeds its two slot actions, move, target, event, acting Pokémon and switch-in tokens; a `preview` candidate its ordered team positions; both add the pending flag, cross-attend over the state and score against the aggregation token) and a value head on the aggregation token. Every size is configuration (`ModelConfig`: `d_model`, layers, heads, `d_ff` and the nested `EncoderConfig`; there are no defaults: the `model` section of the run's `TrainingRunConfig` carries the values and code only bounds them), same-seed initialisation is claimed for one machine and software only, vocabulary sizes come from `GameData`, and attribute tables are buffers derived from the engine data, not parameters. `collate` pads queries into a `Batch` (training may batch); evaluation runs one query per forward pass, a batch of one with no padding, on CPU with `configure_cpu_inference()` (deterministic algorithms, one thread), and `tests/ml/model/test_network.py` shows a query's logits are bit-identical alone and after others, and equal for the A1 and A2 forms. A checkpoint (`checkpoint/files.py`) is one safetensors file: the tensors, and `__metadata__` with the format, role, model config, encoder version and engine-data hash. The writer is our own so the bytes are deterministic (the library orders metadata by hash-map iteration); the id is the SHA-256 of the bytes; `load_checkpoint(data, game, expected_id, role)` (the id is required and checked before anything is read; the configuration is bounded, so a crafted file cannot allocate without limit) refuses bytes that do not hash to the id, another role, engine-data table or encoder version, an invalid configuration, and tensors whose names, dtype or shape differ from the network's. No pickle and no `torch.load` anywhere (a syntactic AST scan of all of `ml/areneon_ml` (a guard, not a proof: it misses aliased and dynamic imports) bans imports of pickle, dill, cloudpickle, shelve, marshal and numpy and calls of `torch.load` / `torch.jit.load`). numpy is not in the closure: the writer and reader move bytes through `ctypes`/`torch.frombuffer`. `python -m areneon_ml.checkpoint init --role … --seed … --engine-data … --run-dir … --model-config f` (the `model` section of a `TrainingRunConfig`, required) writes a seeded, untrained checkpoint (generation 0, and the input of the worker tests); learner state and training are below (#840). `checkpoint/provenance.py` is the C1/C6 checker (`ProvenanceGraph(records, sources)`; the `sources` registry is a HAND-SUPPLIED, UNHASHED input for now, a documented deviation from ADR-010 §5 until follow-up #853 derives and hash-binds it from the league run record: it must be canonical (RFC 8785) JSON, and `classify` / `independent` print its hash so an evaluation plan can bind it; `python -m areneon_ml.checkpoint classify|independent --records <dir of CheckpointRecord json> --sources <json>`): the ancestry of a checkpoint is itself plus everything reachable through `parent`, `league_opponents`, `exploiter_target` and the generators of its training sets (the `sources` registry maps each training-set hash to the checkpoints that generated it; an empty list is an outside behaviour-cloning or fine-tuning source, and a set missing from the registry is refused); C6 independence is disjoint ancestries (learned checkpoints and data sources; scripted baselines and the team pool are not nodes), C1 calls an opponent `seen` when it is in the candidate's ancestry, a scripted baseline, or a related lineage, and `held_out` only when every opponent checkpoint is an evaluation exploiter of the candidate or an independent lineage (one related member of a Preview + Battle pair makes the pair `seen`). The records must agree with each other: a parent shares its child's encoder version, a parent shares the child's role (a warm start cannot cross architectures), league opponents and the exploiter target may be either half of a frozen Preview + Battle pair, and nothing synthetic descends from a private checkpoint. It fails closed: a referenced checkpoint without a record, a repeated record, a cycle, or an exploiter in its own target's league (C3) is a `ProvenanceError`.

**Fixtures** live only under `fixtures/` (CC0, synthetic or sanitized, with provenance). `fixtures/showdown/<format>/` holds the golden request fixtures plus `battle.summary.json` (the log hash and choices), `channels/p1.json` and `p2.json` (each player's own stream of the golden battle as a `PlayerChannelLog`, the only battle input an observation may be built from), and `choices/` the choice corpus. `random/` is the random-play channel corpus (`b00.json`..., each a seed, the two synthetic teams, the actor seeds and both players' `PlayerChannelLog`, plus `manifest.json`). `fixtures/teams/<format>/` holds synthetic PokePaste teams, a `manifest.json` (provenance, expected verdict and reason) and `verdicts.json` (the validator's log). CI re-captures and compares the request fixtures, summary and verdicts, so engine behaviour drift fails the build. Pastes keep Showdown's trailing spaces (`.editorconfig`, `.gitattributes`).

**TrainingRunConfig, PPO learner and learner state** (`packages/schema/contracts/v1/training-run-config.schema.json`, `packages/showdown-bridge/src/training-run-config.ts`, `ml/areneon_ml/learner/`, ADR-010 §1, §5, #840). `TrainingRunConfig` is the one record of a run's values: lineage and format, every seed (`run_key`, the two initialisation seeds, the learner's generator), the `model` section (encoder and network sizes), the `generation` plan (self-play games, games per scripted baseline, `max_turns`, `n_parallel`, latency budgets, handshake timeout, `max_line_bytes`), the `ppo` settings and the learner's `device` (`cpu` or `cuda`) and thread count. Contracts carry no floating-point numbers, so real values are integers in millionths (`learning_rate_micro`, `clip_micro`, ...) or billionths (`adam_eps_nano`); `areneon_ml.learner.config.read_run_config` is the one place that divides them. The reader rules the profile cannot say (heads divide `d_model`, `max_picks` ≤ `max_team`, a baseline listed once) are checked by `read_run_config` and by the TS `readTrainingRunConfig`, which also gives `runConfigHash` (SHA-256 of the JCS bytes, `CheckpointRecord.run_config_hash`). League mixture and freeze-interval values are not in v1: they come with the league scheduler (Wave 5). The learner is PPO with GAE over the TrainingExample stream: `learner/data.py` reads a stream only through `read_stream` with its manifest, refuses a set that is not `learner_ready` or was not played by the `behaviour_policy_id` it trains, and splits each Episode into one Preview step and one Battle trajectory (encoded from the example's observation and candidates alone). The reward is the game score at the last step of a trajectory (win 1, tie ½, loss 0, `ppo.GAME_SCORE`); every earlier step, a refused pending choice among them, has zero immediate reward. `learner/trainer.py` recomputes the behaviour policy's log-probability and the value of every decision from the frozen weights with no gradient (no probability is stored in an Episode), computes advantages with GAE, then runs the configured epochs over minibatches shuffled by the learner's own generator; the loss is the clipped surrogate over a softmax across the real candidates (`ppo.py`, checked against hand-computed values) plus the value error and the entropy bonus. Determinism claim: on CPU, with the config's thread count and deterministic algorithms, the same inputs on the same machine and software give bit-identical weights; nothing is claimed across machines or torch builds, and a CUDA learner is not bit-reproducible (its run config, with `device: cuda`, hashes differently). The learner state (`learner/state.py`) is `learner-<g>.safetensors` (both networks' weights, the Adam moment tensors, the generator's state tensor) plus `learner-<g>.json` (JCS: generation, run config hash, seeds, PPO settings, optimiser step counts); `learner_state_hash` is SHA-256 of `JCS({tensors_sha256, sidecar})`. `restore_state` loads only through safetensors and a JSON parser, recomputes the hash, refuses a state of another run config, a sidecar that contradicts the networks and tensors of another name, dtype or shape, and changes the learner only after every check. `checkpoint/files.py` gained `pack_safetensors` / `unpack_safetensors` (float32 and uint8) beside the checkpoint writer.

**Generation loop** (`ml/areneon_ml/loop/`, `packages/showdown-bridge/src/league-generation.ts`, `generation-cli.ts`, ADR-010 §1, #840). `python -m areneon_ml.loop run --config <TrainingRunConfig.json> --run-dir R --engine-data <engine-data.json> --generations N [--node node] [--worker-python <python>]` continues the run in `R` until N generations are committed (resuming from the last one, a no-op if N are there); `provenance --run-dir R --out D` writes `D/records/` and `D/sources.json` (derived from the run's own manifests) for `python -m areneon_ml.checkpoint classify|independent`. Generation 0 is the seeded random pair (no warm start, ADR-010 §4); generation g plays the pair frozen at g-1 on A1 (`play-generation.ts`: the Python worker on CPU torch behind the TS client, `policyGame` for self-play and for each configured scripted baseline), writes an Episode for every played seat (`episodeFromRecord`, collection kind `league`, `run_id` = the config's `run_key`, the seed the battle ran with), loads only the pair's own seats through `loadTrainingSet` (`behaviour_policy_id` = `policy:` + SHA-256 of `JCS({preview, battle, mode, temperature, precision})`; a baseline's Episodes are kept but the loader would refuse them), trains (`learner/`), freezes the new pair and commits. The frozen pair always plays with temperature-1 sampling, never argmax (`playOne`; the policy id says `mode: sample`), and a baseline seat is never queried or loaded (tests fail on either). The match plan (battle seeds, team indices, baseline seats) is a pure function of the config, the generation and the team pool (`planGeneration`), so a killed generation is replayed from the same plan. Run directory: `run-config.json`, `checkpoints/<id>.safetensors` (the store the worker reads), `generations/g<NNNNNN>/` (Episodes, `stream.jsonl`, `training-set.json`, `plan.json`, `generation.json`, `train-report.json`, `learner-<g>.safetensors|json`, `records/{battle,preview}.json`, the cumulative `team-set.json`, `manifest.json` = SHA-256 of every other file plus the checkpoint ids and hashes). `run()` holds an exclusive `flock` on `<run dir>/.lock` for its whole run (a second driver on the directory fails fast; the operating system releases the lock when the holder dies; caveats: `fcntl` is POSIX only, NFS needs a working lock service, and a WSL2 `/mnt/c` directory (DrvFs/9p) may not honour `flock`, so keep run directories on a local Linux filesystem; `generations/`, `checkpoints/`, the run directory and its parent are fsynced when first created). A generation is built in `.g<NNNNNN>.partial`; every file and directory in it is fsynced (the Node side's own files too: `writeGeneration` fsyncs each file, then both directories, `generation.json` last), the manifest is hashed from the flushed bytes, and one `os.replace` of the directory commits it, followed by an fsync of `generations/` (`write_checkpoint` and `run-config.json` are written the same way, temp file, fsync, rename, fsync of the directory; stale `checkpoints/.*.partial` files of a killed run are deleted at start); the next start deletes partials, finds the newest committed generation, verifies its manifest (only the newest: the learner state, records and team set a resume needs live there, `latest_complete` checks that the numbers run 0..n without a gap, and `provenance` verifies every generation), restores the learner (`restore_state`, hash checked), and refuses unless the restored weights are the stored checkpoints (written again if the store lost them) and the records agree with the state and the manifest (checkpoint id, learner state hash, run config hash, training-set hashes). Each generation's two `CheckpointRecord`s carry the lineage, the parent (the previous generation's same-role checkpoint), the TrainingSet hash, the run config hash, the learner state hash, the encoder version, the cumulative team-set manifest hash and the format's version manifest (from `format-manifest.ts`). The team pool is the interim one (`trainingTeamPool`): the golden team, the legal paste fixtures and the random-play corpus teams, all committed CC0 synthetic and proven synthetic by that source; the ADR-013 team generator does not exist yet. `generation.excluded_abilities` of the config keeps out teams that hold an ability on its list; the tiny and any current config list `Illusion`, a stop-gap for the reducer's `|replace|` gap (follow-up #851) that a random-team game would otherwise hit. Claims: with the CPU learner, one thread count and the same machine and software, an independent rerun gives byte-identical generations and a SIGKILLed run resumes to the same learner-state hashes (`training-loop.python.test.ts` SIGKILLs the driver's whole process group at three points of generation 2 and resumes each to the same hashes: `play`, while Node and the worker are alive (the partial may still be empty); `write`, while Node writes its files (`generation.json` is written last, so Node and the worker are still alive); `seal`, after `train-report.json` exists and before the manifest, so the driver's train/seal phase is killed by a real signal (the window is short; a missed one is retried in a fresh directory). The driver's read and commit phases are otherwise exercised by in-process stage killers (exceptions), `tests/ml/loop/` kills at each stage with a fake simulator side); a CUDA learner is not bit-reproducible and nothing is claimed across machines or torch builds. The training self-play and the learner may batch; evaluation never does (§2). League mixtures, a freeze interval and exploiters are Wave 5.

The planner stays fail-closed on a channel naming a snapshot that is neither released nor stored. `gh` needs `GH_TOKEN`. Its Dockerfile's default target is the production image (node, gh, CA bundle, `/app`); the `e2e` target alone adds a stand-in `gh` replaying `fixtures/rules-releases/`, and `FakeAttestationVerifier` lives only in the `./testing` export.

**Evaluation records and register** (ADR-010 §6, §7, §9 O1/O11, #846; code in `packages/showdown-bridge`, engine-free, Node built-ins only). Values live in reviewed data, never in code: `config/evaluation/evaluation-parameters.v1.json` (`EvaluationParameters`: §6, `maxTurns` included) and `training-gate-rule.v1.json` (`TrainingGateRule`: margins, alternatives, target power, the claim family). Ratios are integer ppm (`PPM` is only the unit). `evaluation-config.ts` reads each against its ADR-008 contract and then enforces what the profile cannot: alpha' = alpha / (m·B_sealed) is whole ppm, `b_boot` exceeds m·B/alpha, `r_cov` is at least 1/alpha', `cov_tol` is derived (never stored), sorted-and-unique lists, and, with both records (`readEvaluationConfig`, `checkGateConsistency`), the family size equals the claims, G2 claims name each baseline once, and each gate's `h` is at most what the target power allows (`maxHalfWidthPpm`, from computed normal quantiles; no z table). The measured entries (`n_teams_floor`, `n_teams`, `n_seeds`, `d_team`) are null in the committed v1 record, which is therefore *provisional*: `requireComplete` refuses to commit a set or register a plan on it. A record, entry, commitment or plan is referenced only by `domainHash(domain, value)` (SHA-256 of `areneon:<domain>:v1\n` plus its JCS bytes: a hash of one kind never stands for another); changing any value is a new version, never an edit. `evaluation-plan.ts` holds the `SealedSetCommitment` (L3: hashes and counts only, E1's stratum counts; `setCommitment`/`keyCommitment`/`checkReveal` compute and open the hashes, and no sealed content is ever a field) and the `EvaluationPlan` (I2) with `checkCommitment`/`checkPlan`, which tie both to the records they name. `evaluation-register.ts` is the register (I6, O1): an append-only JSON Lines file in the isolated store, each line the JCS bytes of an `EvaluationRegisterEntry` (`set_commitment`, `plan_registration`, `l2a_recheck`, `run_outcome`, `incident`, `set_retirement`) carrying the previous entry's hash. `verifyRegister(text, configs)` is pure and offline; given the records (the CLI defaults to the committed v1 files, repeatable `--parameters`/`--rule`) it re-checks every commitment and plan against them, ties their hashes to those files and takes the run budget from the parameters, and it refuses a changed, dropped, reordered or non-canonical line, a time that goes back, more plans than `b_sealed`, a second plan for a candidate, a run without a passing L2a re-check, and any result on a contaminated or retired set. The chain head (`EvaluationRegisterHead`: position and hash, no secret) is merged to `main` by PR as `evaluation/register-heads/<10-digit seq>.json` (or attested; a Redmine note is not a trusted timestamp); `checkHeads` (with `--heads-ref origin/main`, read from git, not the working tree) refuses a register shorter than a published head (rollback) or with another hash at a head's position (rewrite, fork), and `assertPlanPublished` gates a run on its plan's head: `append` of an `l2a_recheck` or `run_outcome` naming a plan is refused unless that head is published. Head files are add-only (`checkHeadsAddOnly`; the `typescript` CI job runs `heads-check --base HEAD^1`; CODEOWNERS covers `evaluation/register-heads/` and `config/evaluation/`). `init` is the only command that starts a register, `gen-secret` writes a 256-bit secret (mode 0600, never overwrites) and prints only its hash, and `checkReveal` also requires `team_count` teams whose strata equal `stratum_counts` (E1 minimum). `scripts/evaluation-register.ts` (logic in `src/evaluation-cli.ts`: `config-check`, `commit-set`, `register-plan`, `append`, `verify`, `head`, `heads-check`) is the owner's tool; `make ts` runs `heads-check`. The sample corpus covers every new contract (`src/evaluation-samples.ts`). The isolated store itself (a separate OS user plus a container, files mounted read-only only into the evaluation container) is created by the owner from `docs/runbooks/evaluation-store.md`; `scripts/check-evaluation-store.sh` (tested in `tests/scripts/test_check_evaluation_store.py` on a scratch directory) is the read-only check the owner runs as the store user (owner, modes, parents, `--code`, container mounts and user) and as the training user (`--probe-denied` needs EACCES, so a missing path fails). This code never creates a user, container or mount, and the evaluation runner and sealed team generation are other tickets.
**Private team store package** (`packages/private-team-store`, ADR-014 §6, §10 item 5, #868): a `private: true` pnpm workspace package that is never shipped and holds no features yet (#870 adds the crypto). Its dependencies (`age-encryption` BSD-3-Clause, `@noble/*` and `@scure/base` MIT) are pinned to exact versions (no `^` or `~`); `@noble/post-quantum` 0.5.4 declares `~2.0.0` for `@noble/curves` and `@noble/hashes`, so the lockfile also holds their 2.0.1 copies: the hybrid ML-KEM path runs on those while age's X25519 uses the 2.4.0 pins, and a later `post-quantum` bump must re-check this. `.github/dependabot.yml` ignores them for version updates, so a bump is a manual, reviewed change (security-update PRs may still open and `osv` still scans). `packages/private-team-store/test/packaging.test.ts` is the packaging rule: no Dockerfile, compose file or Coolify build file names the package, no other `package.json` depends on it, no Dockerfile copies a whole directory of packages or runs `pnpm install` without `--filter`, and the DuckDB CLI, the `age` CLI and OpenSSL appear in no `package.json`, `pyproject.toml` or Dockerfile. The Dockerfile checks parse `COPY`/`ADD` sources (explicit non-glob paths only) and pnpm commands, and `test/packaging-rules.ts` has table-driven bad and good cases for every check. A Coolify application configured in the UI is not visible to a repo test: it is an operator rule (README). `make licences` checks the dependencies like any production dependency.

**CI** (`.github/workflows/ci.yml`) runs `python`, `typescript` (submodule checkout + `make showdown`, and the locked CPU closure of `areneon-ml` so the real-worker test runs; the job fails if a CUDA package comes with it), `database` (rules store on Postgres 18), `importer-image` (`make importer-e2e`), `team-guard`, `licences`, `gitleaks`, `osv` and `dco`. The aggregate `ci` job is the required check on `main`, together with CodeQL.

A2 (ADR-005) is a bot client on a local Showdown server, for local human sparring against the bot; `packages/bot-client/README.md` is the sparring guide (start, connect, challenge, stop). In `packages/bot-client`, `ProtocolReader` (`src/protocol.ts`) numbers each room's requests per channel: a room's `|init|battle` (sent on every join, before the replayed log, which holds no requests) resets its `request_seq`, open request and re-send identity, so the request re-sent after a rejoin is request 1 of the new channel, as `buildObservation` numbers it.
