## Architecture

**Polyglot monorepo** (ADR-002): TypeScript in `packages/*` (pnpm workspace), Python in `scripts/` and `tests/` today plus the generated-contracts package `packages/schema/python` (a uv workspace member next to its schemas; `ml/` for the policy worker in `ml/areneon_ml/worker` (the networks follow), `services/` later), Rust in `crates/` once the first crate lands. `packages/schema` holds the JSON Schema contracts: the rules records (`rules/`, ADR-007) and the cross-language contracts (`contracts/v<N>/`, ADR-008), from which the TS types in `generated/ts/` and the pydantic models in `python/areneon_contracts/models/` (the `areneon-contracts` uv workspace package, `scripts/contract_models.py`) are generated and checked in; serde follows with the first crate. On Python, `areneon_contracts.contracts` validates with python-jsonschema, then parses into the model (`parse`), and hashes with RFC 8785 (`jcs`, `request_hash`). `fixtures/contracts/` is the shared sample corpus (valid and invalid instances of every contract, plus `reader-invalid/` ones that pass the schema and that a TS reader such as `readEpisode` refuses, plus their JCS digests in `hashes.json`): Ajv and python-jsonschema must classify it identically and every language must reproduce the digests. A contract's `$id` (`urn:areneon:schema:<contracts|engine>:v<N>:<name>`) declares its profile, and `src/profile.ts` enforces it as a keyword whitelist: closed objects, bounded integers, local `$ref`s, `kind`-tagged `oneOf`; `engine` schemas, which copy the pinned engine's wire shapes, also allow scalar type unions and get their own Ajv instance (`src/ajv.ts`). `Provenance` gained the optional `collection` as a minor change within v1 (ADR-008 §3): a reader older than it rejects such an Episode, so the generated types and models ship with the schema change. `make contracts` fails on a profile violation or on generated types that differ from a fresh run.

**The reference engine is upstream Showdown, unmodified** (ADR-003). `vendor/pokemon-showdown` is a git submodule pinned to an exact SHA and built with `make showdown`. Areneon never decides legality itself: it asks the engine (`TeamValidator`, `side.choose`) and stops on unknowns. `docs/showdown-champions-gaps.md` lists what the engine does for Champions and what is unverified. It is generated from the gap ledger records in `rules/gaps/` by `scripts/gaps-doc.ts`; edit the records, never the doc (a test compares them). Gap edits move `rules_snapshot_hash` but never `format_rules_hash`.

**`packages/showdown-bridge`** is the only code that talks to the engine:
- `engine.ts`: `loadEngine()` loads `dist/sim` via `createRequire` behind narrow local interfaces (`ShowdownSim`). It refuses a missing build or a checkout whose HEAD is not `PINNED_SHOWDOWN_COMMIT`. A test checks that constant against the submodule gitlink, so a pin bump changes both.
- `rules.ts` / `rules-load.ts` (ADR-007): Areneon's own rules are JSON records in `rules/`, never code constants. That covers which formats it runs and the forbidden engine rules (e.g. `forceopenteamsheets`, because CTS needs Bo1 with sheets declined). They are validated by `packages/schema/rules/v1` (Ajv) and fail closed. `jcs()` (RFC 8785) gives `rules_snapshot_hash` (provenance) and `format_rules_hash` (replay identity). `packages/showdown-bridge/scripts/rules-hash.ts` and everything it pulls in (`rules.ts`, `request-identity.ts`, `canonical-json.ts`, `engine.ts`) import only Node built-ins, because CI reruns old commits' copy of it from bare archives. `canonical-json.ts` (`canonicalJson`, `jcs`) imports nothing at all, so the engine-free observation builder can use it too (ADR-008 §5); a test enforces that.
- `formats.ts`: `resolveFormat` checks a format against the rules snapshot and the pinned engine. It returns the version manifest `{showdown_commit, format_id, regulation, ruleset_hash, format_rules_hash}` plus the embedded format rules record that every fixture (and, later, every episode) carries.
- `scripts/check-rules.ts` (in `make ts` and CI; policy in `rules-channel.ts` / `rules-history.ts`): validates every record and checks `rules/channels/`, which must hold exactly one file per channel in the channel schema's enum. Each channel must name a snapshot built for the current pin, and `seq` rises by 1 per change. A pin bump must also move the channel (CONTRIBUTING).
- `request.ts` / `request-identity.ts`: decode one `|request|` into a phase (`preview`/`move`/`forceSwitch`/`wait`). The body is first validated against the closed engine-mirror schema `packages/schema/contracts/v1/engine-request.schema.json` (the pinned `sim/side.ts` request types, minus fields no supported format has), so only an engine-shaped request is hashed; a pin bump that changes the shape edits that schema. Request identity is `request_seq` + `request_hash`, a SHA-256 of canonical JSON that excludes `rqid`. `request-bytes.ts` is the one definition of the hashed bytes (`requestIdentityBytes`, the `Sha256` port type and `hashRequest`); it imports only `canonical-json.ts`. `parseRequest` is the pure parse step (schema validation, phase, `identity_bytes`; it hashes nothing), `decodeRequest` adds the Node `request_hash`, and `buildObservation` hashes the same bytes through its injected port (a test fixes Node and WebCrypto digests equal on the golden requests and that no other module builds the bytes). `rqid` exists only on the Showdown server path, never on the in-process sim.
- `runner.ts`: `runBattle` runs a seeded in-process BattleStream battle (runtime A1) on copies of the teams (the caller's sets stay as brought) and records `team_hashes` (each seat's set array as brought). Teams are validated first. Each `Actor` sees only its own player's requests. Each request carries its `legal` choice set, judged by a `CloneJudge` on the stream's own battle. The CloneJudge's verdicts on pending candidates go to `hidden_verdicts`, never to an actor. If the actor submits a pending candidate and the engine refuses it as `[Unavailable choice]`, the updated request that follows is a new request (`request_seq` + 1). Any other engine `|error|` aborts; nothing is retried. `|t:|` wall-clock lines are dropped so the same commit, seed and choices reproduce `omniscient_log`. That log holds both sides' hidden information: an evaluation artifact, never actor input. `replayActor` replays recorded choices. The optional `players` option sets each seat's `name` and `avatar` on the `|player|` lines (default `p1`/`p2`, no avatar) so a recorded server battle can be reproduced; `validatePlayers` refuses unsafe names (blank, edge whitespace, no letter or digit, over 18 UTF-16 units, `|` `,` `[` `]`, control characters, double spaces, or two names alike) and avatars that are not 1-32 letters, digits or `-`.
- `teams.ts`: `importPaste` / `exportPaste` wrap the engine's `Teams.import` / `Teams.export`. Showdown silently skips unknown lines (an `SPs:` line zeroes the Stat Points; they belong in `EVs:`), so `importPaste` rejects a paste unless each Pokémon's lines all reappear in that Pokémon's re-export: only the engine's canonical form passes. `validateTeam` returns the pinned `TeamValidator`'s messages verbatim.
- `choices.ts` / `choice-judge.ts` (ADR-006): `enumerateCandidates` turns the player's own request into every engine-distinct joint choice, in a fixed canonical order. It is pure and fails closed on any request field it does not know. Candidates whose legality depends on `maybeTrapped` / `maybeDisabled` / `maybeLocked` are `pending`. `legalChoiceSet` (its `LegalChoiceSet` type is generated from `packages/schema/contracts/v1/legal-choice-set.schema.json`, imported as `@areneon/schema/types/v1/…`) has a `ChoiceJudge` check every non-pending one; it never asks about pending ones, so no hidden-information verdict reaches a policy. `CloneJudge` judges on `Battle.fromJSON(battle.toJSON())`, never on the live battle, and refuses unless the battle is at the request's `request_hash`. `runBattle` builds one per request (A1); the corpus and tests use it too. `Battle.fromJSON` rebuilds `activeRequest` from the Pokémon, so the clone carries the live request over: after an `[Unavailable choice]` the live one was edited in place. `judgeSubmission` (the SubmissionJudge) classifies the engine's `|error|` after a submission. If the engine refuses a non-pending candidate, that is an `EnumeratorDefectError`. Revival Blessing (#910): a request whose `side.pokemon[i].reviving` is set is a forced switch; the one flagged reviving slot offers `switch N` for every fainted Pokémon (active slots included) and `pass` only when no living bench Pokémon exists, and any other shape (a second flagged slot, a reviver outside a forced switch) fails closed. A successful reviving pick clears the reviver's `switchFlag`, which `clearChoice` does not restore, so `CloneJudge` takes a fresh clone after any choice that changed a `switchFlag` (its batch verdicts equal one clone per choice). The corpus has `force-switch-revival` and `-many`, `fixtures/showdown/<format>/revival/` a seeded battle through `runBattle` (`scripts/capture-revival-battle.ts`), and `tests/ml/model/test_revival.py` the reducer and encoder on it. On A2 (`judge: null`), the engine judges only at submission.
- `observation.ts` (ADR-008 §5): `buildObservation` is the only constructor of a `PreviewObservation` / `BattleObservation`. Its battle input is a branded `PlayerChannel` (one player's own stream up to the request being answered), plus that player's own `PrivateTeamSpec`, the version manifest and an optional `DecisionContext`; the omniscient log is a distinct `OmniscientLog` type and cannot be passed. The module imports no engine, runner or Node built-in (a test enforces it), so it runs wherever WebCrypto does; it hashes through an injected `Sha256` port (`nodeSha256` in `player-channel.ts`, `webSha256` on WebCrypto) to exactly `decodeRequest`'s `request_hash`. `player-channel.ts` is the A1 adapter: `playerChannel` validates a `PlayerChannelLog` and every `|request|` in it before branding, and `recordedChannel` cuts a runner record's channel at a `request_seq`. `test/observation.test.ts` holds the ADR-008 privacy tests: golden parsing, the canary test (no opponent secret line or request stats in any observation, with a negative control), schema probes and the type test.
- `episode.ts` / `episode-io.ts` (ADR-008 §3, §5): an `Episode` is one player's recorded battle: their own channel (stored once), their own team, their decisions (a `deadline` record required on A2, absent on A1), provenance, `data_class` and matching `rights`. `episodeFromRecord` writes one from an A1 record, given both teams: it classifies by BOTH (`private` if either is; `rightsFor` follows), checks each team's `teamHash` (JCS of the set array, so it ignores the label) against `record.team_hashes`, and refuses a `synthetic` label whose hash is not in the given `known_synthetic` set; `readEpisode` reads a copy back by its `schema_version` (an unknown version is refused), checks the channel is the player's own and its ending matches `result`, rebuilds the Team Preview observation and every decision's (so the team must be the player's own, in request order), and on A2 requires each decision's deadline record; every refusal is an `EpisodeError`. `playerChannel` refuses `|split|` lines and the opponent's exact HP, the SECRET halves a player never sees. A battle with a reconnect is ONE continuous channel (#813): the server replays the room log to a rejoining connection with no `|request|` or `|error|` line, so the rejoin channel alone has no Team Preview request and `buildObservation` refuses it (the team check anchors on the channel's first request, unchanged; the message names the fix). `continueChannel(earlier, rejoin)` (`player-channel.ts`; reader-side, no schema change) joins the two own channels: the replay lines with the earlier channel's player-alone lines put back where they were, a first request of the rejoin with the earlier last one's `rqid` and body counted once, refusing another player's channel or a replay that does not continue the earlier room log; fold it across several reconnects. The joined channel equals A1's, so its observations equal A1's in full and an Episode stores it as it stores any channel (`readEpisode` is unchanged). `|poke|` lines are no anchor (species and item presence only). `session.ts` and `a2Episode` fold the connections' channels with it (see A2 reconnect below). `episodeFromRecord` also takes an optional `collection` record, which must carry the battle's own `record.seed`. An Episode's optional `provenance.collection` (ADR-009 §4: `league`, `evaluation` or `sparring`, a `kind`-tagged `oneOf`) names the run, the seed (`sodium,<hex>`, null on A2), the evaluation `sealed` flag or the opponent policy; `readEpisode` also refuses a seed on A2 or none on A1, which the schema cannot say. `episodeHash` is SHA-256 of the JCS bytes through the `Sha256` port. `answersRequest` is the stale-invalidation check for a `Recommendation`. A `league` or `evaluation` `provenance.collection` carries a required `opponent_team_data_class`, which `episodeFromRecord` sets from the opponent's `StampedTeam` (never the caller's); `readEpisode` requires the Episode's `data_class` to equal the higher of the own team's class and that field (so a stored Episode relabelled synthetic is refused), and a `sparring` Episode to be `private`.
- `own-team-stats.ts` (#893, ADR-008 §5): the engine-dependent half of the own-team check, outside the engine-free `observation.ts`. `buildObservation` matches the team to the Team Preview request by species, item, ability, moves and nickname only; `assertOwnTeamStats(engine, formatId, team, channel)` builds a battle with the pinned engine from the team the observation will record and requires the engine's own Team Preview request for that player to show the same level, maximum HP and five stats as the channel's first request, Pokémon for Pokémon in team order (no formula is written here; the same team in another order is refused). A difference is an `OwnTeamStatsError` (an `ObservationError`) with a fixed message and a position index only, never a set or a stat; so are a channel that does not start at Team Preview, a team of another size and a team the engine cannot start. It is called by `readEpisode` (so by `episodeFromRecord`, the A2 Episode writer and the training loader; optional `engine`, default the pinned checkout from `pinnedEngine()`, loaded once) and by `policyActor` at the first request of a game (the A1 online observation; optional `engine`, which `policyGame` passes). Limits: the Champions mod ignores IVs (Stat Points replace EVs, IVs fixed at 31) and the request carries no IV, so an IV-only difference cannot be seen (and does not change play); a mirror team that differs in Stat Points, nature or level is refused. Bare Hidden Power: the request names it `hiddenpower<type>`, and the pinned validator allows the move in no supported format ("does not exist in Gen 9"), so no legal team reaches it; the move match keeps refusing it (fail closed) and a test pins the validator's verdict, so a pin bump that allows the move is decided then.
- `training-loader.ts` (ADR-009 §4): `loadTrainingSet` is the one way an Episode becomes training data, and it fails closed. Each Episode goes through `readEpisode` (with `known_synthetic`), then only a `synthetic`, `cc0-synthetic` Episode of collection kind `league` is accepted: a missing collection record, `evaluation`, `sparring` and private data are refused, as is any Episode whose `episodeHash` an `EvaluationRunManifest` lists, and a repeated Episode or manifest. Every refusal is a `TrainingLoaderError`; none is skipped. It writes a stream of `TrainingExample` lines (`episode_hash`, `observation`, `choice`; no provenance, so no seed or opponent id) in Episode-hash order, and a `TrainingSet` (the Episode hashes, the checked manifests' JCS hashes, `data_class`, line count, `stream_sha256`). `readEvaluationRunManifest` / `readTrainingSet` enforce the sorted-and-unique hash lists the profile cannot (corpus samples under `reader-invalid/`). A relabelled copy of an evaluation Episode has another hash, so only the storage partition catches it. `evaluationRunManifest` is the evaluation job's writer (hash-only, sorted and unique); `decisionObservations` (`episode-io.ts`) rebuilds each decision's observation for the examples. On the Python side `areneon_contracts.training.read_stream` reads a stream only with a manifest that matches its digest, line count, Episode hashes and class, validating every line.
- `server-lines.ts` (ADR-005 §5): the A2 server-path filter, an allowlist of the sim's line kinds. `serverOnlyLine` is the stateless check: `>room` headers, plain-text notices and `||text`, `|request|null`, nameless `|player|<slot>|`, and the known server kinds (joins/leaves/renames, chat and PMs, `|raw|`/`|html|`/`|uhtml|`, timer and timestamp lines, room and session state, `|sentchoice|`). `stripServerLines(stream)` returns `{ lines, dropped }`: it keeps sim kinds (`|error|` included), places the engine's `otsrequest` prompt and clear and the sim's `|player|` lines by their position relative to `|gametype|` and `|start`, drops the server's auto-tie `|-hint|` and its inactivity and forfeit `|-message|` lines by exact text, and reports lines of unknown kind in `dropped`. The adapter filters the stream from its first line every time, never a suffix. The channel equals the A1 one up to server-layer `|error|` refusals, which only A2 produces; `|player|` equality is left to the A1/A2 equality test. It imports nothing (a test enforces it), and the golden channels pass through unchanged.
- `choice-corpus.ts`: the golden choice corpus (ADR-006 rule 7). Each case is a seeded battle log that reaches one situation (`CASE_KINDS`: preview, target types, Mega, forced switches, trapping, Imprison, a fainted active, a locked move), plus every candidate with the engine's verdict. Verdicts on pending candidates are hidden state, kept for evaluation. CI replays each log (it never re-runs the search in `scripts/capture-choices.ts`) and compares the result. `missedActions` is the brute-force oracle: it judges every syntactic choice string and fails on any engine-accepted action the enumerator did not offer.
- `team-class.ts` (#817): a class is proven by source, never by a caller's label. `teamHash`, `classOfSets` / `stampTeam` (`synthetic` only for a hash in the known synthetic set, `private` otherwise, `private-data/` teams included), `higherClass`, and `battleClass`, whose branded result is the only value `recordedChannel` takes as a channel's `data_class` (`syntheticFixtureHashes` in `golden.ts` is today's set: the committed fixtures' teams). The set is trusted caller input and the brand is compile-time only; `syntheticTeamHashes(...lists)` builds the set from verified lists of positional `team_hash`es (a non-digest is refused); `datasetSyntheticHashes` / `committedDatasetHashes` in `packages/team-dataset` feed it the teams of the committed, verified datasets, and a caller adds `committedDatasetHashes` (exported from `@areneon/team-dataset`) to the sets it already trusts, e.g. `syntheticTeamHashes(syntheticFixtureHashes(engine), committedDatasetHashes(inputs, format))` (a team is synthetic only if its hash is in the set it passes). `stampTeam` returns a compile-time-branded `StampedTeam`, the only team type `episodeFromRecord` accepts (`runBattle` still takes plain sets: a battle is not an Episode, and `team_hashes` binds the teams to the record). `readEpisode` checks its own team against the required `known_synthetic` and the opponent's class through `collection.opponent_team_data_class`; an Episode without a collection record has no opponent class to check. An A2 stream has no opponent team to hash, so its `data_class` is the caller's label and defaults to `private`.
- `engine-data.ts` (ADR-010 §3): `exportEngineData` reads the species, move, item, ability, type (with the engine's own type chart), status, weather and terrain vocabularies and their numeric attributes from the pinned engine's data for the format's mod, each list sorted by id (the position is the vocabulary index), into the `EngineData` contract (`packages/schema/contracts/v1/engine-data.schema.json`). It refuses any value of a shape it does not know; the vocabularies hold the engine's standard entries plus, so no reference dangles, every base species a standard forme names and every ability a standard species lists even if the engine marks them nonstandard (eight at this pin: cramorant, eiscue, floette, meloetta, minior, ogerpon, terapagos, Aura Guard). Out of v1 scope (a change needs schema_version 2, the contract being closed): natures, volatile conditions, learnsets, evos, requiredItem, move effects, species height and gender. - `private-snapshot.ts` (ADR-015 §2, #897, slice 1 of #887): the `PrivateSnapshotManifest` contract (`packages/schema/contracts/v1/private-snapshot-manifest.schema.json`, generated TS and pydantic types, integers only) and its pure reader, `readPrivateSnapshotManifest`; no engine, no file system, no key. It mirrors `TeamSnapshotManifest` with `data_class` const `private`, no `dataset_hashes`, one split (`owner`), the `label_set_hash`, `records: {active, retired}` and the `holdout` block `{rule: "hmac-sha256-team-id/1", key: <64 hex>, ppm: 200000}`. Decisions where the ADR left room (also on the ticket): (1) the hold-out block holds the KEY itself, as ADR-015 §2 writes it (the key is not a secret and the snapshot reader recomputes every record's flag from it), not a key commitment; (2) a shard names its `index` (its position, 0 first), never an object path, because the path `snapshots/<snapshot_hash>/shards/<index>.parquet` holds the hash of the manifest that lists the shard; (3) a cell range carries `active_rows` beside `rows`: the ranges tile ALL rows of a shard (retired included) and `cells` count active records only, so the reader checks cells and `records` against the shards from the manifest alone; (4) `first: true` or `parent_snapshot_hash`, exactly one (reader-enforced; the schema leaves both optional). The reader adds shards in strictly ascending `logical_hash` with `index` equal to position, ranges tiling each shard with ascending strata and `active_rows <= rows`, `cells` equal to the shards' active sums and listing exactly the cells with an active record (empty when all are retired), `records.active` equal to the cells' sum, active plus retired equal to the shards' rows, and `logical_snapshot_hash` recomputed (`privateLogicalSnapshotHash`: JCS of `{shards (sorted logical hashes), cells, label_set_hash, manifest, holdout, and parent_snapshot_hash or first: true}`; `privateSnapshotHash` is SHA-256 of the whole manifest and names the snapshot in the bucket). Its messages state a rule and never repeat a value or a key name (a canary test). `holdoutFlag(key, team_id, ppm?)`: HMAC-SHA256 with the 32 bytes the hex key spells, over `team_id` as its 32 lower-case hex ASCII characters, first 8 bytes big endian as n, held out when `n * 10^6 < ppm * 2^64` in integers; it depends on the two ids alone, so a team keeps its flag on every revision. Known answers computed with Python `hmac`/`hashlib` are in the comment of `test/private-snapshot.test.ts`, as are the two manifest digests. The snapshot reader (#899) recomputes each record's flag; the manifest reader needs no key. - Play temperature and threshold (ADR-023 §1, ADR-010 erratum A6 items 1-2, #1043; a minor change within v1): `PolicyQuery.sampling` of kind `sample` gains the optional `temperature_ppm` (integer, 1 to 1,000,000) and the optional closed `kind`-tagged `truncation` `{kind: "threshold", min_ppm}` (1 to 999,999); argmax takes neither. Writers omit both at the default, so every existing query keeps its JCS bytes, and the readers (`readPolicyQuery`, the worker's `read_query`) refuse an explicit 1,000,000 (reader-invalid sample `temperature-explicit-default`). The handshake's schema hash changes: client and worker ship together. The scorer (`NetworkScorer.probabilities(view, temperature_ppm=...)`) computes `softmax(logits * (10^6 / temperature_ppm))` in float32 over the real candidates (the worker passes the argument only when the query carries one, so the default path is the untouched computation); `sampler.truncate` then gives 0 to every candidate whose probability is below `min_ppm / 10^6` except the FIRST HIGHEST, which is always kept (otherwise a policy over more than 33 candidates could drop all of them at 0.03), renormalises (float32 values over their float64 sum, rounded to float32) and the existing draw follows (float64 sum in canonical order, first candidate whose sum exceeds `u / 2^53`). The policy id keeps `temperature: 1` when `temperature_ppm` is absent; otherwise `temperature_ppm` replaces `temperature`, and a truncation adds `truncation` (`policyId` in `policy-protocol.ts` and `loop/records.py` `policy_id`, vectors computed with Python hashlib and pinned on both sides; sample mode only, so an argmax id never changes). `policyActor` / `PolicySeat` take `play: {temperature_ppm?, truncation?}` and put it in each query; `sampleU` is unchanged (its label holds the policy id, so a tempered policy draws its own `u`). **Encoder, candidate parser, networks, checkpoints and the C1/C6 checker** (`ml/areneon_ml/model/`, `ml/areneon_ml/checkpoint/`, ADR-010 §3, §5, #839). `GameData.from_table(engine_data)` indexes the hashed engine-data export: one `IdVocab` per vocabulary (species, moves, items, abilities, statuses, weathers, terrains, types; index 0 is none, 1 unknown, the engine's ids follow in the export's order) and the numeric attribute tables (types, base stats, weight; move power, accuracy, priority, PP, target and flag one-hots; item flags), each column scaled by the largest value in the data. No list of game content is written in model code, so a vocabulary grows with the table. `Encoder(game, EncoderConfig).encode(query)` reads only `query["observation"]` (`player`, `kind`, `log`, `team.team`) and `query["candidates"]` (`choice`, `pending`): the log goes through `reduce_channel`, the player's last `|request|` gives the Pokémon order (`switch N` / `team NNNN` name the Pokémon at that request position) and the move ids, and it returns tensors without a batch dimension (`EncodedQuery`: one token row per own then opponent Pokémon, the field features, per-candidate slot parts, the picked team tokens and the `pending` flag). It ignores `decision_context`, `identity` (so `rqid`), the `rqid` inside `|request|` lines and every verdict field, so the A1 and A2 forms of a decision give equal tensors (tests over every request of the `fixtures/a2/` recordings and the `policy-query` samples). Volatiles and field/side conditions are engine-owned ids with no vocabulary yet, so they are SHA-256 bucketed into `volatile_buckets` / `condition_buckets`. `encoder_version` is `enc<format>:` + SHA-256 of the engine-data hash, the attribute tables as built, the config (scales included), the feature layout and the index constants (genders, request kinds, events, target codes, slot letters, the bucket hash), so a pin bump or any such change is a new version, never a silent remap. A change in how a value is computed from the state, with the same names and constants, is not visible to the hash: bump `ENCODER_FORMAT`; a golden test pins one version string and the tensor digests of fixed queries and fails on such a change. The A1/A2 equality is also tested on `fixtures/showdown/<format>/a2-pairs.json` (the A1 replay's observations and the A2 frames' observations of the ADR-005 fixtures with candidates from the real `enumerateCandidates`; rewrite with `node packages/bot-client/scripts/capture-encoder-pairs.ts`, a bot-client test compares it with a fresh capture). The encoder raises (fails closed) when an observation's kind does not match its request or candidates, or a Pokémon shows more moves than `max_moves`. `parse_choice` (`model/candidates.py`, re-exported by the worker) splits a canonical candidate into `SlotAction`s (pass, move with optional target and event, switch) or a Team Preview order and refuses any other shape with `UnsupportedCandidate`; `ParsedChoice.format()` is its exact inverse, and `tests/ml/model/test_candidates.py` round-trips every candidate of every `fixtures/showdown/**/choices/*.json`. `CheckpointRecord` (`packages/schema/contracts/v1/checkpoint-record.schema.json`, generated TS and pydantic types, corpus samples in `fixtures/contracts/v1/checkpoint-record/`) is the content-addressed provenance record of one frozen checkpoint; `checkpoint/record.py` reads it (sorted and unique hash arrays, no id referring to the record itself). Part 2 (networks and checkpoints, #839). `PolicyNetwork(role, game, ModelConfig)` (`model/network.py`) is one architecture per role, built and stored separately: a transformer over the entity tokens plus a field token and an aggregation token (attention written out as matmul and softmax, no fused kernel), a candidate head (a `battle` candidate embeds its two slot actions, move, target, event, acting Pokémon and switch-in tokens; a `preview` candidate its ordered team positions; both add the pending flag, cross-attend over the state and score against the aggregation token) and a value head on the aggregation token. Every size is configuration (`ModelConfig`: `d_model`, layers, heads, `d_ff` and the nested `EncoderConfig`; there are no defaults: the `model` section of the run's `TrainingRunConfig` carries the values and code only bounds them), same-seed initialisation is claimed for one machine and software only, vocabulary sizes come from `GameData`, and attribute tables are buffers derived from the engine data, not parameters. `collate` pads queries into a `Batch` (training may batch); evaluation runs one query per forward pass, a batch of one with no padding, on CPU with `configure_cpu_inference()` (deterministic algorithms, one thread), and `tests/ml/model/test_network.py` shows a query's logits are bit-identical alone and after others, and equal for the A1 and A2 forms. A checkpoint (`checkpoint/files.py`) is one safetensors file: the tensors, and `__metadata__` with the format, role, model config, encoder version and engine-data hash. The writer is our own so the bytes are deterministic (the library orders metadata by hash-map iteration); the id is the SHA-256 of the bytes; `load_checkpoint(data, game, expected_id, role)` (the id is required and checked before anything is read; the configuration is bounded, so a crafted file cannot allocate without limit) refuses bytes that do not hash to the id, another role, engine-data table or encoder version, an invalid configuration, and tensors whose names, dtype or shape differ from the network's. No pickle and no `torch.load` anywhere (a syntactic AST scan of all of `ml/areneon_ml` (a guard, not a proof: it misses aliased and dynamic imports) bans imports of pickle, dill, cloudpickle, shelve, marshal and numpy and calls of `torch.load` / `torch.jit.load`). numpy is not in the closure: the writer and reader move bytes through `ctypes`/`torch.frombuffer`. `python -m areneon_ml.checkpoint init --role … --seed … --engine-data … --run-dir … --model-config f` (the `model` section of a `TrainingRunConfig`, required) writes a seeded, untrained checkpoint (generation 0, and the input of the worker tests); learner state and training are below (#840). `checkpoint/provenance.py` is the C1/C6 checker (`ProvenanceGraph(records, sources)`; the `sources` registry is a HAND-SUPPLIED, UNHASHED input for now, a documented deviation from ADR-010 §5 until follow-up #853 derives and hash-binds it from the league run record: it must be canonical (RFC 8785) JSON, and `classify` / `independent` print its hash so an evaluation plan can bind it; `python -m areneon_ml.checkpoint classify|independent --records <dir of CheckpointRecord json> --sources <json>`): the ancestry of a checkpoint is itself plus everything reachable through `parent`, `league_opponents`, `exploiter_target` and the generators of its training sets (the `sources` registry maps each training-set hash to the checkpoints that generated it; an empty list is an outside behaviour-cloning or fine-tuning source, and a set missing from the registry is refused); C6 independence is disjoint ancestries (learned checkpoints and data sources; scripted baselines and the team pool are not nodes), C1 calls an opponent `seen` when it is in the candidate's ancestry, a scripted baseline, or a related lineage, and `held_out` only when every opponent checkpoint is an evaluation exploiter of the candidate or an independent lineage (one related member of a Preview + Battle pair makes the pair `seen`). The records must agree with each other: a parent shares its child's encoder version, a parent shares the child's role (a warm start cannot cross architectures), league opponents and the exploiter target may be either half of a frozen Preview + Battle pair, and nothing synthetic descends from a private checkpoint. It fails closed: a referenced checkpoint without a record, a repeated record, a cycle, or an exploiter in its own target's league (C3) is a `ProvenanceError`.

**Mechanics probe** (ADR-016 slice 1, `packages/showdown-bridge/src/mechanics-*.ts`, `scripts/mechanics.ts`). A Mega Evolution is its own action (order 104, speed before the Evolution): Mega groups come first in speed order, `runMegaEvo` runs on the scenario battle in that order, `getActionSpeed` is read again for every action, and the move groups follow, so a Mega's new Speed counts that turn. Tie groups are the runs of actions `comparePriority` calls equal (indices ascending in a group, an Evolution's index appearing again for its move), never sampled; `order`, `priority` and `speed` are the action's own keys after the Evolutions (a switch is order 103, priority 0; Trick Room makes `speed` negative, the champions mod has no wrap, so Speed 1809 and up acts last: the contract's `speed` minimum is -99999, a bound loosened within v1). **Damage probe** (slice 3, `mechanics-damage.ts`, `mechanics-random.ts`). The engine's own `getDamage` deals every number. The scenario battle always holds two Pokemon a side: the declared one in slot 0 and a partner of the same species with no ability and no item (so both foes are present and the engine sets `spreadHit` itself, a screen sees more than one active Pokemon, and no ally ability changes the declared Pokemon's damage). Declared state is applied after the start, absolute: Mega (`runMegaEvo`), HP, status, boosts, side conditions, Trick Room, and the field is cleared first so a weather or terrain a switch-in set never survives unless declared. **Opponent usage prior and belief configuration contracts** (ADR-025 §2, §5, slice 1 part 1, #1119; `packages/schema/contracts/v1/usage-prior.schema.json` and `belief-config.schema.json`, generated TS and pydantic types, samples in `fixtures/contracts/v1/usage-prior/` and `belief-config/`; readers `packages/showdown-bridge/src/usage-prior.ts` / `belief-config.ts` and `areneon_contracts.usage_prior`; integers only, closed, no derivation or belief code yet). **TrainingRunConfig, PPO learner and learner state** (`packages/schema/contracts/v1/training-run-config.schema.json`, `packages/showdown-bridge/src/training-run-config.ts`, `ml/areneon_ml/learner/`, ADR-010 §1, §5, #840). `TrainingRunConfig` is the one record of a run's values: lineage and format, every seed (`run_key`, the two initialisation seeds, the learner's generator), the `model` section (encoder and network sizes), the `generation` plan (self-play games, games per scripted baseline, `max_turns`, `n_parallel`, latency budgets, handshake timeout, `max_line_bytes`), the `ppo` settings and the learner's `device` (`cpu` or `cuda`) and thread count. Contracts carry no floating-point numbers, so real values are integers in millionths (`learning_rate_micro`, `clip_micro`, ...) or billionths (`adam_eps_nano`); `areneon_ml.learner.config.read_run_config` is the one place that divides them. `ppo.target_kl_micro` (optional, ADR-010 erratum A1, a minor change within v1): after each complete epoch, if the mean of that epoch's per-minibatch `approx_kl` (minibatch order) is greater than it, the role's remaining epochs are skipped; the train report then carries per role `epochs_run` and `kl_stopped`, and both keys are omitted without the field so existing reports keep their bytes (the dashboard reader takes them as optional keys). `ppo.learning_rate_schedule` (optional, ADR-010 erratum A1, a `kind`-tagged `oneOf`: `constant` or `linear {final_micro, generations >= 1}`): update `t` (the learner generation counter, from 0) uses `L0 + trunc((Lf - L0) * min(t, generations) / generations)` millionths in exact integers (`LinearSchedule.rate_micro`), set on both optimisers before the epochs; the learner-state sidecar records `learning_rate_micro` (the newest update's rate) only for `linear`, so other runs keep their `learner_state_hash`, and a restore refuses a sidecar whose rate is not the schedule's. The reader rules the profile cannot say (heads divide `d_model`, `max_picks` ≤ `max_team`, a baseline listed once) are checked by `read_run_config` and by the TS `readTrainingRunConfig`, which also gives `runConfigHash` (SHA-256 of the JCS bytes, `CheckpointRecord.run_config_hash`). League mixture and freeze-interval values are not in v1: they come with the league scheduler (Wave 5). The learner is PPO with GAE over the TrainingExample stream: `learner/data.py` reads a stream only through `read_stream` with its manifest, refuses a set that is not `learner_ready` or was not played by the `behaviour_policy_id` it trains, and splits each Episode into one Preview step and one Battle trajectory (encoded from the example's observation and candidates alone). The reward is the game score at the last step of a trajectory (win 1, tie ½, loss 0, `ppo.GAME_SCORE`); every earlier step, a refused pending choice among them, has zero immediate reward. `learner/trainer.py` recomputes the behaviour policy's log-probability and the value of every decision from the frozen weights with no gradient (no probability is stored in an Episode), computes advantages with GAE, then runs the configured epochs over minibatches shuffled by the learner's own generator; the loss is the clipped surrogate over a softmax across the real candidates (`ppo.py`, checked against hand-computed values) plus the value error and the entropy bonus. Determinism claim: on CPU, with the config's thread count and deterministic algorithms, the same inputs on the same machine and software give bit-identical weights; nothing is claimed across machines or torch builds, and a CUDA learner is not bit-reproducible (its run config, with `device: cuda`, hashes differently). The learner state (`learner/state.py`) is `learner-<g>.safetensors` (both networks' weights, the Adam moment tensors, the generator's state tensor) plus `learner-<g>.json` (JCS: generation, run config hash, seeds, PPO settings, optimiser step counts); `learner_state_hash` is SHA-256 of `JCS({tensors_sha256, sidecar})`. `restore_state` loads only through safetensors and a JSON parser, recomputes the hash, refuses a state of another run config, a sidecar that contradicts the networks and tensors of another name, dtype or shape, and changes the learner only after every check. `checkpoint/files.py` gained `pack_safetensors` / `unpack_safetensors` (float32 and uint8) beside the checkpoint writer.

**Supervised cloning learner** (`packages/schema/contracts/v1/clone-run-config.schema.json`, `packages/showdown-bridge/src/clone-run-config.ts`, `ml/areneon_ml/learner/clone*.py`, ADR-019 track 1, ADR-010 erratum A2, #967). `python -m areneon_ml.learner clone --config C --stream-dir D --engine-data E --version-manifest V --out O` trains a Preview and a Battle network, separately, to imitate a scripted teacher (`damage-aware@v1`) from its learner-ready `TrainingSet` (`D/stream.jsonl` and `D/training-set.json`, read only through `trajectories` / `read_stream`), and writes the new directory `O` (never overwritten; built beside it and renamed): `checkpoints/<id>.safetensors`, `records/<id>.json` (a `CheckpointRecord` each, named by id so `python -m areneon_ml.checkpoint classify|independent --records O/records --sources O/sources.json` reads it as it is), `sources.json` (the teacher set hash mapped to `[]`, an outside behaviour-cloning source), `clone-state.safetensors` / `clone-state.json` (weights, Adam moments, generator state, a JCS sidecar of `kind: "clone"`; its `state_hash` is the records' `learner_state_hash`), `clone-report.json` and `clone-run-config.json`. `CloneRunConfig` v1 (integers only, closed; `cloneRunConfigHash` / `CloneConfig.hash` is SHA-256 of its JCS bytes and the records' `run_config_hash`) holds the lineage, format, seeds (`run_key`, the two initialisation seeds, the learner generator), the `model` section (the shape of `TrainingRunConfig.model`; heads divide `d_model`, `max_picks` ≤ `max_team` are reader rules on both sides), the `teacher` (`behaviour_policy_id` `<name>@<commit>`, never a learned `policy:<hash>` pair, and `training_set_hash`, the SHA-256 of the manifest's JCS bytes), the `clone` settings (`epochs`, `minibatch_size`, `learning_rate_micro`, Adam betas and epsilon, `max_grad_norm_micro`, `holdout {key, ppm}`) and the learner `device` / `threads`. `clone.check_teacher` fails closed: the manifest must be synthetic, `learner_ready`, played by the named teacher and hash to `teacher.training_set_hash`. The loss is `ppo.policy_terms`' softmax over the real candidates (padding masked), `-mean(log p[teacher choice])`, per minibatch of a seeded shuffle (`torch.randperm` on the learner generator, Preview first then Battle); the value head has no label and is untrained here (the PPO phase learns it). The held-back part is chosen per Episode by `held_back(key, episode_hash, ppm)`: HMAC-SHA256 over the 64 hex characters, first 8 bytes big endian as n, held back when `n * 10^6 < ppm * 2^64` (the rule shape of ADR-015; ppm at most 500,000; a role with nothing left to train on is refused). The report holds, per role, the loss of each epoch and the agreement on the training and the held-back parts (steps, mean cross-entropy, top-1 hits against the teacher's choice, and `chance`, the mean of 1/candidates), deterministic values only. The records carry `parent` absent, `training_set_hashes` the teacher set, no league opponents, `data_class` synthetic, a `team_set_manifest_hash` over the own teams the examples' observations carry, and the version manifest of the teacher games (the `--version-manifest` file: the teacher run must provide it). Determinism claim as for the PPO learner (CPU, one machine and software; `configure_learner` sets it up). `Trajectory.episode` (new, optional) lets the split find an Episode; `state.gather_tensors` is the shared tensor collection of `pack_state`. Not here: `TrainingRunConfig.warm_start`, the loop and the KL anchor (next slices), the teacher run (#965).

**Warm start** (`TrainingRunConfig.warm_start`, `ml/areneon_ml/loop/warm_start.py`, ADR-010 erratum A2, ADR-019 §4, §6, #966). An optional `warm_start: {preview, battle}` (two 64-hex checkpoint ids; a minor change within v1: absent keeps today's bytes and `run_config_hash`, an older reader refuses it; both readers also refuse one id for both roles) makes generation 0 a declared cloned pair instead of the seeded random pair. Nothing is fetched: `python -m areneon_ml.loop import-clone --clone-dir O --run-dir R` copies a `learner clone` output into the run directory (the checkpoints into `checkpoints/`, the records into `warm-start/records/<role>.json`; it checks each record is a clone record, each file hashes to its record's id and `sources.json` maps the teacher sets to `[]`; rerunning is a no-op and it never replaces a record with other bytes). At the start of generation 0 (and when a run is resumed at generation 0) `load_warm_start` loads both through `load_checkpoint` and refuses, as a `LoopError` (exit 3), a file missing from the store, one that does not hash to its id, another role, another engine-data table, encoder version or `model` section than the run's (the whole `ModelConfig` must be equal) or bytes that do not re-serialise as themselves, and a record that is not a clone record (empty `training_set_hashes`, a `parent`, an exploiter target or league opponents, not synthetic), made for another encoder version or format, or naming another checkpoint. Generation 0 freezes the pair with no learner step: its checkpoint ids are the cloned ids and its `records/<role>.json` are the clone records byte for byte (a checkpoint has one record and the provenance graph refuses a second), so `learner_state_hash` and `run_config_hash` inside them are the cloning run's; the generation's manifest and learner state (`learner-0`) are this run's. The learner's Adam moments and generator start fresh from the cloned weights (the supervised phase's optimiser state is not carried over); generation 1 is the first policy-gradient step and its records name the cloned ids as `parent`. `sources_registry` / `export_provenance` map every training set a generation-0 record names to `[]` (an outside behaviour-cloning source), so `classify` / `independent` see the teacher set in the ancestry: two warm runs on one teacher set are not independent (C6, ADR-019 §6), runs on different teacher sets or none are. Resume and the SIGKILL claims hold (tests kill at every stage of generations 0 to 2 of a tiny warm run and compare manifests and learner state bytes). **Battle-only (#1165):** `warm_start` may be `{battle}` alone (`preview` optional, a minor change within v1; `{preview, battle}` and an absent key keep every hash and byte; both readers refuse `preview` as the only key through the schema's `required: [battle]`, and one id for both roles). Only the named roles are imported (`import-clone --roles battle` copies the Battle checkpoint and record and neither reads nor copies the output's Preview; `import_clone(..., roles=("battle",))`), loaded and checked (`load_warm_start` iterates the named roles), and carry clone records; the other role starts from the seeded init of its `seeds.init_*` exactly as a scratch run's generation 0 (same checkpoint id) with an ordinary built record (no training sets, no parent, this run's state hash), and `Sealing.records` holds the clone records of the warm roles only. `ppo.value_warmup` and `ppo.anchor` act only on the warm-started roles (`Learner.warm_roles`): an unwarmed role trains as plain PPO from update 0, the anchor networks are given exactly for the warm roles (`LearnerError` otherwise), and `train-report.json` carries `value_warmup`, `anchor_kl` and `anchor_beta_micro` for the warm roles alone (the learner-state sidecar's `anchor_beta_micro` is the schedule's value for the warm role). Provenance: the Preview lineage starts at the seeded init (generation 0's Preview has no teacher set), the Battle lineage names the clone; from generation 1 both descend from the cloned Battle network through the games it played (the sources registry maps the set to the pair that played it). Why: damage-aware@v1 plays one fixed actor-rule Preview choice, so a cloned Preview would start near-deterministic and the anchor would hold it there. Tests: `tests/ml/loop/test_warm_start_battle_only.py`. Not here: the KL anchor, human-data warm starts, the experiment runs.

**Value warm-up** (`ppo.value_warmup`, `ml/areneon_ml/learner/trainer.py`, ADR-019 §4, #1111; `docs/training-run.md` section 5). Optional `{generations: N}` in the `ppo` block (integer at least 1; a minor change within v1: absent keeps today's run config hash, learner-state hash and every generation file); a reader rule on both sides (`readTrainingRunConfig`, `read_run_config`) requires `warm_start`. The learner updates with index below N (`value_warmup_active`; generation 1 is update 0) train the value head only: every parameter outside `value.*`, the shared trunk included, has `requires_grad` off for the update (restored after), so the cloned policy's outputs stay byte-identical, the backward pass is the value error alone (`value_coef` is not applied and `target_kl` is skipped), and Adam, which skips a parameter without a gradient, holds moments for the value head only; the same optimiser serves PPO afterwards (the value head's moments carry on, the rest start at update N + 1). The learning-rate schedule's index counts the warm-up updates. `RoleReport.value_warmup` (`true`, in `train-report.json` only on a warm-up update; the dashboard reader's optional key set gained it) and the sidecar's `ppo` block record it only when set. Resume needs nothing new: the position is the restored generation counter. Tests: `tests/ml/learner/test_value_warmup.py` (frozen policy, value-only Adam state, byte-identical logits, resume at and inside the warm-up) and `tests/ml/loop/test_value_warmup.py` (a warm loop: only `value.*` tensors move through the warm-up, killed anywhere resumes to the same files).

**Model options** (`ml/areneon_ml/model/options.py`, ADR-010 erratum A4 item 2, #1002; the base of the architecture arms of Epic #1000). `model.options` (network) and `model.encoder.options` (encoder) are optional closed objects of the `TrainingRunConfig` (a minor change within v1; `EncoderConfig.options` and `ModelConfig.options` hold them as sorted tuples). **Absent keeps today's bytes**: `as_dict` omits the key when no option is set (an empty object counts as none for the bytes and `encoder_version`; its run config hash still differs from an absent key), so `encoder_version`, checkpoint bytes and ids, learner state hashes and the layout of every existing record are unchanged (tests pin a checkpoint id and the encoder version computed before the change). Present, an option is part of the run config hash, `encoder_version` (encoder options, through the config) and the checkpoint's `model_config` metadata. `REGISTRY` (per scope, `OptionSpec(name, check, layout_changing)`) holds one option so far, the encoder option `candidate_matchup` (below); any other name is refused, and each further arm's ticket adds its spec and its schema property (tests register test-only specs with `monkeypatch`). **`candidate_matchup`** (ADR-022 tier B, ADR-010 erratum A5 item 1, #1023; `"model": {"encoder": {..., "options": {"candidate_matchup": true}}}`, only `true` is a value, layout changing): a battle candidate's move slot actions gain seven categorical columns after the five base ones (`BASE_CAND_COLUMNS`): for each opposing position and the ally, the engine-data type-chart cell (`GameData.type_chart`, the export's `types[].damage_taken` code) of the move's type against each of the position's first two shown types, and a same-type flag (the move's type is one of the acting Pokemon's shown types). A cell is `RESERVED` + the export's code (so the network embeds the engine's own codes; no multiplier, product of types or same-type bonus value is written anywhere, and a source scan in `tests/ml/model/test_matchup.py` holds that), `NONE` for an empty or fainted position, a missing second type, a status move, a switch or a pass. Only the species a position shows enters (`temp_species` or `species`, else the roster's base species): never an unrevealed item, ability or move, and a type change by a volatile is not tracked. The format has no Terastallisation (the reducer refuses a `-terastallize` line). The Battle network embeds the columns (`matchup`, `same_type` embeddings, wider `slot_parts`); the Preview network ignores them. With the option absent the layout, `encoder_version`, tensors and checkpoint ids are today's (pinned tests); with it the config and layout move `encoder_version` and `GameData` gained the chart tables (not part of `attribute_digest`). The checkpoint `format` is `"2"` (`FORMAT_OPTIONS`) only for a config with a `layout_changing` option and `"1"` otherwise; `load_checkpoint` refuses a format that does not fit the file's options and, given `configured` (the caller's `ModelConfig`), a file whose network or encoder options differ (`CheckpointOptionsError`, a `CheckpointFileError`); the worker passes the model section of `<run-dir>/run-config.json` as `configured` when that file exists (a hand-made run directory without it is checked by the checkpoint alone; exit 4 on a mismatch or an unusable section). The learner-state sidecar carries `model_options` (`network` / `encoder`) only when an option is set, and `restore_state` refuses any difference, in either direction, with `LearnerOptionsError` (a `LearnerStateError`) before the run config hash check. The `clone-run-config` contract takes the same optional `model.options` and `model.encoder.options` objects (#1168; same rules, absent keeps the record's bytes and `clone_run_config_hash`; present flows through `ModelConfig.from_dict` into the clone's networks, `encoder_version`, checkpoint metadata and format), so a clone made with `candidate_matchup` warm-starts only a run that sets it and a run without it (or the reverse) refuses the clone at generation 0 (`tests/ml/loop/test_warm_start_clone_options.py`).

**Damage-aware baseline inputs** (ADR-018 §3 to §5, slice 1, #943; the scorer, `ActorContext.team` and the A1 actor are slice 2). `DamageAwareConfig` (`packages/schema/contracts/v1/damage-aware-config.schema.json`, generated TS and pydantic types, samples in `fixtures/contracts/v1/damage-aware-config/`, integers only) is the reviewed assumption record, committed as `config/baselines/damage-aware.v1.json` (a new version is a new file, never an edit): the rule for every unrevealed opponent field (`item`: `none` or `fixed`; `ability` and `filler_move`: first or last in the team vocabulary's order; `nature`; a six-value `stat_points` spread), `hp_rounding` (`ceil`, `floor`, `nearest`), the `scoring` weights in ppm (`ko_weight_ppm`, `turn_order_discount_ppm`, `crit_weight_ppm`) and `epsilon_ppm` (0 for evaluation). `damage-aware-config.ts` reads it (`readDamageAwareConfig(value, vocabulary)`: the schema, then the format, the nature, a fixed item and the spread's sum against the pinned engine's `TeamVocabulary`; `damageAwareConfigHash` is the `baseline_config_hash` of the identity); `scripts/check-damage-aware-config.ts` (in `make ts` and CI) checks the committed file against the golden vocabulary, which `team-vocabulary.test.ts` holds equal to a fresh export. `damage-aware-assumed-set.ts` builds an `AssumedSet` from ONE opponent `PublicMon` of the shared reader, the vocabulary, the record and the engine: a revealed species (a forme the roster does not list falls back to its base species; a Mega Evolved Pokemon is its base forme holding the revealed stone, `mega: true`), level, gender, item, ability (only one the vocabulary lists for the species), and moves are used as revealed, the rest follows the record, and an unrevealed move is never invented: a `filler_move` is added only to a set with no placeable revealed move, listed in `filler_moves` and never a threat; a revealed move no legal set can hold (Struggle, Transform copies) is listed in `unplaceable_moves`. The interpreter's `omniscient` option (`interpretChannel(player, lines, dex, true)`) makes p1 `own` and p2 `opponent`, builds both rosters from `|poke|` lines, accepts exact HP on both sides (`state.omniscient` is true, winner is `p1`/`p2`/`tie`), refuses a `|request|` and a `|split|` marker (the engine's omniscient stream already carries the secret line and no marker, so one is a defect: fail closed). The mode is the page generator's, not the data's: `replay_page.assets(mode)` writes `var AR_MODE = "player"` or `"omniscient"` as the first line of the hashed script, `boot` passes it to `init` as `options.omniscient`, and a data block that claims `omniscient` on a player-view page changes nothing (a test). Decisions are placed by the log's structure (`decision_points`: Team Preview after `|teampreview`, the k-th move decision at `|turn|k`, a forced switch at that seat's replacement `|switch|` after one of its faints, else at the end of its turn; a refused choice and its retry share a place); request numbers are shown, never used to place, because they count wait requests. **Damage-aware actor** (ADR-018 §1, §2, §4, §5, §6, slice 2, #944; `packages/showdown-bridge/src/damage-aware-actor.ts`, `-view.ts`, `-score.ts`, `-choice.ts`, `-identity.ts`). `damageAwareActor({engine, vocabulary, config, mechanics, snapshot?, data_class, commit?, seed?})` is an A1 `Actor` for ONE seat of ONE game (a second use of it, another seat or a shorter channel is a `DamageAwareError`); it needs `ActorContext.team` (a missing context or team is a `DamageAwareError`) and plays under `guardActor` with role `scripted`. At Team Preview it plays the `actor-rule` candidate. At a move request with at least two non-pending candidates it feeds the new channel lines to the shared reader (`createInterpreter`, incremental), joins each own active Pokemon of the request to its set of `ActorContext.team` (by the request's name; exact HP, status and held item from the request, boosts and Mega from the reader) and builds each opposing active's assumed set (`buildAssumedSet`, never the real team). Every candidate is the sum of its slot parts; a part is a damaging move's value per target (status moves, switches, `pass`, ally targets and a locked move without a target score 0; the request's target type picks single, every opposing active, or a random one averaged; any other type fails closed), each from ONE `damage` query (one attacker, one defender, one move, one declared field: weather, terrain, Trick Room and the four side conditions read from the reader) whose result is `damageValue` in integer ppm: the mean over the 16 no-crit rolls of `min(roll, hp) / hp` plus `ko_weight_ppm` times the share of rolls that reach the target's HP, mixed with the crit vector by the probe's exact chance times `crit_weight_ppm` (the probe gives no KO counts yet, so the share is counted from the rolls here). A spread move is the sum of its single-target values (no spread modifier and no ally damage in v1). The turn-order discount: when a foe's revealed damaging move can knock the actor out (some no-crit roll reaches its HP) one 1v1 `speed_order` query (the own Pokemon's action against that foe's first KO-capable revealed move; other actives do not enter the order) puts both actions in the order the engine gives, and a foe in a strictly earlier tie group discounts that (action, target) term, not the whole action, by `turn_order_discount_ppm`. The highest non-pending score wins, the first of equal scores in canonical order (so all-zero scores play the `actor-rule` candidate); forced switches, a lone candidate and pending-only sets are answered without scoring. A `unsupported` probe result scores 0 and is counted; a speed order the probe cannot queue (an action that queues more than a move and a Mega Evolution, as Focus Punch does) is counted as `unsupported` too and applies no discount (every other probe failure propagates); `refused` throws. A reader-flagged line among the lines fed since the previous request (per request, not sticky: a later request scores on a state that holds the flagged line verbatim, which is the reader's one known limit, an Illusion twin), an own Pokemon the reader does not show, or an `AssumedSetError` plays the `actor-rule` candidate and is counted (`reader_fallbacks`, `assumed_set_fallbacks`). `report()` gives `{policy_id: damage-aware@<commit> (v1 by default), identity, identity_hash, counts}`; the counts (`decisions`, `preview_decisions`, `scored_decisions`, `queries`, `probe_runs`, `unsupported_queries`, `reader_fallbacks`, `assumed_set_fallbacks`, `epsilon_plays`) are integers per game, and the ProgressGameRecord fields that store them are slice 4. A per-game memo of probe results by query hash saves repeated queries (a pure function of the query, so no answer changes; `probe_runs` counts the probes actually run). `damageAwareIdentity` / `damageAwareIdentityHash` is the baseline identity of ADR-018 §5: SHA-256 of the JCS of `{baseline_config_hash, mechanics_config_hash, adapter_format, reader_sha256, version_manifest}`. `epsilon_ppm` above 0 needs the seat's baseline seed and draws from the `random-legal` Mulberry32 stream (`randomBelow(1,000,000)`, a small export added to `random-legal.ts`, once per move or forced-switch request, then `randomLegal` when the draw falls under it); with 0 nothing is ever drawn (a spy test). The actor's choice is a pure function of the pin, both configs, the reader, the own channel, the own team and the candidates: `test/damage-aware-invariance.test.ts` plays seeded battle pairs against a first-legal opponent whose team differs in unrevealed fields (nature, Stat Points, rotated items, moves 2 to 4) and requires equal choices at every request with an equal player channel, shows the test has teeth with a baseline given the real team (`assume` option, different choices), repeats it for a changed battle seed and a changed actor seed, and checks two runs equal in choices, counts and identity. The test seams are `probe`, `random` and `assume` options (the defaults are the real probe, the real stream and `buildAssumedSet`). **Measured cost** (`scripts/damage-aware-budget.ts`, the random-play corpus teams against `random-legal`, baseline seat alternating, real probe; one shared machine, Intel i7-14700KF, load average 9 to 18 from another run, so the figures are pessimistic and are not claimed to repeat): two runs of 30 games each (run 2 also gives the extrapolation below; per game it measured a mean match of 6.2 minutes per 200 games and 10.5 at the 95th percentile game, run 1 5.9 and 9.6) gave per decision a median of 169 and 174 ms, a mean of 168 and 167 ms, a 95th percentile of 359 and 349 ms and a worst of 518 and 505 ms (302 and 318 decisions, all well under the run's 30 s battle budget), and per game a mean of 1.78 and 1.87 s (11 to 12 decisions a game: random-legal opponents lose early), about 13 probe queries a decision, about 10% of them `unsupported`. ADR-018 assumes about 25 baseline decisions per game against a learned policy: at the measured mean decision that is 14 minutes for a 200-game match, and 29 minutes if every decision cost the 95th percentile, against the proposed 30 minutes (so the budget holds with little margin in the pessimistic reading; the owner confirms or changes it).

**Candidate feature builder** (ADR-022 tier A, slice D1 builder part, #1026; `packages/showdown-bridge/src/candidate-features.ts`, `damage-aware-view.ts`). `candidateFeatures(engine, configs, channel, team, candidates, memo?)` is a pure function of the player's own `PlayerChannel` (the channel must end in the request being answered, read from its last `|request|` line), the player's own team as brought, the candidate strings and the configs `feature_set_hash` names. It feeds the channel to the shared reader, builds each opposing active's assumed set exactly as the v1 baseline does (the shared `damage-aware-view.ts`: `buildAssumedSet`, the public-status ability rule, `assumedHp`; the belief-based sets are ADR-025 slice 5, #1135, and would be a new feature set id) and asks the probe ONE `damage` query per distinct row `(slot, move position, target position, Mega flag)` that some candidate (pending ones included) uses with a damaging move into an opposing active; a spread or random-target move gets one row per foe it can hit, each a single-defender query; a status move, a switch, a pass and an ally or self target have no row. A request with no move to score (Team Preview, forced switch, wait) has no rows. Rows are returned in canonical order (slot, move, target, Mega false first), so bytes depend neither on candidate order nor on the memo. A row is `computed` with `mean_ppm` (the mean over the 16 no-crit rolls of `min(roll, hp) / hp`, floored, the baseline's `rollsValue` with no KO weight), `max_ppm`, `min_ppm` (the largest and smallest roll, clamped at `hp`, as a share of `hp`) and `ohko_rolls` (the probe's own `ko.ohko_no_crit` count of the 16 rolls, or null when the probe's `ko` is `unsupported`; ADR-016 slice 5 exists, so the row has it from the first feature set), or `unsupported` with the probe's closed reason, never a guess. `hp` is the shown percentage applied to the assumed maximum HP with the record's `hp_rounding`. `featureSetIdentity` / `featureSetHash`: SHA-256 of the JCS of `{feature_set: "probe-damage/1", mechanics_config_hash, assumed_set_config_hash, adapter_format, reader_sha256, version_manifest}`; a change of any part (or of what a row holds) is a new feature set. The per-game memo is `createFeatureMemo()` (`results` keyed by the probe query's hash, the defender's HP stays in the query so it stays in the key; `counts` has `queries`, `probe_runs` and `unsupported_queries`, where `queries` includes the maximum-HP and status-ability queries the assumed sets need). A request that cannot be featured throws `FeatureBuildError` with a code (`no_request`, `reader_flagged` (a line the reader could not take since the previous request), `reader_gap`, `assumed_set`, `probe_refused`) and a fixed message; the caller (D2's `policyActor`) decides what then, and a defect (a shape the baseline does not know) propagates as `DamageAwareError`. The type rule: the channel parameter is the branded `PlayerChannel`, so an `OmniscientLog`, `HiddenVerdicts`, `BattleRecord`, a seed or an unchecked log is a compile error (a type test), and a source scan requires no runner, omniscient or seed import. The shared module `damage-aware-view.ts` holds what the baseline and the builder both read a request with (own combatants, foes, declared field, the memoised probe call, `DamageAwareError`); `damage-aware-actor.ts` uses it and is unchanged in behaviour (its tests pass unmodified; `foesHit` takes the foes as a thunk so a move that hits no foe builds none and asks the probe nothing, as before). Measured on four recorded random-play seats (two seeded battles, both seats, real probe, one shared machine): 15 to 19 decisions each, 106 to 148 rows, memo hit rate on the probe queries 19 to 21 percent (random teams repeat few queries; a longer game with stable matchups would hit more), 65 to 105 ms per decision. Invariance (#1029, `test/candidate-features-invariance.test.ts`, real probe): seeded battle pairs whose p2 teams differ in nature, Stat Points, items, moves 2 to 4 and abilities give byte-identical `CandidateFeatures` (rows and `feature_set_hash`) at every p1 request with an equal channel (at least 20 points over at least 2 pairs); a revealed ability is used as revealed; a builder given the real opponent team through `FeatureConfigs.assume` (a test seam) gives different rows (negative control); a canary scan of never-public names in the JCS bytes; a type test. Not here: latency and the worker-thread pool, the `PolicyQuery` / `TrainingExample` field, the encoder, `probe-damage/2` (incoming threats, turn order).

Nothing about the generation depends on the split: a game's result is a function of its plan entry alone (the worker is deterministic and `u` is the harness's), and `training-loop.python.test.ts` and `league-generation.test.ts` require the same files and learner-state hashes for any `S` and `K`. Measured on this machine (shared, CPU, full size 384 games, generation 1): the script took 332 s and 330 s with one worker and 101 s, 102 s and 102 s with `S=4 K=3` (`S=3 K=3` 110 s, `S=6 K=2` 105 s; the generation directories are byte-identical to the one-worker run's); about 34 s of both is the pool load (`readDataset` validates every record, then `datasetPoolDetail` normalises each team again), which every game process repeats in parallel, and about 12 s the parent's serial merge (training loader, hashing, files). Progress evaluation stays unbatched and unchanged.

**Failing game processes** (#1100). A game process that exits non-zero fails the generation at once: `startShard` reports it on `exit` (not `close`, which waits for every holder of its stderr pipe) with its stderr tail, `playGeneration` aborts this process's own games (`GenerationOptions.signal`, checked before each wave and after each worker restart, so no wave and no worker restart follows) and rethrows, the CLI's `finally` kills the other children, closes the workers and removes the scratch directory, and the play scripts `process.exit` on a non-zero code so a game still running cannot keep the process alive (the cause of a 7.6-hour hang: `others` rejected, the parent returned 1, but its own games went on and restarted workers). An idle watchdog (`live_children`, `idle_grace_ms` default 60 s) fails a generation that still awaits the other processes' games with none alive and none of its own in flight. The driver's `--generation-timeout-minutes` (default 180, `NodePlayer.generation_timeout_s`) keeps the Node process in the driver's own process group (so a kill of the driver's group still ends it, as `training-loop.python.test.ts` requires) and past the limit kills it and every descendant found under `/proc` (`PlayError`, nothing committed). All operational: no output byte changes.

**KL anchor** (`ppo.anchor`, `ml/areneon_ml/learner/{config,ppo,trainer,state}.py`, `loop/driver.py`, ADR-019 §4, ADR-010 erratum A2 item 3, #968; `docs/training-run.md` section 5). Optional `{kl_micro, schedule}` in the `ppo` block (`kl_micro` 1 to 10^8; `schedule` is `constant` or `linear {final_micro 0 to 10^8, generations >= 1}`, schema defs `AnchorSchedule` / `AnchorLinearSchedule`, since the learning-rate `LinearSchedule` forbids a final of 0; a minor change within v1: absent keeps every hash, report and file); both readers require `warm_start`. The loss adds `beta * KL(pi_theta || pi_anchor)` per decision (`ppo.anchor_kl`: softmax over the real candidates, padding masked), `pi_anchor` the warm-start pair loaded by the driver (`_new_learner` calls `load_warm_start` again, a separate frozen copy: `Learner(..., anchors)`, required exactly when the config has an anchor; evaluation mode, `requires_grad` off) and scored once per generation per role with no gradient (`_anchor_scores`, one log-probability vector per step over its real candidates). `AnchorSettings.beta_micro(t)` is the integer rule of `learning_rate_schedule` started from `kl_micro`; `Learner.anchor_beta_micro(update)` decides what `t` counts: with `value_warmup` N the updates below N have beta 0 (policy frozen; no anchor pass, KL reported as 0) and update `u` >= N uses `t = u - N` (the decay starts with the first policy update; the learning-rate schedule keeps counting the warm-up), without it `t` is the update index. `RoleReport.anchor_kl` (mean over the role's minibatches, measured before each step) and `anchor_beta_micro` are in `train-report.json` only when the anchor is set (the dashboard reader's optional keys, both or neither, KL not negative; it charts "Anchor KL" beside approximate KL); the learner-state sidecar records `anchor_beta_micro` (the newest update's beta) only when set and `restore_state` refuses a sidecar whose beta is not the schedule's. **Team generator** (`packages/team-dataset`, ADR-013 §2, §3, #816; imports the engine only through the bridge). `config/teams/<format>/labels.json` (a `TeamLabelSet`) and `generator.json` (a `TeamGeneratorConfig`) are data; `check-team-labels.ts` (in `make ts` and CI) reads them against the pinned engine (every id exists, sorted and unique, no default equal to a listed value, every leaf can hold in the vocabulary, at most 65,536 cells). `labeller.ts` is a pure interpreter of the label-set record (`all_of` of leaves, first match else default) and holds no id (a test greps its source for the committed ids); a base cell is the label values read as a mixed-radix number, first label most significant (64 cells for the five committed labels). `stream.ts`: draw k of a plan has seed `"sodium," + hex32(HMAC-SHA256(generation_key, JCS({config_hash, k, plan_id, purpose: "draw"})))`; the pilot's preimage is `{config_hash, k, purpose: "pilot"}` (no plan id: one recorded pilot serves every plan of a config). `proposal.ts` draws a team uniformly from the bridge's vocabulary (roster, move pools, abilities, natures; level, team size, Stat Point total and Item Clause from the rule table; IVs, the per-stat maximum, gender, nicknames and integer item weights from the config); `draw.ts` puts it in canonical order, round-trips it through `importPaste`/`exportPaste`, asks `validateTeam` (on a copy: the validator normalises sets in place) and labels it. `plan.ts` makes the quota plan from the pilot counts: proportional quotas with a floor of `n_stratum_min` per split, and the D20 merge before any generation (a group is affordable when it has `pilot_min_hits` hits and `quota * pilot_draws <= d_max * hits`; an unaffordable group is replaced by the group one level up, dropping the last label first, which absorbs every cell under it; a plan that is infeasible even with all cells merged is refused). `binner.ts` bins accepted draws in counter order (full bin: overflow; known hash: duplicate; else binned), so a bin is an exact sample of the proposal conditioned on its stratum; `dedupe.ts` is the two-stage known-hash index (a sorted 64-bit prefix array, 8 bytes per hash, then an exact comparison in memory or in a sorted file); `rejection-log.ts` writes and hashes the log as the run goes. `generate.ts` runs it: pilot (recorded, or run), plan, one stream, then each stratum's full bin is dealt to dev, validation and training by HMAC-SHA256(assignment_key, canonical hash) order (the assignment rule of §2 so that every record has its split; `assignSplits` of #860 owns this later), every record is re-read with `readTeamRecord` and the labeller, and a bin still short at `d_max` re-plans with the short strata coarsened one more level under `<plan_id>-r<n>`. `provision.ts` sizes the ranges from a negative-binomial fill-time quantile; `range.ts` summarises a range of draws as one SHA-256 over fixed-width per-draw records, the unit the two-platform check compares. `command.ts` is the CLI (`generate`, `pilot`); output is JCS-canonical, so the same commit, config, label set, keys and references give the same bytes (`records.<split>.jsonl`, `manifest.json`, `coverage.json`, `pilot.json`, `rejections.jsonl`). The generation key of a public dataset is a public key given on the command line; sealed generation is #861. Package tests run the real validator on a few thousand draws; keep any new generation test small. Quotas: a split's share of a stratum is its share of the ACCEPTED pilot draws (rejected draws belong to no cell), while the cost rule uses the rate per draw of the stream; the `n_stratum_min` floor per stratum and split can lift a split above its request (20/20/100 over 23 strata delivers about 55/55/116), so `coverage.json` lists requested and delivered per split and the CLI prints any difference. `provisioning.exceeds_d_max` (and a CLI warning) says the 0.99 fill quantile is beyond `d_max`, because the merge decides on mean fill times and the stream stops at `d_max`. `coverage.json` also records `replan` (0 or the re-plan count) and each base cell's `held` teams per split inside merged strata. The seed preimage is the JSON object `{config_hash, k, plan_id, purpose}` (the pilot's has no `plan_id`), not the tuple the ADR writes: an ADR-013 erratum candidate. `moves_per_set` is a named config field (optional in the schema, required by the proposal). `generator.json` gives every Mega Stone (the items the roster's Mega formes require) weight 0 so a stone appears only with its Mega species; otherwise about half the free item slots hold a useless stone and the Mega label is nearly constant (a test holds the label's stones and the zero weights equal to the roster's required items, so a pin bump that adds a stone fails). Scale limits of this slice (#883): the dataset files stream. `writeDataset` writes each `records.<split>.jsonl` in 1 MiB chunks (`writeLines`), and `recordHashes` and `readDataset` read line by line (`eachLine`, `endsWithNewline` in `dataset-io.ts`), so no file is held as one string and the 512 MB string limit no longer applies to them; the bytes written are unchanged. What still sits in memory: the records themselves (`GenerateResult.records`, and `readDataset`'s `VerifiedDataset`, as objects, roughly the file size or more), the known hashes as JS strings while `sortedUnique` builds the sorted list (about 100 bytes per hash; 1.2M hashes peak near 400 MB of RSS in `scripts/measure-streaming.ts`, which writes, reads back and indexes 1.2M padded lines of a 930 MB file; the previous joined-string code fails on it with `RangeError: Invalid string length`), the binner's in-run `Set`, which holds at most 2^24 (about 16.7 million) binned teams (a V8 limit, unchanged), and the JCS string of the sorted hash list that `datasetHash` and `recordHash` build (fine to some millions of records). The CLI reports an oversize failure as exit 1; 10^8 teams needs the shard slice's binary builder. `assign-splits.ts` (#860): `assignSplits(pool, plan, assignment_key, n_stratum_min?)` is the one split rule (ADR-013 §2): within each stratum it orders the teams by HMAC-SHA256(assignment_key, canonical hash) and deals dev, validation and training by the plan's quotas; it is pure, order-insensitive, and refuses a stratum that is not exactly its bin, a team twice, a quota below `n_stratum_min` and a key that is not 64 lowercase hex digits; `generate.ts` calls it. **Committed fixtures** (`fixtures/teams/<format>/datasets/fixtures-v1/`, CC0, see its README): `teams-dev.jsonl`, `teams-validation.jsonl` (JCS lines), `manifest.json`, `hashes.json` (sorted `record_hash` / `canonical_team_hash` lists per split and the manifest hash: a Parquet shard of the split must list the same `record_hash`es), `pilot.json`, `coverage.json`, `run.json` (the public keys, sizes and generator commit); the training split is generated in the same run but never committed. `dataset-reader.ts`: `readDataset(dir, ctx)` trusts nothing (manifest against config and label set and the engine's version manifest; each record through `readTeamRecord`, the labeller, `importPaste` round trip and `validateTeam`; every stratum holds its quota; no team in two splits; the hash lists recomputed), `trainingPool(datasets, engine)` takes only `readDataset` results, recomputes every canonical hash from the paste, and returns a branded pool of dev records that `drawTrainingTeam` alone accepts: a validation record, a forged hash, a hand-built dataset or pool, or a team repeating a validation team is refused (`readDataset` also checks `vocabulary_hash` and `reference_pool_hash` against its context; `generator_commit` is checked only by the regeneration test). `fixtures.ts` + `scripts/fixtures.ts` (`write` / `check`, `--full` also reruns the 40,000-draw pilot, about 45 s) regenerate the files from the committed config; a test (about 5 s with the recorded pilot) requires them byte for byte.

**Parquet shards** (`packages/team-dataset/src/shards/`, ADR-013 §4, §6, §7, #862). A snapshot is immutable, content-addressed Parquet shards plus a `TeamSnapshotManifest`; shards live in R2 and Releases, never in git (`check_binary_files.py` rejects `.parquet`), so every test writes them to a temp dir. `columns.ts` is the column layout (parquet schema version 1: one column per record scalar, `labels` as a list of `{label_id, value}` structs, derived `stratum` and `label:<id>` columns) and the rebuild rule (`recordOf`: null, a missing or extra column, an int64 outside +-(2^53-1) or a derived column that differs from the labels refuses the shard). `layout.ts` is the layout (`S = ceil(R / 2^18)`, shard = first 8 bytes of HMAC-SHA256(`shard_key`, canonical hash) mod S, rows sorted by stratum then canonical hash, `cell_ranges`). `reader.ts` (`readShard`, hyparquet and hyparquet-compressors, both MIT, production dependencies that pass `make licences`) decodes, rebuilds, computes `record_hash` and checks row count, order, split, `logical_hash` and `cell_ranges` against the manifest; it never calls the engine. `snapshot.ts` builds the manifest (`buildSnapshotManifest`, checked by the bridge's `readTeamSnapshotManifest`), reads a snapshot shard by shard (`eachSnapshotShard`: file SHA-256 and size, one-to-one shard indices) and holds `checkFixtureAgreement` (a committed split's `hashes.json` and the shards of that split must list the same sorted `record_hash`es). `convert.ts` turns a dataset directory (`records.<split>.jsonl` or the committed `teams-<split>.jsonl`, plus `manifest.json`) into shards under `pub/v1/shards/<sha256>` and `snapshot.json` with bounded memory (one shard at a time) and reads every shard back once; `verifySnapshot` checks the shards against the dataset file byte for byte. The writer is the DuckDB command-line tool run as a child process (`duckdb.ts`): never a library import, never in a `package.json`, lockfile, Dockerfile or image (a test scans every tracked manifest), user-installed (`DUCKDB_BIN` or the PATH); `scripts/duckdb-pin.json` holds the version URL and SHA-256 of the zip and binary per platform, CI downloads and checks it and sets `ARENEON_REQUIRE_DUCKDB=1` so the real-tool tests cannot skip there (without the tool they skip, and a stand-in that writes through hyparquet-writer, a dev dependency, covers the conversion paths). The manifest's `writer` is read from the binary that ran. File bytes depend on the writer version and settings; `logical_hash` and `logical_snapshot_hash` do not (tests cross two DuckDB settings, and two versions when `DUCKDB_BIN_ALT` is set). Cross-architecture byte equality is not established: see ADR-013 §6. Measured rebuild is about 20 us per record (about 5 s per 2^18-row shard) against the ADR-013 d1 and section 5 budget of about 7.8 us (about 2 s); a read of one 250k-row shard peaks at 2.1 GB RSS (maxRSS, includes uncollected garbage), a write at 3.5 GB, while the decoded shard retains about 0.42 GB of heap after a forced GC (the ADR's 0.4 GB holds for the cache, not for the peak). The miss is to be recorded as an ADR erratum (#882). Publishing, the sampler and the working database are later slices.

**Private shards** (`packages/team-dataset/src/shards/private-shards.ts`, `private-reader.ts`, ADR-015 §2, #899): the d1 layout with the `PrivateTeamRecord` columns (`privateColumnsFor`: the record's scalars, `supersedes_record_hash` nullable, `tags` a list of strings, `holdout` a boolean, `labels`, the derived `stratum` and `label:<id>` columns; parquet schema version 1, `data_class` private, one split `owner`). It reuses `shardCount`, `shardAssigner` (HMAC of the canonical hash), `cellRanges`, the int64 rule and `recordHash` / `shardLogicalHash`. Differences: rows are ordered by stratum, canonical hash, then `team_id` (a retired record may share its team's canonical hash with an active one), cell ranges carry `active_rows` (`privateCellRanges`), and every refusal message is fixed text naming a layout column or a row position, never a value, a column name read from the file or library text (a canary test in `private-team-store`). `readPrivateShard` is engine-free and keyless like `readShard`, but the Parquet decode runs in a worker thread (`private-decode.ts`: `decodeIsolated`, an empty environment, a 4 GB heap limit, a wall-clock limit of 5 minutes by default, terminated afterwards; the worker is a `data:` module that imports the decode, so there is no separate worker script): hyparquet is written for trusted files and a damaged one can make it loop forever (a page header with a negative size), allocate without bound, or leave a rejected promise unhandled, which ends the process with library text; a seeded corruption fuzz (`snapshot-fuzz.test.ts`) found all three. Whatever the worker meets, the main thread sees the rows, a layout refusal's fixed message or `not a readable Parquet file`. The footer checks and the column-by-column read are `decodePrivateParquet` (tested in process, because the worker is not instrumented for coverage). The new column kinds (`NULLABLE_VARCHAR`, `BOOLEAN`, `VARCHAR_LIST`) are in `ColumnType`, and `DuckdbWriter.writeShard` takes `isolated: { dir, timeoutMs? }` for the private path: the tool runs with HOME, TMPDIR and cwd set to a scratch directory made inside `dir`, `DUCKDB_HISTORY=/dev/null` and nothing else in its environment (the `Runner` gained an optional cwd and timeout), the SQL starts with `SET autoinstall_known_extensions = false; SET autoload_known_extensions = false;` and locks the configuration (`SET lock_configuration = true;`) after the other settings and before the copy (a real-tool test reads the three settings back inside a child of the same shape), the tool is killed after `timeoutMs` (10 minutes by default), a failure is the fixed `WITHHELD_MESSAGE` (DuckDB's stderr can quote a paste and is never forwarded; a real-tool test provokes a DuckDB error that quotes the row and checks the public path forwards it and the private one does not), and the scratch directory is removed by `removeTree` (a best-effort chmod of leftovers, then a second try; it never throws, so cleanup cannot replace the original error; a removal that fails after a successful write is the fixed `CLEANUP_MESSAGE`). The public `writeShard` path is unchanged.

**Evaluation records and register** (ADR-010 §6, §7, §9 O1/O11, #846; code in `packages/showdown-bridge`, engine-free, Node built-ins only). **Sealed team generation** (`packages/team-dataset/src/sealed*.ts`, ADR-013 §2, protocol L1 to L5, #861). Runs only inside the isolated evaluation store (`docs/runbooks/evaluation-store.md` §9; `node packages/team-dataset/scripts/sealed.ts generate|reveal-hash|retire|verify`); no agent or CI job runs it against a real store, and the repository holds no sealed data and no key (tests use throwaway counter-derived keys and a temp store). `sealed-store.ts` is the file discipline: the store directory must be absolute, a real directory, owned by the invoking user, mode 0700, outside any git working tree and below no group- or world-writable parent (sticky accepted); directories are created 0700 and files 0600, never overwritten, and a loosened file is refused on read; JSON parse errors never quote the text. `sealed.ts`: the key and the salt are 256 bits from `generateSecret` (the OS CSPRNG; tests inject a source) and are written only to `<store>/sealed/<set_id>/{key,salt}`; they are never an option, a return value, a log line or an output. The set shares the public pool's generator, config, label set, vocabulary, version manifest and D20 strata (`sealedPlan` reads the public `TeamDatasetManifest`; it never merges again): `n_teams` is shared over the strata by pilot hits (largest remainder, at least `n_stratum_min`), the draw budget is the public `d_max` raised by the config's `sealed_margin_permille`, and a bin still short discards the whole generation (key, teams and rejections dropped; one `discards.jsonl` line of counts and the key's hash), then redraws a new key, up to `maxAttempts` (`SealedShortfallError` after that, nothing committed). L1 is the canonical hash, L2 is `NearIndex` (distance at most `d_team`, the fewest differing fields over all pairings of the sets' species, item, ability, nature, move set and Stat Points; an inverted index on whole sets finds candidates, then the exact distance), both against every `--known` team (public splits, released datasets, the training pool, retired sealed sets); `rejection-log.ts` gained the `near_duplicate` reason. The L3 commitment (`setCommitment`/`keyCommitment` over the teams `{k, paste, stratum}` in stratum then draw order) is checked with `checkCommitment`; the register CLI (not this module) commits it. Contracts: `SealedTeamSetManifest` (hashes, counts, plan and log hashes; no secret; `readSealedTeamSetManifest`) and `RetiredSealedManifest` (the reveal: key, salt, file hashes; `readRetiredSealedManifest`, `retiredManifestHash` is the register's `reveal_hash`), readers in `showdown-bridge/src/sealed-records.ts`. `SealedTeamHashes` is built only by `loadSealedTeamHashes` after the commitment is recomputed from the store, unions with the public hashes for stamping (`withPublic`), and refuses to serialise. `sealed-retire.ts`: `retireSealedSet` writes the reveal bundle (a new 0700 directory) only when the register logs `set_retirement` for the set with exactly that bundle's `reveal_hash` and the stored commitment; `verifyRetiredSealed` needs no store: it opens both commitments, runs `checkReveal` with the stratum from each team, regenerates the set from the revealed key against the reference pool (teams and the whole rejection log must be byte-equal, which replays every L1/L2 skip) and re-checks each team. `scripts/check_data_class.py` now rejects a reveal (`set_id` + `reveal.key`/`salt` + `files`) or a sealed-team line `{k, paste, stratum}` anywhere but the exact paths in `REVEAL_ALLOWED` (the corpus samples; a retired bundle is added by a reviewed edit). The index is in memory (the shard-scale build is a later slice).
**Private teams** (ADR-015, which supersedes ADR-014 and its encrypted store; the wording rules are in AGENTS.md; the owner's bucket, lock and token setup is `docs/runbooks/private-store.md`, #889). The owner's real teams are inputs to a separate private run after the Training gate (#878), never to public datasets, published checkpoints or Episodes. They are kept, once the bucket is set up (ADR-015; #889, #891), as plain `PrivateTeamRecord`s in Parquet shards (the ADR-013 d1 layout, `data_class: private`) in a private R2 bucket, written once per snapshot, as plain objects with no client-side encryption (R2 encryption at rest only); the owner accepts the residual token risk (ADR-015 section 1); on the owner's workstation they appear only under gitignored `private-data/` (`teams/` is staging, `snapshots/<snapshot_hash>/` the verified local copy, run outputs stay there). Two bucket-scoped tokens exist, a write token for the import only and a read token for readers; both come from the environment of one command on the owner's workstation, never from the repository, a log, a chat or a command line, and an agent never runs a command that holds one. Built (#898): the pure import planner in `packages/private-team-store/src` (`planImport` in `import-plan.ts`, `parseStagedFile` in `staged-file.ts`, typed refusals in `import-error.ts`). Built (#899): the snapshot writer and reader there (below). It takes the staged files as `{name, text}` items, the parent snapshot's `PrivateTeamRecord`s (or null for `--first`), the `--retire` team_ids, the engine and the resolved format, and ports for labels, the hold-out flag (the snapshot layer plugs in the keyed HMAC; the planner holds no key) and fresh team_ids; it returns the next record list (one record per `team_id`, sorted) and a summary of five counts (`new`, `duplicate`, `revised`, `unchanged`, `retired`), or throws an `ImportPlanError`. Header `#! team_id=<32 hex> tags=...` (either key optional, order fixed, tags sorted and unique, at most 16; an empty `tags=` clears the tags, an absent one keeps the parent's), any other `#` line refused; each team goes through `importPaste` and `validateTeam`; a `team_id` not in the parent is refused (never created). A file without an id whose canonical hash equals an active record's, or an earlier file's, changes nothing and counts as a `duplicate` (ADR-015 section 3), so re-importing the same staged folder against its own result is a no-op. An edit is revision +1; a staged record identical to its parent (paste and tags, active) is unchanged; a retired one staged with its id becomes active again; a team absent from staging is unchanged; retirement is only `--retire` (retiring a retired record is a no-op counted as unchanged); a revision or revival that takes another active record's team is `duplicate_canonical_hash`; a result that loses an active parent record is refused; parent records' hold-out flags must equal the hold-out port's value. Beyond the ADR text (to be listed in its erratum, #892): a tag-only edit and a Pokemon-order-only change each make a new revision. A refusal is a code plus a 1-based position that indexes the caller's list (staged files as passed, or the `--retire` list; the command slice maps it back to a file), never text from an input: no paste, file name, tag, header value, id, species or move, and an exception thrown by a port is replaced by a fixed `hook_failed`; the canary tests (`test/import-canary.test.ts`, which asserts every refusal code and has a negative control) enforce it. Shards are ordered by logical hash, each with its position as `index` (the HMAC placement index is a separate property the reader checks). The records must already carry their hold-out flags (the writer refuses a flag that differs from `holdoutFlag(key, team_id)`) and satisfy `checkPrivateRecordSet`; a stratum is the label set's base cell (`labelPlan`; no merged strata for owner teams). Intermediates (the rows file and the shard file, which hold pastes in the clear) exist only in a fresh 0700 directory inside `workDir`, which `assertWorkDir` accepts only if it is absolute, a real directory (no symbolic link), owned by the invoking user, mode 0700, no parent writable by group or other (a sticky bit is accepted, as in the sealed store) and every parent owned by the user or root, and either has a `private-data` path segment or is on tmpfs/ramfs (`statfs`); a Windows drive mounted in WSL (`/mnt/<drive>`) is accepted only on tmpfs, because a 0700 mode proves little there; the owner and file-system probes are a test seam of `assertWorkDir` only (the writer's input has no `probe`, and a test reads its source to say so). They are removed afterwards, on failure too; if the write succeeded but the removal did not, the call fails with `cleanup_failed`, and a write that failed keeps its own error. `readPrivateSnapshot({engine, manifest, shard(index), labelSet, expectedSnapshotHash, expected})` is what the import (after writing and after downloading) and #888-era readers run: `readPrivateSnapshotManifest`, a parent equal to the snapshot's own hash refused, the hash the manifest was fetched under (`expectedSnapshotHash` is REQUIRED: there is no option to read without an anchor), the version manifest and vocabulary hash the caller derives from the pinned engine and rules in `expected` (`version_manifest_mismatch`; REQUIRED like the hash: a reader of a snapshot made under another pin says `expected: INSPECT_ONLY` out loud, and `publishSnapshot` refuses that value), `label_set_hash` = `recordHash(labelSet)`, the Parquet layout version, no two shards with one `file_sha256`, `shardCount(rows)` = number of shards, each file's size and SHA-256, `readPrivateShard` (columns, order, placement, logical hash, ranges with active rows), no two shards on one layout index, each record through `readPrivateTeamRecord` (engine round trip), each hold-out flag recomputed from the manifest's key and ppm, and `checkPrivateRecordSet`; it returns the records sorted by `team_id`. The counts need no check of their own: the manifest reader ties `records` and `cells` to the shards' ranges and each shard read ties its ranges to the decoded rows. Every refusal is a `SnapshotIoError` with a code (`SNAPSHOT_IO_REFUSALS`), a fixed message and at most a shard index and row number; whatever a lower layer threw (DuckDB stderr, hyparquet, the engine, ajv) is dropped and not attached as `cause`. Keys are checked against the layout (`current.json`, `snapshots/<64 hex>/manifest.json`, `snapshots/<64 hex>/shards/<n>.parquet`): anything else, `snapshots/_lock-check/` included, can be neither written nor fetched, and `listSnapshotHashes` returns only the hashes that have a manifest object, so an unknown key under `snapshots/` is never a snapshot (a test seeds one); `fetchSnapshot` is the verification (`readPrivateSnapshot` on the downloaded bytes). `InMemoryObjectStore` (tests; `seed` puts an object where the port would refuse to, as the owner's lock-check object) and `R2ObjectStore` implement it; one contract suite runs against both (the R2 client on a fake bucket behind `fetch`, so no test opens a socket; `test/network-isolation.test.ts` requires that only `r2-client.ts` calls `fetch` or imports a network module). The R2 client is path-style (`<endpoint>/<bucket>/<key>`), signed with `aws4fetch` 1.0.20 (MIT, no dependencies, pinned exactly, ignored by Dependabot, imported by `r2-settings.ts` only; the `age-encryption`, `@noble/*` and `@scure/base` pins of the superseded design are gone) with the real SHA-256 of the body in `x-amz-content-sha256`, no redirects, no retries, a time limit; 412 and 409 on a conditional write are `exists`, 401/403 `denied`, 429/5xx and any transport failure `unavailable`, other statuses `failed`, a listing or head that is not in the expected form `response_invalid`; every message is fixed and carries no response body, URL, header, bucket or key (`ObjectStoreError`, no `cause`). `R2Settings.fromEnvironment(env, argv, bucket)` reads `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL` (https, an `*.r2.cloudflarestorage.com` host, nothing else in the URL) and `AWS_DEFAULT_REGION` (`auto`) from the environment only; a command line that names one of them (`AWS_*`, `--secret`, `--token`, `--endpoint`, `--account`, `--region`, ...) or contains a value (key id, secret, endpoint, the account id) is `credentials_on_argv` before the environment is read. The values live in `#` fields; the object prints as `[R2Settings]` to String, JSON and `util.inspect`, and it signs requests itself, so only the signing library sees the secret. The bucket name is an argument, not a credential. `test/credential-canary.test.ts` puts markers in all four variables and the bucket, scans errors (message, stack, fields, inspect) and process output on every settings, client and publish error path, including fake responses that echo the markers, checks that the secret appears in no request, and has negative controls. `publishSnapshot({store, engine, labelSet, written, expected, expectedCurrent, snapshotsDir, ...})` runs the ADR-015 section 3 sequence: the snapshot's parent must equal `expectedCurrent` (null for the first) and `current.json` must still name it; the local copy's place must be free and safe; every shard then the manifest (JCS bytes) uploaded with `If-None-Match: *`; every object downloaded again and verified with `fetchSnapshot` (required `expected`, the manifest bytes compared with the sent ones); the verified copy written to `private-data/snapshots/<hash>/` (`assertWorkDir` rules, directories 0700, files 0600, built in a hidden partial directory and renamed, never replacing a copy); `current.json` (`{parent_snapshot_hash, schema_version, snapshot_hash}`, strict reader) checked once more and overwritten last. The final check and the overwrite are a read and a write, not one atomic request: a second writer in between is not excluded (one owner, one write token, ADR-015 section 7). A failure before the last step leaves `current.json` as it was; uploaded objects stay (the lock keeps them; they are unreferenced), and a retry with the very same bytes meets `exists`, so the next attempt needs another `snapshot_id` (another hash). A 404 reads as "absent", so a wrong bucket name looks like an empty bucket until the first write is refused. **Owner-session guard, private output root and canary harness** (ADR-015 erratum E1, #1059; groundwork for the owner-run private commands of Epic #1058). `packages/showdown-bridge/src/owner-session.ts` and `ml/areneon_ml/private/owner_session.py` are one behaviour in two languages: every command that reads private teams calls `assertOwnerSession` / `assert_owner_session` before it reads any team. **Private test** (ADR-015 erratum E1 item 2, #1060; `docs/training-run.md` section 6). `python -m areneon_ml.loop private-test` (owner only, no override) measures a frozen pair of a committed generation on the owner's teams, both seats, counts and scores only. Python never holds a team; it re-reads the record with its own reader, ties it to the request, writes it (0600, never overwritten; an identical rerun is a no-op) and logs a look (`private-test.looks.jsonl` in the root, the validation look log's format). Sources: `staging` (`PasteDirectorySource`, subset `all`), `snapshot` (the verified local copy through `readPrivateSnapshot`, `src/test-source.ts`, subset `all` = active records or `holdout`) and `dataset` (`datasetValidationPool`). **A2 reconnect (ADR-008 §3-5, ADR-005 gate 3, #895).** `session.ts` joins each connection's channel to the ones before it with `continueChannel` as it goes (`Battle.joined`, the fold of the kept channels; `#build` returns the joined channel, `#keepChannel` keeps the connection's own channel in `A2BattleRecord.channels` and folds it into `joined`), so after a reconnect the bot builds observations, decides and numbers `channel_request_seq` on the battle's one continuous channel, with the actor rule and the watchdog unchanged. A rejoin on another seat is a `SessionError`; one that does not continue the earlier channel (`ObservationError` from the join) is a fatal error like any channel that cannot be built. `a2Episode` folds `record.channels` with `continueChannel` (a refusal is an `A2EpisodeError` that quotes nothing) and stores that one channel; folding covers several reconnects. A decision first made on a rejoin with no timer snapshot (the snapshot went to the old connection; the server does not replay it) has no deadline record, and none is invented (ADR-008 Errata E1b, #904, no contract change): the session marks the `DecisionRecord` `rejoin_without_snapshot` and logs an `incident` (`rejoin_without_timer_snapshot`), the battle plays on and its record is kept, and `a2Episode` refuses it with an `A2EpisodeError` whose `code` is `rejoin_without_timer_snapshot` and whose fixed message quotes nothing. Such a battle is never an Episode or training data. `test/session.reconnect-episode.test.ts` drives the real session through the committed reconnect fixtures (`fixtures/a2/<format>/bot-vs-bot-3.json`: a reconnect after the choice, Episode equal to the A1 Episode in channel, decisions and observations; `-4.json`: no snapshot, record equal, no Episode), two reconnects in a row, and the negative controls (a rejoin that does not replay the room log, a spliced `rqid`, the wrong seat).

A2 (ADR-005) is a bot client on a local Showdown server, for local human sparring against the bot; `packages/bot-client/README.md` is the sparring guide (start, connect, challenge, stop). In `packages/bot-client`, `ProtocolReader` (`src/protocol.ts`) numbers each room's requests per channel: a room's `|init|battle` (sent on every join, before the replayed log, which holds no requests) resets its `request_seq`, open request and re-send identity, so the request re-sent after a rejoin is request 1 of the new channel, as `buildObservation` numbers it.
