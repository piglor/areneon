## Architecture

**Polyglot monorepo** (ADR-002): TypeScript in `packages/*` (pnpm workspace), Python in `scripts/` and `tests/` today plus the generated-contracts package `packages/schema/python` (a uv workspace member next to its schemas; `ml/` for the policy worker in `ml/areneon_ml/worker` (the networks follow), `services/` later), Rust in `crates/` once the first crate lands. `packages/schema` holds the JSON Schema contracts: the rules records (`rules/`, ADR-007) and the cross-language contracts (`contracts/v<N>/`, ADR-008), from which the TS types in `generated/ts/` and the pydantic models in `python/areneon_contracts/models/` (the `areneon-contracts` uv workspace package, `scripts/contract_models.py`) are generated and checked in; serde follows with the first crate. On Python, `areneon_contracts.contracts` validates with python-jsonschema, then parses into the model (`parse`), and hashes with RFC 8785 (`jcs`, `request_hash`). `fixtures/contracts/` is the shared sample corpus (valid and invalid instances of every contract, plus `reader-invalid/` ones that pass the schema and that a TS reader such as `readEpisode` refuses, plus their JCS digests in `hashes.json`): Ajv and python-jsonschema must classify it identically and every language must reproduce the digests. A contract's `$id` (`urn:areneon:schema:<contracts|engine>:v<N>:<name>`) declares its profile, and `src/profile.ts` enforces it as a keyword whitelist: closed objects, bounded integers, local `$ref`s, `kind`-tagged `oneOf`; `engine` schemas, which copy the pinned engine's wire shapes, also allow scalar type unions and get their own Ajv instance (`src/ajv.ts`). `Provenance` gained the optional `collection` as a minor change within v1 (ADR-008 §3): a reader older than it rejects such an Episode, so the generated types and models ship with the schema change. `make contracts` fails on a profile violation or on generated types that differ from a fresh run.

**The reference engine is upstream Showdown, unmodified** (ADR-003). `vendor/pokemon-showdown` is a git submodule pinned to an exact SHA and built with `make showdown`. Areneon never decides legality itself: it asks the engine (`TeamValidator`, `side.choose`) and stops on unknowns. `docs/showdown-champions-gaps.md` lists what the engine does for Champions and what is unverified. It is generated from the gap ledger records in `rules/gaps/` by `scripts/gaps-doc.ts`; edit the records, never the doc (a test compares them). Gap edits move `rules_snapshot_hash` but never `format_rules_hash`.

**`packages/showdown-bridge`** is the only code that talks to the engine:
- `engine.ts`: `loadEngine()` loads `dist/sim` via `createRequire` behind narrow local interfaces (`ShowdownSim`). It refuses a missing build or a checkout whose HEAD is not `PINNED_SHOWDOWN_COMMIT`. A test checks that constant against the submodule gitlink, so a pin bump changes both.
- `rules.ts` / `rules-load.ts` (ADR-007): Areneon's own rules are JSON records in `rules/`, never code constants. That covers which formats it runs and the forbidden engine rules (e.g. `forceopenteamsheets`, because CTS needs Bo1 with sheets declined). They are validated by `packages/schema/rules/v1` (Ajv) and fail closed. `jcs()` (RFC 8785) gives `rules_snapshot_hash` (provenance) and `format_rules_hash` (replay identity). `packages/showdown-bridge/scripts/rules-hash.ts` and everything it pulls in (`rules.ts`, `request-identity.ts`, `canonical-json.ts`, `engine.ts`) import only Node built-ins, because CI reruns old commits' copy of it from bare archives. `canonical-json.ts` (`canonicalJson`, `jcs`) imports nothing at all, so the engine-free observation builder can use it too (ADR-008 §5); a test enforces that.
- `formats.ts`: `resolveFormat` checks a format against the rules snapshot and the pinned engine. It returns the version manifest `{showdown_commit, format_id, regulation, ruleset_hash, format_rules_hash}` plus the embedded format rules record that every fixture (and, later, every episode) carries.
- `scripts/check-rules.ts` (in `make ts` and CI; policy in `rules-channel.ts` / `rules-history.ts`): validates every record and checks `rules/channels/`, which must hold exactly one file per channel in the channel schema's enum. Each channel must name a snapshot built for the current pin, and `seq` rises by 1 per change. A pin bump must also move the channel (CONTRIBUTING).
- `request.ts` / `request-identity.ts`: decode one `|request|` into a phase (`preview`/`move`/`forceSwitch`/`wait`). The body is first validated against the closed engine-mirror schema `packages/schema/contracts/v1/engine-request.schema.json` (the pinned `sim/side.ts` request types, minus fields no supported format has), so only an engine-shaped request is hashed; a pin bump that changes the shape edits that schema. Request identity is `request_seq` + `request_hash`, a SHA-256 of canonical JSON that excludes `rqid`. `request-bytes.ts` is the one definition of the hashed bytes (`requestIdentityBytes`, the `Sha256` port type and `hashRequest`); it imports only `canonical-json.ts`. `parseRequest` is the pure parse step (schema validation, phase, `identity_bytes`; it hashes nothing), `decodeRequest` adds the Node `request_hash`, and `buildObservation` hashes the same bytes through its injected port (a test fixes Node and WebCrypto digests equal on the golden requests and that no other module builds the bytes). `rqid` exists only on the Showdown server path, never on the in-process sim.
- `runner.ts`: `runBattle` runs a seeded in-process BattleStream battle (runtime A1) on copies of the teams (the caller's sets stay as brought) and records `team_hashes` (each seat's set array as brought). Teams are validated first. Each `Actor` sees only its own player's requests. Each request carries its `legal` choice set, judged by a `CloneJudge` on the stream's own battle. The CloneJudge's verdicts on pending candidates go to `hidden_verdicts`, never to an actor. If the actor submits a pending candidate and the engine refuses it as `[Unavailable choice]`, the updated request that follows is a new request (`request_seq` + 1). Any other engine `|error|` aborts; nothing is retried. `|t:|` wall-clock lines are dropped so the same commit, seed and choices reproduce `omniscient_log`. That log holds both sides' hidden information: an evaluation artifact, never actor input. `replayActor` replays recorded choices. The optional `players` option sets each seat's `name` and `avatar` on the `|player|` lines (default `p1`/`p2`, no avatar) so a recorded server battle can be reproduced; `validatePlayers` refuses unsafe names (blank, edge whitespace, no letter or digit, over 18 UTF-16 units, `|` `,` `[` `]`, control characters, double spaces, or two names alike) and avatars that are not 1-32 letters, digits or `-`.
- `teams.ts`: `importPaste` / `exportPaste` wrap the engine's `Teams.import` / `Teams.export`. Showdown silently skips unknown lines (an `SPs:` line zeroes the Stat Points; they belong in `EVs:`), so `importPaste` rejects a paste unless each Pokémon's lines all reappear in that Pokémon's re-export: only the engine's canonical form passes. `validateTeam` returns the pinned `TeamValidator`'s messages verbatim.
- `choices.ts` / `choice-judge.ts` (ADR-006): `enumerateCandidates` turns the player's own request into every engine-distinct joint choice, in a fixed canonical order. It is pure and fails closed on any request field it does not know. Candidates whose legality depends on `maybeTrapped` / `maybeDisabled` / `maybeLocked` are `pending`. `legalChoiceSet` (its `LegalChoiceSet` type is generated from `packages/schema/contracts/v1/legal-choice-set.schema.json`, imported as `@areneon/schema/types/v1/…`) has a `ChoiceJudge` check every non-pending one; it never asks about pending ones, so no hidden-information verdict reaches a policy. `CloneJudge` judges on `Battle.fromJSON(battle.toJSON())`, never on the live battle, and refuses unless the battle is at the request's `request_hash`. `runBattle` builds one per request (A1); the corpus and tests use it too. `Battle.fromJSON` rebuilds `activeRequest` from the Pokémon, so the clone carries the live request over: after an `[Unavailable choice]` the live one was edited in place. `judgeSubmission` (the SubmissionJudge) classifies the engine's `|error|` after a submission. If the engine refuses a non-pending candidate, that is an `EnumeratorDefectError`. Revival Blessing (#910): a request whose `side.pokemon[i].reviving` is set is a forced switch; the one flagged reviving slot offers `switch N` for every fainted Pokémon (active slots included) and `pass` only when no living bench Pokémon exists, and any other shape (a second flagged slot, a reviver outside a forced switch) fails closed. A successful reviving pick clears the reviver's `switchFlag`, which `clearChoice` does not restore, so `CloneJudge` takes a fresh clone after any choice that changed a `switchFlag` (its batch verdicts equal one clone per choice). The corpus has `force-switch-revival` and `-many`, `fixtures/showdown/<format>/revival/` a seeded battle through `runBattle` (`scripts/capture-revival-battle.ts`), and `tests/ml/model/test_revival.py` the reducer and encoder on it. On A2 (`judge: null`), the engine judges only at submission.
- `observation.ts` (ADR-008 §5): `buildObservation` is the only constructor of a `PreviewObservation` / `BattleObservation`. Its battle input is a branded `PlayerChannel` (one player's own stream up to the request being answered), plus that player's own `PrivateTeamSpec`, the version manifest and an optional `DecisionContext`; the omniscient log is a distinct `OmniscientLog` type and cannot be passed. The module imports no engine, runner or Node built-in (a test enforces it), so it runs wherever WebCrypto does; it hashes through an injected `Sha256` port (`nodeSha256` in `player-channel.ts`, `webSha256` on WebCrypto) to exactly `decodeRequest`'s `request_hash`. `player-channel.ts` is the A1 adapter: `playerChannel` validates a `PlayerChannelLog` and every `|request|` in it before branding, and `recordedChannel` cuts a runner record's channel at a `request_seq`. `test/observation.test.ts` holds the ADR-008 privacy tests: golden parsing, the canary test (no opponent secret line or request stats in any observation, with a negative control), schema probes and the type test.
- `episode.ts` / `episode-io.ts` (ADR-008 §3, §5): an `Episode` is one player's recorded battle: their own channel (stored once), their own team, their decisions (a `deadline` record required on A2, absent on A1), provenance, `data_class` and matching `rights`. `episodeFromRecord` writes one from an A1 record, given both teams: it classifies by BOTH (`private` if either is; `rightsFor` follows), checks each team's `teamHash` (JCS of the set array, so it ignores the label) against `record.team_hashes`, and refuses a `synthetic` label whose hash is not in the given `known_synthetic` set; `readEpisode` reads a copy back by its `schema_version` (an unknown version is refused), checks the channel is the player's own and its ending matches `result`, rebuilds the Team Preview observation and every decision's (so the team must be the player's own, in request order), and on A2 requires each decision's deadline record; every refusal is an `EpisodeError`. `playerChannel` refuses `|split|` lines and the opponent's exact HP, the SECRET halves a player never sees. A battle with a reconnect is ONE continuous channel (#813): the server replays the room log to a rejoining connection with no `|request|` or `|error|` line, so the rejoin channel alone has no Team Preview request and `buildObservation` refuses it (the team check anchors on the channel's first request, unchanged; the message names the fix). `continueChannel(earlier, rejoin)` (`player-channel.ts`; reader-side, no schema change) joins the two own channels: the replay lines with the earlier channel's player-alone lines put back where they were, a first request of the rejoin with the earlier last one's `rqid` and body counted once, refusing another player's channel or a replay that does not continue the earlier room log; fold it across several reconnects. The joined channel equals A1's, so its observations equal A1's in full and an Episode stores it as it stores any channel (`readEpisode` is unchanged). `|poke|` lines are no anchor (species and item presence only). `session.ts` and `a2Episode` fold the connections' channels with it (see A2 reconnect below). `episodeFromRecord` also takes an optional `collection` record, which must carry the battle's own `record.seed`. An Episode's optional `provenance.collection` (ADR-009 §4: `league`, `evaluation` or `sparring`, a `kind`-tagged `oneOf`) names the run, the seed (`sodium,<hex>`, null on A2), the evaluation `sealed` flag or the opponent policy; `readEpisode` also refuses a seed on A2 or none on A1, which the schema cannot say. `episodeHash` is SHA-256 of the JCS bytes through the `Sha256` port. `answersRequest` is the stale-invalidation check for a `Recommendation`. A `league` or `evaluation` `provenance.collection` carries a required `opponent_team_data_class`, which `episodeFromRecord` sets from the opponent's `StampedTeam` (never the caller's); `readEpisode` requires the Episode's `data_class` to equal the higher of the own team's class and that field (so a stored Episode relabelled synthetic is refused), and a `sparring` Episode to be `private`.
- `own-team-stats.ts` (#893, ADR-008 §5): the engine-dependent half of the own-team check, outside the engine-free `observation.ts`. `buildObservation` matches the team to the Team Preview request by species, item, ability, moves and nickname only; `assertOwnTeamStats(engine, formatId, team, channel)` builds a battle with the pinned engine from the team the observation will record and requires the engine's own Team Preview request for that player to show the same level, maximum HP and five stats as the channel's first request, Pokémon for Pokémon in team order (no formula is written here; the same team in another order is refused). A difference is an `OwnTeamStatsError` (an `ObservationError`) with a fixed message and a position index only, never a set or a stat; so are a channel that does not start at Team Preview, a team of another size and a team the engine cannot start. It is called by `readEpisode` (so by `episodeFromRecord`, the A2 Episode writer and the training loader; optional `engine`, default the pinned checkout from `pinnedEngine()`, loaded once) and by `policyActor` at the first request of a game (the A1 online observation; optional `engine`, which `policyGame` passes). Limits: the Champions mod ignores IVs (Stat Points replace EVs, IVs fixed at 31) and the request carries no IV, so an IV-only difference cannot be seen (and does not change play); a mirror team that differs in Stat Points, nature or level is refused. Bare Hidden Power: the request names it `hiddenpower<type>`, and the pinned validator allows the move in no supported format ("does not exist in Gen 9"), so no legal team reaches it; the move match keeps refusing it (fail closed) and a test pins the validator's verdict, so a pin bump that allows the move is decided then.
- `training-loader.ts` (ADR-009 §4): `loadTrainingSet` is the one way an Episode becomes training data, and it fails closed. Each Episode goes through `readEpisode` (with `known_synthetic`), then only a `synthetic`, `cc0-synthetic` Episode of collection kind `league` is accepted: a missing collection record, `evaluation`, `sparring` and private data are refused, as is any Episode whose `episodeHash` an `EvaluationRunManifest` lists, and a repeated Episode or manifest. Every refusal is a `TrainingLoaderError`; none is skipped. It writes a stream of `TrainingExample` lines (`episode_hash`, `observation`, `choice`; no provenance, so no seed or opponent id) in Episode-hash order, and a `TrainingSet` (the Episode hashes, the checked manifests' JCS hashes, `data_class`, line count, `stream_sha256`). `readEvaluationRunManifest` / `readTrainingSet` enforce the sorted-and-unique hash lists the profile cannot (corpus samples under `reader-invalid/`). A relabelled copy of an evaluation Episode has another hash, so only the storage partition catches it. `evaluationRunManifest` is the evaluation job's writer (hash-only, sorted and unique); `decisionObservations` (`episode-io.ts`) rebuilds each decision's observation for the examples. On the Python side `areneon_contracts.training.read_stream` reads a stream only with a manifest that matches its digest, line count, Episode hashes and class, validating every line.
- `server-lines.ts` (ADR-005 §5): the A2 server-path filter, an allowlist of the sim's line kinds. `serverOnlyLine` is the stateless check: `>room` headers, plain-text notices and `||text`, `|request|null`, nameless `|player|<slot>|`, and the known server kinds (joins/leaves/renames, chat and PMs, `|raw|`/`|html|`/`|uhtml|`, timer and timestamp lines, room and session state, `|sentchoice|`). `stripServerLines(stream)` returns `{ lines, dropped }`: it keeps sim kinds (`|error|` included), places the engine's `otsrequest` prompt and clear and the sim's `|player|` lines by their position relative to `|gametype|` and `|start`, drops the server's auto-tie `|-hint|` and its inactivity and forfeit `|-message|` lines by exact text, and reports lines of unknown kind in `dropped`. The adapter filters the stream from its first line every time, never a suffix. The channel equals the A1 one up to server-layer `|error|` refusals, which only A2 produces; `|player|` equality is left to the A1/A2 equality test. It imports nothing (a test enforces it), and the golden channels pass through unchanged.
- `choice-corpus.ts`: the golden choice corpus (ADR-006 rule 7). Each case is a seeded battle log that reaches one situation (`CASE_KINDS`: preview, target types, Mega, forced switches, trapping, Imprison, a fainted active, a locked move), plus every candidate with the engine's verdict. Verdicts on pending candidates are hidden state, kept for evaluation. CI replays each log (it never re-runs the search in `scripts/capture-choices.ts`) and compares the result. `missedActions` is the brute-force oracle: it judges every syntactic choice string and fails on any engine-accepted action the enumerator did not offer.
- `team-class.ts` (#817): a class is proven by source, never by a caller's label. `teamHash`, `classOfSets` / `stampTeam` (`synthetic` only for a hash in the known synthetic set, `private` otherwise, `private-data/` teams included), `higherClass`, and `battleClass`, whose branded result is the only value `recordedChannel` takes as a channel's `data_class` (`syntheticFixtureHashes` in `golden.ts` is today's set: the committed fixtures' teams). The set is trusted caller input and the brand is compile-time only; `syntheticTeamHashes(...lists)` builds the set from verified lists of positional `team_hash`es (a non-digest is refused); `datasetSyntheticHashes` / `committedDatasetHashes` in `packages/team-dataset` feed it the teams of the committed, verified datasets, and a caller adds `committedDatasetHashes` (exported from `@areneon/team-dataset`) to the sets it already trusts, e.g. `syntheticTeamHashes(syntheticFixtureHashes(engine), committedDatasetHashes(inputs, format))` (a team is synthetic only if its hash is in the set it passes). `stampTeam` returns a compile-time-branded `StampedTeam`, the only team type `episodeFromRecord` accepts (`runBattle` still takes plain sets: a battle is not an Episode, and `team_hashes` binds the teams to the record). `readEpisode` checks its own team against the required `known_synthetic` and the opponent's class through `collection.opponent_team_data_class`; an Episode without a collection record has no opponent class to check. An A2 stream has no opponent team to hash, so its `data_class` is the caller's label and defaults to `private`.
- `engine-data.ts` (ADR-010 §3): `exportEngineData` reads the species, move, item, ability, type (with the engine's own type chart), status, weather and terrain vocabularies and their numeric attributes from the pinned engine's data for the format's mod, each list sorted by id (the position is the vocabulary index), into the `EngineData` contract (`packages/schema/contracts/v1/engine-data.schema.json`). It refuses any value of a shape it does not know; the vocabularies hold the engine's standard entries plus, so no reference dangles, every base species a standard forme names and every ability a standard species lists even if the engine marks them nonstandard (eight at this pin: cramorant, eiscue, floette, meloetta, minior, ogerpon, terapagos, Aura Guard). Out of v1 scope (a change needs schema_version 2, the contract being closed): natures, volatile conditions, learnsets, evos, requiredItem, move effects, species height and gender. The table is derived from the pinned Showdown data files (MIT, not CC0; `NOTICE-engine-data.txt` beside it keeps the upstream notice). `readEngineData` adds what the profile cannot say (sorted unique ids, references that resolve). `engineDataHash` is SHA-256 of the JCS bytes: the engine-data hash of the encoder version, so a pin bump yields a new one. The golden table and `engine-data.summary.json` (hash, counts) sit in `fixtures/showdown/<format>/`; a test re-exports and compares them. `scripts/export-engine-data.ts` rewrites them.
- `team-vocabulary.ts` (ADR-013 §2, #859): `exportTeamVocabulary(engine, format, table?)` is what the team generator may draw from, read from the pinned engine and built on the `exportEngineData` table (it names that table by `engine_data_hash` and its ids resolve in it). It adds the roster the validator accepts, each roster species' abilities and move pool, the natures, the items the format does not ban, and the rule-table values (`adjustLevel`, `evLimit`, Item Clause, team sizes, from the resolved rule table; an unset one is refused, never defaulted). No game rule is written by hand: a species, ability, move, nature or item is in the vocabulary exactly when the pinned `TeamValidator` takes a probe set with it (one Stat Point and a neutral nature, so the "0 Stat Points" check stays quiet) or `checkItem` does not ban it. IVs, the per-stat draw maximum and item weights are `TeamGeneratorConfig` fields, not here. `teamVocabularyHash` (SHA-256 of the JCS bytes) is the `vocabulary_hash` the team manifests carry; `readTeamVocabulary` adds sorted-and-unique ids and, given the table, that every id resolves. The golden `team-vocabulary.json` and `.summary.json` sit beside the engine-data table (MIT-derived, same `NOTICE`); a test re-exports and compares byte for byte (about 10 s), `scripts/export-team-vocabulary.ts` rewrites them.
- `team-records.ts` (ADR-013 §4, #859): the identities and readers of the team records (`packages/schema/contracts/v1/team-{vocabulary,record,label-set,generator-config,dataset-manifest,snapshot-manifest}.schema.json`; all integers-only, no `number`). `canonicalTeamHash(sets)` is SHA-256 of the JCS bytes of the sets sorted by species id (ties by each set's JCS bytes): the same for every permutation, equal to the positional `teamHash` only for the canonical order. `recordHash`, `shardLogicalHash`, `logicalSnapshotHash` (writer-independent) and `snapshotHash` (one physical publication) follow ADR-013 §4. `readTeamRecord(engine, value, labelSet?)` adds the engine round trip (the paste must be the engine's own export of its sets), both team hashes recomputed and the labels' order; `readTeamLabelSet`, `readTeamGeneratorConfig`, `readTeamDatasetManifest` and `readTeamSnapshotManifest` add what the profile cannot say (sorted and unique lists, sums, tiling cell ranges, the recomputed logical hash). A `data_class` of `synthetic` is a constant of every record and manifest. `readTeamDatasetManifest(value, { config, labelSet })` also ties `d_max`, `pilot_draws` and `config_hash` to the config and `label_set_hash` and every cell number to the label set, and checks `merged_cells` (the D20 merge: only merged strata are listed; a stratum is numbered by its lowest member base cell; absence means nothing was merged). `readTeamLabelSet` refuses a default that is also a listed value. The generator is `packages/team-dataset` (below); the Parquet shard reader is a later slice (ADR-013 d1).
- `private-records.ts` (ADR-015 §2, §5, #869): the reader of the `PrivateTeamRecord` contract, crypto-free. `readPrivateTeamRecord(engine, value)` checks `private-team-record.schema.json` (data class `private`, a `paste` of at most 8,192 characters, tags, labels, a boolean `holdout`), the paste's engine round trip, both team hashes, `supersedes_record_hash` null exactly for revision 1, sorted and unique tags and unique label ids; its messages never repeat the paste (tests cover the schema-failure, too-long-paste, engine-refusal and hash-mismatch paths with a canary). `holdout` is the flag ADR-015 derives from a snapshot's keyed HMAC-SHA256 of `team_id` (200000 ppm of teams); this reader has no key and checks only that it is a boolean, so the snapshot reader (#887) recomputes it. `checkPrivateRecordSet` enforces the snapshot rules (unique `team_id`, unique `canonical_team_hash` among active records). `private-samples.ts` builds the corpus samples (the pastes are `fixtures/teams` pastes; one hold-out record). The `PrivateSnapshotManifest` is `private-snapshot.ts` (below).
- `private-snapshot.ts` (ADR-015 §2, #897, slice 1 of #887): the `PrivateSnapshotManifest` contract (`packages/schema/contracts/v1/private-snapshot-manifest.schema.json`, generated TS and pydantic types, integers only) and its pure reader, `readPrivateSnapshotManifest`; no engine, no file system, no key. It mirrors `TeamSnapshotManifest` with `data_class` const `private`, no `dataset_hashes`, one split (`owner`), the `label_set_hash`, `records: {active, retired}` and the `holdout` block `{rule: "hmac-sha256-team-id/1", key: <64 hex>, ppm: 200000}`. Decisions where the ADR left room (also on the ticket): (1) the hold-out block holds the KEY itself, as ADR-015 §2 writes it (the key is not a secret and the snapshot reader recomputes every record's flag from it), not a key commitment; (2) a shard names its `index` (its position, 0 first), never an object path, because the path `snapshots/<snapshot_hash>/shards/<index>.parquet` holds the hash of the manifest that lists the shard; (3) a cell range carries `active_rows` beside `rows`: the ranges tile ALL rows of a shard (retired included) and `cells` count active records only, so the reader checks cells and `records` against the shards from the manifest alone; (4) `first: true` or `parent_snapshot_hash`, exactly one (reader-enforced; the schema leaves both optional). The reader adds shards in strictly ascending `logical_hash` with `index` equal to position, ranges tiling each shard with ascending strata and `active_rows <= rows`, `cells` equal to the shards' active sums and listing exactly the cells with an active record (empty when all are retired), `records.active` equal to the cells' sum, active plus retired equal to the shards' rows, and `logical_snapshot_hash` recomputed (`privateLogicalSnapshotHash`: JCS of `{shards (sorted logical hashes), cells, label_set_hash, manifest, holdout, and parent_snapshot_hash or first: true}`; `privateSnapshotHash` is SHA-256 of the whole manifest and names the snapshot in the bucket). Its messages state a rule and never repeat a value or a key name (a canary test). `holdoutFlag(key, team_id, ppm?)`: HMAC-SHA256 with the 32 bytes the hex key spells, over `team_id` as its 32 lower-case hex ASCII characters, first 8 bytes big endian as n, held out when `n * 10^6 < ppm * 2^64` in integers; it depends on the two ids alone, so a team keeps its flag on every revision. Known answers computed with Python `hmac`/`hashlib` are in the comment of `test/private-snapshot.test.ts`, as are the two manifest digests. The snapshot reader (#899) recomputes each record's flag; the manifest reader needs no key. The corpus samples (`private-samples.ts`, `privateSnapshotSamples`) carry the private label and are listed in `PRIVATE_MANIFEST_MARKERS` (`check_data_class.py`), which accepts such a file only in the strict manifest shape (below).
- `actor-rule.ts`: `actorRule`, the shared A1/A2 actor rule (ADR-005 §1). It plays the first non-pending candidate in canonical order, else the first pending one, and refuses only an empty set (`NoCandidateError`). It is pure and imports only types, so the A2 bot client reuses it.
- `random-legal.ts`: the random-legal baseline (evaluation protocol pool B). `randomLegal(legal, state)` picks uniformly among the non-pending candidates, else among the pending ones (the `actorRule` order of preference), refuses an empty set with `NoCandidateError`, and returns the next state of its explicit Mulberry32 PRNG (a uint32 seed; integer-only, so stable across Node versions; never `Math.random`). `randomLegalActor(seed)` is an A1 `Actor` (it checks the seed at construction); the A2 choice step would thread `randomLegal`'s state through its own battle state, since `session.ts` calls `actorRule` with no per-seat state. Protocol D9 seeding: the caller reduces the HMAC for the seat and policy label to a uint32 (`parseInt(h.slice(0, 8), 16)`; never `Number()` or `>>> 0` on a raw 128-bit value); about 10^5 streams collide in the 32-bit space, every stream is the same 2^32 cycle at another offset, and the label must carry seat and policy id.
- `private-team-source.ts` / `team-inventory.ts` (#775): the owner-team feature inventory, run as `scripts/team-inventory.ts`. Teams come through the `PrivateTeamSource` port (an async iterable of `{name, paste}`; no file system, network or crypto assumed). `PasteDirectorySource` is the one adapter here: it reads `private-data/teams/*.txt` and refuses any path without a `private-data` segment. The inventory runs `importPaste` and `validateTeam`, lists species, items, abilities, moves and Mega use, and flags features that a gap record names (advisory name matches; the detail also lists every gap as `format_wide_gaps`). It writes no file. It refuses unless stdin, stdout and stderr are terminals (and `CLAUDECODE` / `AI_AGENT` are unset; accident prevention) and `/dev/tty` opens, before reading any team; stdout gets counts and per-gap match counts only, and the detail goes to `/dev/tty`. The planned snapshot-backed `PrivateTeamSource` (ADR-015, #888) is not in this package. See `packages/showdown-bridge/README.md`.
- `policy-protocol.ts` / `policy-worker.ts` / `policy-actor.ts` (ADR-010 §2): the policy worker's TS side. `policy-protocol.ts` holds the three worker contracts' validators and reader rules (`readPolicyQuery`: `identity` equals `observation.identity`, no candidate twice; `readHandshake`: contracts sorted by name, checkpoints by role), `contractVersions()` (name, `schema_version` and the SHA-256 of the schema's JCS bytes, for the handshake) and `encodeFrame` (JCS plus `\n`, bounded by the run's maximum line length). `PolicyWorkerClient` spawns the worker with stdio only and an explicit environment, opens the session with the handshake (a different contract set, `encoder_version`, engine-data hash or checkpoint ids is a `PolicyHandshakeError` before any battle), allows one outstanding query per battle and at most `n_parallel` at once, and re-checks every reply (`answersRequest`, the policy id, the `choice` among the query's candidates). Reply lines must be the JCS bytes of their value. Failures are classified for `guardActor`: a dead worker is a `PolicyWorkerError` (its detail names only the class of the last stderr line), an invalid reply a `PolicyReplyError` (the actor turns it into a forfeit `invalid_reply`), `unsupported_candidate` an `UnsupportedCandidateError` and a query the harness cannot send or a worker that refuses it a `PolicyProtocolError` (incidents `unsupported_candidate` and `policy_protocol`). Nothing is retried. A query that overran its budget stays outstanding (`guardActor` cannot cancel it): call `client.beginGame()` before each game, while no game runs on the client, and it restarts the worker if a query was abandoned or the session failed. `policyActor` is the A1 online observation adapter (the player's own stream from the `ActorContext`, the observation through `observe`, the candidates from `enumerateCandidates`, never a `CloneJudge` verdict or the seed) and `sampleU` the hash-based sampler (first 53 bits of SHA-256 over the JCS of `{seed, game, player, policy_id, request_seq}`). `policyGame` takes the battle seed once and uses it for both the engine and the sampler: use it rather than `policyActor` directly. `test/policy-worker.python.test.ts` drives the real Python worker and is skipped where `.venv` does not exist.
- `ActorContext`: `runBattle` calls an `Actor` as `actor(request, { player, channel })`, where `channel` is a copy of that player's own stream up to and including the request (no `|t:|` lines, never the omniscient log). The second argument is optional in the type, so actors that ignore it are unchanged; `guardActor` forwards it.
- `ml/areneon_ml/worker` (ADR-010 §2, Python): the policy worker, `python -m areneon_ml.worker --run-dir … --preview <id> --battle <id> --engine-data … --max-line-bytes …`. One JCS line per frame, strict (duplicate keys, floats and non-canonical lines refused); first frame the hello, answered with `ready` (and the session ends if the contracts differ); then one `PolicyReply` per `PolicyQuery`, in order, one query per pass. A malformed frame ends the process (exit 2); a query that breaks a contract or reader rule gets an `invalid_query` reply, one with a candidate shape `candidates.py` does not know an `unsupported_candidate` reply. Checkpoints are read only as `<run dir>/checkpoints/<id>.safetensors`, must hash to their id, must hold the network of the role they were named for, and must have been made for the worker's engine-data table and encoder version (`ready` carries the encoder version, the engine-data hash and the checkpoint ids). A reducer or encoder refusal of a query's observation is an `invalid_query` reply (no log line echoed), a candidate the encoder cannot back with the request an `unsupported_candidate` reply. CPU inference is made deterministic (`configure_cpu_inference`) before the first query. `view.py` is what an encoder may read of a query (no `decision_context`, no `rqid` even inside the log's `|request|` lines, no sampling or policy fields), `sampler.py` picks from the probabilities (float32 values summed in float64, first candidate whose sum exceeds `u / 2^53`), and the scorer is `model/scorer.py`'s `NetworkScorer` (below). No module of `ml/areneon_ml` (worker, model, checkpoint, reducer) imports a network module (an AST test scans them; third-party code such as torch is not scanned, and a session test runs with sockets disabled). `PolicyQuery`, `PolicyReply` and `PolicyHandshake` (`packages/schema/contracts/v1`) are the worker's contracts. `PolicyReply`, `PolicyHandshake` and the `query_id` field (correlating replies when a worker serves several battles) go beyond the ADR-010 §5 table and are to be listed in its next erratum.
- `golden.ts`: the golden battle (each side plays `firstLegal`, which applies `actorRule` to the request's legal choice set), team-fixture and verdict builders shared by the tests and the capture script.

**Log-to-state reducer** (`ml/areneon_ml/reducer/`, ADR-010 §3, R10, #838), Python and clean-room (grammar from the repo fixtures, `sim/SIM-PROTOCOL.md` and ADR-006/008; no Showdown client parser): `reduce_channel(player, lines, team, vocab)` turns ONE player's own channel plus that player's own team into a `BattleState` (`own` / `opponent` halves: HP as the player sees it, status, boosts, volatiles, revealed moves/items/abilities, Mega, active slots, weather, terrain, field and side conditions, turn, winner; own exact values come from the player's own requests). Ids are checked against a `Vocabulary` built from the hashed engine-data export, never against lists of its own. It fails closed with typed `ReducerError`s (`UnknownLineError`, `UnknownFieldError`, `MalformedLineError`, `VocabularyError`, `OpponentSecretError`): an unknown line type, tag, positional field or request key raises, a `|split|`, an opponent HP not out of 100 or a request for the other player is an `OpponentSecretError`. A `[from] item:`/`ability:` counts only without `[of]`, and a move is revealed only when chosen (not when called by another effect). Limits, known and deliberate: volatile ids (`-start`/`-end`) are kept as opaque public strings after a shape check, because the engine-data export has no volatile or condition table (a volatile/condition vocabulary, engine-data schema_version 2, is a follow-up the encoder will need); a field or side condition must still be a move or an ability of the vocabulary. Illusion (#851): every switch-in is bound to the Pokemon it is shown as, with a copy of that roster entry as it was before (`_Disguise`), and `|replace|POKEMON|DETAILS` (the engine sends only the new id and details, no HP) says who it was: `_settle` carries everything seen at that position since the switch-in (hit points, status, boosts, volatiles, item and ability changes, moves used) to the real Pokemon's entry, puts the Pokemon it was shown as back as it was before the switch-in (out of play, if the Illusion user took its place), names the real one from the line and records its ability (Illusion). Before that line nothing of the real Pokemon is known: its roster entry stays as the preview gave it (the species is public from `|poke|`; its name, position, hit points, moves and ability are not). The player's own Illusion user is found at its next own request instead (the request lists the real Pokemon in each position, and an own mismatch whose real Pokemon holds Illusion is settled there, so boosts and volatiles are right before the replace; the position keeps the disguise's name for the lines that follow). Limits, deliberate: a disguise that leaves play without a `|replace|` stays attributed to the Pokemon it was shown as (the player saw that Pokemon; a later replace corrects only the stint it ends); a Pokemon that fainted shown as another (no replace) leaves a fainted `phantom` entry (an extra roster entry flagged `phantom` in `to_dict`, not counted against the encoder's `max_team`) when the Pokemon it was shown as is shown again, because a fainted Pokemon cannot come back; the same Pokemon shown in two positions (one is an Illusion user) gets a phantom entry for the second until a replace or an own request says which, and the encoder takes it as the extra row the player sees. Ambiguity the channel cannot settle raises `IllusionError` (a Pokemon shown in three positions, a replace that fits two roster entries or none, a replace with no disguise on record, an own pair the request leaves open). `moves_revealed` is what a Pokemon can have at one time (#938): Transform (`-transform`) replaces the whole list with what the Pokemon uses as the copy (the engine's `moveSlots` is the target's; the target's own list is not copied) and the list it had comes back on switching out or fainting (`moves_base`, not in `to_dict`), and the target's stat stages are copied (the engine's `transformInto`; no line states them), so a Pokemon shows at most four slots plus Struggle (which is no slot); Mimic and Sketch are not moves of the format (not in the engine-data vocabulary: a `|move|` of them is a `VocabularyError`), so their slot replacement is not tracked, and a pin or format that adds them needs it (`-start|P|Mimic|MOVE`, `-activate|P|move: Sketch|MOVE`). `fixtures/showdown/<format>/transform/battle.json` is the captured game that stopped run public-main-002 (a Ditto transformed twice showed nine moves under max_moves 8), `tests/ml/reducer/test_moves.py`. Trace (or Role Play) records the copied ability on both the tracer and the `[of]` target (the tracer's original ability is not tracked). `-activate` of Skill Swap clears both abilities (unknown), as the per-Pokemon result is not stated. Channel lines of the A2 server path (`|t:|`, `|c|`, `|inactive|`) raise here and belong to the A2 adapter slice, which strips them first. The HP colour class the champions mod appends at exactly 50% and 20% (`50/100g`, `20/100y`) is accepted and dropped. Transform (#938): on `-transform` the reducer stashes the user's revealed move list (`moves_base`, not in `to_dict`, so never in an observation) and starts the copy's list empty, filling it only from `|move|` lines; switching out or fainting restores the stash, and the target's stat stages are copied (the engine's `transformInto` copies boosts; `-transform` is SOURCE then TARGET). So a list is at most four slots plus Struggle. The reducer's state logic is not part of the encoder version (`ENCODER_FORMAT` is not bumped), so a reducer change alters the encoded inputs of the games it affects (here those with Transform) without a new encoder version; the bit-identical rerun claim holds per reducer commit, and a run resumed after a reducer change re-verifies only its newest generation. A repeated `[spread]` tag is accepted (the engine's `attrLastMove` appends one per call that reaches the move line, e.g. Magic Bounce reflecting a spread move; the last value is kept), every other repeated tag with a value still fails closed. `-copyboost|A|B` sets A's boosts from B's (the engine's Psych Up and Costar code; sim/SIM-PROTOCOL.md says the reverse). The #919 sweep (5,500 seeded battles on the generated dataset, five actor mixes) found these two and no other refusal. A player-alone `|error|[Unavailable choice] <text>` (the engine's refusal of a pending candidate, #909; on A2 also `[Invalid choice] <text>` from the server layer) changes no state and the text is dropped; any other `|error|` shape is a `MalformedLineError`. `-zbroken` (a Z-move breaking Protect, champions mod) changes no state. Tests: `tests/ml/reducer/test_unavailable.py` over `fixtures/showdown/<format>/unavailable/` (seeded pending-first battles that reach the refusal, with reduced snapshots `reduced/unavailable-*.json`).

**Encoder, candidate parser, networks, checkpoints and the C1/C6 checker** (`ml/areneon_ml/model/`, `ml/areneon_ml/checkpoint/`, ADR-010 §3, §5, #839). `GameData.from_table(engine_data)` indexes the hashed engine-data export: one `IdVocab` per vocabulary (species, moves, items, abilities, statuses, weathers, terrains, types; index 0 is none, 1 unknown, the engine's ids follow in the export's order) and the numeric attribute tables (types, base stats, weight; move power, accuracy, priority, PP, target and flag one-hots; item flags), each column scaled by the largest value in the data. No list of game content is written in model code, so a vocabulary grows with the table. `Encoder(game, EncoderConfig).encode(query)` reads only `query["observation"]` (`player`, `kind`, `log`, `team.team`) and `query["candidates"]` (`choice`, `pending`): the log goes through `reduce_channel`, the player's last `|request|` gives the Pokémon order (`switch N` / `team NNNN` name the Pokémon at that request position) and the move ids, and it returns tensors without a batch dimension (`EncodedQuery`: one token row per own then opponent Pokémon, the field features, per-candidate slot parts, the picked team tokens and the `pending` flag). It ignores `decision_context`, `identity` (so `rqid`), the `rqid` inside `|request|` lines and every verdict field, so the A1 and A2 forms of a decision give equal tensors (tests over every request of the `fixtures/a2/` recordings and the `policy-query` samples). Volatiles and field/side conditions are engine-owned ids with no vocabulary yet, so they are SHA-256 bucketed into `volatile_buckets` / `condition_buckets`. `encoder_version` is `enc<format>:` + SHA-256 of the engine-data hash, the attribute tables as built, the config (scales included), the feature layout and the index constants (genders, request kinds, events, target codes, slot letters, the bucket hash), so a pin bump or any such change is a new version, never a silent remap. A change in how a value is computed from the state, with the same names and constants, is not visible to the hash: bump `ENCODER_FORMAT`; a golden test pins one version string and the tensor digests of fixed queries and fails on such a change. The A1/A2 equality is also tested on `fixtures/showdown/<format>/a2-pairs.json` (the A1 replay's observations and the A2 frames' observations of the ADR-005 fixtures with candidates from the real `enumerateCandidates`; rewrite with `node packages/bot-client/scripts/capture-encoder-pairs.ts`, a bot-client test compares it with a fresh capture). The encoder raises (fails closed) when an observation's kind does not match its request or candidates, or a Pokémon shows more moves than `max_moves`. `parse_choice` (`model/candidates.py`, re-exported by the worker) splits a canonical candidate into `SlotAction`s (pass, move with optional target and event, switch) or a Team Preview order and refuses any other shape with `UnsupportedCandidate`; `ParsedChoice.format()` is its exact inverse, and `tests/ml/model/test_candidates.py` round-trips every candidate of every `fixtures/showdown/**/choices/*.json`. `CheckpointRecord` (`packages/schema/contracts/v1/checkpoint-record.schema.json`, generated TS and pydantic types, corpus samples in `fixtures/contracts/v1/checkpoint-record/`) is the content-addressed provenance record of one frozen checkpoint; `checkpoint/record.py` reads it (sorted and unique hash arrays, no id referring to the record itself). Part 2 (networks and checkpoints, #839). `PolicyNetwork(role, game, ModelConfig)` (`model/network.py`) is one architecture per role, built and stored separately: a transformer over the entity tokens plus a field token and an aggregation token (attention written out as matmul and softmax, no fused kernel), a candidate head (a `battle` candidate embeds its two slot actions, move, target, event, acting Pokémon and switch-in tokens; a `preview` candidate its ordered team positions; both add the pending flag, cross-attend over the state and score against the aggregation token) and a value head on the aggregation token. Every size is configuration (`ModelConfig`: `d_model`, layers, heads, `d_ff` and the nested `EncoderConfig`; there are no defaults: the `model` section of the run's `TrainingRunConfig` carries the values and code only bounds them), same-seed initialisation is claimed for one machine and software only, vocabulary sizes come from `GameData`, and attribute tables are buffers derived from the engine data, not parameters. `collate` pads queries into a `Batch` (training may batch); evaluation runs one query per forward pass, a batch of one with no padding, on CPU with `configure_cpu_inference()` (deterministic algorithms, one thread), and `tests/ml/model/test_network.py` shows a query's logits are bit-identical alone and after others, and equal for the A1 and A2 forms. A checkpoint (`checkpoint/files.py`) is one safetensors file: the tensors, and `__metadata__` with the format, role, model config, encoder version and engine-data hash. The writer is our own so the bytes are deterministic (the library orders metadata by hash-map iteration); the id is the SHA-256 of the bytes; `load_checkpoint(data, game, expected_id, role)` (the id is required and checked before anything is read; the configuration is bounded, so a crafted file cannot allocate without limit) refuses bytes that do not hash to the id, another role, engine-data table or encoder version, an invalid configuration, and tensors whose names, dtype or shape differ from the network's. No pickle and no `torch.load` anywhere (a syntactic AST scan of all of `ml/areneon_ml` (a guard, not a proof: it misses aliased and dynamic imports) bans imports of pickle, dill, cloudpickle, shelve, marshal and numpy and calls of `torch.load` / `torch.jit.load`). numpy is not in the closure: the writer and reader move bytes through `ctypes`/`torch.frombuffer`. `python -m areneon_ml.checkpoint init --role … --seed … --engine-data … --run-dir … --model-config f` (the `model` section of a `TrainingRunConfig`, required) writes a seeded, untrained checkpoint (generation 0, and the input of the worker tests); learner state and training are below (#840). `checkpoint/provenance.py` is the C1/C6 checker (`ProvenanceGraph(records, sources)`; the `sources` registry is a HAND-SUPPLIED, UNHASHED input for now, a documented deviation from ADR-010 §5 until follow-up #853 derives and hash-binds it from the league run record: it must be canonical (RFC 8785) JSON, and `classify` / `independent` print its hash so an evaluation plan can bind it; `python -m areneon_ml.checkpoint classify|independent --records <dir of CheckpointRecord json> --sources <json>`): the ancestry of a checkpoint is itself plus everything reachable through `parent`, `league_opponents`, `exploiter_target` and the generators of its training sets (the `sources` registry maps each training-set hash to the checkpoints that generated it; an empty list is an outside behaviour-cloning or fine-tuning source, and a set missing from the registry is refused); C6 independence is disjoint ancestries (learned checkpoints and data sources; scripted baselines and the team pool are not nodes), C1 calls an opponent `seen` when it is in the candidate's ancestry, a scripted baseline, or a related lineage, and `held_out` only when every opponent checkpoint is an evaluation exploiter of the candidate or an independent lineage (one related member of a Preview + Battle pair makes the pair `seen`). The records must agree with each other: a parent shares its child's encoder version, a parent shares the child's role (a warm start cannot cross architectures), league opponents and the exploiter target may be either half of a frozen Preview + Battle pair, and nothing synthetic descends from a private checkpoint. It fails closed: a referenced checkpoint without a record, a repeated record, a cycle, or an exploiter in its own target's league (C3) is a `ProvenanceError`.

**Fixtures** live only under `fixtures/` (CC0, synthetic or sanitized, with provenance). `fixtures/showdown/<format>/` holds the golden request fixtures plus `battle.summary.json` (the log hash and choices), `channels/p1.json` and `p2.json` (each player's own stream of the golden battle as a `PlayerChannelLog`, the only battle input an observation may be built from), and `choices/` the choice corpus. `random/` is the random-play channel corpus (`b00.json`..., each a seed, the two synthetic teams, the actor seeds and both players' `PlayerChannelLog`, plus `manifest.json`). `fixtures/teams/<format>/` holds synthetic PokePaste teams, a `manifest.json` (provenance, expected verdict and reason) and `verdicts.json` (the validator's log). **TrainingRunConfig, PPO learner and learner state** (`packages/schema/contracts/v1/training-run-config.schema.json`, `packages/showdown-bridge/src/training-run-config.ts`, `ml/areneon_ml/learner/`, ADR-010 §1, §5, #840). `TrainingRunConfig` is the one record of a run's values: lineage and format, every seed (`run_key`, the two initialisation seeds, the learner's generator), the `model` section (encoder and network sizes), the `generation` plan (self-play games, games per scripted baseline, `max_turns`, `n_parallel`, latency budgets, handshake timeout, `max_line_bytes`), the `ppo` settings and the learner's `device` (`cpu` or `cuda`) and thread count. Contracts carry no floating-point numbers, so real values are integers in millionths (`learning_rate_micro`, `clip_micro`, ...) or billionths (`adam_eps_nano`); `areneon_ml.learner.config.read_run_config` is the one place that divides them. The reader rules the profile cannot say (heads divide `d_model`, `max_picks` ≤ `max_team`, a baseline listed once) are checked by `read_run_config` and by the TS `readTrainingRunConfig`, which also gives `runConfigHash` (SHA-256 of the JCS bytes, `CheckpointRecord.run_config_hash`). League mixture and freeze-interval values are not in v1: they come with the league scheduler (Wave 5). The learner is PPO with GAE over the TrainingExample stream: `learner/data.py` reads a stream only through `read_stream` with its manifest, refuses a set that is not `learner_ready` or was not played by the `behaviour_policy_id` it trains, and splits each Episode into one Preview step and one Battle trajectory (encoded from the example's observation and candidates alone). The reward is the game score at the last step of a trajectory (win 1, tie ½, loss 0, `ppo.GAME_SCORE`); every earlier step, a refused pending choice among them, has zero immediate reward. `learner/trainer.py` recomputes the behaviour policy's log-probability and the value of every decision from the frozen weights with no gradient (no probability is stored in an Episode), computes advantages with GAE, then runs the configured epochs over minibatches shuffled by the learner's own generator; the loss is the clipped surrogate over a softmax across the real candidates (`ppo.py`, checked against hand-computed values) plus the value error and the entropy bonus. Determinism claim: on CPU, with the config's thread count and deterministic algorithms, the same inputs on the same machine and software give bit-identical weights; nothing is claimed across machines or torch builds, and a CUDA learner is not bit-reproducible (its run config, with `device: cuda`, hashes differently). The learner state (`learner/state.py`) is `learner-<g>.safetensors` (both networks' weights, the Adam moment tensors, the generator's state tensor) plus `learner-<g>.json` (JCS: generation, run config hash, seeds, PPO settings, optimiser step counts); `learner_state_hash` is SHA-256 of `JCS({tensors_sha256, sidecar})`. `restore_state` loads only through safetensors and a JSON parser, recomputes the hash, refuses a state of another run config, a sidecar that contradicts the networks and tensors of another name, dtype or shape, and changes the learner only after every check. `checkpoint/files.py` gained `pack_safetensors` / `unpack_safetensors` (float32 and uint8) beside the checkpoint writer.

**League seeds and the LeagueRunRecord** (`packages/showdown-bridge/src/league-seed.ts`, `league-run-record.ts`, `packages/schema/contracts/v1/league-run-record.schema.json`, `ml/areneon_ml/loop/league.py`, ADR-009 §3, ADR-010 §4, #843). `league-seed/1` is the pure derivation of everything a league game is built from: `leagueGameStreams(run_key, generation, game)` is SHA-256 over the JCS of `{run_key, generation, game, purpose: "league-game"}`; the first 16 bytes are the battle seed in the engine's `sodium,<32 hex>` form, bytes 16 to 23 are the two sides' team draws (the caller takes them modulo its pool) and bytes 24 to 27 seed a scripted baseline's stream. `planGeneration` calls it, and it was moved out of the planner byte for byte: **no seed, plan or committed hash changed**, so the tiny-loop determinism tests pass unchanged. `policyStreamLabel(seed, game, player, policy_id)` is the per-seat policy stream label (protocol D9 with the game index); `sampleU` adds the request number to it and keeps its draw. Seeds and stream labels are the harness's: the worker is given only the draw `u`, never a seed, and no observation or `TrainingExample` carries one. The `LeagueRunRecord` (contract v1, integers only, hashed by `leagueRunRecordHash`) is written as `league-run.json` beside `plan.json` for each generation (`playGeneration` builds it, `writeGeneration` writes it before `generation.json`). It may also hold `forfeit_causes` (ADR-017 slice 2, #923): `[{cause, count}]` sorted by cause, each cause once (`crash`, `invalid_reply`, `latency_overrun`, `out_of_memory`, the harness's `ForfeitCause`), each count at least 1, summing to `forfeits`; written only when a game forfeited, so a forfeit-free run writes the same bytes as before, and derived from the same per-game rows as `generation.json`'s `forfeit_causes` object. A minor change within v1 (ADR-008 §3): a reader older than the field rejects a record that carries it, so the generated types and models ship with it. The Python driver refuses a record whose causes differ from `generation.json`'s. Reader rules the profile cannot say, in `readLeagueRunRecord` and `read_league_run_record`: `played + forfeits = games`, causes sorted, unique and summing to `forfeits`, two Episodes per played game, opponents sorted and unique and summing to `games`. `checkLeagueRunRecord` and the Python reader tie a record to its `TrainingRunConfig` (run key and hash). The Python loop driver reads `league-run.json` and `plan.json` after each generation and refuses one whose record belongs to another run, config, generation or pair, whose plan does not hash to `plan_hash`, whose forfeits differ from `generation.json`, or whose plan carries a battle seed the run key does not give. The league scheduler, the `L2` lineage and the exploiters (#844, #845) build on this and are not here.

**Progress evaluation** (ADR-017 slice 4, `packages/showdown-bridge/src/progress-*.ts`, `packages/team-dataset/src/progress-pool.ts`, `packages/team-dataset/scripts/progress.ts`, `ml/areneon_ml/progress/`, `python -m areneon_ml.loop progress`; the docs section is `docs/training-run.md` section 4). **Generation loop** (`ml/areneon_ml/loop/`, `packages/showdown-bridge/src/league-generation.ts`, `generation-cli.ts`, ADR-010 §1, #840). `python -m areneon_ml.loop run --config <TrainingRunConfig.json> --run-dir R --engine-data <engine-data.json> --generations N [--node node] [--worker-python <python>]` continues the run in `R` until N generations are committed (resuming from the last one, a no-op if N are there); `provenance --run-dir R --out D` writes `D/records/` and `D/sources.json` (derived from the run's own manifests) for `python -m areneon_ml.checkpoint classify|independent`. Generation 0 is the seeded random pair (no warm start, ADR-010 §4); generation g plays the pair frozen at g-1 on A1 (`play-generation.ts`: the Python worker on CPU torch behind the TS client, `policyGame` for self-play and for each configured scripted baseline), writes an Episode for every played seat (`episodeFromRecord`, collection kind `league`, `run_id` = the config's `run_key`, the seed the battle ran with), loads only the pair's own seats through `loadTrainingSet` (`behaviour_policy_id` = `policy:` + SHA-256 of `JCS({preview, battle, mode, temperature, precision})`; a baseline's Episodes are kept but the loader would refuse them), trains (`learner/`), freezes the new pair and commits. A forfeited game's row in `generation.json` carries `forfeit: {loser, cause, request_seq, detail}` and the file a `forfeit_causes` count by cause (both absent without a forfeit, so such a run writes the same bytes); the policy worker client's handshake timer ends with the handshake, not the session (#912: left running it killed the worker 60 s into a session). The frozen pair always plays with temperature-1 sampling, never argmax (`playOne`; the policy id says `mode: sample`), and a baseline seat is never queried or loaded (tests fail on either). The match plan (battle seeds, team indices, baseline seats) is a pure function of the config, the generation and the team pool (`planGeneration`), so a killed generation is replayed from the same plan. Run directory: `run-config.json`, `checkpoints/<id>.safetensors` (the store the worker reads), `generations/g<NNNNNN>/` (Episodes, `stream.jsonl`, `training-set.json`, `plan.json`, `generation.json`, `train-report.json`, `learner-<g>.safetensors|json`, `records/{battle,preview}.json`, the cumulative `team-set.json`, `manifest.json` = SHA-256 of every other file plus the checkpoint ids and hashes). `run()` holds an exclusive `flock` on `<run dir>/.lock` for its whole run (a second driver on the directory fails fast; the operating system releases the lock when the holder dies; caveats: `fcntl` is POSIX only, NFS needs a working lock service, and a WSL2 `/mnt/c` directory (DrvFs/9p) may not honour `flock`, so keep run directories on a local Linux filesystem; `generations/`, `checkpoints/`, the run directory and its parent are fsynced when first created). A generation is built in `.g<NNNNNN>.partial`; every file and directory in it is fsynced (the Node side's own files too: `writeGeneration` fsyncs each file, then both directories, `generation.json` last), the manifest is hashed from the flushed bytes, and one `os.replace` of the directory commits it, followed by an fsync of `generations/` (`write_checkpoint` and `run-config.json` are written the same way, temp file, fsync, rename, fsync of the directory; stale `checkpoints/.*.partial` files of a killed run are deleted at start); the next start deletes partials, finds the newest committed generation, verifies its manifest (only the newest: the learner state, records and team set a resume needs live there, `latest_complete` checks that the numbers run 0..n without a gap, and `provenance` verifies every generation), restores the learner (`restore_state`, hash checked), and refuses unless the restored weights are the stored checkpoints (written again if the store lost them) and the records agree with the state and the manifest (checkpoint id, learner state hash, run config hash, training-set hashes). Each generation's two `CheckpointRecord`s carry the lineage, the parent (the previous generation's same-role checkpoint), the TrainingSet hash, the run config hash, the learner state hash, the encoder version, the cumulative team-set manifest hash and the format's version manifest (from `format-manifest.ts`). The team pool is the interim one (`trainingTeamPool`): the golden team, the legal paste fixtures and the random-play corpus teams, all committed CC0 synthetic and proven synthetic by that source; the ADR-013 team generator does not exist yet. `generation.excluded_abilities` of the config keeps out teams that hold an ability on its list; the tiny and the current configs list `Illusion`, a stop-gap for the reducer's former `|replace|` gap, which #851 closed. To drop it: remove `"Illusion"` from `generation.excluded_abilities` of a NEW run's config (a new `run_key`; the list is part of the run config hash, and the pool, hence every team index of `planGeneration`, changes with it, so never edit a run in progress), then sweep first: `node packages/team-dataset/scripts/reducer-sweep.ts --config <config> --mix uniform-all --battles 300 --only-ability Illusion --out OUT.jsonl` and `uv run python scripts/reducer_sweep.py OUT.jsonl` must report `unexplained: 0`. A new run restarts from generation 0 (ADR-010 §4); the committed `config/training/public-gpu16.json` still lists Illusion until a follow-up decides. Claims: with the CPU learner, one thread count and the same machine and software, an independent rerun gives byte-identical generations and a SIGKILLed run resumes to the same learner-state hashes (`training-loop.python.test.ts` SIGKILLs the driver's whole process group at three points of generation 2 and resumes each to the same hashes: `play`, while Node and the worker are alive (the partial may still be empty); `write`, while Node writes its files (`generation.json` is written last, so Node and the worker are still alive); `seal`, after `train-report.json` exists and before the manifest, so the driver's train/seal phase is killed by a real signal (the window is short; a missed one is retried in a fresh directory). The driver's read and commit phases are otherwise exercised by in-process stage killers (exceptions), `tests/ml/loop/` kills at each stage with a fake simulator side); a CUDA learner is not bit-reproducible and nothing is claimed across machines or torch builds. The training self-play and the learner may batch; evaluation never does (§2). League mixtures, a freeze interval and exploiters are Wave 5.

**GPU learner** (`ml/gpu-env/`, ADR-010 §4, §5.2, #840). **Team generator** (`packages/team-dataset`, ADR-013 §2, §3, #816; imports the engine only through the bridge). `config/teams/<format>/labels.json` (a `TeamLabelSet`) and `generator.json` (a `TeamGeneratorConfig`) are data; `check-team-labels.ts` (in `make ts` and CI) reads them against the pinned engine (every id exists, sorted and unique, no default equal to a listed value, every leaf can hold in the vocabulary, at most 65,536 cells). `labeller.ts` is a pure interpreter of the label-set record (`all_of` of leaves, first match else default) and holds no id (a test greps its source for the committed ids); a base cell is the label values read as a mixed-radix number, first label most significant (64 cells for the five committed labels). `stream.ts`: draw k of a plan has seed `"sodium," + hex32(HMAC-SHA256(generation_key, JCS({config_hash, k, plan_id, purpose: "draw"})))`; the pilot's preimage is `{config_hash, k, purpose: "pilot"}` (no plan id: one recorded pilot serves every plan of a config). `proposal.ts` draws a team uniformly from the bridge's vocabulary (roster, move pools, abilities, natures; level, team size, Stat Point total and Item Clause from the rule table; IVs, the per-stat maximum, gender, nicknames and integer item weights from the config); `draw.ts` puts it in canonical order, round-trips it through `importPaste`/`exportPaste`, asks `validateTeam` (on a copy: the validator normalises sets in place) and labels it. `plan.ts` makes the quota plan from the pilot counts: proportional quotas with a floor of `n_stratum_min` per split, and the D20 merge before any generation (a group is affordable when it has `pilot_min_hits` hits and `quota * pilot_draws <= d_max * hits`; an unaffordable group is replaced by the group one level up, dropping the last label first, which absorbs every cell under it; a plan that is infeasible even with all cells merged is refused). `binner.ts` bins accepted draws in counter order (full bin: overflow; known hash: duplicate; else binned), so a bin is an exact sample of the proposal conditioned on its stratum; `dedupe.ts` is the two-stage known-hash index (a sorted 64-bit prefix array, 8 bytes per hash, then an exact comparison in memory or in a sorted file); `rejection-log.ts` writes and hashes the log as the run goes. `generate.ts` runs it: pilot (recorded, or run), plan, one stream, then each stratum's full bin is dealt to dev, validation and training by HMAC-SHA256(assignment_key, canonical hash) order (the assignment rule of §2 so that every record has its split; `assignSplits` of #860 owns this later), every record is re-read with `readTeamRecord` and the labeller, and a bin still short at `d_max` re-plans with the short strata coarsened one more level under `<plan_id>-r<n>`. `provision.ts` sizes the ranges from a negative-binomial fill-time quantile; `range.ts` summarises a range of draws as one SHA-256 over fixed-width per-draw records, the unit the two-platform check compares. `command.ts` is the CLI (`generate`, `pilot`); output is JCS-canonical, so the same commit, config, label set, keys and references give the same bytes (`records.<split>.jsonl`, `manifest.json`, `coverage.json`, `pilot.json`, `rejections.jsonl`). The generation key of a public dataset is a public key given on the command line; sealed generation is #861. Package tests run the real validator on a few thousand draws; keep any new generation test small. Quotas: a split's share of a stratum is its share of the ACCEPTED pilot draws (rejected draws belong to no cell), while the cost rule uses the rate per draw of the stream; the `n_stratum_min` floor per stratum and split can lift a split above its request (20/20/100 over 23 strata delivers about 55/55/116), so `coverage.json` lists requested and delivered per split and the CLI prints any difference. `provisioning.exceeds_d_max` (and a CLI warning) says the 0.99 fill quantile is beyond `d_max`, because the merge decides on mean fill times and the stream stops at `d_max`. `coverage.json` also records `replan` (0 or the re-plan count) and each base cell's `held` teams per split inside merged strata. The seed preimage is the JSON object `{config_hash, k, plan_id, purpose}` (the pilot's has no `plan_id`), not the tuple the ADR writes: an ADR-013 erratum candidate. `moves_per_set` is a named config field (optional in the schema, required by the proposal). `generator.json` gives every Mega Stone (the items the roster's Mega formes require) weight 0 so a stone appears only with its Mega species; otherwise about half the free item slots hold a useless stone and the Mega label is nearly constant (a test holds the label's stones and the zero weights equal to the roster's required items, so a pin bump that adds a stone fails). Scale limits of this slice (#883): the dataset files stream. `writeDataset` writes each `records.<split>.jsonl` in 1 MiB chunks (`writeLines`), and `recordHashes` and `readDataset` read line by line (`eachLine`, `endsWithNewline` in `dataset-io.ts`), so no file is held as one string and the 512 MB string limit no longer applies to them; the bytes written are unchanged. What still sits in memory: the records themselves (`GenerateResult.records`, and `readDataset`'s `VerifiedDataset`, as objects, roughly the file size or more), the known hashes as JS strings while `sortedUnique` builds the sorted list (about 100 bytes per hash; 1.2M hashes peak near 400 MB of RSS in `scripts/measure-streaming.ts`, which writes, reads back and indexes 1.2M padded lines of a 930 MB file; the previous joined-string code fails on it with `RangeError: Invalid string length`), the binner's in-run `Set`, which holds at most 2^24 (about 16.7 million) binned teams (a V8 limit, unchanged), and the JCS string of the sorted hash list that `datasetHash` and `recordHash` build (fine to some millions of records). The CLI reports an oversize failure as exit 1; 10^8 teams needs the shard slice's binary builder. `assign-splits.ts` (#860): `assignSplits(pool, plan, assignment_key, n_stratum_min?)` is the one split rule (ADR-013 §2): within each stratum it orders the teams by HMAC-SHA256(assignment_key, canonical hash) and deals dev, validation and training by the plan's quotas; it is pure, order-insensitive, and refuses a stratum that is not exactly its bin, a team twice, a quota below `n_stratum_min` and a key that is not 64 lowercase hex digits; `generate.ts` calls it. **Committed fixtures** (`fixtures/teams/<format>/datasets/fixtures-v1/`, CC0, see its README): `teams-dev.jsonl`, `teams-validation.jsonl` (JCS lines), `manifest.json`, `hashes.json` (sorted `record_hash` / `canonical_team_hash` lists per split and the manifest hash: a Parquet shard of the split must list the same `record_hash`es), `pilot.json`, `coverage.json`, `run.json` (the public keys, sizes and generator commit); the training split is generated in the same run but never committed. `dataset-reader.ts`: `readDataset(dir, ctx)` trusts nothing (manifest against config and label set and the engine's version manifest; each record through `readTeamRecord`, the labeller, `importPaste` round trip and `validateTeam`; every stratum holds its quota; no team in two splits; the hash lists recomputed), `trainingPool(datasets, engine)` takes only `readDataset` results, recomputes every canonical hash from the paste, and returns a branded pool of dev records that `drawTrainingTeam` alone accepts: a validation record, a forged hash, a hand-built dataset or pool, or a team repeating a validation team is refused (`readDataset` also checks `vocabulary_hash` and `reference_pool_hash` against its context; `generator_commit` is checked only by the regeneration test). `fixtures.ts` + `scripts/fixtures.ts` (`write` / `check`, `--full` also reruns the 40,000-draw pilot, about 45 s) regenerate the files from the committed config; a test (about 5 s with the recorded pilot) requires them byte for byte.

**Parquet shards** (`packages/team-dataset/src/shards/`, ADR-013 §4, §6, §7, #862). A snapshot is immutable, content-addressed Parquet shards plus a `TeamSnapshotManifest`; shards live in R2 and Releases, never in git (`check_binary_files.py` rejects `.parquet`), so every test writes them to a temp dir. `columns.ts` is the column layout (parquet schema version 1: one column per record scalar, `labels` as a list of `{label_id, value}` structs, derived `stratum` and `label:<id>` columns) and the rebuild rule (`recordOf`: null, a missing or extra column, an int64 outside +-(2^53-1) or a derived column that differs from the labels refuses the shard). `layout.ts` is the layout (`S = ceil(R / 2^18)`, shard = first 8 bytes of HMAC-SHA256(`shard_key`, canonical hash) mod S, rows sorted by stratum then canonical hash, `cell_ranges`). `reader.ts` (`readShard`, hyparquet and hyparquet-compressors, both MIT, production dependencies that pass `make licences`) decodes, rebuilds, computes `record_hash` and checks row count, order, split, `logical_hash` and `cell_ranges` against the manifest; it never calls the engine. `snapshot.ts` builds the manifest (`buildSnapshotManifest`, checked by the bridge's `readTeamSnapshotManifest`), reads a snapshot shard by shard (`eachSnapshotShard`: file SHA-256 and size, one-to-one shard indices) and holds `checkFixtureAgreement` (a committed split's `hashes.json` and the shards of that split must list the same sorted `record_hash`es). `convert.ts` turns a dataset directory (`records.<split>.jsonl` or the committed `teams-<split>.jsonl`, plus `manifest.json`) into shards under `pub/v1/shards/<sha256>` and `snapshot.json` with bounded memory (one shard at a time) and reads every shard back once; `verifySnapshot` checks the shards against the dataset file byte for byte. The writer is the DuckDB command-line tool run as a child process (`duckdb.ts`): never a library import, never in a `package.json`, lockfile, Dockerfile or image (a test scans every tracked manifest), user-installed (`DUCKDB_BIN` or the PATH); `scripts/duckdb-pin.json` holds the version URL and SHA-256 of the zip and binary per platform, CI downloads and checks it and sets `ARENEON_REQUIRE_DUCKDB=1` so the real-tool tests cannot skip there (without the tool they skip, and a stand-in that writes through hyparquet-writer, a dev dependency, covers the conversion paths). The manifest's `writer` is read from the binary that ran. File bytes depend on the writer version and settings; `logical_hash` and `logical_snapshot_hash` do not (tests cross two DuckDB settings, and two versions when `DUCKDB_BIN_ALT` is set). Cross-architecture byte equality is not established: see ADR-013 §6. Measured rebuild is about 20 us per record (about 5 s per 2^18-row shard) against the ADR-013 d1 and section 5 budget of about 7.8 us (about 2 s); a read of one 250k-row shard peaks at 2.1 GB RSS (maxRSS, includes uncollected garbage), a write at 3.5 GB, while the decoded shard retains about 0.42 GB of heap after a forced GC (the ADR's 0.4 GB holds for the cache, not for the peak). The miss is to be recorded as an ADR erratum (#882). Publishing, the sampler and the working database are later slices.

**Private shards** (`packages/team-dataset/src/shards/private-shards.ts`, `private-reader.ts`, ADR-015 §2, #899): the d1 layout with the `PrivateTeamRecord` columns (`privateColumnsFor`: the record's scalars, `supersedes_record_hash` nullable, `tags` a list of strings, `holdout` a boolean, `labels`, the derived `stratum` and `label:<id>` columns; parquet schema version 1, `data_class` private, one split `owner`). It reuses `shardCount`, `shardAssigner` (HMAC of the canonical hash), `cellRanges`, the int64 rule and `recordHash` / `shardLogicalHash`. Differences: rows are ordered by stratum, canonical hash, then `team_id` (a retired record may share its team's canonical hash with an active one), cell ranges carry `active_rows` (`privateCellRanges`), and every refusal message is fixed text naming a layout column or a row position, never a value, a column name read from the file or library text (a canary test in `private-team-store`). `readPrivateShard` is engine-free and keyless like `readShard`, but the Parquet decode runs in a worker thread (`private-decode.ts`: `decodeIsolated`, an empty environment, a 4 GB heap limit, a wall-clock limit of 5 minutes by default, terminated afterwards; the worker is a `data:` module that imports the decode, so there is no separate worker script): hyparquet is written for trusted files and a damaged one can make it loop forever (a page header with a negative size), allocate without bound, or leave a rejected promise unhandled, which ends the process with library text; a seeded corruption fuzz (`snapshot-fuzz.test.ts`) found all three. Whatever the worker meets, the main thread sees the rows, a layout refusal's fixed message or `not a readable Parquet file`. The footer checks and the column-by-column read are `decodePrivateParquet` (tested in process, because the worker is not instrumented for coverage). The new column kinds (`NULLABLE_VARCHAR`, `BOOLEAN`, `VARCHAR_LIST`) are in `ColumnType`, and `DuckdbWriter.writeShard` takes `isolated: { dir, timeoutMs? }` for the private path: the tool runs with HOME, TMPDIR and cwd set to a scratch directory made inside `dir`, `DUCKDB_HISTORY=/dev/null` and nothing else in its environment (the `Runner` gained an optional cwd and timeout), the SQL starts with `SET autoinstall_known_extensions = false; SET autoload_known_extensions = false;` and locks the configuration (`SET lock_configuration = true;`) after the other settings and before the copy (a real-tool test reads the three settings back inside a child of the same shape), the tool is killed after `timeoutMs` (10 minutes by default), a failure is the fixed `WITHHELD_MESSAGE` (DuckDB's stderr can quote a paste and is never forwarded; a real-tool test provokes a DuckDB error that quotes the row and checks the public path forwards it and the private one does not), and the scratch directory is removed by `removeTree` (a best-effort chmod of leftovers, then a second try; it never throws, so cleanup cannot replace the original error; a removal that fails after a successful write is the fixed `CLEANUP_MESSAGE`). The public `writeShard` path is unchanged.

**Rules importer** (`packages/rules-importer`, ADR-007 §6, #768), the last step of the rules pipeline (publish, then import): `GitHubReleaseSource` lists the non-draft `rules-snapshot-*` / `rules-channel-*` Releases through `gh` (an injected `CommandRunner` whose children see only an env allowlist), resolves each tag to its commit, downloads each asset into a private temp dir and keeps only the bytes `GhAttestationVerifier` returns. **Evaluation records and register** (ADR-010 §6, §7, §9 O1/O11, #846; code in `packages/showdown-bridge`, engine-free, Node built-ins only). Values live in reviewed data, never in code: `config/evaluation/evaluation-parameters.v1.json` (`EvaluationParameters`: §6, `maxTurns` included) and `training-gate-rule.v1.json` (`TrainingGateRule`: margins, alternatives, target power, the claim family). Ratios are integer ppm (`PPM` is only the unit). `evaluation-config.ts` reads each against its ADR-008 contract and then enforces what the profile cannot: alpha' = alpha / (m·B_sealed) is whole ppm, `b_boot` exceeds m·B/alpha, `r_cov` is at least 1/alpha', `cov_tol` is derived (never stored), sorted-and-unique lists, and, with both records (`readEvaluationConfig`, `checkGateConsistency`), the family size equals the claims, G2 claims name each baseline once, and each gate's `h` is at most what the target power allows (`maxHalfWidthPpm`, from computed normal quantiles; no z table). A record, entry, commitment or plan is referenced only by `domainHash(domain, value)` (SHA-256 of `areneon:<domain>:v1\n` plus its JCS bytes: a hash of one kind never stands for another); changing any value is a new version, never an edit. `evaluation-plan.ts` holds the `SealedSetCommitment` (L3: hashes and counts only, E1's stratum counts; `setCommitment`/`keyCommitment`/`checkReveal` compute and open the hashes, and no sealed content is ever a field) and the `EvaluationPlan` (I2) with `checkCommitment`/`checkPlan`, which tie both to the records they name. `evaluation-register.ts` is the register (I6, O1): an append-only JSON Lines file in the isolated store, each line the JCS bytes of an `EvaluationRegisterEntry` (`set_commitment`, `plan_registration`, `l2a_recheck`, `run_outcome`, `incident`, `set_retirement`) carrying the previous entry's hash. `verifyRegister(text, configs)` is pure and offline; given the records (the CLI defaults to the committed v1 files, repeatable `--parameters`/`--rule`) it re-checks every commitment and plan against them, ties their hashes to those files and takes the run budget from the parameters, and it refuses a changed, dropped, reordered or non-canonical line, a time that goes back, more plans than `b_sealed`, a second plan for a candidate, a run without a passing L2a re-check, and any result on a contaminated or retired set. Head files are add-only (`checkHeadsAddOnly`; the `typescript` CI job runs `heads-check --base HEAD^1`; CODEOWNERS covers `evaluation/register-heads/` and `config/evaluation/`). `init` is the only command that starts a register, `gen-secret` writes a 256-bit secret (mode 0600, never overwrites) and prints only its hash, and `checkReveal` also requires `team_count` teams whose strata equal `stratum_counts` (E1 minimum). `scripts/evaluation-register.ts` (logic in `src/evaluation-cli.ts`: `config-check`, `commit-set`, `register-plan`, `append`, `verify`, `head`, `heads-check`) is the owner's tool; `make ts` runs `heads-check`. The sample corpus covers every new contract (`src/evaluation-samples.ts`). The isolated store itself (a separate OS user plus a container, files mounted read-only only into the evaluation container) is created by the owner from `docs/runbooks/evaluation-store.md`; `scripts/check-evaluation-store.sh` (tested in `tests/scripts/test_check_evaluation_store.py` on a scratch directory) is the read-only check the owner runs as the store user (owner, modes, parents, `--code`, container mounts and user) and as the training user (`--probe-denied` needs EACCES, so a missing path fails). This code never creates a user, container or mount, and the evaluation runner and sealed team generation are other tickets.

**Sealed team generation** (`packages/team-dataset/src/sealed*.ts`, ADR-013 §2, protocol L1 to L5, #861). Runs only inside the isolated evaluation store (`docs/runbooks/evaluation-store.md` §9; `node packages/team-dataset/scripts/sealed.ts generate|reveal-hash|retire|verify`); no agent or CI job runs it against a real store, and the repository holds no sealed data and no key (tests use throwaway counter-derived keys and a temp store). `sealed-store.ts` is the file discipline: the store directory must be absolute, a real directory, owned by the invoking user, mode 0700, outside any git working tree and below no group- or world-writable parent (sticky accepted); directories are created 0700 and files 0600, never overwritten, and a loosened file is refused on read; JSON parse errors never quote the text. `sealed.ts`: the key and the salt are 256 bits from `generateSecret` (the OS CSPRNG; tests inject a source) and are written only to `<store>/sealed/<set_id>/{key,salt}`; they are never an option, a return value, a log line or an output. The set shares the public pool's generator, config, label set, vocabulary, version manifest and D20 strata (`sealedPlan` reads the public `TeamDatasetManifest`; it never merges again): `n_teams` is shared over the strata by pilot hits (largest remainder, at least `n_stratum_min`), the draw budget is the public `d_max` raised by the config's `sealed_margin_permille`, and a bin still short discards the whole generation (key, teams and rejections dropped; one `discards.jsonl` line of counts and the key's hash), then redraws a new key, up to `maxAttempts` (`SealedShortfallError` after that, nothing committed). L1 is the canonical hash, L2 is `NearIndex` (distance at most `d_team`, the fewest differing fields over all pairings of the sets' species, item, ability, nature, move set and Stat Points; an inverted index on whole sets finds candidates, then the exact distance), both against every `--known` team (public splits, released datasets, the training pool, retired sealed sets); `rejection-log.ts` gained the `near_duplicate` reason. The L3 commitment (`setCommitment`/`keyCommitment` over the teams `{k, paste, stratum}` in stratum then draw order) is checked with `checkCommitment`; the register CLI (not this module) commits it. Contracts: `SealedTeamSetManifest` (hashes, counts, plan and log hashes; no secret; `readSealedTeamSetManifest`) and `RetiredSealedManifest` (the reveal: key, salt, file hashes; `readRetiredSealedManifest`, `retiredManifestHash` is the register's `reveal_hash`), readers in `showdown-bridge/src/sealed-records.ts`. `SealedTeamHashes` is built only by `loadSealedTeamHashes` after the commitment is recomputed from the store, unions with the public hashes for stamping (`withPublic`), and refuses to serialise. `sealed-retire.ts`: `retireSealedSet` writes the reveal bundle (a new 0700 directory) only when the register logs `set_retirement` for the set with exactly that bundle's `reveal_hash` and the stored commitment; `verifyRetiredSealed` needs no store: it opens both commitments, runs `checkReveal` with the stratum from each team, regenerates the set from the revealed key against the reference pool (teams and the whole rejection log must be byte-equal, which replays every L1/L2 skip) and re-checks each team. `scripts/check_data_class.py` now rejects a reveal (`set_id` + `reveal.key`/`salt` + `files`) or a sealed-team line `{k, paste, stratum}` anywhere but the exact paths in `REVEAL_ALLOWED` (the corpus samples; a retired bundle is added by a reviewed edit). The index is in memory (the shard-scale build is a later slice).
**Private teams** (ADR-015, which supersedes ADR-014 and its encrypted store; the wording rules are in AGENTS.md; the owner's bucket, lock and token setup is `docs/runbooks/private-store.md`, #889). The owner's real teams are inputs to a separate private run after the Training gate (#878), never to public datasets, published checkpoints or Episodes. They are kept, once the bucket is set up (ADR-015; #889, #891), as plain `PrivateTeamRecord`s in Parquet shards (the ADR-013 d1 layout, `data_class: private`) in a private R2 bucket, written once per snapshot, as plain objects with no client-side encryption (R2 encryption at rest only); the owner accepts the residual token risk (ADR-015 section 1); on the owner's workstation they appear only under gitignored `private-data/` (`teams/` is staging, `snapshots/<snapshot_hash>/` the verified local copy, run outputs stay there). Two bucket-scoped tokens exist, a write token for the import only and a read token for readers; both come from the environment of one command on the owner's workstation, never from the repository, a log, a chat or a command line, and an agent never runs a command that holds one. Built (#898): the pure import planner in `packages/private-team-store/src` (`planImport` in `import-plan.ts`, `parseStagedFile` in `staged-file.ts`, typed refusals in `import-error.ts`). Built (#899): the snapshot writer and reader there (below). It takes the staged files as `{name, text}` items, the parent snapshot's `PrivateTeamRecord`s (or null for `--first`), the `--retire` team_ids, the engine and the resolved format, and ports for labels, the hold-out flag (the snapshot layer plugs in the keyed HMAC; the planner holds no key) and fresh team_ids; it returns the next record list (one record per `team_id`, sorted) and a summary of five counts (`new`, `duplicate`, `revised`, `unchanged`, `retired`), or throws an `ImportPlanError`. Header `#! team_id=<32 hex> tags=...` (either key optional, order fixed, tags sorted and unique, at most 16; an empty `tags=` clears the tags, an absent one keeps the parent's), any other `#` line refused; each team goes through `importPaste` and `validateTeam`; a `team_id` not in the parent is refused (never created). A file without an id whose canonical hash equals an active record's, or an earlier file's, changes nothing and counts as a `duplicate` (ADR-015 section 3), so re-importing the same staged folder against its own result is a no-op. An edit is revision +1; a staged record identical to its parent (paste and tags, active) is unchanged; a retired one staged with its id becomes active again; a team absent from staging is unchanged; retirement is only `--retire` (retiring a retired record is a no-op counted as unchanged); a revision or revival that takes another active record's team is `duplicate_canonical_hash`; a result that loses an active parent record is refused; parent records' hold-out flags must equal the hold-out port's value. Beyond the ADR text (to be listed in its erratum, #892): a tag-only edit and a Pokemon-order-only change each make a new revision. A refusal is a code plus a 1-based position that indexes the caller's list (staged files as passed, or the `--retire` list; the command slice maps it back to a file), never text from an input: no paste, file name, tag, header value, id, species or move, and an exception thrown by a port is replaced by a fixed `hook_failed`; the canary tests (`test/import-canary.test.ts`, which asserts every refusal code and has a negative control) enforce it. The package depends on `@areneon/showdown-bridge` as a `workspace:*` link (the packaging test accepts that form for `@areneon/*` only; no registry dependency was added). **Snapshot writer and reader** (#899, slice 3 of #887; `snapshot-writer.ts`, `snapshot-reader.ts`, `work-dir.ts`, `snapshot-io-error.ts`, `snapshot-plan.ts`; the package now depends on `@areneon/team-dataset` as `workspace:*`). `writePrivateSnapshot({records, holdoutKey, parentSnapshotHash | null, labelSet, manifest, vocabularyHash, shardKey, writer, pin, workDir, ...})` lays the records out in shards (`layoutPrivate`), writes each through the pinned DuckDB tool on the private path (`writer.requirePinned(pin)` first; the stand-in or real tool in tests), reads every shard back with the engine-free private shard reader, and returns `{manifest, snapshotHash, shards}` in memory (shard files by manifest index; the writer uploads nothing: that is `publishSnapshot`, below; the CLI, `export` and the collision count are #901). Shards are ordered by logical hash, each with its position as `index` (the HMAC placement index is a separate property the reader checks). The records must already carry their hold-out flags (the writer refuses a flag that differs from `holdoutFlag(key, team_id)`) and satisfy `checkPrivateRecordSet`; a stratum is the label set's base cell (`labelPlan`; no merged strata for owner teams). Intermediates (the rows file and the shard file, which hold pastes in the clear) exist only in a fresh 0700 directory inside `workDir`, which `assertWorkDir` accepts only if it is absolute, a real directory (no symbolic link), owned by the invoking user, mode 0700, no parent writable by group or other (a sticky bit is accepted, as in the sealed store) and every parent owned by the user or root, and either has a `private-data` path segment or is on tmpfs/ramfs (`statfs`); a Windows drive mounted in WSL (`/mnt/<drive>`) is accepted only on tmpfs, because a 0700 mode proves little there; the owner and file-system probes are a test seam of `assertWorkDir` only (the writer's input has no `probe`, and a test reads its source to say so). They are removed afterwards, on failure too; if the write succeeded but the removal did not, the call fails with `cleanup_failed`, and a write that failed keeps its own error. `readPrivateSnapshot({engine, manifest, shard(index), labelSet, expectedSnapshotHash, expected})` is what the import (after writing and after downloading) and #888-era readers run: `readPrivateSnapshotManifest`, a parent equal to the snapshot's own hash refused, the hash the manifest was fetched under (`expectedSnapshotHash` is REQUIRED: there is no option to read without an anchor), the version manifest and vocabulary hash the caller derives from the pinned engine and rules in `expected` (`version_manifest_mismatch`; REQUIRED like the hash: a reader of a snapshot made under another pin says `expected: INSPECT_ONLY` out loud, and `publishSnapshot` refuses that value), `label_set_hash` = `recordHash(labelSet)`, the Parquet layout version, no two shards with one `file_sha256`, `shardCount(rows)` = number of shards, each file's size and SHA-256, `readPrivateShard` (columns, order, placement, logical hash, ranges with active rows), no two shards on one layout index, each record through `readPrivateTeamRecord` (engine round trip), each hold-out flag recomputed from the manifest's key and ppm, and `checkPrivateRecordSet`; it returns the records sorted by `team_id`. The counts need no check of their own: the manifest reader ties `records` and `cells` to the shards' ranges and each shard read ties its ranges to the decoded rows. Every refusal is a `SnapshotIoError` with a code (`SNAPSHOT_IO_REFUSALS`), a fixed message and at most a shard index and row number; whatever a lower layer threw (DuckDB stderr, hyparquet, the engine, ajv) is dropped and not attached as `cause`. Tests: `snapshot.test.ts` (round trip, every code), `snapshot-canary.test.ts` (markers in a paste nickname, tag, label, column name, file bytes, the tool's stderr, a key, a path and a failing shard source; error text, stack, fields and process output scanned; negative controls show the scan flags a leaking message and the public writer path), `snapshot-forged.test.ts` and `snapshot-self-parent.test.ts` (consistent forgeries the writer cannot make). The real-tool case runs where `DUCKDB_BIN` is the pinned binary and cannot skip when `ARENEON_REQUIRE_DUCKDB=1` (CI sets it for `pnpm test`; no workflow change was needed). Not checked by the reader: that the manifest's hold-out block and key equal the parent's (needs the parent), and `vocabulary_hash` / the version manifest against the engine (the caller's). `manifest.regulation` stays `minLength 1` because `make contracts` requires every contract's `$defs/VersionManifest` to equal `version-manifest.schema.json`; a pattern needs a change of that shared definition (not done here). **Object store and publish** (#900, slice 4 of #887; `object-store.ts`, `memory-store.ts`, `r2-client.ts`, `r2-settings.ts`, `current-pointer.ts`, `local-copy.ts`, `snapshot-store.ts`, `publish.ts`). `ObjectStore` is the port: `putIfAbsent(key, body)` (`If-None-Match: *`; an existing object is `ObjectStoreError("exists")` and nothing is overwritten), `get`/`head` (null when absent), `list(prefix)` (only `snapshots/` or `snapshots/<hash>/`) and `overwriteCurrent(body)`, the only overwrite, which cannot reach any key but `current.json`; there is no delete. Keys are checked against the layout (`current.json`, `snapshots/<64 hex>/manifest.json`, `snapshots/<64 hex>/shards/<n>.parquet`): anything else, `snapshots/_lock-check/` included, can be neither written nor fetched, and `listSnapshotHashes` returns only the hashes that have a manifest object, so an unknown key under `snapshots/` is never a snapshot (a test seeds one); `fetchSnapshot` is the verification (`readPrivateSnapshot` on the downloaded bytes). `InMemoryObjectStore` (tests; `seed` puts an object where the port would refuse to, as the owner's lock-check object) and `R2ObjectStore` implement it; one contract suite runs against both (the R2 client on a fake bucket behind `fetch`, so no test opens a socket; `test/network-isolation.test.ts` requires that only `r2-client.ts` calls `fetch` or imports a network module). The R2 client is path-style (`<endpoint>/<bucket>/<key>`), signed with `aws4fetch` 1.0.20 (MIT, no dependencies, pinned exactly, ignored by Dependabot, imported by `r2-settings.ts` only; the `age-encryption`, `@noble/*` and `@scure/base` pins of the superseded design are gone) with the real SHA-256 of the body in `x-amz-content-sha256`, no redirects, no retries, a time limit; 412 and 409 on a conditional write are `exists`, 401/403 `denied`, 429/5xx and any transport failure `unavailable`, other statuses `failed`, a listing or head that is not in the expected form `response_invalid`; every message is fixed and carries no response body, URL, header, bucket or key (`ObjectStoreError`, no `cause`). `R2Settings.fromEnvironment(env, argv, bucket)` reads `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL` (https, an `*.r2.cloudflarestorage.com` host, nothing else in the URL) and `AWS_DEFAULT_REGION` (`auto`) from the environment only; a command line that names one of them (`AWS_*`, `--secret`, `--token`, `--endpoint`, `--account`, `--region`, ...) or contains a value (key id, secret, endpoint, the account id) is `credentials_on_argv` before the environment is read. The values live in `#` fields; the object prints as `[R2Settings]` to String, JSON and `util.inspect`, and it signs requests itself, so only the signing library sees the secret. The bucket name is an argument, not a credential. `test/credential-canary.test.ts` puts markers in all four variables and the bucket, scans errors (message, stack, fields, inspect) and process output on every settings, client and publish error path, including fake responses that echo the markers, checks that the secret appears in no request, and has negative controls. `publishSnapshot({store, engine, labelSet, written, expected, expectedCurrent, snapshotsDir, ...})` runs the ADR-015 section 3 sequence: the snapshot's parent must equal `expectedCurrent` (null for the first) and `current.json` must still name it; the local copy's place must be free and safe; every shard then the manifest (JCS bytes) uploaded with `If-None-Match: *`; every object downloaded again and verified with `fetchSnapshot` (required `expected`, the manifest bytes compared with the sent ones); the verified copy written to `private-data/snapshots/<hash>/` (`assertWorkDir` rules, directories 0700, files 0600, built in a hidden partial directory and renamed, never replacing a copy); `current.json` (`{parent_snapshot_hash, schema_version, snapshot_hash}`, strict reader) checked once more and overwritten last. The final check and the overwrite are a read and a write, not one atomic request: a second writer in between is not excluded (one owner, one write token, ADR-015 section 7). A failure before the last step leaves `current.json` as it was; uploaded objects stay (the lock keeps them; they are unreferenced), and a retry with the very same bytes meets `exists`, so the next attempt needs another `snapshot_id` (another hash). A 404 reads as "absent", so a wrong bucket name looks like an empty bucket until the first write is refused. Also carried from the #899 review: the decode worker settles on `exit` with the fixed message instead of waiting for its time limit. **A2 reconnect (ADR-008 §3-5, ADR-005 gate 3, #895).** `session.ts` joins each connection's channel to the ones before it with `continueChannel` as it goes (`Battle.joined`, the fold of the kept channels; `#build` returns the joined channel, `#keepChannel` keeps the connection's own channel in `A2BattleRecord.channels` and folds it into `joined`), so after a reconnect the bot builds observations, decides and numbers `channel_request_seq` on the battle's one continuous channel, with the actor rule and the watchdog unchanged. A rejoin on another seat is a `SessionError`; one that does not continue the earlier channel (`ObservationError` from the join) is a fatal error like any channel that cannot be built. `a2Episode` folds `record.channels` with `continueChannel` (a refusal is an `A2EpisodeError` that quotes nothing) and stores that one channel; folding covers several reconnects. A decision first made on a rejoin with no timer snapshot (the snapshot went to the old connection; the server does not replay it) has no deadline record, and none is invented (ADR-008 Errata E1b, #904, no contract change): the session marks the `DecisionRecord` `rejoin_without_snapshot` and logs an `incident` (`rejoin_without_timer_snapshot`), the battle plays on and its record is kept, and `a2Episode` refuses it with an `A2EpisodeError` whose `code` is `rejoin_without_timer_snapshot` and whose fixed message quotes nothing. Such a battle is never an Episode or training data. `test/session.reconnect-episode.test.ts` drives the real session through the committed reconnect fixtures (`fixtures/a2/<format>/bot-vs-bot-3.json`: a reconnect after the choice, Episode equal to the A1 Episode in channel, decisions and observations; `-4.json`: no snapshot, record equal, no Episode), two reconnects in a row, and the negative controls (a rejoin that does not replay the room log, a spliced `rqid`, the wrong seat).

A2 (ADR-005) is a bot client on a local Showdown server, for local human sparring against the bot; `packages/bot-client/README.md` is the sparring guide (start, connect, challenge, stop). In `packages/bot-client`, `ProtocolReader` (`src/protocol.ts`) numbers each room's requests per channel: a room's `|init|battle` (sent on every join, before the replayed log, which holds no requests) resets its `request_seq`, open request and re-send identity, so the request re-sent after a rejoin is request 1 of the new channel, as `buildObservation` numbers it.
