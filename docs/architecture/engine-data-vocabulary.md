# Engine data, team vocabulary and role sets

The engine-data export (v1 and v2), the team vocabulary and the role-set table, all derived from the pinned engine.

Part of the architecture documentation split out of `CLAUDE.md` (index: [README](README.md)). Ticket references such as `#1179` point to Redmine (`redmine.piglor.com/projects/areneon`), where measured figures and verdicts are recorded.

- `engine-data.ts` (ADR-010 §3): `exportEngineData` reads the species, move, item, ability, type (with the engine's own type chart), status, weather and terrain vocabularies and their numeric attributes from the pinned engine's data for the format's mod, each list sorted by id (the position is the vocabulary index), into the `EngineData` contract (`packages/schema/contracts/v1/engine-data.schema.json`). It refuses any value of a shape it does not know; the vocabularies hold the engine's standard entries plus, so no reference dangles, every base species a standard forme names and every ability a standard species lists even if the engine marks them nonstandard (eight at this pin: cramorant, eiscue, floette, meloetta, minior, ogerpon, terapagos, Aura Guard). Out of v1 scope (a change needs schema_version 2, the contract being closed): natures, volatile conditions, learnsets, evos, requiredItem, move effects, species height and gender. The table is derived from the pinned Showdown data files (MIT, not CC0; `NOTICE-engine-data.txt` beside it keeps the upstream notice). `readEngineData` adds what the profile cannot say (sorted unique ids, references that resolve). `engineDataHash` is SHA-256 of the JCS bytes: the engine-data hash of the encoder version, so a pin bump yields a new one. The golden table and `engine-data.summary.json` (hash, counts) sit in `fixtures/showdown/<format>/`; a test re-exports and compares them. `scripts/export-engine-data.ts` rewrites them.
- `engine-data.ts` version 2 (ADR-010 erratum A4 item 7, #1018): `exportEngineDataV2` / `readEngineDataV2` are the `EngineDataV2` contract (`packages/schema/contracts/v1/engine-data-2.schema.json`, beside v1 as `damage-aware-config-2` is; generated TS and pydantic types, corpus samples `engine-data-2/`): every list of v1 plus `conditions`, the ids of effect type Condition that the mod's condition table and the `condition` of its moves, abilities and items define (`conditionIds`, shared with `volatile-copy.ts`; statuses, weathers and terrains stay in their lists), sorted by id; 148 at this pin. The v1 table, `export-engine-data.ts` and the v1 golden file and hash are untouched; the v2 golden `engine-data-2.json` and `.summary.json` sit beside them (same MIT `NOTICE`; `engine-data.test.ts` re-exports and compares byte for byte, `scripts/export-engine-data-2.ts` rewrites them). Python: `GameData.from_table` and `Vocabulary.from_engine_data` take either version (`GameData.conditions` is an `IdVocab` for v2 and None for v1; nothing in the encoder reads it unless the encoder option `exact_volatiles` (#1019, see [reducer-encoder.md](reducer-encoder.md)) is set, so v1 tensors, `encoder_version` and checkpoint ids are unchanged). A table is chosen by file: the worker, learner and loop load the `--engine-data` file they are given and the checkpoint check compares its hash, so a v1 checkpoint keeps working with the v1 table and a v2 table needs checkpoints made for it. **Reducer:** with a v2 table `Vocabulary.volatile` checks every `-start`/`-end` volatile id (not `ability:` names, which were always looked up): it resolves as a condition id, a condition id plus the derived suffix (`stockpile1`), the name of a move, ability or item (`Fire Spin`, `Illusion`) or one of `PROTOCOL_VOLATILES` (`typechange`, `typeadd`, `fallen`: Supreme Overlord's `fallen1`..`fallen5`, which the engine prints and no condition defines); a v1 table keeps volatiles opaque as before. `-start|POKEMON|typechange|TYPE[/TYPE]` sets the new `PokemonState.types` (type ids of the vocabulary, plus the engine's typeless marker `???` of Burn Up; an empty list for the copy form `[from] move: Reflect Type`, which names no type; any other type is a `VocabularyError`), cleared on switching out and carried by an Illusion settle; `to_dict` has the `types` key only while it is set, so no committed reduced snapshot changed (none holds a typechange at its end). The shared TS interpreter does not port the field (the parity test strips `types`, as it strips `item_received`); `typeadd` stays a volatile id only. A `-end|…|typechange` (Mimicry), a `|detailschange|` (a permanent forme change, Mega Evolution) and a `|-formechange|` clear `types`, as the engine's `setSpecies` resets them. The `typechange` type is checked against the type vocabulary for v1 tables too (a reducer behaviour change; no encoder change, since the encoder does not read `types`). The worker support of this slice is only that `GameData` / `Vocabulary` accept either table: the worker loads the file it is given and the checkpoint's engine-data hash check is unchanged. A `kind:` prefix (`move: Taunt`) resolves only against that vocabulary or the conditions. `PROTOCOL_VOLATILES` (`typechange`, `typeadd`, `fallen`, `perish`: Perish Song's `perish3`..`perish0`) is held to the pinned source by `tests/ml/reducer/test_protocol_volatiles.py`, which scans `sim/`, `data/` and the mod for literal `-start`/`-end` volatile words: any literal that resolves nowhere, and any stale entry, fails it (skipped without the engine checkout, a failure under `CI`; the python job checks out the submodule source). Known limits: `typeadd` (Trick-or-Treat, Forest's Curse) adds a type and is kept as a volatile id only, no type is tracked; Roost's removal of Flying prints no line and Transform's type copy is not tracked in `types`. Tests: `tests/ml/reducer/test_engine_data_2.py` (every volatile of the random corpus resolves in v2, the refusals, `typechange`), `tests/ml/model/test_gamedata.py`, `engine-data.test.ts`, `samples.test.ts`.
- `team-vocabulary.ts` (ADR-013 §2, #859): `exportTeamVocabulary(engine, format, table?)` is what the team generator may draw from, read from the pinned engine and built on the `exportEngineData` table (it names that table by `engine_data_hash` and its ids resolve in it). It adds the roster the validator accepts, each roster species' abilities and move pool, the natures, the items the format does not ban, and the rule-table values (`adjustLevel`, `evLimit`, Item Clause, team sizes, from the resolved rule table; an unset one is refused, never defaulted). No game rule is written by hand: a species, ability, move, nature or item is in the vocabulary exactly when the pinned `TeamValidator` takes a probe set with it (one Stat Point and a neutral nature, so the "0 Stat Points" check stays quiet) or `checkItem` does not ban it. IVs, the per-stat draw maximum and item weights are `TeamGeneratorConfig` fields, not here. `teamVocabularyHash` (SHA-256 of the JCS bytes) is the `vocabulary_hash` the team manifests carry; `readTeamVocabulary` adds sorted-and-unique ids and, given the table, that every id resolves. The golden `team-vocabulary.json` and `.summary.json` sit beside the engine-data table (MIT-derived, same `NOTICE`); a test re-exports and compares byte for byte (about 10 s), `scripts/export-team-vocabulary.ts` rewrites them.
- `role-sets.ts` (ADR-020 §3, #971): `exportRoleSets(engine, format, vocabulary, table?, dir?)` reads the Champions doubles random-battle sets file of the pinned checkout (`data/random-battles/<mod>/doubles-sets.json`, MIT; the format must be doubles; `dir` defaults to the pinned checkout and exists so a test can doctor a copy) and returns the `RoleSetTable` contract (`packages/schema/contracts/v1/role-set-table.schema.json`, integers only, closed): the commit, `engine_data_hash` and `vocabulary_hash` it was resolved against, `source_path` and `source_sha256`, and per species id a sorted list of `{role, moves[], abilities[]}` (sets sorted by role, then moves, then abilities; moves and abilities sorted ids). Names map to ids by exact name through the engine-data table; the file's `level`, `preferredTypes` and `teraTypes` are dropped (the latter two shape-checked first). It fails closed (`RoleSetError`): a species not in the engine-data table or not in the vocabulary roster, a move or ability name that does not resolve, a move outside the species' roster move pool, an ability the roster does not list for it, a field of the file it does not know, an empty list. A Mega forme's sets name the abilities of the forme it comes from (the form Team Preview shows: venusaurmega lists Chlorophyll, its roster has Thick Fat), so for a roster entry with a required item the exporter accepts the abilities of the roster entries whose forme the stone changes into it (the item's `megaStone` map in the engine's data). `readRoleSetTable(value, vocabulary?)` adds sorted-and-unique ids and sets and, given the vocabulary, its hash, commit, format and engine-data hash and that every id is in the roster (it has no item data, so for a Mega forme it accepts any ability a non-Mega roster entry lists: a hand-edited table that is otherwise consistent passes it, and the exporter plus the byte-for-byte golden test are the exact check; a consumer plays such an entry as the base forme plus its stone, never as a literal Mega forme with those abilities). `roleSetTableHash` is SHA-256 of the JCS bytes. The golden `role-sets.json` and `.summary.json` (342 species, 495 sets at this pin) sit beside the team vocabulary under the engine's MIT notice; `test/role-sets.test.ts` re-exports and compares byte for byte, `scripts/export-role-sets.ts` rewrites them (after `export-team-vocabulary.ts`; it reads the golden vocabulary). No role logic is ported: nothing turns a role into an item or a spread. `check_data_class.py` refuses a role-set table (an object with `source_path`, `source_sha256` and `species`) that holds a `paste`, an `evs` key or a team-shaped object anywhere, `fixtures/` included. The mixture config field and drawing from the table are a later slice.

**Mechanics coverage inventory** (ADR-030 groundwork G5, #1465; `packages/showdown-bridge/src/mechanics-inventory*.ts`, `scripts/mechanics-inventory.ts`, `docs/mechanics-inventory.md`). Every move of the roster's pools, every roster ability, every vocabulary item and every condition (engine-data v2's conditions, statuses, weathers, terrains and the ids entities start), each with the engine handlers it carries, read from the pinned engine's data for the format's mod by REFLECTION (`mechanics-inventory.ts`): the handlers are the function-valued keys of the entity's data object (nested blocks dotted: `condition.onStart`, `secondaries.onHit`; `on*Priority/Order/SubOrder` siblings as `orders`), `data_flags` the other keys with a non-default value (a stat change as `boosts.atk=-1`), `starts` the conditions it starts (the string fields `volatileStatus`, `sideCondition`, `slotCondition`, `weather`, `terrain`, `pseudoWeather`, `status`, its own `condition` block, and the literals of `addVolatile`/`setStatus`/`setWeather`/`setTerrain`/`addSideCondition`/`addPseudoWeather`/`addSlotCondition` in the handlers' own source text, `Function.prototype.toString`), `body_refs` the ids the bodies test, and `sim_refs` the simulation files that test the entity's id (`hasAbility('x')`, `hasItem`, `hasMove`, `.ability/.item/.status/.id ===`, `volatiles['x']`, `isWeather`, a switch on an `.id` or `.name`), scanned from `sim/*.ts` and the `scripts.ts`/`conditions.ts` of the mod chain (`scanRefs`, `scanFiles`; the file list with SHA-256 is in the inventory), so an effect implemented outside a handler is listed per entity. The only knowledge in code is how to walk the object, the call names the scan reads and `DAMAGE_HANDLER_NAMES` (ADR-030's list of damage-relevant handler names, which only labels a handler). A condition's `defined_in` is `table` (the mod's condition table) or the kind of the entity whose `condition` block it is (then its handlers are that entity's, not counted twice) and `started_by` lists the roster entities that start it. Golden files (MIT-derived, under the engine-data `NOTICE`): `fixtures/showdown/<format>/mechanics-inventory.json` (one entity per line), `.summary.json` (hash and counts), `mechanics-inventory.weights.json` and the rendered `docs/mechanics-inventory.md` (`mechanics-inventory-doc.ts`; tests compare all four with a fresh export and render). **Weights** (`mechanics-inventory-weights.ts`; integers, ppm or counts): per damage-relevant entity the dataset teams holding it (the committed fixtures-v1 DEV split, read from the file list `teams-dev.jsonl`, `records.dev.jsonl`, `records.training.jsonl` only: validation is never opened, and `private-data/` is refused, `mechanics-inventory-teams.ts`), its Smogon usage slot share (the latest `config/teams/<format>/usage/*.json`; a move's share scaled by the moves a set holds; a condition's the capped sum of its starters) and, per `curve`, the build order and the share of teams fully covered when the top N entities are implemented (also by handler NAME, and an independence estimate under the usage table); pair counts (dataset pairs, and the number of pairs reaching 10^-4 under independence: ADR-028 section 5's input). **Run weights** (`mechanics-inventory-run.ts`): counts over a run's synthetic Episodes' own channels (`|move|` without `[from]`, `ability:`/`item:` names, `-start`/`-sidestart`/`-fieldstart`/`-weather`/`-status` ids), per entity uses, turns and Episodes, coverage curves over Episodes and turns and turn-level pair counts; printed, journaled, never committed; the reader refuses a non-synthetic Episode and a path under `private-data/`; it reads `generations/gNNNNNN/episodes` and `.../members/*/episodes`. **Findings at the pin (M-C):** the reflective count of damage-relevant handler definitions over every entry of the mod is 379 (ADR-030's grep: 382); the roster reaches 230 of them in 200 entities (moves 76, abilities 81, items 48, condition table 25); implementing the handler names alone needs 13 names for 90% of fixtures-v1 teams (16 of the 17 damage handler names are held by any dataset team; the 17th appears only on roster entities no dataset team holds); by entity the 90% mark is 149 entities on the (uniform generator) fixtures-v1 teams and 82 under the usage independence estimate. Limits: a literal is found only when written as a string in a scan pattern (an id in a variable is not), a start made through a helper is not seen, and a condition no roster entity starts keeps an empty `started_by`. Re-run after the Regulation M-D pin bump (#1103) and read the diff against this baseline. Tests: `test/mechanics-inventory.test.ts` (golden bytes, consistency with the vocabulary and engine-data v2, `koCandidates` (#1166) reproduced exactly as a filter and the move-class table (#1164) reproduced exactly for `status`, `side_condition`, `field_condition` and `protection` but only as a subset for `lowers_target_stat` and `raises_own_stat` (the inventory keeps a secondary's chance only as a key), a doctored dex copy that gets a new handler name and a new `hasAbility` literal, the scan patterns, reader refusals) and `test/mechanics-inventory-weights.test.ts` (curves, usage slots, committed weights and document freshness, the team reader, run counts).
