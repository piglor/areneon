# Mechanics probe

The ADR-016 mechanics probe (stats, speed order, damage, KO counts), its config and the calc differential.

Part of the architecture documentation split out of `CLAUDE.md` (index: [README](README.md)). Ticket references such as `#1179` point to Redmine (`redmine.piglor.com/projects/areneon`), where measured figures and verdicts are recorded.

**Mechanics probe** (ADR-016 slice 1, `packages/showdown-bridge/src/mechanics-*.ts`, `scripts/mechanics.ts`). Areneon computes no stat, Speed or damage value: the probe builds a scenario battle from declared sets on the pinned engine and reads the engine's own values. Contracts (`packages/schema/contracts/v1/mechanics-{query,result,config}.schema.json`, generated TS and pydantic types, corpus samples in `fixtures/contracts/v1/mechanics-*/`): a `MechanicsQuery` is `{data_class, format_id, query}` with a `kind`-tagged `query` (`stats`, `speed_order`, `damage`; sets are PokePaste in the engine's canonical form, state uses engine ids, boosts are absolute); a `MechanicsResult` is `computed`, `unsupported` (closed `reason`: `query_kind`, `scenario_rule_table`, `random_effect`; a position or null) or `refused` (closed code `invalid_set` and the set's position), integers only, no free text, with `query_hash` (SHA-256 of the query's JCS bytes), the version manifest, `mechanics_config_hash`, `adapter_format` (`MECHANICS_ADAPTER_FORMAT`, bumped when the probe changes how it reads a value) and `gap_ids`. A document that fails the query schema has no `query_hash`: `readMechanicsQuery` throws `MechanicsQueryError` and the CLI exits 2 with no result. `config/mechanics/<format>.json` (`MechanicsConfig`, read by `mechanics-config.ts`) is reviewed data outside `rules/`: it is not in the rules snapshot, so `RULES_SCHEMA_VERSION` stays 1 and neither `format_rules_hash` nor `rules_snapshot_hash` moves because of it; it lists the rules removed from the target to make the scenario format (`removed_rules`, today the five non-mechanics rules), the exact rule-table keys that removal takes away (`removed_rule_keys`, 12 at this pin), the query kinds in scope with the gap ledger rows each depends on, and `ko_blockers` (items and abilities, slice 5). Scope can only restrict: a kind the config lists that the probe cannot answer throws, never approximates. `mechanicsConfigHash` is SHA-256 of the config's JCS bytes. `mechanics-scenario.ts`: `checkScenario` refuses (`ScenarioError`, and an `unsupported` `scenario_rule_table` result from the probe) unless the scenario format's rule table equals the target's minus exactly the listed keys with no key of its own, the same mod, game type, battle options, shared rule sources and values, and the same level, EV-limit and move-count fields; `startScenario` starts a two-a-side battle at once with no Team Preview. `mechanics-probe.ts`: `probeMechanics(context, query)` takes only a `ParsedMechanicsQuery`, a brand only `readMechanicsQuery` makes, so a Battle, BattleRecord, OmniscientLog, hidden verdicts or PlayerChannel is a compile error (a type test shows it) and a run-time schema refusal. Order: each declared set must be the engine's canonical paste of one Pokemon and pass the target format's `TeamValidator.validateSet` (else `refused`, the validator's own words go to the diagnostics and the CLI's stderr, never into a result), then the scope, then the scenario check, then the probe. `stats` (the six stats of one set, `maxhp` and `storedStats` of a scenario battle) and `damage` (slice 3, below) are answered; **`speed_order`** (ADR-016 slice 2, `mechanics-speed.ts`): Areneon computes no Speed or priority. The probe starts a scenario battle (a side with one declared Pokémon also starts a copy, fainted at once through the engine's `faint`/`faintMessages` so it is no active Pokémon and ties nothing), replaces the engine's PRNG with one whose every method throws, applies the declared state through the engine's own methods and reads the keys with the engine's `queue.resolveAction` (which runs `getActionSpeed`, the priority events and the fractional priority) and `comparePriority`. State is absolute: weather and terrain are set or cleared (a switch-in weather the query does not declare is gone), Trick Room, the four side conditions, status (`setStatus`), HP (`sethp`), the five boost stages and an already evolved Mega (`runMegaEvo`) are written as declared (a Pokemon that is not declared already evolved first tries to take its status BEFORE the field, #1198: it is an observed fact, and Misty Terrain and Electric Terrain refuse a status once up, so a status seen before the terrain started used to refuse the whole query. Only success counts: a refusal there, for instance by a switch-in terrain the query clears, changes nothing and the old place decides, a random draw is raised at the old place, so every query answered before has the same bytes and `adapter_format` stays 1: only refused queries became answers. A Pokemon declared already evolved keeps the old order, Evolution then status, because its new ability may change the field, so Misty Terrain still refuses its status: a known limit), and a state the engine refuses (not a weather, a status the Pokémon cannot take, HP above the maximum) is a `MechanicsProbeError` (no result), as is a move the engine lacks, a Mega Evolution that is not possible (a switch, no stone) and a move that adds actions of its own (Focus Punch's before-turn action). Each action is resolved with a fixed foe target so the move's own target draw cannot end the probe (`getRandomTarget` answers its first candidate: the target never enters the order keys; the contract's action has none). A Mega Evolution is its own action (order 104, speed before the Evolution): Mega groups come first in speed order, `runMegaEvo` runs on the scenario battle in that order, `getActionSpeed` is read again for every action, and the move groups follow, so a Mega's new Speed counts that turn. Groups come in the engine's order values: switches (103), then the Evolutions (104), then the moves (200). Tie groups are the runs of actions `comparePriority` calls equal (indices ascending in a group, an Evolution's index appearing again for its move), never sampled; `order`, `priority` and `speed` are the action's own keys after the Evolutions (a switch is order 103, priority 0; Trick Room makes `speed` negative, the champions mod has no wrap, so Speed 1809 and up acts last: the contract's `speed` minimum is -99999, a bound loosened within v1). Any draw (Quick Claw, a declared sleep) is `unsupported` with reason `random_effect` and the position of the action (or of the Pokémon, while the state is declared); a fractional priority (an item or ability with a fractional bonus; none is legal in the format at this pin) cannot be an integer and is a `MechanicsProbeError`. A random-draw `position` is a Pokémon's index while the state is declared and an action's index afterwards. The side-condition, Trick Room and stage names are the query schema's fixed names mapped to engine ids; a test requires each id in the pinned data. `order_basis` is `turn_start`: a speed change during the turn (Icy Wind, a paralysing hit) is not modelled. Every result lists the config's gap ids (`paralysis`, `trick-room`) and `mega-evolution` when an action or a combatant Mega Evolves (`MEGA_GAP_ID`, a probe constant that `checkMechanicsConfig` requires in the ledger whenever the kind is in scope); the config schema has no list of state inputs, so Tailwind, Trick Room, paralysis and Choice Scarf are carried by the probe code and these gap ids. `readMechanicsQuery` adds the reader rules the profile cannot say for a speed order (each action names a declared Pokémon, once, and no Evolution of one that already evolved). `MechanicsProbeError` lives in `mechanics-error.ts` and is re-exported from the probe. Tests: `mechanics-speed.test.ts` holds the hand-worked fixtures `fixtures/mechanics/<format>/speed/cases.json` (synthetic sets; the expected speeds, priorities and groups were worked on paper from the stat formula, see the README beside it: priority brackets, an exact tie, Tailwind, Trick Room with Speed 1872, paralysis, Choice Scarf, stages, declared and cleared weather, Mega faster and moving first, two Megas, Quick Claw `unsupported`) and the refusals; `mechanics-speed-battle.test.ts` is the required cross-check: for every untied fixture case and for the committed dev dataset's team pairs (with the state the real battle starts in, read from it) the order of the probe equals the order of the `|move|`/`|cant|` lines of a real turn of the engine, skipping a pair whose real turn changes a Speed or field condition between its first and last action. The required `mechanics-stats.test.ts` holds the probe's stats equal to the target format's own Team Preview request stats for every committed fixture team (the `champions-stats.test.ts` seam) and to the five displayed reference cases. CLI: `node packages/showdown-bridge/scripts/mechanics.ts QUERY.json [--config FILE]` prints the result as one JCS line (exit 0 for any result, 2 for no result); `scripts/check-mechanics-config.ts` (in `make ts` and CI) checks the config against the pinned engine and the gap ledger. The `computed-damage-ko-counts` sample is a shape sample, not a probe output; the `speed_order` result sample is a probe output, and the `unsupported` sample comes from a config that lists `stats` alone.  The `damage-formula` gap record names the pin's own Champions `modifyDamage` override as evidence (still `unverified`; the rules snapshot hash moved, the channel did not).

**Damage probe** (slice 3, `mechanics-damage.ts`, `mechanics-random.ts`). The engine's own `getDamage` deals every number. The scenario battle always holds two Pokemon a side: the declared one in slot 0 and a partner of the same species with no ability and no item (so both foes are present and the engine sets `spreadHit` itself, a screen sees more than one active Pokemon, and no ally ability changes the declared Pokemon's damage). Declared state is applied after the start, absolute: Mega (`runMegaEvo`), HP, status, boosts, side conditions, Trick Room, and the field is cleared first so a weather or terrain a switch-in set never survives unless declared. The move runs through the engine's own `useMoveInner` on a clone (target resolution, `ModifyMove`, the immunity and `TryHit` steps) with two instance replacements: the accuracy step passes and the damage loop calls `getDamage` for the defender only and reads the value, so nothing is dealt. 33 clones per query (the reference path, see the one-clone path below): the 16 rolls with `willCrit` set false, the 16 with it true, and one with the move's own crit rule to observe the chance. The recording random source (`recordingRandom`) answers `random(16)` with the roll index and `randomChance` with a fixed outcome, and records every call; `acceptedDraws` accepts a run only when its draws are one `random(16)` (preceded in the observation run by at most one `randomChance`) or none (an immunity, a fixed-damage move), and any other draw (a random base power such as Magnitude, an ability or item with a random effect, any other PRNG member) makes the result `unsupported` (`random_effect`, position null); no ability or item of this pin draws on the damage path, so the refusal is shown with random-base-power moves and the source's own tests. The crit chance is read from the observation run: the engine's one `randomChance(n, d)` pair as passed (`chance`), a crit it makes with no draw (`always`), or none or a cancelled crit (`never`); the probe holds no crit table. A move the engine's immunity or protection steps stop (the run notes it from the engine's own `hitStepInvulnerabilityEvent`, `hitStepTryHitEvent`, `hitStepTypeImmunity` and `hitStepTryImmunity` results) deals nothing: sixteen zeros; a move that never reaches the damage step otherwise (a charge turn, a failed precondition such as Sucker Punch, a self-targeting move) is `unsupported` (`query_kind`); fixed and HP-based damage (`damage`, `damageCallback`, `ohko` in the move data) and a move the engine makes multi-hit after `ModifyMove` (Parental Bond) are `unsupported` (`query_kind`). A spread move always meets two foes (a lone foe cannot be declared). Known gap: Beat Up is not marked multi-hit in the pinned data, so it is answered as one hit. Outside the v1 scope the result is `unsupported` (`query_kind`, position null): a status move and a multi-hit move. A query the engine cannot take (an unknown move, status, weather or terrain id, HP above the maximum, Mega Evolution of a Pokemon that cannot) throws `MechanicsProbeError` (the CLI exits 2, no result). The KO field is slice 5 (`mechanics-ko.ts`, below). Results list the gap ids `damage-formula`, `level`, `mega-evolution` and `stat-points` (the `damage` entry of the config). Required tests: `mechanics-damage.test.ts` holds the probe equal to `fixtures/mechanics/<format>/damage/cases.json` (twelve hand-worked cases, Python integer arithmetic outside the probe from the `modifyDamage` steps: single target, spread, Reflect, Light Screen with spread, rain and sun, a Mega Evolution, burn, an always-crit move, a crit-immune defender, a high-crit-ratio move and absolute boosts with declared HP; base powers and stats are inputs from the pinned data, which patches Slash to 80) and holds the damage equal to the HP lost in seeded real battles on the same declared state (the real turn is played with `choose`; a spy on the PRNG reads the roll the attacker's move drew, the log the crit; 40 non-missing turns per case, at least one crit).

**One-clone damage path** (ADR-022 section 4 mitigation 4, ADR-016, #1179; `mechanics-damage.ts` `probeDamage(..., path)`, `MechanicsContext.damage_path`). The 33 clones above are the reference (`"per-roll"`); the default is `"one-clone"`, which gives the same bytes (so `adapter_format` stays 1 and no feature set id moves). The engine still computes every number. The engine's move step (`useMoveInner`) runs once on the declared scenario battle itself; where the reference stops at the damage loop, the loop calls the engine's own `getDamage` 33 times in turn on that battle: once with the move's own crit rule (the observation, random source answering `randomChance` true), then the 16 rolls with the crit forced off and the 16 with it forced on (the recorder's new `answer(roll, chance)` sets what the next calls answer). Before each call the active move's hit data is reset to what a fresh clone holds; each call's draws are the move step's draws before the loop, the call's own and those after it, which is what its clone drew (equal because `acceptedDraws` is strict: it refuses any draw but one `random(16)` and the observation's one `randomChance`), and `acceptedDraws` judges that list as before. A call is a clone only if it leaves the battle as it found it, so the battle (`toJSON` with the engine's own random source put back, the field effects' lazily set `target` left out) and the active move (minus its hit data) are serialised before the first call and after the last: any difference (an eaten resist berry; a stacking volatile would be another) returns to the reference path on a rebuilt scenario battle (`damagePathStats.fell_back`, 0 in 9,462 bench queries). A move the engine's immunity or protection steps stop before the damage loop deals nothing: one extra reference-style clone shows the draws and the 32 values are 0. Multi-hit after `ModifyMove`, a charge turn and a failed precondition are decided from the observation call alone, as before. `probeMechanics` also keeps what depends on the engine, config, snapshot and format alone (version manifest, config hash, scenario format id) and the validated sets by paste in per-engine tables (bounded, a failure is never kept; a set is copied per query). Equality is tested, not assumed: `test/mechanics-damage-paths.test.ts` runs both paths on every committed damage fixture case (the calc differential's damage set), the KO cases, every `ko_blockers` item and ability as the defender, a Haban Berry defender (the fallback), an immunity, unanswerable moves (Magnitude, Present, a charge turn, status, fixed damage, multi-hit, an unknown move), queries over the committed dataset team pairs (every damaging move, `ARENEON_PATHS_TEAMS` widens the sweep, 240 teams was run once) and the feature builder's requests over three seeded corpus battles, and requires equal result bytes (and equal refusal words). Bench figures (an identical `rows_digest` before and after, per-decision cost and the generation estimate against the gate): see #1179. **Kept scenario start** (#1179, second step): `declaredBattle` takes the started scenario (before any declared state) from a bounded per-engine table keyed by (scenario format id, attacker set, defender set) that holds its `toJSON` string, and every caller, the first included, builds its battle with `Battle.fromJSON` of it, so no result depends on the table's contents; the `"per-roll"` reference still starts the scenario itself every time, so the equality test also compares the kept start with a fresh one (`scenarioStartStats`). The trigger items are met only with a play-time sidecar and at least five game processes, or on a quieter machine (verdicts and figures on #1179). The remaining cost is the 33 `getDamage` calls and the two serialisations. See the ticket for the trigger verdicts.

**Probe caches: kept starts for every probe path and the resolved scenario format** (#1453; `mechanics-scenario.ts` `keptScenario`, `restoreScenario`, `probeCaches`, `scenarioCacheStats`). The kept scenario start of the damage probe is now shared by the `speed_order` and `move_outcome` probes (the outcome, threat, speed and priority rows of `probe-outcome/1`): `keptScenario(engine, scenarioId, teams)` keeps the `toJSON` string of the started scenario in a bounded per-engine table (256, emptied when full) keyed by (scenario format, the two teams' sets), and EVERY caller, the first included, gets its battle from `Battle.fromJSON` of that string, so no result depends on the table's contents. A scenario format with custom rules (the `@@@!rule` id) is a new `Format` object at every `formats.get(id, true)`, so the engine rebuilt its rule table (`getRuleTable`) for every `new Battle` and every `Battle.fromJSON`; `startScenario` and `restoreScenario` now run with the engine's trusted format lookup answered from a bounded per-engine table (16 formats) for the duration of the call (a scoped patch of `Dex.formats.get`, restored in a `finally`), so the rule table the engine caches on the format object is built once. No rule is read or written by the cache; the format is the engine's own object. `probeCaches.enabled = false` is the test seam: every probe then starts its scenario itself with no kept format (the reference), and a stand-in `Battle` class (a test that replaces the engine's `Battle`) needs it, because `fromJSON` rebuilds with the real class. Equality is tested, not assumed: `test/probe-caches.test.ts` builds the `probe-outcome/1` arrays (rows, threats, speeds, priorities, outcomes) over seeded corpus battles with the caches off, cold and warm and requires equal bytes (and that the second pass reused kept starts), a kept scenario equal to a fresh start (as canonical JSON), the bounded table, and the format lookup restored after every call; `mechanics-damage-paths`, `mechanics-speed`, `mechanics-outcome`, `candidate-features*`, `feature-recompute` and `feature-sidecar` pass unchanged (`mechanics-scenario.ts` joined the reviewed `fromJSON` files of the isolation scan). Figures on #1453 (`feature-bench.ts --feature-set probe-outcome/1`, run `public-l1-lineage-001` generation 60, 60 evenly spaced Episodes, 442 move decisions, one thread, i7-14700KF 28 logical CPUs shared with a running training at load 7 to 10, so noisy; before and after alternated in the same window): `rows_digest` `ac2737e4...` before and after (and `af225741...` before and after on 20 Episodes, 136 decisions); per decision mean 93.1 and 78.1 ms before, 75.5 and 70.6 ms after, p99 365.1 and 338.6 ms before, 238.2 and 266.3 ms after (about 10 to 20 percent of the builder). The profile after the change: `getRuleTable` 0.27 s of 14 s (it was the rule-table rebuild at every start); what remains is the deserialisation of the kept start (`deserializeBattle` 2.7 s of 14 s), the move step and `getDamage` (the damage rows) and the event-handler search; avoiding `fromJSON` altogether would need an engine-side fork and is not done.

**Declared Mega Evolution and the rest of the declared state** (#1243). `runMegaEvo` on a declared already-evolved Pokemon starts the new forme's ability, which can change what the query declared: Intimidate (Mega Manectric) lowers the other combatant's Attack stage (and can consume its White Herb, Adrenaline Orb or Eject Pack), Drought, Sand Stream, Snow Warning or Electric Surge replace the declared weather or terrain. Both probes now make the declared state absolute after the Evolutions. `declaredBattle` (damage) clears and sets the field after both declares and then `restoreStagesAndItem` writes each combatant's declared stages again and puts its set's item back if it changed. `speed_order`'s `declare` keeps its first pass (the #1198 status-first rule, the field, the Evolutions, statuses) and, when any combatant is declared evolved, runs `declareField` again (it removes Trick Room and the four side conditions and clears weather and terrain before setting the declared ones), then restores each item and writes every combatant's stages after all Evolutions. A query with no evolved combatant keeps its bytes. Answers change for damage queries with such a Mega and for speed queries where an evolved Mega's ability replaced the declared field, so `MECHANICS_ADAPTER_FORMAT` is 2: every `damageAwareIdentity`, `feature_set_hash`, the mechanics-result corpus samples and `hashes.json` moved. The search identity gained `mechanics_adapter_format` as a thirteenth input (`searchIdentity`, `search_identity_hash`), so a search policy id moves when probe answers change (vector computed with Python's hashlib and pinned on both sides; no run had used a search policy id). **Consequence:** a pair trained with `candidate_features` under an older `feature_set_hash` (a run in progress on an older commit) cannot be evaluated, warm-started or resumed by code after this merge, because its config names a hash this checkout does not compute (`featureSetup` refuses it); its checkpoints keep their ids. The item and stages are written last, after the declared field (a Seed item under a declared terrain would otherwise fire again), and the item is put back silently (assigned with a fresh effect state, not `setItem`, whose Start event would refire a Seed). Limits: a Protosynthesis or Quark Drive volatile started by a Booster Energy (or the Mega's weather/terrain) is lost when the declared field replaces what a Mega's ability set; Trace (a roster Mega ability copying the other side's ability on start) is not restored, since the declaration has no ability field; an Eject Pack switch cannot be undone; `damage-check.ts` `ownFighter` states an own evolved Mega since #1247 (the damage check of [opponent-model.md](opponent-model.md), `DAMAGE_CHECK_FORMAT` 2): its shown forme must equal what the request item's `megaStone` data makes of the set's species, it is declared as the set holding the stone, evolved, with the set's own pre-Evolution ability (the Evolution replaces it); on the turn it evolves the request in force still shows the base forme, which is accepted too (the stone decides); every other decline (no request, no or two team matches, a shown forme the stone does not make, a set that already is the Mega forme, Palafin Hero) gives `null` and is counted in `own_unstated`. Limits: the set's pre-Evolution ability is declared (a Trace-like ability is not restored, see above) and the probe's Evolution runs the Mega's ability start effects. **Identity:** `beliefIdentityHash` takes the optional `damage_check_format` (the bridge's `DAMAGE_CHECK_FORMAT`, now 2) and puts it in the preimage ONLY when given; the two composition roots (`damage-aware-worlds.ts`, `search-worlds.ts`) give it only when the belief config has `damage_evidence`, so every existing identity and pinned vector is unchanged (no committed config enables it yet) and a belief that reads damage evidence changes identity with the check (vector with Python in `identity.test.ts`; Python has no belief identity twin). The sweep asserts hits on an own Mega now constrain and rule no true set out. Tests: `mechanics-damage.test.ts` (Intimidate stage, White Herb), `mechanics-speed.test.ts` (Drought against declared rain with a Swift Swim foe; stages and White Herb read at every action-speed call), `search-config.test.ts`, `tests/ml/loop/test_search_identity.py`.

**KO counts and the parity report** (ADR-016 slice 5, #936; `mechanics-ko.ts`, `mechanics-parity.ts`, `scripts/mechanics-parity.ts`, `docs/mechanics-parity.md`). The `ko` field of a `damage` answer holds integers computed from the engine's two roll vectors as `getDamage` returns them, before the HP clamp and before damage-time effects: `ohko_no_crit` and `ohko_crit` are the rolls (of 16) at or above the defender's current HP, `thko_no_crit` the ordered pairs (of 256) of two independent rolls of the NO-CRIT vector, the same vector for both hits, whose sum reaches it (the crit vector is never used for the two-hit count); never a probability. The defender is read as the scenario battle holds it after the declared state (a Mega Evolution changes its ability); if its item or ability id is on the mechanics config's `ko_blockers` the field is `{kind: "unsupported", reason: "ko_state_change"}` and the vectors, HP and crit chance are still returned. `config/mechanics/<format>.json` `ko_blockers` listed 22 items (Focus Sash, Focus Band, Sitrus and Oran Berry, the 18 type-damage-halving berries) and 5 abilities (Sturdy, Disguise, Multiscale, plus Stamina and Weak Armor, which change the defender's Defense after the first hit); the roster drift check below added 3 items and 8 abilities; every id is checked against the pinned engine by `checkMechanicsConfig` (the list is conservative: an attacker's Mold Breaker is not modelled, so a defender holding a blocker is blocked). The list moved `mechanics_config_hash`, so the config-hash fields of the mechanics corpus samples and `hashes.json` were regenerated and every `damageAwareIdentity` (it names the mechanics config hash) is new; `adapter_format` stays 1 (no value is read differently) and the result contract did not change (`KoCounts` was already in v1). The damage-aware actor still counts its KO share from the rolls itself (`damage-aware-score.ts`) and could read the probe's counts later; it is unchanged. Fixtures: `fixtures/mechanics/<format>/ko/cases.json` (vector cases with the boundary where the lowest roll equals HP, an explicit 256-sum enumeration table, and probe cases that declare the defender's HP on the hand-worked `single-target` damage case, counted with Python outside the probe) and the `ko` entries of `damage/cases.json`; `test/mechanics-ko.test.ts` holds them, the blocker cases (an item, an ability, an empty list, an unknown id) and the immunity case. The parity report is generated like `docs/showdown-champions-gaps.md`: `node packages/showdown-bridge/scripts/mechanics-parity.ts` renders it from the speed, damage and KO fixture files (case ids, descriptions, SHA-256 of each file), the divergence list `fixtures/mechanics/<format>/calc-divergences.json` and the gap rows the config's results depend on (every row with its status, unverified ones counted), and `test/mechanics-parity.test.ts` compares the committed file with a fresh render (edit the fixtures, config or gap records, never the doc). Without the divergence file the report says "differential not built yet (#935)"; the @smogon/calc differential (#935) adds that file (`{data_class: "synthetic", divergences: [{case, reason}]}`, any other shape is refused) and regenerates the report. The report states that the game comparison waits for the owner's in-game captures (#937, Wave 9) and that no gap row is verified by this work.

**KO blocker drift check** (#1166; `mechanics-ko-candidates.ts`, `scripts/check-mechanics-config.ts`, `test/mechanics-ko-candidates.test.ts`). The `ko_blockers` list is tied to the roster through the engine's own data. `koCandidates(engine, formatId, vocabulary)` returns every roster-legal item (the team vocabulary's item list) and ability (every ability some roster species may hold) whose data in the format's mod defines an event handler from `KO_HOOKS`, the only knowledge in code: the handler NAMES `onDamage`, `onDamagingHit`, `onSourceModifyDamage`, `onAnyModifyDamage`, `onAnyDamage`, `onTryHit`, `onEffectiveness`, `onEat`, `onTryEatItem`, `onEmergencyExit` and `onAfterMoveSecondary` (a test requires each to be found on some roster entry, so a mistyped name fails). `checkKoBlockers(engine, config, vocabulary)` (run by `check-mechanics-config.ts`, in `make ts` and CI, against the committed golden vocabulary, which must be for the pin) fails when a candidate is in neither `ko_blockers` nor the new `ko_non_blockers`, when an id is in both, and when a `ko_non_blockers` entry is not a candidate (a stale entry). `ko_non_blockers` is optional in the `MechanicsConfig` contract (`{abilities: [{id, reason}], items: [{id, reason}]}`, sorted by id and unique, a one-sentence reason each, a minor change within v1; a config without it keeps its bytes and then fails the check for every unreviewed candidate); it never changes what the probe answers, only `ko_blockers` does. A handler's presence is a prompt to review, not a verdict: at this pin 92 candidates were found (35 items and 57 abilities, incl. the 27 existing blockers) and classified by one rule, recorded in the reasons. A BLOCKER changes what a repeated hit faces: the defender's HP, stats, item or ability, its presence, the weather or terrain, or the attacker's burn, item or ability (added: Air Balloon, Eject Button, Red Card, Emergency Exit, Flame Body, Mummy, Pickpocket, Sand Spit, Seed Sower, Spicy Spray, Wandering Spirit). A NON-BLOCKER is an immunity or absorb step the probe's own hit steps already apply (sixteen zeros), a constant damage multiplier already in the roll vector (Filter, Solid Rock, Fluffy, Punk Rock, Aura Guard), indirect-damage handling, a boost to a stat that does not enter the damage it takes, an effect on the attacker alone, a status-cure berry, or an effect that fires only on the knockout. Limit: an effect the engine implements in its simulation code instead of a handler has no hook to find (Tera Shell's effectiveness is in `sim/pokemon.ts`); Tera Shell, Ice Face, Shadow Shield and Wonder Guard are not roster-legal at this pin, and the test shows Ice Face and Shadow Shield flagged when a doctored vocabulary adds them. Adding the lists moved `mechanics_config_hash`: the config-hash fields of the mechanics corpus samples and `hashes.json`, the pinned identity in `damage-aware-worlds.test.ts` (computed with the test's dummy reader hash) and `docs/mechanics-parity.md` were regenerated, and every `damageAwareIdentity` from now on is new (records written earlier keep the identity they name). The new blockers change behaviour: a defender holding one now gets `unsupported` KO counts (`ko_state_change`), where it got counts before. The corpus gained the samples `mechanics-config/regmc-no-non-blockers` (the field absent), `non-blocker-without-reason` and `unsorted-ko-non-blockers`. The `ko` expectations of `damage/cases.json` are held independent of the module under test: `mechanics-ko.test.ts` recounts them with plain loops of its own (it used `countKos`/`countPairKos`) and `tests/scripts/test_mechanics_ko_fixture.py` recounts them in Python.

**Calc differential** (ADR-016 slice 4, `packages/showdown-bridge/test/mechanics-differential.test.ts`, `fixtures/mechanics/<format>/calc-divergences.json`, #935). `@smogon/calc` (MIT) is an exact-pinned `devDependency` of `@areneon/showdown-bridge` (0.12.0, no range) and is on `.github/dependabot.yml`'s `ignore` list, so a bump is a deliberate PR that re-triages the list. It is an oracle only: never a runtime path, a fallback or a tie-breaker, imported by that test alone, and no set data from the calc's front end is used. Calc generation 0 is Champions (the calc's data tables list `CHAMPIONS` first and `Stats.calcStat` has a generation 0 branch: base + Stat Points + 20, HP base + Stat Points + 75). The test runs every damage fixture case (no-crit and crit rolls, both in a Doubles field so the spread and screen modifiers apply; the declared weather, terrain, screens, boosts, status and HP; a Mega attacker by the calc's own Mega forme) and the six stats of every set of the damage cases, the five reference cases, the golden and legal teams and the committed dataset teams through the probe and the calc. A species the calc names differently is mapped by the engine's data (the engine's base forme spelled out, a cosmetic forme to its base species), and a species it lacks stays a divergence. `calc-divergences.json` (`data_class` synthetic, also the input of the mechanics parity report's calc section, `docs/mechanics-parity.md`, regenerated with `node packages/showdown-bridge/scripts/mechanics-parity.ts` after a list change; a test compares the committed report with a fresh render; the report treats a case id as a free string) lists every difference as `{case, reason, probe, calc}` with both exact values; an unlisted difference fails, an entry that no longer differs or differs otherwise fails, and the entries are sorted and unique. Triage follows ADR-016 section 4: the hand-worked fixture or the in-game value decides, never the calc. At this pin it holds one entry, `damage:always-crit:no_crit` (the fixture's no-crit vector for Frost Breath is the probe's forced non-crit run; the calc ignores `isCrit: false` for an always-crit move); every other roll and stat agrees. `ARENEON_PRINT_DIVERGENCES=1` prints the found differences as JSON when the list is being rewritten.
