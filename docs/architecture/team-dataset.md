# Team dataset and generator

The synthetic team generator, mixtures, pilot gates, Parquet shards and the DuckDB working database.

Part of the architecture documentation split out of `CLAUDE.md` (index: [README](README.md)). Ticket references such as `#1179` point to Redmine (`redmine.piglor.com/projects/areneon`), where measured figures and verdicts are recorded.

- `team-records.ts` (ADR-013 §4, #859): the identities and readers of the team records (`packages/schema/contracts/v1/team-{vocabulary,record,label-set,generator-config,dataset-manifest,snapshot-manifest}.schema.json`; all integers-only, no `number`). `canonicalTeamHash(sets)` is SHA-256 of the JCS bytes of the sets sorted by species id (ties by each set's JCS bytes): the same for every permutation, equal to the positional `teamHash` only for the canonical order. `recordHash`, `shardLogicalHash`, `logicalSnapshotHash` (writer-independent) and `snapshotHash` (one physical publication) follow ADR-013 §4. `readTeamRecord(engine, value, labelSet?)` adds the engine round trip (the paste must be the engine's own export of its sets), both team hashes recomputed and the labels' order; `readTeamLabelSet`, `readTeamGeneratorConfig`, `readTeamDatasetManifest` and `readTeamSnapshotManifest` add what the profile cannot say (sorted and unique lists, sums, tiling cell ranges, the recomputed logical hash). A `data_class` of `synthetic` is a constant of every record and manifest. `readTeamDatasetManifest(value, { config, labelSet })` also ties `d_max`, `pilot_draws` and `config_hash` to the config and `label_set_hash` and every cell number to the label set, and checks `merged_cells` (the D20 merge: only merged strata are listed; a stratum is numbered by its lowest member base cell; absence means nothing was merged). `readTeamLabelSet` refuses a default that is also a listed value. The generator is `packages/team-dataset` (below); the Parquet shard reader is a later slice (ADR-013 d1).

**Mixture generator-matched prior and the per-prior prediction quality** (ADR-025 §10, §12 slice 3b, #1134; `packages/showdown-bridge/src/mixture-prior.ts`, `scripts/export-generator-prior.ts`, `packages/team-dataset/src/prediction-quality.ts` `qualityContextFor`, `scripts/prior-quality.ts`). `deriveMixturePrior({vocabulary, config, generator_commit, shows_as, holder_abilities, role_sets?, usage?})` builds the `generator-matched` `UsagePrior` of a `TeamGeneratorConfig` whose `proposal` is a mixture of `uniform`, `role_sets` and `usage` components; `deriveGeneratorPrior` (the uniform proposal) is untouched, so `generator-matched.uniform-v1.json`, `prior_hash` and every identity keep their bytes, and a mixture is a SEPARATE record (`config/opponent-model/<format>/generator-matched.mixture-r-v1.json`, `mixture-u-v1.json`; `source.generator_config_hash` covers the proposal and so the component table hashes; `script_version` `generator-prior-mixture.v1`; `generator_commit` the last commit that changed the proposal code, `26a12563...`). **Reading of the mixture:** a team's component is drawn first, so given a roster entry its set lists are the shares-weighted mix of the components' lists, each weighted by `share * inclusion(entry)` (the posterior of the component given the entry is on the team); the entry's weight within its preview species is that sum (a Mega forme's share follows the components that can draw it); a Mega forme's `holder_abilities` are the validator's rewrite and the same for every component. Components: `uniform` as `deriveGeneratorPrior` (inclusion team_size / N); `role_sets` inclusion team_size / E over the table's entries, a role uniform within the entry, moves `min(slots, pool)` of the role's pool (k / n per role, averaged over the entry's roles; a move outside every role of the entry has no mass), abilities uniform over a role's list (a Mega forme keeps the roster's post-Evolution list); `usage` abilities, items and spreads are the table's lists under `set_root` with each draw uniform with probability `floor`, the moves' INCLUSION is exact (a dynamic programme over the listed moves taken so far, `successiveInclusion`, held to the real `UsageSampler` within 5.5 binomial sigma and to a direct enumeration), and the species INCLUSION is ESTIMATED by simulating the component's species draw (200,000 teams on a fixed-seed Mulberry32, Rao-Blackwellized: each pick adds the probability that each open entry is the next one; the teammate correlation is in it; relative standard error at most sqrt(1/(p * 200,000)): 7% at an inclusion of 0.001, 22% at 0.0001; also stated in `generator-matched.mixture-u-v1.NOTICE.txt`; the simulation runs only for a config with a usage component and a usage component with `floor_permille` 0 is refused, `MixturePriorError`, because an entry the table lacks would otherwise have no inclusion). Lists are fixed to the denominator 1,000,000 by the largest-remainder rule (ties by id); the lists are computed in IEEE doubles (fixed summation order, only + - * / and `Math.round`: platform-identical), which is the builder's choice and not the opponent model's no-float rule. Not modelled, as in the uniform prior: the Item Clause (the belief's DP), the validator's rejections and the stratum quotas. A config without a `proposal`, a missing or foreign table (hash checked), a table without its component, a component kind the builder does not know, a component twice and shares not summing to 1000 are `MixturePriorError`s. `export-generator-prior.ts` dispatches on the config (`--role-sets`, `--usage-table` default the golden table and the committed table the config's hash names). Measured against the proposal itself (`team-dataset/test/mixture-prior.test.ts`, 30,000 teams each of `mixture-u-v1` and `mixture-r-v1`, a Mega entry the role component plays as its preview species holding the stone counted as the stone holder): the absolute inclusion of every roster entry (forme weight over 10^6) and, for entries with at least 400 sets, the forme share, ability, item, move-inclusion and spread marginals are each within 5.5 binomial sigma plus 0.012 absolute of the record (the slack covers the Item Clause the proposal applies and the species-inclusion estimate); both records are rebuilt byte for byte by that test. **Later-month usage table and evaluation-only configs:** `config/teams/<format>/usage/2026-10-1630.json` (`usage_table_hash` `95d814d0...`, 287 species, 1,649,648 battles, every list kind mapped at least 999,977 ppm; input record `smogon-chaos.2026-10-1630.inputs.json`, fetched with `scripts/fetch_usage_stats.py` after the 2026-10 files were published, raw files in the gitignored `.tmp`; its own `.NOTICE.txt`) and `config/teams/<format>/generator.usage-eval-2026-10.json` (a pure `usage` component, set_root 3, floor 100) are the usage-shaped evaluation set of a month later than the 2026-09 prior (ADR-009 T5, erratum 2). **Prediction quality per prior** (`prior-quality.ts --label --prior FILE --dataset DIR [--generator FILE] [--games N]`; `qualityContextFor(engine, vocabulary, {prior, generator})` is `qualityContext` for any prior, the port built from the model's sampler and the pinned engine's set legality without `createBeliefWorlds`' committed-generator check; `oracleGames(..., validationDataset)` plays the VALIDATION split of a generated dataset): evaluation-only, counts and integer ppm, descriptive, never a gate. The generated datasets are not committed (`generate --dev 20 --validation 100 --training 20`, public keys `a1..` and `b2..`, `--evaluation-only --d-team 2 --reference fixtures-v1/teams-dev.jsonl` for the usage-shaped and role-set-shaped sets); the table of the six runs (hashes, scores) is on the ticket.

**Team generator** (`packages/team-dataset`, ADR-013 §2, §3, #816; imports the engine only through the bridge). `config/teams/<format>/labels.json` (a `TeamLabelSet`) and `generator.json` (a `TeamGeneratorConfig`) are data; `check-team-labels.ts` (in `make ts` and CI) reads them against the pinned engine (every id exists, sorted and unique, no default equal to a listed value, every leaf can hold in the vocabulary, at most 65,536 cells). `labeller.ts` is a pure interpreter of the label-set record (`all_of` of leaves, first match else default) and holds no id (a test greps its source for the committed ids); a base cell is the label values read as a mixed-radix number, first label most significant (64 cells for the five committed labels). `stream.ts`: draw k of a plan has seed `"sodium," + hex32(HMAC-SHA256(generation_key, JCS({config_hash, k, plan_id, purpose: "draw"})))`; the pilot's preimage is `{config_hash, k, purpose: "pilot"}` (no plan id: one recorded pilot serves every plan of a config). `proposal.ts` draws a team uniformly from the bridge's vocabulary (roster, move pools, abilities, natures; level, team size, Stat Point total and Item Clause from the rule table; IVs, the per-stat maximum, gender, nicknames and integer item weights from the config); `draw.ts` puts it in canonical order, round-trips it through `importPaste`/`exportPaste`, asks `validateTeam` (on a copy: the validator normalises sets in place) and labels it. `plan.ts` makes the quota plan from the pilot counts: proportional quotas with a floor of `n_stratum_min` per split, and the D20 merge before any generation (a group is affordable when it has `pilot_min_hits` hits and `quota * pilot_draws <= d_max * hits`; an unaffordable group is replaced by the group one level up, dropping the last label first, which absorbs every cell under it; a plan that is infeasible even with all cells merged is refused). `binner.ts` bins accepted draws in counter order (full bin: overflow; known hash: duplicate; else binned), so a bin is an exact sample of the proposal conditioned on its stratum; `dedupe.ts` is the two-stage known-hash index (a sorted 64-bit prefix array, 8 bytes per hash, then an exact comparison in memory or in a sorted file); `rejection-log.ts` writes and hashes the log as the run goes. `generate.ts` runs it: pilot (recorded, or run), plan, one stream, then each stratum's full bin is dealt to dev, validation and training by HMAC-SHA256(assignment_key, canonical hash) order (the assignment rule of §2 so that every record has its split; `assignSplits` of #860 owns this later), every record is re-read with `readTeamRecord` and the labeller, and a bin still short at `d_max` re-plans with the short strata coarsened one more level under `<plan_id>-r<n>`. `provision.ts` sizes the ranges from a negative-binomial fill-time quantile; `range.ts` summarises a range of draws as one SHA-256 over fixed-width per-draw records, the unit the two-platform check compares. `command.ts` is the CLI (`generate`, `pilot`); output is JCS-canonical, so the same commit, config, label set, keys and references give the same bytes (`records.<split>.jsonl`, `manifest.json`, `coverage.json`, `pilot.json`, `rejections.jsonl`). The generation key of a public dataset is a public key given on the command line; sealed generation is #861. Package tests run the real validator on a few thousand draws; keep any new generation test small. Quotas: a split's share of a stratum is its share of the ACCEPTED pilot draws (rejected draws belong to no cell), while the cost rule uses the rate per draw of the stream; the `n_stratum_min` floor per stratum and split can lift a split above its request (20/20/100 over 23 strata delivers about 55/55/116), so `coverage.json` lists requested and delivered per split and the CLI prints any difference. `provisioning.exceeds_d_max` (and a CLI warning) says the 0.99 fill quantile is beyond `d_max`, because the merge decides on mean fill times and the stream stops at `d_max`. `coverage.json` also records `replan` (0 or the re-plan count) and each base cell's `held` teams per split inside merged strata. The seed preimage is the JSON object `{config_hash, k, plan_id, purpose}` (the pilot's has no `plan_id`), not the tuple the ADR writes: an ADR-013 erratum candidate. `moves_per_set` is a named config field (optional in the schema, required by the proposal). `generator.json` gives every Mega Stone (the items the roster's Mega formes require) weight 0 so a stone appears only with its Mega species; otherwise about half the free item slots hold a useless stone and the Mega label is nearly constant (a test holds the label's stones and the zero weights equal to the roster's required items, so a pin bump that adds a stone fails). Scale limits of this slice (#883): the dataset files stream. `writeDataset` writes each `records.<split>.jsonl` in 1 MiB chunks (`writeLines`), and `recordHashes` and `readDataset` read line by line (`eachLine`, `endsWithNewline` in `dataset-io.ts`), so no file is held as one string and the 512 MB string limit no longer applies to them; the bytes written are unchanged. What still sits in memory: the records themselves (`GenerateResult.records`, and `readDataset`'s `VerifiedDataset`, as objects, roughly the file size or more), the known hashes as JS strings while `sortedUnique` builds the sorted list (about 100 bytes per hash; 1.2M hashes peak near 400 MB of RSS in `scripts/measure-streaming.ts`, which writes, reads back and indexes 1.2M padded lines of a 930 MB file; the previous joined-string code fails on it with `RangeError: Invalid string length`), the binner's in-run `Set`, which holds at most 2^24 (about 16.7 million) binned teams (a V8 limit, unchanged), and the JCS string of the sorted hash list that `datasetHash` and `recordHash` build (fine to some millions of records). The CLI reports an oversize failure as exit 1; 10^8 teams needs the shard slice's binary builder. `assign-splits.ts` (#860): `assignSplits(pool, plan, assignment_key, n_stratum_min?)` is the one split rule (ADR-013 §2): within each stratum it orders the teams by HMAC-SHA256(assignment_key, canonical hash) and deals dev, validation and training by the plan's quotas; it is pure, order-insensitive, and refuses a stratum that is not exactly its bin, a team twice, a quota below `n_stratum_min` and a key that is not 64 lowercase hex digits; `generate.ts` calls it. **Committed fixtures** (`fixtures/teams/<format>/datasets/fixtures-v1/`, CC0, see its README): `teams-dev.jsonl`, `teams-validation.jsonl` (JCS lines), `manifest.json`, `hashes.json` (sorted `record_hash` / `canonical_team_hash` lists per split and the manifest hash: a Parquet shard of the split must list the same `record_hash`es), `pilot.json`, `coverage.json`, `run.json` (the public keys, sizes and generator commit); the training split is generated in the same run but never committed. `dataset-reader.ts`: `readDataset(dir, ctx)` trusts nothing (manifest against config and label set and the engine's version manifest; the reference pool: `generate --reference` also writes `reference-hashes.txt` (the sorted, unique canonical hashes it deduplicated against, one per line; absent without `--reference`), and the reader recomputes `reference_pool_hash` from `ctx.referenceHashes` if given, else from that file, refusing a missing, doctored, unsorted or malformed list and any record that repeats a listed team, so the evaluation paths (`--eval-dataset-dir`, the scripted head-to-head, `datasetValidationPool`) read such a dataset with no extra input, #1170; each record through `readTeamRecord`, the labeller, `importPaste` round trip and `validateTeam`; every stratum holds its quota; no team in two splits; the hash lists recomputed), `trainingPool(datasets, engine)` takes only `readDataset` results, recomputes every canonical hash from the paste, and returns a branded pool of dev records that `drawTrainingTeam` alone accepts: a validation record, a forged hash, a hand-built dataset or pool, or a team repeating a validation team is refused (`readDataset` also checks `vocabulary_hash` and `reference_pool_hash` against its context; `generator_commit` is checked only by the regeneration test). `fixtures.ts` + `scripts/fixtures.ts` (`write` / `check`, `--full` also reruns the 40,000-draw pilot, about 45 s) regenerate the files from the committed config; a test (about 5 s with the recorded pilot) requires them byte for byte.

**Mixture proposal (ADR-020 §1-§3, #972).** `TeamGeneratorConfig` gains the optional `proposal {kind: "mixture", components}` (a minor change within v1; absent keeps every draw, fixture, dataset hash and the generator golden digest). Components are `uniform` and `role_sets {role_set_table_hash}`, each with an integer `share_permille`; `readTeamGeneratorConfig` requires them sorted by kind, unique and summing to 1000 (a `usage` component fails the schema; it comes with the sampler slice), and `config_hash` covers the field. With a mixture, draw k's FIRST draw from its own seeded stream is `rng.below(1000)` against the cumulative shares in component order (`Proposal.component(rng)`, recomputable from the seed), then the chosen path runs; `uniform` is the old path. Component R lives in `role-set-proposal.ts`: `team_size` distinct table entries uniformly, a role uniformly among the entry's sets, up to `moves_per_set` moves without replacement from the role's pool, an ability from the role's list; item (a Mega entry keeps its required item), nature and Stat Points use the uniform draws (`Proposal.#set`). A Mega-forme entry is proposed as the forme it shows as (`megaPreviewSpecies`) holding its stone, with the role's pre-Evolution ability. `Proposal(vocabulary, table, config, roleSets?)` refuses a role_sets component with no `RoleSetsSource` (`roleSetsSource(engine, vocabulary, engineData, table)` reads it against the vocabulary) or whose hash is not the one named; `generate` takes `roleSets`, the CLI `--role-sets FILE` (default the golden `fixtures/showdown/<format>/role-sets.json`, read only when the config has a role_sets component); the sealed generator takes no table, so a config with a role_sets component is refused there (a uniform-only mixture is accepted; `sealed.test.ts`). Two table entries may show as one species (a base forme and its Mega forme): the validator rejects such a team, as in the uniform path, which costs about 2% extra validator rejections of R teams (a reviewer's simulation: 200,000 draws, about 2.0% of R teams). `config/teams/<format>/generator.mixture-r.json` (role_sets 700, uniform 300) is checked by `check-team-labels.ts`, which now reads every `generator*.json` and requires a role_sets hash to be the committed table's. Tests: `packages/team-dataset/test/mixture.test.ts`.

**Pilot gates, contamination counts and evaluation-only datasets (ADR-020 §6-§8, E-13.5, E-13.6, #973).** All new report fields are omitted when no `proposal` is set (a uniform dataset keeps every byte; `fixtures.ts check` stays green). `proposal.gates {p2_min_accept_permille, p3_min_bits, p4_min_strata_permille}` is optional on the config (minor change within v1; the ADR's proposed 500, 40 and 750 are in `generator.mixture-r.json`, which therefore has a new `config_hash`; no dataset used it). A mixture's pilot records `components` (`draws`, `rejected`, `cell_hits` per component in config order, the component of pilot draw k recomputed from its seed by `Drawer.pilotComponent`; optional on the `Pilot`, absent for uniform; `generate` refuses a mixture with a recorded pilot lacking it). `pilot-gates.ts` (`proposalCoverage`) writes `coverage.proposal`: per component the pilot counts, P1 (role_sets: share of the table's species, move and ability ids that resolve in the vocabulary, required to be 1000: the ADR fixes R at 100%, so there is no config field; uniform has none; the usage component's P1 is per list kind against the optional `p1_min_usage_permille`, see Component U), P2 (accepted pilot draws, permille), P3 (`bitsOf`: the largest b with the bound <= 2^-b, an exact BigInt rational: size!/(N)_size x the product of the six largest per-entry bounds, where an entry's bound is 1/(abilities x C(pool, moves)) (role_sets: the mean over the entry's roles) x the nature, gender and Item Clause item factors (the clause removes the `floor((size-1)/limit)` largest weights from the total; a required item is 1); Stat Points are ignored, which keeps it an upper bound; a team is the set of its members, moves unordered), the pilot and delivered per-cell counts and the delivered split counts (the component of each delivered record is recomputed from its seed); `mixture_p3_bits` (share-weighted sum); P4 (`strata` of the final plan against `reference_strata`, the plan of `--uniform-pilot`, a pilot of the same config without `proposal` made by `pilot --without-proposal`, at the same d_max, sizes and parameters; thousandths); `failed` (`P1:<kind>`, `P2:`, `P3:`, `P4`, `gates:not_configured`; a gate with no threshold or no reference is not met) and `publishable`. A PUBLISHING run is one given `--publish`: the files are still written, and the exit code is 1 when any gate failed or could not be evaluated (stderr lists them); without it the notice is printed and the exit stays 0. `coverage.population` (E-13.6) states the proposal and shares and "conditioned on the merged cells, weighted by the published quotas" (mixture or evaluation-only runs only). `--d-team N` adds `coverage.near_duplicates {d_team, pairs[{of, against, teams, near}]}` (validation to dev, validation to training, dev to training; counts only) using `NearIndex` (moved to `near-index.ts` with `teamDistance` and `SealedError`, re-exported by `sealed.ts`, behaviour unchanged). `--evaluation-only --d-team N --reference FILE...` (needs a pure component config, one component) builds a `NearIndex` of the references' pastes and `Binner` drops, after the full-bin and duplicate checks, every candidate within N differing fields of one, logging it as `near_reference` (`RejectionLog` counts `near_references`); the manifest gets `evaluation_only {d_team, near_references}` (optional, minor change within v1; the reader requires near_references <= draws and, with the config, one component). `trainingPool` refuses such a dataset (`TrainingDrawError`) and `datasetPoolDetail`/`datasetTeamPool` with a `GenerationError`; `readDataset`, `datasetValidationPool` and `--eval-dataset-dir` accept it. `loadFixtureInputs(engine, format, datasetDir?)` now picks, from `config/teams/<format>/generator*.json`, the config whose hash the dataset's manifest names, so a mixture or role-set dataset reads against its own config. Only COMMITTED generator configs can be read back this way (`generator.role-sets-eval.json`, role_sets 1000, is the pure config for EXP-M1's V_M*); a dataset from an uncommitted config fails to read with a config-hash mismatch. Tests: `pilot-gates.test.ts` (P3 against hand-worked toys, the gate arithmetic, cross-split counts on a hand-built split pair, a small mixture generation), `evaluation-only.test.ts` (Binner exclusion, a generation from the committed config, the readers and pools), `command.test.ts`.

**Component U of the mixture proposal** (ADR-020 section 4, slice 7, #977; `packages/team-dataset/src/usage-proposal.ts`, `proposal.ts`, `pilot-gates.ts`). `TeamGeneratorConfig.proposal.components` may hold a `usage` component (`share_permille`, `usage_table_hash`, `species_root`, `set_root`, `floor_permille`; sorted by kind after `role_sets` and `uniform`, at most three; a minor change within v1, so a config without it keeps every byte and hash, held by `generator-golden.test.ts`). `Proposal(vocabulary, table, config, roleSets?, usage?)` refuses a missing table, a hash other than the named one and a `species_root` other than the table's own `derivation.species_root` (the species and teammate weights are the table's precomputed roots). `generate` and `pilot` load the table through `usageTable` in `command.ts`: `--usage-table FILE`, else the file under `config/teams/<format>/usage/` whose `usageTableHash` the component names (exit 2 when none, or when `--usage-table` is another table); `check-team-labels` requires the named table to be committed there with the same `species_root`. **Draw rule** (`UsageSampler`, integer `rng.below` picks only, on the draw's own stream): species 1 by `w_species`; species k+1 by the summed teammate weights of the chosen species over the unchosen roster entries (a roster entry the table lacks weighs 0), falling back to `w_species`, then to uniform, when the sum is zero; a Mega forme holds its required item, else an item by weight among those the Item Clause still allows (the table's no-item share is an option; truncated and unmapped mass is not), an ability by weight, `moves_per_set` moves by weight without replacement (the rest of the pool uniformly once the table's entries run out), one spread (nature and Stat Points as listed) by weight. Set weights are the table's ppm under the integer root `set_root` (`rootedWeight`, 1 leaves the ppm). **Floor (decision where the ADR left room):** with probability `floor_permille` (one `below(1000)` per categorical draw, nothing drawn at 0) a draw is the UNIFORM component's own: a species uniformly among the unchosen roster entries, the item by the config's `item_weights` (Mega Stones stay weight 0), the ability and moves uniformly from the roster entry, the nature uniformly and the Stat Points by `drawStatPoints`; an empty list falls back the same way. The validator still judges every team. **Gates:** `proposalCoverage` reports P1, P2 and P3 for `usage` beside the other components. P1 (`usageMapping`) is the mapped share, in permille, of each of the table's six list kinds (species usage, abilities, items, moves, spreads, teammates; an unmapped species counts in all six, a list's unmapped mass is weighted by species usage); the gate takes the MINIMUM over the kinds (ADR-020 section 6: 95% per kind) against the optional `p1_min_usage_permille` (no verdict when absent), and the aggregate `mapped`/`total` and the per-kind `kinds` are reported beside it. P2 is the pilot acceptance. P3 is reported two ways: `usageBounds().set`, which the gate uses, is a sound integer bound on the probability of the most likely team as a SET (orderings times the first-pick share times the product of the largest later-pick bounds, each from the mediant inequality over the teammate lists, times the six largest member bounds under the Item Clause and the floor, with the moves' orderings), times 2 for each Mega roster entry a team can hold (m = min(team size, Mega entries): the validator rewrites a Mega entry to its base forme holding the stone, which the base entry can also reach, so a canonical team can have two routes per Mega member), with the last-resort uniform species pick and uniform item pick (no listed weight left) bounded by their own probability; `p3_sequence_bits` (usage only, never gated) is the ADR-literal figure, the product of the largest conditional weights along ONE draw route with no ordering factors and no Mega factor, so it bounds one draw order. The pilot also records `max_team_count` for the usage component (a count: the most draws that produced one canonical team, accepted or not) and the coverage reports it as `pilot.max_team_count`, a measured check beside the bound and never gated. The gate's optional fields are named in the schema: `p1_min_usage_permille` (P1 for usage) and `p3_min_bits_usage` (P3 for usage; falls back to `p3_min_bits`). On the committed table (2026-09, cutoff 1630) at floor 100: set_root 1 gives set-level 2^-12 (2^-18 before the Mega factor) and sequence 2^-49, set_root 2 gives 2^-35 and 2^-69, set_root 3 gives 2^-48 and 2^-75 (set_root 4: 2^-56 and 2^-76). **ADR-020 erratum E-20.1 (owner, option A): component U uses `set_root` 3 and keeps the 40-bit P3 gate like every other component**; the example config sets it and has no `p3_min_bits_usage`, which stays in the schema and reader as an optional field no committed config uses. The 2^-48 set-level figure assumes (a) the unconditioned proposal: a dataset conditions each draw on its merged stratum, so the probability of a team within its cell can be higher than the bound, which P3 does not cover, and (b) every Mega roster entry has a single ability (true at this pin; a Mega entry with several abilities adds routes and the bound must be revisited; `usageBounds` refuses such a vocabulary with a fixed `GateError`). Both are bounds on the generator, not the probability of any real team. `test/usage-proposal.test.ts` checks the set-level bound against an exhaustive exact enumeration of a tiny table (floor 0, 300 and 1000) and against a toy with a Mega entry whose canonical team has two routes (the bound without the 2^m factor fails it). `config/teams/<format>/generator.mixture-u.json` is the example with the target shares (role_sets 200, uniform 300, usage 500; floor 100, roots 2 and 3; it passes all gates P1 to P4 in the small generation of `test/usage-proposal.test.ts`). Measured on the committed table: pure-usage pilot acceptance 391 of 400 draws (97.8%, P2 threshold 50%); P1 (every kind at least 999 permille) and both P3 figures are pinned in `test/usage-proposal.test.ts`, which also holds, on a toy table read through the real reader, the species-pair frequencies against the teammate rule and the floor share (species, item and spread) within 5.5 binomial standard deviations, the items still allowed under the Item Clause in proportion to their weights, the hand-worked P3 toy, the refusals and a small three-component generation that is byte-identical on rerun. Not here: EXP-M2, publishing a usage dataset, pool U.

**Evaluation-only usage config of the later month (EXP-M2, #979).** `config/teams/<format>/generator.usage-eval-2026-10.json` is a PURE `usage` mixture (one component, share 1000, `set_root` 3, floor 100) naming the 2026-10 table `usage/2026-10-1630.json` (`usage_table_hash` `95d814d0...`, derived from `config/opponent-model/<format>/smogon-chaos.2026-10-1630.inputs.json` with `scripts/derive_usage_weights.py`, byte for byte; P1 mapping shares in ppm: abilities 999,977, items 1,000,000, moves 999,993, spreads 1,000,000, teammates 1,000,000). It exists so `readDataset` can read back an `--evaluation-only` dataset made from it (only committed generator configs can be read back); it is the held-out set V_U* of the usage arm of ADR-020 section 9 and must never be named by a training config or a training dataset (the training mixtures name the 2026-09 table by hash, and `usageTable` looks a table up by the hash a component names, so nothing under `usage/` is picked up implicitly).

**Parquet shards** (`packages/team-dataset/src/shards/`, ADR-013 §4, §6, §7, #862). A snapshot is immutable, content-addressed Parquet shards plus a `TeamSnapshotManifest`; shards live in R2 and Releases, never in git (`check_binary_files.py` rejects `.parquet`), so every test writes them to a temp dir. `columns.ts` is the column layout (parquet schema version 1: one column per record scalar, `labels` as a list of `{label_id, value}` structs, derived `stratum` and `label:<id>` columns) and the rebuild rule (`recordOf`: null, a missing or extra column, an int64 outside +-(2^53-1) or a derived column that differs from the labels refuses the shard). `layout.ts` is the layout (`S = ceil(R / 2^18)`, shard = first 8 bytes of HMAC-SHA256(`shard_key`, canonical hash) mod S, rows sorted by stratum then canonical hash, `cell_ranges`). `reader.ts` (`readShard`, hyparquet and hyparquet-compressors, both MIT, production dependencies that pass `make licences`) decodes, rebuilds, computes `record_hash` and checks row count, order, split, `logical_hash` and `cell_ranges` against the manifest; it never calls the engine. `snapshot.ts` builds the manifest (`buildSnapshotManifest`, checked by the bridge's `readTeamSnapshotManifest`), reads a snapshot shard by shard (`eachSnapshotShard`: file SHA-256 and size, one-to-one shard indices) and holds `checkFixtureAgreement` (a committed split's `hashes.json` and the shards of that split must list the same sorted `record_hash`es). `convert.ts` turns a dataset directory (`records.<split>.jsonl` or the committed `teams-<split>.jsonl`, plus `manifest.json`) into shards under `pub/v1/shards/<sha256>` and `snapshot.json` with bounded memory (one shard at a time) and reads every shard back once; `verifySnapshot` checks the shards against the dataset file byte for byte. The writer is the DuckDB command-line tool run as a child process (`duckdb.ts`): never a library import, never in a `package.json`, lockfile, Dockerfile or image (a test scans every tracked manifest), user-installed (`DUCKDB_BIN` or the PATH); `scripts/duckdb-pin.json` holds the version URL and SHA-256 of the zip and binary per platform, CI downloads and checks it and sets `ARENEON_REQUIRE_DUCKDB=1` so the real-tool tests cannot skip there (without the tool they skip, and a stand-in that writes through hyparquet-writer, a dev dependency, covers the conversion paths). The manifest's `writer` is read from the binary that ran. File bytes depend on the writer version and settings; `logical_hash` and `logical_snapshot_hash` do not (tests cross two DuckDB settings, and two versions when `DUCKDB_BIN_ALT` is set). Cross-architecture byte equality is not established: see ADR-013 §6. (Rebuild time and memory figures against the ADR-013 budget: see #862.) The miss is to be recorded as an ADR erratum (#882). Publishing, the sampler and the working database are later slices.

**DuckDB working database** (ADR-013 section 7, #865; `packages/team-dataset/src/duckdb/`, `sql/working-db.v1.sql`, `scripts/teams.ts`, `README.md`). `node packages/team-dataset/scripts/teams.ts duckdb --snapshot DIR|FILE --out teams.duckdb [--dataset DIR] [--labels FILE] [--shards DIR] [--require-pinned]` builds a derived local DuckDB file from a PUBLIC snapshot with the user-installed CLI (`DuckdbWriter.runScript`; DuckDB is never imported). `buildWorkingDatabase` first verifies every shard through `eachSnapshotShard` (the reader's rules), requires every record's `label_set_hash` to be the label set's and expands each paste with `importPaste`; it writes the six tables as JSON Lines into a scratch directory and the versioned script loads them (`snapshot` with `duckdb_schema_version`, `shards`, `teams`, `labels`, `sets`, `moves`; a layout change is a new `working-db.v2.sql`, never an edit). `--dataset` supplies the merged strata the verification needs (without it every base cell is its own stratum). The output is built beside its name and renamed, never replaces a file, leaves nothing on failure, and must end in `.duckdb` (gitignored; the binary guard refuses it; a test checks tracked files, `git check-ignore` and the guard's list). The README recipes (species, item, move and label filters, reading the shards' Parquet, exporting a selection) are run by `test/duckdb/working-database.test.ts` against a database built from the committed fixtures with the real tool (skipped without a binary, not skippable under `ARENEON_REQUIRE_DUCKDB=1`; the expectations come from the fixtures read with the pinned engine); the `duckdb -ui` and `TYPE r2` recipes need network and credentials and are documented, not run. Built from a local snapshot only: no snapshot is published to R2 yet, so the R2 path is not exercised. Private data is out of scope (ADR-015).

**Teams publish** (ADR-013 section 6, #863; `packages/team-dataset/src/publish/`, `scripts/teams-publish.ts`, `.github/workflows/teams-publish.yml`, `docs/runbooks/teams-r2.md`). Public synthetic snapshots only, in the shape of rules-publish; manual (`workflow_dispatch` on main), nothing runs on a push. `plan.ts`: `buildPlan(dir)` reads a snapshot directory (`snapshot.json` plus `pub/v1/shards/<sha256>`) through the bridge's manifest reader, checks every shard's key, SHA-256 and size and the snapshot hash (`snapshotHash` = SHA-256 of the manifest's JCS bytes) and returns the `PublishPlan` (`teams-<snapshot_hash>` tag, manifest and shard hashes); `writePlan` writes `plan.json` and the Release asset `release/teams-<hash>.json` (the JCS bytes), `verifyDir` requires the plan on disk to equal the plan made again from the files, `parsePlan` fails closed. `upload.ts`: every shard then the manifest (`pub/v1/snapshots/<hash>/snapshot.json`) with `putIfAbsent`; an existing key is accepted only with identical bytes (a retry), other bytes are a `PublishError`, never an overwrite. `layout.ts`: `TEAMS_LAYOUT` for the shared object-store client (two key shapes, no overwritable key, no delete). `platform-check.ts`: the two-platform check, logical hashes only (file bytes depend on the writer): `checkPlan(totalDraws, sizeBound, key)` is `full` up to the bound, above it 16 distinct ranges of 2^20 draws chosen by HMAC-SHA256 of a public key (all ranges when there are no more than 16); `platformReport`, `parseReport`, `comparePlatforms`. The workflow runs the full-pipeline comparison on an x86-64 and an arm64 runner; computing range digests (`rangeSummary`) inside the workflow is NOT wired (a fixture-sized dataset is under the bound). `command.ts` is the CLI (`plan|verify|report|compare|upload`; `upload` reads the R2 credentials from the environment only and, with `--skip-without-store` and no credential variable, does nothing). The `publish` job runs in the protected environment `teams-public`, is skipped until the repository variable `TEAMS_PUBLISH_ENABLED` is `true`, and with it set but an R2 secret or the bucket variable empty FAILS with a message. The R2 environment is given only to the verify-credentials and upload steps; the upload to R2 runs first, then the attestation, and the Release last (an existing Release must carry an asset whose SHA-256 equals the plan's `manifest_sha256`, else the job fails); the `check` job also requires the amd64 report's `logical_snapshot_hash` to equal the `teams-snapshot` manifest's. Owner steps (bucket, 365-day lock on `pub/v1/`, multipart-abort rule, scoped token with expiry, environment, secrets) are in the runbook and are not done by any code. Tests use a real snapshot made by the stand-in writer and `InMemoryObjectStore`; no network. The GitHub matrix, job-time and artifact limits are quoted in the runbook (owner to verify); a real dry run against a test bucket needs the owner's setup.
