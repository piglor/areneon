# League seeds

League seed derivation and the LeagueRunRecord.

Part of the architecture documentation split out of `CLAUDE.md` (index: [README](README.md)). Ticket references such as `#1179` point to Redmine (`redmine.piglor.com/projects/areneon`), where measured figures and verdicts are recorded.

**League seeds and the LeagueRunRecord** (`packages/showdown-bridge/src/league-seed.ts`, `league-run-record.ts`, `packages/schema/contracts/v1/league-run-record.schema.json`, `ml/areneon_ml/loop/league.py`, ADR-009 §3, ADR-010 §4, #843). `league-seed/1` is the pure derivation of everything a league game is built from: `leagueGameStreams(run_key, generation, game)` is SHA-256 over the JCS of `{run_key, generation, game, purpose: "league-game"}`; the first 16 bytes are the battle seed in the engine's `sodium,<32 hex>` form, bytes 16 to 23 are the two sides' team draws (the caller takes them modulo its pool) and bytes 24 to 27 seed a scripted baseline's stream. `planGeneration` calls it, and it was moved out of the planner byte for byte: **no seed, plan or committed hash changed**, so the tiny-loop determinism tests pass unchanged. `policyStreamLabel(seed, game, player, policy_id)` is the per-seat policy stream label (protocol D9 with the game index); `sampleU` adds the request number to it and keeps its draw. A test pins the vector `league-seed/1` gives for four (run key, generation, game) triples and one `sampleU` draw, all computed outside the TS code with Python's hashlib, and the Python `league_game_seed` reproduces the same four. Seeds and stream labels are the harness's: the worker is given only the draw `u`, never a seed, and no observation or `TrainingExample` carries one. The `LeagueRunRecord` (contract v1, integers only, hashed by `leagueRunRecordHash`) is written as `league-run.json` beside `plan.json` for each generation (`playGeneration` builds it, `writeGeneration` writes it before `generation.json`). It holds `run_id` (the run key), `run_config_hash`, `generation`, `seed_derivation` (the schema fixes `league-seed/1`), `plan_hash` (SHA-256 of `plan.json`'s JCS bytes), `pair_policy_id`, the counts (`games`, `played`, `forfeits`, `episodes`) and `opponents` (games per `opponent_policy_id`). Reader rules the profile cannot say, in `readLeagueRunRecord` and `read_league_run_record`: `played + forfeits = games`, two Episodes per played game, opponents sorted and unique and summing to `games`. `checkLeagueRunRecord` and the Python reader tie a record to its `TrainingRunConfig` (run key and hash). The Python loop driver reads `league-run.json` and `plan.json` after each generation and refuses one whose record belongs to another run, config, generation or pair, whose plan does not hash to `plan_hash`, whose forfeits differ from `generation.json`, or whose plan carries a battle seed the run key does not give. The league scheduler, the `L2` lineage and the exploiters (#844, #845) build on this and are not here. **Version 2 (ADR-021 sections 2 and 8, ADR-010 erratum A3 LE.5, #983; a new schema version beside v1, not a minor change: the root no longer has one frozen pair; single-lineage runs keep writing v1 and every v1 sample, `league-run.json` fixture and byte is unchanged).** `LeagueRunRecordV2` (`league-run-record-2.schema.json`, generated TS and pydantic types, samples `league-run-record-2/`) has `run_id`, `run_config_hash`, `generation`, `seed_derivation`, `plan_hash`, the root totals, `forfeit_causes`, `copy_decision_hash` (required, null when that generation took no copy decision) and `members`: one entry per learning member (`m<k>`) and exploiter seat (`x<k>`) with `pair_policy_id`, `checkpoints {preview, battle}`, `games`, `played`, `forfeits`, `episodes`, `opponents` (`{opponent_policy_id, member?, games, played}`) and the optional `forfeit_causes` and `baselines` (the v1 shapes, per member). **Counting rule (the schema descriptions state it too; it assumes every game has at least one learning seat):** a member entry counts every game in which it holds at least one seat (`played + forfeits = games`); a game between two learning members (m vs m, m vs x) appears in BOTH entries, under each other's member id (`member` set, `opponent_policy_id` = that member's pair); a self-play game appears once, with the member's own id; `episodes` are the Episodes of the member's OWN seats, `played + played self-play games`; a member's forfeit causes are those of its games. The root counts DISTINCT games as v1 does (`episodes = 2 * played`): root games and played = the members' sums minus each member-vs-member pair counted once; each root cause count lies between the largest member count and the sum over the members and the cause set is the union of the members'. Reader rules (TS `readLeagueRunRecordV2`, Python `read_league_run_record_v2`, held equal by the corpus): members sorted (`m<k>` by k, then `x<k>` by k) and unique; per member the counts, opponents sorted by (policy id, member) with `played <= games` and sums, the own-seat Episodes, causes present exactly with forfeits, baselines as in v1 against the member's member-less opponents; a named member exists, the opponent's policy id is its pair, and the two members' entries about each other agree in games and played. The v1 readers (`readLeagueRunRecord`, `read_league_run_record`) stay v1-only and refuse a v2 document; `readAnyLeagueRunRecord` / `read_any_league_run_record` dispatch on `schema_version` and refuse another. `checkLeagueRunRecord` (dispatching on the record's version; Python's v2 reader takes the config) ties a v2 record to its config: run key, hash, and the numbers of `m` and `x` entries to `population.members` and `population.exploiters` (the typed config field; Python reads `config.raw`), ids numbered from 0 without gaps; a v2 record for a config without `population` is refused. `leagueRunRecordHash` hashes either version. Writing v2 is slice 4; `LadderRecord` is #984. Damage-aware training opponent (ADR-018 slice 3, #945): `Baseline.actor` gained `damage-aware` (a minor change within v1; `baseline_games` holds up to three entries; an older reader refuses such a config), and `LeagueRunRecord` gained the optional `baselines` (policy id, baseline identity hash, games and the nine summed per-game counts of `DamageAwareActor.report()`; absent for every other run, so those keep their bytes; reader rules: sorted and unique, games equal the opponent entry's, probe runs and unsupported queries at most the queries, preview plus scored decisions at most the decisions; one identity hash per policy id per generation or the generation fails). `league-generation.ts` builds a fresh `damageAwareActor` per baseline game from `config/baselines/damage-aware.v1.json` and the mechanics config (golden vocabulary: the committed format only), seeded with bytes 24-27 of `league-seed/1` (drawn only when `epsilon_ppm` > 0), and requires the config's `policy_id` to be the one the actor plays as; the seat is never queried against the worker and the loader still takes only the pair's seats. Wall-clock cost is not recorded in the run files (see `docs/training-run.md` for the measured figures). `checkLeagueRunRecord` and the Python reader also require `baselines` to list exactly the config's damage-aware entries (policy id and games); the one-identity-hash rule is enforced when the record is built.
