# Private teams

The private team store, snapshots, owner-session guard, private test and inventory.

Part of the architecture documentation split out of `CLAUDE.md` (index: [README](README.md)). Ticket references such as `#1179` point to Redmine (`redmine.piglor.com/projects/areneon`), where measured figures and verdicts are recorded.

- `private-training-loader.ts` (ADR-015 erratum E1 items 5 and 6, #1062): the private run's own loader; `loadTrainingSet` is unchanged and still refuses every private Episode (a test pins it, a floor-raised one included). `loadPrivateTrainingSet({episodes: [{episode, opponent_team_hash}], evaluation_manifests, known_synthetic, behaviour_policy_id, run_key, holdout_team_hashes})` accepts only `private` / `owner-private` `league` Episodes whose `collection.run_id` equals `run_key`, each through `readEpisode`, and writes a `private` TrainingSet (the stream and set bytes are the public writer's: `streamTraining` gained a `data_class` argument and is exported for it). Refused, each a `PrivateTrainingLoaderError` with a `code` (`PRIVATE_LOADER_REFUSALS`), a FIXED message and at most the 0-based list position, never a team, hash, run key or reader text (the reader's message is dropped): an Episode the reader refuses, no collection record, `evaluation`, `sparring`, a synthetic (not private) Episode, another run, another policy than `behaviour_policy_id`, an Episode whose own team (positional `teamHash` or `canonicalTeamHash`) or whose opponent's team hash is in `holdout_team_hashes`, a malformed opponent hash, a hash an `EvaluationRunManifest` lists, a repeated Episode or manifest, an invalid manifest, a run key that is not an id token, no Episode, a stream over `max_string_chars`. Decisions where the ticket left room: an Episode does not store the opponent's team, so the caller gives each Episode its `opponent_team_hash`, derived from the battle's `record.team_hashes` for the opponent's seat; the hold-out set is the caller's hashes (its construction is the hold-out ticket's); only the in-memory path exists (no chunked writer for private streams yet). **Class floor:** `episodeFromRecord` takes `class_floor` (`DataClass`), and a floor above synthetic is STORED as the optional `class_floor` (const `private`; a minor change within v1, absent keeps every byte) of a `league` / `evaluation` `provenance.collection`; the Episode's class is the higher of both teams' classes and the floor (a private run passes `private`, so a game of two synthetic teams is private too, with `owner-private` rights; a floor never lowers a class). `readEpisode` accepts a class at or above the higher team class and refuses one below (the relabel-to-synthetic refusal stands), and refuses a `data_class` below a stored `class_floor`, so a floor-raised Episode relabelled synthetic is refused by the reader. The public `loadTrainingSet` refuses any Episode that carries a `class_floor` (`TrainingLoaderError.code` `class_floor`, a fixed message) before its class rule. An Episode written without a collection record cannot carry a floor (the private loader refuses it anyway). Corpus: `episode/reader-invalid/class-below-floor.json` (a private opponent, synthetic label), `class-below-stored-floor.json` (synthetic teams, stored floor, label flipped) and `episode/invalid/collection-floor-synthetic.json` (a floor of synthetic is schema-invalid); a valid floor sample would be private-labelled, which the data-class guard refuses, so valid floors are built in tests. **Python:** `areneon_contracts.training` (`read_stream`, `check_stream_file`, `check_stream_digest`, `StreamChecker`) and `areneon_ml.learner.data.trajectories` / `learner.parallel` take `private_pool` (default False): a run without a private pool refuses a `private` TrainingSet and a private-pool run refuses a synthetic one, with fixed messages. The `TrainingRunConfig.private_pool` field and driver do not exist yet, so the caller states the flag; the driver passes `True` from the config field. The Python side cannot yet tell "another run": a TrainingSet manifest has no run key, so only the pool kind is checked there; the driver ticket adds the run check. The CLONE learner and the loop drivers keep the default (public). Tests: `private-training-loader.test.ts` (every acceptance and refusal, the canary on stand-in teams with negative controls), `episode.test.ts`, `tests/contracts/test_training.py`, `tests/ml/learner/test_private_pool.py`.
- `private-records.ts` (ADR-015 §2, §5, #869): the reader of the `PrivateTeamRecord` contract, crypto-free. `readPrivateTeamRecord(engine, value)` checks `private-team-record.schema.json` (data class `private`, a `paste` of at most 8,192 characters, tags, labels, a boolean `holdout`), the paste's engine round trip, both team hashes, `supersedes_record_hash` null exactly for revision 1, sorted and unique tags and unique label ids; its messages never repeat the paste (tests cover the schema-failure, too-long-paste, engine-refusal and hash-mismatch paths with a canary). `holdout` is the flag ADR-015 derives from a snapshot's keyed HMAC-SHA256 of `team_id` (200000 ppm of teams); this reader has no key and checks only that it is a boolean, so the snapshot reader (#887) recomputes it. `checkPrivateRecordSet` enforces the snapshot rules (unique `team_id`, unique `canonical_team_hash` among active records). `private-samples.ts` builds the corpus samples (the pastes are `fixtures/teams` pastes; one hold-out record). The `PrivateSnapshotManifest` is `private-snapshot.ts` (below).
- `private-snapshot.ts` (ADR-015 §2, #897, slice 1 of #887): the `PrivateSnapshotManifest` contract (`packages/schema/contracts/v1/private-snapshot-manifest.schema.json`, generated TS and pydantic types, integers only) and its pure reader, `readPrivateSnapshotManifest`; no engine, no file system, no key. It mirrors `TeamSnapshotManifest` with `data_class` const `private`, no `dataset_hashes`, one split (`owner`), the `label_set_hash`, `records: {active, retired}` and the `holdout` block `{rule: "hmac-sha256-team-id/1", key: <64 hex>, ppm: 200000}`. Decisions where the ADR left room (also on the ticket): (1) the hold-out block holds the KEY itself, as ADR-015 §2 writes it (the key is not a secret and the snapshot reader recomputes every record's flag from it), not a key commitment; (2) a shard names its `index` (its position, 0 first), never an object path, because the path `snapshots/<snapshot_hash>/shards/<index>.parquet` holds the hash of the manifest that lists the shard; (3) a cell range carries `active_rows` beside `rows`: the ranges tile ALL rows of a shard (retired included) and `cells` count active records only, so the reader checks cells and `records` against the shards from the manifest alone; (4) `first: true` or `parent_snapshot_hash`, exactly one (reader-enforced; the schema leaves both optional). The reader adds shards in strictly ascending `logical_hash` with `index` equal to position, ranges tiling each shard with ascending strata and `active_rows <= rows`, `cells` equal to the shards' active sums and listing exactly the cells with an active record (empty when all are retired), `records.active` equal to the cells' sum, active plus retired equal to the shards' rows, and `logical_snapshot_hash` recomputed (`privateLogicalSnapshotHash`: JCS of `{shards (sorted logical hashes), cells, label_set_hash, manifest, holdout, and parent_snapshot_hash or first: true}`; `privateSnapshotHash` is SHA-256 of the whole manifest and names the snapshot in the bucket). Its messages state a rule and never repeat a value or a key name (a canary test). `holdoutFlag(key, team_id, ppm?)`: HMAC-SHA256 with the 32 bytes the hex key spells, over `team_id` as its 32 lower-case hex ASCII characters, first 8 bytes big endian as n, held out when `n * 10^6 < ppm * 2^64` in integers; it depends on the two ids alone, so a team keeps its flag on every revision. Known answers computed with Python `hmac`/`hashlib` are in the comment of `test/private-snapshot.test.ts`, as are the two manifest digests. The snapshot reader (#899) recomputes each record's flag; the manifest reader needs no key. The corpus samples (`private-samples.ts`, `privateSnapshotSamples`) carry the private label and are listed in `PRIVATE_MANIFEST_MARKERS` (`check_data_class.py`), which accepts such a file only in the strict manifest shape (below).
- `private-team-source.ts` / `team-inventory.ts` (#775): the owner-team feature inventory, run as `scripts/team-inventory.ts`. Teams come through the `PrivateTeamSource` port (an async iterable of `{name, paste}`; no file system, network or crypto assumed). `PasteDirectorySource` is the one adapter here: it reads `private-data/teams/*.txt` and refuses any path without a `private-data` segment. The inventory runs `importPaste` and `validateTeam`, lists species, items, abilities, moves and Mega use, and flags features that a gap record names (advisory name matches; the detail also lists every gap as `format_wide_gaps`). It writes no file. It refuses unless stdin, stdout and stderr are terminals (and `CLAUDECODE` / `AI_AGENT` are unset; accident prevention) and `/dev/tty` opens, before reading any team; stdout gets counts and per-gap match counts only, and the detail goes to `/dev/tty`. The planned snapshot-backed `PrivateTeamSource` (ADR-015, #888) is not in this package. See `packages/showdown-bridge/README.md`.

**Private shards** (`packages/team-dataset/src/shards/private-shards.ts`, `private-reader.ts`, ADR-015 §2, #899): the d1 layout with the `PrivateTeamRecord` columns (`privateColumnsFor`: the record's scalars, `supersedes_record_hash` nullable, `tags` a list of strings, `holdout` a boolean, `labels`, the derived `stratum` and `label:<id>` columns; parquet schema version 1, `data_class` private, one split `owner`). It reuses `shardCount`, `shardAssigner` (HMAC of the canonical hash), `cellRanges`, the int64 rule and `recordHash` / `shardLogicalHash`. Differences: rows are ordered by stratum, canonical hash, then `team_id` (a retired record may share its team's canonical hash with an active one), cell ranges carry `active_rows` (`privateCellRanges`), and every refusal message is fixed text naming a layout column or a row position, never a value, a column name read from the file or library text (a canary test in `private-team-store`). `readPrivateShard` is engine-free and keyless like `readShard`, but the Parquet decode runs in a worker thread (`private-decode.ts`: `decodeIsolated`, an empty environment, a 4 GB heap limit, a wall-clock limit of 5 minutes by default, terminated afterwards; the worker is a `data:` module that imports the decode, so there is no separate worker script): hyparquet is written for trusted files and a damaged one can make it loop forever (a page header with a negative size), allocate without bound, or leave a rejected promise unhandled, which ends the process with library text; a seeded corruption fuzz (`snapshot-fuzz.test.ts`) found all three. Whatever the worker meets, the main thread sees the rows, a layout refusal's fixed message or `not a readable Parquet file`. The footer checks and the column-by-column read are `decodePrivateParquet` (tested in process, because the worker is not instrumented for coverage). The new column kinds (`NULLABLE_VARCHAR`, `BOOLEAN`, `VARCHAR_LIST`) are in `ColumnType`, and `DuckdbWriter.writeShard` takes `isolated: { dir, timeoutMs? }` for the private path: the tool runs with HOME, TMPDIR and cwd set to a scratch directory made inside `dir`, `DUCKDB_HISTORY=/dev/null` and nothing else in its environment (the `Runner` gained an optional cwd and timeout), the SQL starts with `SET autoinstall_known_extensions = false; SET autoload_known_extensions = false;` and locks the configuration (`SET lock_configuration = true;`) after the other settings and before the copy (a real-tool test reads the three settings back inside a child of the same shape), the tool is killed after `timeoutMs` (10 minutes by default), a failure is the fixed `WITHHELD_MESSAGE` (DuckDB's stderr can quote a paste and is never forwarded; a real-tool test provokes a DuckDB error that quotes the row and checks the public path forwards it and the private one does not), and the scratch directory is removed by `removeTree` (a best-effort chmod of leftovers, then a second try; it never throws, so cleanup cannot replace the original error; a removal that fails after a successful write is the fixed `CLEANUP_MESSAGE`). The public `writeShard` path is unchanged.

**Private teams** (ADR-015, which supersedes ADR-014 and its encrypted store; the wording rules are in AGENTS.md; the owner's bucket, lock and token setup is `docs/runbooks/private-store.md`, #889). The owner's real teams are inputs to a separate private run after the Training gate (#878), never to public datasets, published checkpoints or Episodes. They are kept, once the bucket is set up (ADR-015; #889, #891), as plain `PrivateTeamRecord`s in Parquet shards (the ADR-013 d1 layout, `data_class: private`) in a private R2 bucket, written once per snapshot, as plain objects with no client-side encryption (R2 encryption at rest only); the owner accepts the residual token risk (ADR-015 section 1); on the owner's workstation they appear only under gitignored `private-data/` (`teams/` is staging, `snapshots/<snapshot_hash>/` the verified local copy, run outputs stay there). Two bucket-scoped tokens exist, a write token for the import only and a read token for readers; both come from the environment of one command on the owner's workstation, never from the repository, a log, a chat or a command line, and an agent never runs a command that holds one. Built (#898): the pure import planner in `packages/private-team-store/src` (`planImport` in `import-plan.ts`, `parseStagedFile` in `staged-file.ts`, typed refusals in `import-error.ts`). Built (#899): the snapshot writer and reader there (below). It takes the staged files as `{name, text}` items, the parent snapshot's `PrivateTeamRecord`s (or null for `--first`), the `--retire` team_ids, the engine and the resolved format, and ports for labels, the hold-out flag (the snapshot layer plugs in the keyed HMAC; the planner holds no key) and fresh team_ids; it returns the next record list (one record per `team_id`, sorted) and a summary of five counts (`new`, `duplicate`, `revised`, `unchanged`, `retired`), or throws an `ImportPlanError`. Header `#! team_id=<32 hex> tags=...` (either key optional, order fixed, tags sorted and unique, at most 16; an empty `tags=` clears the tags, an absent one keeps the parent's), any other `#` line refused; each team goes through `importPaste` and `validateTeam`; a `team_id` not in the parent is refused (never created). A file without an id whose canonical hash equals an active record's, or an earlier file's, changes nothing and counts as a `duplicate` (ADR-015 section 3), so re-importing the same staged folder against its own result is a no-op. An edit is revision +1; a staged record identical to its parent (paste and tags, active) is unchanged; a retired one staged with its id becomes active again; a team absent from staging is unchanged; retirement is only `--retire` (retiring a retired record is a no-op counted as unchanged); a revision or revival that takes another active record's team is `duplicate_canonical_hash`; a result that loses an active parent record is refused; parent records' hold-out flags must equal the hold-out port's value. Beyond the ADR text (to be listed in its erratum, #892): a tag-only edit and a Pokemon-order-only change each make a new revision. A refusal is a code plus a 1-based position that indexes the caller's list (staged files as passed, or the `--retire` list; the command slice maps it back to a file), never text from an input: no paste, file name, tag, header value, id, species or move, and an exception thrown by a port is replaced by a fixed `hook_failed`; the canary tests (`test/import-canary.test.ts`, which asserts every refusal code and has a negative control) enforce it. The package depends on `@areneon/showdown-bridge` as a `workspace:*` link (the packaging test accepts that form for `@areneon/*` only; no registry dependency was added). **Snapshot writer and reader** (#899, slice 3 of #887; `snapshot-writer.ts`, `snapshot-reader.ts`, `work-dir.ts`, `snapshot-io-error.ts`, `snapshot-plan.ts`; the package now depends on `@areneon/team-dataset` as `workspace:*`). `writePrivateSnapshot({records, holdoutKey, parentSnapshotHash | null, labelSet, manifest, vocabularyHash, shardKey, writer, pin, workDir, ...})` lays the records out in shards (`layoutPrivate`), writes each through the pinned DuckDB tool on the private path (`writer.requirePinned(pin)` first; the stand-in or real tool in tests), reads every shard back with the engine-free private shard reader, and returns `{manifest, snapshotHash, shards}` in memory (shard files by manifest index; the writer uploads nothing: that is `publishSnapshot`, below; the CLI, `export` and the collision count are #901). Shards are ordered by logical hash, each with its position as `index` (the HMAC placement index is a separate property the reader checks). The records must already carry their hold-out flags (the writer refuses a flag that differs from `holdoutFlag(key, team_id)`) and satisfy `checkPrivateRecordSet`; a stratum is the label set's base cell (`labelPlan`; no merged strata for owner teams). Intermediates (the rows file and the shard file, which hold pastes in the clear) exist only in a fresh 0700 directory inside `workDir`, which `assertWorkDir` accepts only if it is absolute, a real directory (no symbolic link), owned by the invoking user, mode 0700, no parent writable by group or other (a sticky bit is accepted, as in the sealed store) and every parent owned by the user or root, and either has a `private-data` path segment or is on tmpfs/ramfs (`statfs`); a Windows drive mounted in WSL (`/mnt/<drive>`) is accepted only on tmpfs, because a 0700 mode proves little there; the owner and file-system probes are a test seam of `assertWorkDir` only (the writer's input has no `probe`, and a test reads its source to say so). They are removed afterwards, on failure too; if the write succeeded but the removal did not, the call fails with `cleanup_failed`, and a write that failed keeps its own error. `readPrivateSnapshot({engine, manifest, shard(index), labelSet, expectedSnapshotHash, expected})` is what the import (after writing and after downloading) and #888-era readers run: `readPrivateSnapshotManifest`, a parent equal to the snapshot's own hash refused, the hash the manifest was fetched under (`expectedSnapshotHash` is REQUIRED: there is no option to read without an anchor), the version manifest and vocabulary hash the caller derives from the pinned engine and rules in `expected` (`version_manifest_mismatch`; REQUIRED like the hash: a reader of a snapshot made under another pin says `expected: INSPECT_ONLY` out loud, and `publishSnapshot` refuses that value), `label_set_hash` = `recordHash(labelSet)`, the Parquet layout version, no two shards with one `file_sha256`, `shardCount(rows)` = number of shards, each file's size and SHA-256, `readPrivateShard` (columns, order, placement, logical hash, ranges with active rows), no two shards on one layout index, each record through `readPrivateTeamRecord` (engine round trip), each hold-out flag recomputed from the manifest's key and ppm, and `checkPrivateRecordSet`; it returns the records sorted by `team_id`. The counts need no check of their own: the manifest reader ties `records` and `cells` to the shards' ranges and each shard read ties its ranges to the decoded rows. Every refusal is a `SnapshotIoError` with a code (`SNAPSHOT_IO_REFUSALS`), a fixed message and at most a shard index and row number; whatever a lower layer threw (DuckDB stderr, hyparquet, the engine, ajv) is dropped and not attached as `cause`. Tests: `snapshot.test.ts` (round trip, every code), `snapshot-canary.test.ts` (markers in a paste nickname, tag, label, column name, file bytes, the tool's stderr, a key, a path and a failing shard source; error text, stack, fields and process output scanned; negative controls show the scan flags a leaking message and the public writer path), `snapshot-forged.test.ts` and `snapshot-self-parent.test.ts` (consistent forgeries the writer cannot make). The real-tool case runs where `DUCKDB_BIN` is the pinned binary and cannot skip when `ARENEON_REQUIRE_DUCKDB=1` (CI sets it for `pnpm test`; no workflow change was needed). Not checked by the reader: that the manifest's hold-out block and key equal the parent's (needs the parent), and `vocabulary_hash` / the version manifest against the engine (the caller's). `manifest.regulation` stays `minLength 1` because `make contracts` requires every contract's `$defs/VersionManifest` to equal `version-manifest.schema.json`; a pattern needs a change of that shared definition (not done here). **Object store and publish** (#900, slice 4 of #887; `object-store.ts`, `memory-store.ts`, `r2-client.ts`, `r2-settings.ts`, `current-pointer.ts`, `local-copy.ts`, `snapshot-store.ts`, `publish.ts`). **Shared client (ADR-024 S-a, #1077):** the port, `ObjectStoreError`, `R2Settings`, `R2ObjectStore` and `InMemoryObjectStore` live in the workspace package `packages/object-store` (`@areneon/object-store`, depends on `aws4fetch` 1.0.20 only, imports no other package); behaviour, refusal codes and fixed messages are unchanged (the key-refusal text is "the key is not part of this store's layout"; `overwriteCurrent` enforces `MAX_OBJECT_BYTES` like `putIfAbsent`; `R2Settings.sign()` is `@internal` to the client, held by a source scan). Each user INJECTS its key layout, `ObjectLayout {allowsKey, allowsListPrefix, overwriteKey}`: the client and the in-memory store refuse any key, listing prefix or overwrite the layout does not declare (`key_invalid`) before a request is signed, `putIfAbsent` never reaches the `overwriteKey`, a layout whose `overwriteKey` is not one of its keys is `config_invalid`, and `overwriteKey: null` is a store with no overwrite. The private store binds the shared classes to `PRIVATE_LAYOUT` (`object-store.ts`) in thin subclasses (`memory-store.ts`, `r2-client.ts`) and re-exports the settings (`r2-settings.ts`), so its API and tests are as before; it keeps `aws4fetch` in its own `package.json` (its packaging test requires the pin) and nothing depends on it (the shared package never names it). `AWS_SESSION_TOKEN` is an optional fifth variable (empty counts as unset; form `[A-Za-z0-9/+=_.~-]{16,4096}`, else `credentials_invalid`): held in the same private field as the secret, passed to `aws4fetch` as `sessionToken` so every request signs `x-amz-security-token` (and none without one), never printed, and `credentials_on_argv` covers its name (`AWS_SESSION_TOKEN`, a `--session...` or `--token...` flag) and its value on the command line. Tests in the shared package: `credential-canary.test.ts` (markers in key id, secret, session token, endpoint and bucket, a bad region carrying the echo; errors, process output, echoing and throwing fakes, the token only in its signed header, negative controls), `session-token.test.ts` (header present/absent, layout refusals with `fetch` never called, a second user's layout), `network-isolation.test.ts` (only `r2-client.ts` calls `fetch` or imports a network module, only `r2-settings.ts` imports the signing library; the private store's copy now asserts it has none). The sections below describe the same behaviour. `ObjectStore` is the port: `putIfAbsent(key, body)` (`If-None-Match: *`; an existing object is `ObjectStoreError("exists")` and nothing is overwritten), `get`/`head` (null when absent), `list(prefix)` (only `snapshots/` or `snapshots/<hash>/`) and `overwriteCurrent(body)`, the only overwrite, which cannot reach any key but `current.json`; there is no delete. Keys are checked against the layout (`current.json`, `snapshots/<64 hex>/manifest.json`, `snapshots/<64 hex>/shards/<n>.parquet`): anything else, `snapshots/_lock-check/` included, can be neither written nor fetched, and `listSnapshotHashes` returns only the hashes that have a manifest object, so an unknown key under `snapshots/` is never a snapshot (a test seeds one); `fetchSnapshot` is the verification (`readPrivateSnapshot` on the downloaded bytes). `InMemoryObjectStore` (tests; `seed` puts an object where the port would refuse to, as the owner's lock-check object) and `R2ObjectStore` implement it; one contract suite runs against both (the R2 client on a fake bucket behind `fetch`, so no test opens a socket; `test/network-isolation.test.ts` requires that only `r2-client.ts` calls `fetch` or imports a network module). The R2 client is path-style (`<endpoint>/<bucket>/<key>`), signed with `aws4fetch` 1.0.20 (MIT, no dependencies, pinned exactly, ignored by Dependabot, imported by `r2-settings.ts` only; the `age-encryption`, `@noble/*` and `@scure/base` pins of the superseded design are gone) with the real SHA-256 of the body in `x-amz-content-sha256`, no redirects, no retries, a time limit; 412 and 409 on a conditional write are `exists`, 401/403 `denied`, 429/5xx and any transport failure `unavailable`, other statuses `failed`, a listing or head that is not in the expected form `response_invalid`; every message is fixed and carries no response body, URL, header, bucket or key (`ObjectStoreError`, no `cause`). `R2Settings.fromEnvironment(env, argv, bucket)` reads `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL` (https, an `*.r2.cloudflarestorage.com` host, nothing else in the URL) and `AWS_DEFAULT_REGION` (`auto`) from the environment only; a command line that names one of them (`AWS_*`, `--secret`, `--token`, `--endpoint`, `--account`, `--region`, ...) or contains a value (key id, secret, endpoint, the account id) is `credentials_on_argv` before the environment is read. The values live in `#` fields; the object prints as `[R2Settings]` to String, JSON and `util.inspect`, and it signs requests itself, so only the signing library sees the secret. The bucket name is an argument, not a credential. `test/credential-canary.test.ts` puts markers in all four variables and the bucket, scans errors (message, stack, fields, inspect) and process output on every settings, client and publish error path, including fake responses that echo the markers, checks that the secret appears in no request, and has negative controls. `publishSnapshot({store, engine, labelSet, written, expected, expectedCurrent, snapshotsDir, ...})` runs the ADR-015 section 3 sequence: the snapshot's parent must equal `expectedCurrent` (null for the first) and `current.json` must still name it; the local copy's place must be free and safe; every shard then the manifest (JCS bytes) uploaded with `If-None-Match: *`; every object downloaded again and verified with `fetchSnapshot` (required `expected`, the manifest bytes compared with the sent ones); the verified copy written to `private-data/snapshots/<hash>/` (`assertWorkDir` rules, directories 0700, files 0600, built in a hidden partial directory and renamed, never replacing a copy); `current.json` (`{parent_snapshot_hash, schema_version, snapshot_hash}`, strict reader) checked once more and overwritten last. The final check and the overwrite are a read and a write, not one atomic request: a second writer in between is not excluded (one owner, one write token, ADR-015 section 7). A failure before the last step leaves `current.json` as it was; uploaded objects stay (the lock keeps them; they are unreferenced), and a retry with the very same bytes meets `exists`, so the next attempt needs another `snapshot_id` (another hash). A 404 reads as "absent", so a wrong bucket name looks like an empty bucket until the first write is refused. Also carried from the #899 review: the decode worker settles on `exit` with the fixed message instead of waiting for its time limit. The only private source in the code today is `PasteDirectorySource`. The `packages/private-team-store` package (#868) is a `private: true` pnpm workspace package that is never shipped and holds the import planner, the snapshot writer and reader, the object store port with its R2 client and the publish sequence so far; the import commands will live there too. `packages/private-team-store/test/packaging.test.ts` is the packaging rule: no Dockerfile, compose file or Coolify build file names the package, no other `package.json` depends on it, no Dockerfile copies a whole directory of packages or runs `pnpm install` without `--filter`, and the DuckDB CLI, the `age` CLI and OpenSSL appear in no `package.json`, `pyproject.toml` or Dockerfile. The Dockerfile checks parse `COPY`/`ADD` sources (explicit non-glob paths only) and pnpm commands, and `test/packaging-rules.ts` has table-driven bad and good cases for every check. Nothing may rewrite its pinned versions (`overrides`, `resolutions`, `packageExtensions`, `patchedDependencies`), with one reviewed exception: a root `pnpm.overrides` entry equal to the `ALLOWED_OVERRIDES` constant (today `minimatch` `^11.0.1`, GHSA-g3hv-75wg-m249, dev-only lint tooling) that names no package in the private package's production closure, which `productionClosure` reads from `pnpm-lock.yaml`. A Coolify application configured in the UI is not visible to a repo test: it is an operator rule (README). "Owner's machines" means the owner's workstation only; keeping the read token and any private run off every other host is an operator rule, not a code guarantee (the code guards are `loadTrainingSet`, `stampTeam` / `readEpisode` and the provenance checker, above). `make licences` checks the dependencies like any production dependency.

**Owner-session guard, private output root and canary harness** (ADR-015 erratum E1, #1059; groundwork for the owner-run private commands of Epic #1058). `packages/showdown-bridge/src/owner-session.ts` and `ml/areneon_ml/private/owner_session.py` are one behaviour in two languages: every command that reads private teams calls `assertOwnerSession` / `assert_owner_session` before it reads any team. It refuses when `CLAUDECODE` or `AI_AGENT` is set (any non-empty value), unless stdin, stdout and stderr are all terminals, and unless `/dev/tty` opens (a tmux terminal is a terminal and passes). There is no override flag. A child process that a guarded driver starts has pipes for stdio and calls `assertGuardedChild` / `assert_guarded_child`, which checks the environment only. A refusal is an `OwnerSessionError` with a code (`agent_session`, `not_a_terminal`, `no_controlling_terminal`) and fixed words that name no path or value; `fixtures/private-guard/refusals.json` holds the words of both guards and of the root check, and a test on each side pins its constants to it. It is accident prevention, not a boundary. `team-inventory` uses the shared `terminalRefusal` and `openControllingTerminal` with unchanged messages. `private-root.ts` / `private_root.py` are the one rule for where a private command may write: `assertPrivateRoot` accepts a directory only if it is absolute, a real directory (no symbolic link in the path), owned by the invoking user, mode 0700, below no group- or world-writable parent (sticky accepted), every parent owned by the user or root, not on a Windows drive mount, and has a `private-data` path segment (the `assertWorkDir` rules, which also admit tmpfs for snapshot intermediates; an output root does not, and each failure has its own code). `uid` and `parentUid` are test seams. `privateRootFile` / `writePrivateFile` re-check the root, accept one plain file name only and create the file 0600 without overwriting. `packages/showdown-bridge/test/support/private-canary.ts` is the privacy canary harness for any later private command: `makeCanaryWorld` stages stand-in teams from `fixtures/teams/` (private-classed, each Pokemon given a marker nickname) in a throwaway 0700 `private-data` root; `observe` runs a command capturing stdout, stderr, the console, the exception (message, stack, fields, cause chain), extra surfaces the command returns, and every file or file name written outside the private root (and the modes inside it); `findLeaks` / `expectNoLeak` look for markers, species, items, abilities, moves, set lines, team hashes and pastes. `test/private-canary.test.ts` holds the negative controls that show each surface is flagged. Python tests of a later private driver use the same fixture teams and the guard's pseudo-terminal pattern in `tests/ml/private/`.

**Private test** (ADR-015 erratum E1 item 2, #1060; `docs/training-run.md` section 6). `python -m areneon_ml.loop private-test` (owner only, no override) measures a frozen pair of a committed generation on the owner's teams, both seats, counts and scores only. The Python top level (`ml/areneon_ml/private/private_test.py`) runs `assert_owner_session` first, then `assert_private_root` on `--out-root`, then verifies the run exactly as the progress evaluation does (`_source`, now with `allow_private` and `needs_dataset` keywords: a pair with private ancestry reads as `candidate_data_class: private`), and starts the Node child `packages/private-team-store/scripts/private-test.ts` (guarded by `assertGuardedChild`, environment only), which reads the teams, plays through `playPrivateTest` (`packages/showdown-bridge/src/private-test.ts`, built from the progress evaluation's seats: `rowOf`, `tallyRows`, `damageAwareBaseline`, `frozenPairClient`) and prints one line with the record. Python never holds a team; it re-reads the record with its own reader, ties it to the request, writes it (0600, never overwritten; an identical rerun is a no-op) and logs a look (`private-test.looks.jsonl` in the root, the validation look log's format). Sources: `staging` (`PasteDirectorySource`, subset `all`), `snapshot` (the verified local copy through `readPrivateSnapshot`, `src/test-source.ts`, subset `all` = active records or `holdout`) and `dataset` (`datasetValidationPool`). The pair is refused unless it has no private ancestry, or the source is a snapshot's `holdout` or the public dataset (`privateTestAllowed`; the staged directory and a whole snapshot are refused for a private-ancestry pair; the ticket text allows both a public dataset and holdout-only, read here as either). `seed`/pairing/commitment are keyed by a per-test 256-bit salt (`private-test-seed/1`, `private-test-pairing/1`, `private-test-seed.ts`; the salt file stays in the root; the commitment is SHA-256 of the JCS of `{salt, sorted canonical team hashes}`). Plan kind `disjoint-pairs` only; the `all-pairs` option of the ticket (bootstrap over teams) is not built. `PrivateTestRecord` (`packages/schema/contracts/v1/private-test-record.schema.json`, `data_class` const `private`, integers only, closed): the pair's ids and class, the test set (commitment, team and pair counts, source kind, snapshot or dataset hash, subset), the plan, and per match games, wins, ties, losses, turn-cap ties, forfeits by side and cause, pairs and a pair-score histogram (the bootstrap needs the pairs' scores, and a histogram of five counts holds them with no team). Readers in TS (`private-test-record.ts`) and Python (`private/private_test_record.py`) recompute the counts. The interval (`areneon_ml.progress.stats.pair_interval`) is seeded from the commitment and the match id (`private-test-bootstrap/1`), so it is derived from the record alone, never stored, and always labelled `private test set; not the Training gate; not validation`. The corpus samples that carry the private label are listed in `PRIVATE_TEST_RECORD_MARKERS` (`check_data_class.py`; the guard accepts them only in the strict `PRIVATE_TEST_RECORD_SPEC` shape). Every failure is a fixed `private-test: <code>` (and a 1-based team position); the child's stderr is forwarded only if it is exactly such a line. Tests: `packages/showdown-bridge/test/private-test.test.ts` (canary harness with marker nicknames and negative controls, determinism, every refusal), `packages/private-team-store/test/test-source.test.ts`, `tests/ml/private/test_private_test.py` and `test_private_test_record.py`. The real Python worker is not driven by these tests (stand-in clients), and no run ever reads real teams in CI.

**Private team pool for the loop** (ADR-015 erratum E1 item 3, #1061; `packages/private-team-store/src/private-pool.ts`, `showdown-bridge/src/league-generation.ts` `planGames`, `league-seed.ts` `privateTeamSource`). The loop's pool can have a second, private component beside the synthetic one. `loadPrivatePool({engine, format_id, snapshotsDir, snapshot_hash, holdout, excluded_abilities?})` reads ONE pinned snapshot (through `readActiveRecords`, `active-records.ts`, shared with the private test's `snapshotTeams`) from its verified local copy (`private-data/snapshots/<hash>/`, through `readPrivateSnapshot`, the same check as the private test; the staged directory is never a source: it has no hold-out flag), keeps the active records, normalises each team through the pinned validator on a copy (the played form, as `datasetPoolDetail`), leaves out a team holding an excluded ability (and, with `holdout: "exclude"`, every hold-out team), sorts by the record's `canonical_team_hash` and returns `{teams, hashes (teamHash of the played form), holdout flags}`. `withPrivatePool(syntheticSource, pool, share_permille)` is an ordinary `PoolSource` (the bridge cannot import the private package; the private package composes it, nothing depends on it): the pool is the synthetic teams then the private ones, `TrainingPool.private` `{count, share_permille, holdout}` names the tail, and `known_synthetic` is the synthetic pool's own set untouched, so `stampTeam` makes every private team `private`; a private team whose hash is in that set, a pool that already has a private component and a share outside 1 to 1000 are refused. **Plan:** `planGames`/`planGeneration` take a number (as before) or a `PoolShape` (`poolShape(pool)`). With a private component a seat takes its team from it when `privateTeamSource(run_key, generation, game, seat, share)` is true: SHA-256 over the JCS of `{run_key, generation, game, seat, purpose: "league-team-source/1"}`, first four bytes big-endian as n, private when `n * 1000 < share_permille * 2^32` (exact in integers; a Python vector is pinned in `test/league-team-source.test.ts`); the index within the component is the existing `league-seed/1` team draw modulo the component's size, so seeds, baseline streams and, without a private component, every plan byte are unchanged (no extra draw is made). `syntheticDrawnHashes(plan, pool)` (pure, tested) is the `GenerationResult.team_hashes` list that `team-set.json` is written from: synthetic teams only, so a private team's hash is not in that list. `plan.json` is written from the plan and DOES carry private team indices (positions in the pool, no team content, but derived from private data); it is private data of the run. **A generation refuses a pool with a private component for now:** `playGeneration` and `playEntries` throw a fixed `GenerationError` (`refusePrivatePool`), because a private Episode would otherwise be written into the public run directory (`<out>/episodes`) before the loader refuses it; the guard is removed only by the ticket that writes private outputs to the private root (#1063). The inspector and replay tooling (and the dashboard) need a private-aware slice before they read such a run. **Hold-out:** `holdout` has no default (`"include"` or `"exclude"`); a training pool MUST say `"exclude"`: training on hold-out teams is forbidden. Refusals (`PrivatePoolRefusal`, `PRIVATE_POOL_REFUSALS`, words aligned with the private test's) are fixed codes and at most a 1-based position (for `team_invalid`: the place of the team among the active records the load considers, hold-out ones left out under `exclude`, in the snapshot reader's order, counting teams later dropped for an excluded ability) (`source_unreadable`, `snapshot_unverified`, `source_empty`, `team_invalid`, `share_invalid`, `pool_has_private_component`, `synthetic_overlap`), never validator text or a team field. Decision where the ticket left room: the sort key is the record's canonical hash (checked against its paste by the reader), not a recomputed one, so the order does not depend on how the validator normalises. Not here: the run config field and the driver (`play-generation` does not yet pass a private source), the loader's class floor wiring, the bucket download path. Tests: `showdown-bridge/test/league-team-source.test.ts` (vectors, binomial share over 40,000 seats, purity, unchanged seeds and baseline streams), `private-team-store/test/private-pool.test.ts` (stand-in snapshot from the canary harness's teams: pool, stamping, refusals, canary over pool construction and plan writing with negative controls).
