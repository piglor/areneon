# Differential harness and backend admission

The engine-agnostic differential harness of ADR-030 (groundwork G1): the backend port, byte comparison against the pinned engine as the oracle, the `BackendAdmission` ledger, the fresh-corpus rule, the shadow sampler and the self-differential report.

Part of the architecture documentation split out of `CLAUDE.md` (index: [README](README.md)). Ticket references such as `#1461` point to Redmine (`redmine.piglor.com/projects/areneon`), where measured figures and verdicts are recorded.

**What it is for** (ADR-030 common rules 2, 4, 6 and 7; ADR-028 §5 to §7; #1461). Any non-Showdown backend of ADR-030 (step 3's damage kernel, #1457; later the step-5 battle step, via G2) may answer for training games only what it was admitted on by byte-equality with the pinned engine. This harness is the one machinery that compares, admits, revokes and shadow-checks, written once. Showdown is always the oracle. Nothing here is wired into the loop yet: `generation.backends`, routing in the batch seam and the taint record are #1457's (level 1) and the build ADR's (level 2).

**Packages and the seam.** The engine-free core is the workspace package `packages/differential` (`@areneon/differential`, depends on `@areneon/schema` only; imports no engine, bridge or network module and no Node built-in but `node:crypto`; holds no float: a source scan in `test/packaging.test.ts`, as `opponent-model`'s; named by no image or deployment file; depended on by `packages/team-dataset` alone and imported only by its `differential*.ts` files, so no evaluation path reaches it). Limit of that scan: it reads import statements (`from`, `import(`, `require(` of the package name) in tracked TS and JS files; a path that reached the package by another route (a re-export from the composition root, a dynamic specifier built at run time) would not be seen, so a consumer outside the composition root is caught at review, and the composition root's index does not export the harness. The bridge stays the engine's owner and does NOT import the core: `packages/showdown-bridge/src/differential-probe.ts` declares its shapes structurally (`ProbeBackend`, `QueryFacts`), and the composition root `packages/team-dataset/src/differential-mechanics.ts` joins the two, as `createSearchWorlds` joins the opponent model.

**Backend port** (`backend.ts`). `Backend<In, Out>` = `{id, backend_format, backend_commit, run(batch) -> Settled<Out>[]}`: a batch in, outcomes in input order, a refusal kept as the input's outcome (the `BatchRunner` of the batch seam, `probe-batch.ts`, and `FeaturePool.run` already return exactly this). A `Level<In, Out>` says how one level is compared: `entities(in)` and `exercised(in, oracleOutcome)` (sorted `<kind>:<id>` strings; exercised read from the ORACLE's outcome), `key(in)` (a stable key: level 1's query hash, what a corpus's content hash and the shadow sample are keyed by), `answers(in, out)` (an output names its input), `bytes(out)` (compared by JCS bytes) and `errorKey(error)` (a refusal's class and fixed words). Level 1 is the mechanics-query level (`In` a parsed mechanics query, `Out` its `MechanicsResult`); level 2 (a battle step and its player view) is G2's adapter on the same core.

**Comparison** (`compare.ts`, `harness.ts`, `tally.ts`). `compareBatch` runs the inputs through both backends and compares item by item: `value` (JCS bytes differ; `field` is the JSON path of the first difference in sorted key order, e.g. `$.answer.no_crit[3]`), `refusal` (both refused, differently), `settled` (one answered, one refused), `answer` (the backend's output names another input: a reordered or misattributed answer), `missing` (no outcome), `count` (the batch came back with another number of outcomes than inputs: an extra or a dropped result; every item of the batch that otherwise compared equal is a `count` difference, so every entity of the batch is revoked, and the tally's `count_mismatches` blocks any admission). The oracle must answer every input (a `HarnessError` otherwise). `runCorpus` compares a corpus in batches into a `CorpusTally`: per entity `present`, `exercised`, `equal` (equal exercising items), `differing` and the first difference's position; per pair (fresh corpora only) `co_present`, `co_exercised`, `co_equal`; every difference with its reason, field and entities.

**Level-1 entity and exercising rule** (`mechanics-level.ts`, reviewed; the facts come from the bridge, which reads each query's own sets with the pinned engine's `importPaste` and its declared state, so no list of game content is written in the core). Entities: the query kind; each Pokemon's species forme (an evolved Mega by the forme its stone's engine data makes), ability, item, set moves, declared status and declared history volatiles; the moves the actions use; declared weather, terrain, Trick Room, side conditions and pending slot conditions. Exercising: always the kind; nothing else on a refusal or a `refused` result; on `unsupported`, the used moves only when the move itself decides the reason (`query_kind`: a status, fixed-damage or multi-hit move), the kind alone for any other reason (a random effect an item or ability may cause, an unknown history fact, the scenario rule table); a computed `stats` answer the species; `damage` the used move, both Pokemon's species, ability, item and status, and the declared field and sides; `speed_order` the same over every combatant; `move_outcome` that plus the declared volatiles and slot conditions. Unused set moves and volatiles outside a move outcome are present but never exercised (no evidence claimed for what the answer may not have read).

**The ledger** (`BackendAdmission`, `packages/schema/contracts/v1/backend-admission.schema.json`, generated TS and pydantic types, corpus samples `fixtures/contracts/v1/backend-admission/`, readers `admission.ts` `readBackendAdmission` and `areneon_contracts.backend_admission.read_backend_admission`; integers only, closed, `data_class` synthetic, `rule` `admission/1`). It names the level, the backend (`kind`, `backend_format`, `backend_commit`), `showdown_commit`, every corpus (`id`, `kind` fresh / regression / shadow, `seed`, `pool_hash` (what the items were drawn from), `content_hash` (SHA-256 over the JCS of the pool hash and the sorted item keys), `tally_hash` (SHA-256 over every count of the tally, pairs included), `items`, `distinct_items`, `count_mismatches`), every entity with its per-corpus counts, its `kinds` (per query kind, the fresh items that exercised it with that kind) and `admitted` flag, the listed pairs and the revocations. `admission_hash` (`admissionHash`, `admission_hash`) is SHA-256 of its JCS bytes: the hash `generation.backends` will name. A committed ledger is written in its lines form (`admission-lines.ts` `admissionLines` / `readAdmissionLines`; Python `backend_admission_lines` / `read_backend_admission_lines`): a header line, then one canonical line per entity, pair and revocation in the ledger's order, which reads back to the same ledger and hash and diffs line by line (#1457). **Rules** (`buildLedger` writes them, both readers recompute them): nothing is admitted unless the ledger holds one fresh corpus of at least `MIN_FRESH_ITEMS[level]` distinct items (200,000 at both levels: ADR-030 step 3 gate 3, ADR-028 section 5; at least 3 x `PAIR_ODDS`, so a pair at the listing threshold is expected three times) and no corpus has a count mismatch ("nothing is admitted without a fresh corpus of the level's minimum size and with any count mismatch"); then an entity is admitted iff the fresh corpus holds at least `N_EXERCISED` = 20 exercising items, all equal, no corpus has a difference naming it and it is not revoked; regression and shadow counts never admit, and a ledger that admits from them is refused with "admission evidence must come from the fresh corpus"; a pair of admitted entities present together in at least 1 in `PAIR_ODDS` = 10^4 fresh items is listed and admitted iff at least `N_PAIR` = 5 fresh items exercise both, all equal (a listed pair that is not admitted routes to the oracle; rarer pairs are covered only by the shadow check, ADR-028 §5's accepted residual); any difference revokes every entity of its item, recorded at the first corpus (in id order) that found one; `withCorpus` adds a regression or shadow tally later (admission only falls; a fresh corpus is never added later). A fresh corpus holds each item once: its tally refuses a repeated key (`TallyError`, "draw without replacement") rather than counting distinct keys, so a draw with replacement or copies of a few queries fail where they are made instead of quietly giving a smaller corpus than it claims, and every count of a fresh tally (items, exercised, pairs, kinds) is a count of distinct items; the ledger records `distinct_items` and both readers require it equal to `items` for a fresh corpus (and at most `items` for any). A test feeds 200,000 copies of 100 queries and requires that nothing is admitted. Entities are not scoped by query kind (an entity admitted from damage queries says nothing about move outcomes), so routing also needs each entity co-exercised at least `N_PAIR` times, all equal, with each query kind the query names; every unseen or thin kind x entity pair routes to the oracle. `verifyLedger(ledger, tallies)` holds a ledger to the corpora it claims: every corpus's content and tally hash and the whole ledger must be what `buildLedger` gives, so a hand-edited ledger (a pair or count dropped) is refused; `withCorpus` equals `buildLedger` over all the tallies. **Pin:** a ledger whose `showdown_commit` is not the reading checkout's is refused ("every query routes to the engine"), so a pin bump empties admission. **Routing:** `admissionRouter(ledger | null).route(entities)` takes only a ledger the reader returned (deeply frozen, then held in a `WeakSet` of read ledgers; any other object is refused) and is null when the backend may answer, else `{kinds: n}` when the query does not name exactly one query kind, the first unadmitted entity, the first unseen or thin kind x entity pair, or a blocked pair (for run metrics).

**Fresh corpus by construction** (ADR-030 rule 7, PokaiEngine's warning). `freshSeed(backend)` is SHA-256 over the JCS of `{backend_commit, backend_format, purpose: "differential-fresh/1"}`; `freshCorpus(backend, pool, draw)` calls `draw` with that seed and nothing else, records the pool it samples from and names the corpus `fresh-<first 16 hex>`. The readers refuse a fresh corpus whose seed is not the backend version's and a second fresh corpus. So the admission corpus cannot exist before the backend version is frozen, and corpora used to debug it (kind `regression`) are counted and reported, never evidence.

**Shadow sampler** (`shadow.ts`). #1195's bottom-k (`inference-divergence.ts`): an item's key is the first 8 bytes of SHA-256 over the JCS of `{key: <stable key>, purpose: "differential-shadow/1"}`, the sample the smallest keys (ties by position), so the same items are sampled whatever order they were answered in. One function; the size rule is a parameter: `LEVEL_1_RULE` max(1% of backend answers, 256), `LEVEL_2_RULE` max(5% of games, 64), never above n, integers only (`shadowSize` equals the bridge's `sampleTarget` for level 1; a test holds them equal). `shadowCheck(level, oracle, inputs, recorded, stableKey, rule)` recomputes the sample with the oracle and compares it with the answers the generation actually used (`recorded`, one per input; the backend is never asked again) and throws a typed `ShadowDivergence` on any difference (its `differences` and the sorted `entities` to revoke); when `recorded` is not exactly one answer per input it throws with `whole_backend` set and every sampled item's entities: stop the generation and revoke the backend. Wiring it into the loop and the taint record is not here.

**Oracle and composition root** (`differential-probe.ts`, `differential-mechanics.ts`). `probeBackend(engine, {config, snapshot?, damage_path?, id?})` is the pinned probe through `batchOf` (format `MECHANICS_ADAPTER_FORMAT`, commit the engine's); a second `loadEngine()` object has its own per-engine probe tables, so two oracles are two instances. `queryFacts(engine)` reads a query's facts. The composition root collects the queries the feature builders themselves issue: every request (but `wait`) of both seats of a committed battle is built with `probe-damage/2` and `probe-outcome/1` through their generator form (`buildFeaturesG` driven by `driveSync`, one memo per game and set, as in play), every yielded query recorded once; the oracle answers each as it is asked (`remembering` keeps its outcomes by query hash, so the builders' run and the comparison share one probe call). Every probe answer is made under the outcome set's mechanics config (a superset of `/2`'s query kinds).

**What the self-differential checks.** Both engine objects come from `loadEngine()` in one Node process, so they share Node's module cache: the same simulator code and data objects. The comparison therefore checks the probe's own determinism and its per-engine caches (kept scenario starts, rule tables, validated sets, all keyed by the `Engine` object), and that the harness itself (collection, comparison, tallies) finds no difference where there is none; it is not a comparison of two independent engine builds. **Self-differential report** (gate 1; `scripts/differential-report.ts`, `fixtures/showdown/<format>/differential/self-report.{json,md}`, generated like ADR-026's fidelity report; do not edit). The probe on one engine object against the probe on a second, over the random, search-fidelity and unavailable corpora as regression corpora; per corpus items, differences by reason and first differing field, count mismatches; per entity present, exercised, equal and differing summed over the corpora; entity kinds. Its `inputs` (harness format, pin, `MECHANICS_ADAPTER_FORMAT`, the feature sets and their `feature_set_hash`es, the mechanics, damage-aware and outcome config hashes, each corpus's files hash, and `sources_sha256` over every file the probe backend (`differential-probe.ts`), the builders' dispatch (`feature-build.ts`) and the core reach through their imports, followed from those roots (relative, workspace and schema imports and the shared reader's `createRequire` of `interpreter.cjs`; registry packages are pinned by the lockfile), plus the composition root itself, so a change of any file they import (for example `teams.ts`) makes the report stale; a test shows an edited `teams.ts` changes the hash) are recomputed by `test/differential-mechanics.test.ts`, which fails on a stale report and re-renders the Markdown from the JSON; CI also runs the self-differential on the first battle of each corpus (zero differences, every entity kind tallied). The full run is about half an hour of probe work on one thread (`--part` per corpus in separate processes, then `--merge`). **Result at pin `7244fe8e`:** 509,737 distinct queries (random 95,718 from 3,218 builds; search-fidelity 407,990 from 13,306; unavailable 6,029 from 156; 28 builds refused by the builder itself, `reader_flagged` and `assumed_set`), zero differences, 1,229 distinct entities tallied (species 371, move 440, ability 200, item 166, volatile 28, status 6, weather 4, terrain 4, side 3, slot 2, field 1, the four query kinds). The run took about 6, 29 and 0.4 minutes per corpus on one thread each at nice 19 on a shared machine, under 1.2 GB per process once it streams battle by battle.

**Negative controls** (gate 2, `test/differential-mechanics.test.ts`, real probe on the first random battle's queries): a backend that perturbs one roll of one move (`value` at `$.answer.no_crit[3]`, only items with that move, each naming it), one that swaps the crit vectors (`value` at `$.answer.crit[i]`), one that returns `unsupported` with another reason (`value` at `$.reason`), one that answers out of order (`answer` on every item, with the item's own entities), one that drops a result (`answer` from the dropped item on, `missing` last, a count mismatch); the shadow check throws `ShadowDivergence` on a broken backend and passes the probe. A ledger from a fresh corpus drawn by the backend's own seed over those queries admits `kind:damage`, routes, and is refused at another pin. The arithmetic edge cases (gate 3) are `packages/differential/test/admission.test.ts`: 20 against 19 exercising items, equal counts, presence without exercise, a pair at 5 and at 4 and a rare pair, revocation and its first corpus, `withCorpus` from a shadow sample, regression evidence refused, another pin refused, every reader rule; the corpus samples are read by both readers (`packages/differential/test/samples.test.ts`, `tests/contracts/test_backend_admission.py`) and classified alike by `make contracts`.

**Not here:** the damage kernel and `generation.backends` (#1457), any routing in the batch seam, any run that uses a backend. The battle level is G2, below.

## Level 2: the battle step (G2)

Groundwork G2 (#1462; ADR-028 section 5 F0 and the protocol path of its differential, ADR-030 step 5 and rules 1, 2, 7). A battle backend is driven by forced-draw traces of the unmodified pinned engine and compared with it request by request, so the M-D battle-engine spike starts with a working oracle. Nothing here is a non-Showdown backend, a projection (G4), a natural-draw test or loop wiring.

**Where it lives.** The engine-free half is in `packages/differential` behind its own entry point `@areneon/differential/battle` (`src/battle.ts`, so level 1's self-differential report, which hashes every file the main entry reaches, does not depend on it): the port (`battle-backend.ts`), the trace reader (`battle-trace.ts`), the comparison (`battle-compare.ts`), the entity and exercising rule (`battle-level.ts`), the interaction classes (`battle-classes.ts`), the corpus run and its summary (`battle-corpus.ts`, `battle-report.ts`). The engine side is in the bridge: the recorder and the random sources (`battle-trace.ts`), the Showdown battle backend (`battle-replay.ts`), the committed battles (`battle-trace-corpus.ts`); the bridge does not import the core and declares the port's shapes structurally. The composition root is `packages/team-dataset/src/differential-battle.ts` (and `scripts/differential-battle.ts`).

**`BattleTrace`** (`packages/schema/contracts/v1/battle-trace.schema.json`, generated TS and pydantic types, samples `fixtures/contracts/v1/battle-trace/`, reader `readBattleTrace` in the core; `data_class` synthetic, strings and integers only, `trace_format` is the recorder's `TRACE_FORMAT`). Per battle: the pin, format, seed, both teams as brought and their `team_hashes`, the outcome (winner or null, turns) and the steps. A step is the engine's work between two requests: step 0 is the start (no action), every later step the run of writes up to and including the next write that emitted a request or ended the battle. A step holds the actions written (a seat's `choice`, or the runner's `forcetie` command, in order), every call the battle made on its random source in order (`method`, `args`, `result`; numbers as their shortest decimal strings, so a `random()` real is exact; `sample` records the length and the index drawn, `shuffle` the length, the range as passed and the permutation), each player's channel lines and the omniscient lines emitted (`|t:|` dropped), each seat's requests (`request_seq`, `request_hash`, and unless a wait request or the battle has ended the `mask`: every candidate in canonical order with its verdict, `legal`, `pending_legal` or `pending_illegal`, the engine's `CloneJudge` on the battle at the step's end), and `state_sha256`, the SHA-256 of the JSON text of the engine's `toJSON()` after the step with the log's wall-clock `|t:|` lines dropped (the only non-reproducible part). Reader rules: only step 0 has no action, each seat's requests are numbered 1, 2, ... across the steps, each team hashes to its entry, and the last step, and only it, ends the battle. A trace holds both sides' hidden information: an evaluation artifact, never an Episode, never actor input; only the hand-made samples are committed. The full `toJSON` is not stored (about 100 KB a request): its hash is, and a replay on the oracle rebuilds the state that has it.

**The recorder** (`recordBattleTrace(engine, spec)`). `runBattle` plays as it always does on the unmodified engine; the engine's `BattleStream` is replaced by a subclass (`tracedStreamClass`) that reports every write, input line and engine message synchronously and, right after `>start` builds the battle, installs a recording source in place of `battle.prng` (`installSource`, the one assignment of this file, allowlisted in `fidelity-isolation.test.ts`). The source (`interceptedSource`) is a Proxy over the engine's own generator: `random`, `randomChance`, `sample` and `shuffle` run on the generator exactly as the engine would run them (`sample` and `shuffle` on an index array, so their answers are integers) and every other string-named function member but `getSeed` and `clone` is called on the generator and recorded too, so an unexpected member is a draw the comparison sees, never an exception class. The channels are split from the engine's messages as `getPlayerStreams` splits them (its `|split|` rule; an update with no line for a player gives that player one empty line, as the player stream does). At the end of each step the recorder judges the step's requests on the live battle (`stepRequests`); where the runner judged a request too, its legal set and hidden verdicts must equal the mask (`agreesWithRecord`). Judging at the step's end makes a mask a function of the battle: the runner's turn cap (`forcetie`) can overtake a player loop, so the runner leaves the last requests of three random-corpus battles unjudged where the trace judges them. A forfeit (a `forcewin` the trace has no action for) is refused.

**The port** (`BattleBackend`): `{id, backend_format, backend_commit, start(batch of {battle_id, format_id, seed, teams, draws}), step(batch of {handle, actions, draws}), release(handles)}`, each call one `Settled` outcome per input in input order. An output is per seat the channel lines and requests (identity and mask) of the step, the draw requests made with the answers used, `ended`, `winner`, `turns` and, when the backend has the engine's state, `state_sha256`. `project(handle, seat)`, the player-view tensors, belongs to the port and is filled by G4 (#1464).

**The Showdown battle backend** (`showdownBattleBackend(engine, {snapshot?, id?})`, `REPLAY_FORMAT` 1). It validates both teams as the runner does (on copies) and drives the engine's own `BattleStream` with the runner's exact chunks (one `_write` per start chunk, choice and command), its `battle.prng` replaced by the forcing source (`forcingSource`): a call is answered from the step's forced draws when its method and arguments equal the next one's, else by the engine's generator, which advances in lock step either way, so the engine's serialised state stays its own; every call is reported. The masks are `stepRequests` on its own battle, as the recorder's. A second `loadEngine()` object is a fresh engine instance with its own tables, but shares Node's module cache (the same simulator code), as at level 1.

**Comparison** (`compareBattles(backend, traces, batchSize, listen?)`, `compareStep`). The live battles of a batch are stepped together; a battle leaves its batch at its first difference or its last step. At every step, in this order: (1) each player's channel lines other than requests, byte-equal (`channel`); (2) each request, its `|request|` line byte-equal and its number and `request_hash` equal (`request`); (3) every candidate's verdict, pending ones included, and a mask present on both sides or neither (`mask`); (4) the draw requests, method and arguments, as one joint sequence (`draws`), then the state hash when the backend gives one (`state`); (5) the end where the trace ends, the winner and the turn count (`outcome`). A refused start or step is `refusal`, a batch with another number of outcomes than inputs is `count` for every battle of it. The first difference is `{kind, step, seat, where}`, `where` fixed words (a line or candidate index, never a line of the battle).

**Entities and exercising** (`stepFacts`, reviewed; ADR-026 slice F's carrier rule, written again here because `test/fidelity/` is test code). Present at a step: every species, ability, item and move of both teams as brought, plus everything an earlier or this step exercised. Exercised at a step, from its omniscient lines: each `|move|`'s move; the shown species, ability and item of every Pokemon that acted (`|move|`, `|cant|`); the species a switch, drag, replace or forme change shows; the ability, item, effect (`move:`, `ability:`, `item:` prefixes keep their kind, else `volatile:`), status, weather, field (`field:`) or side condition (`side:`) a line names directly or in a `[from]` tag. Every compared step is one item of the level-1 `CorpusTally` (key: SHA-256 over the JCS of the seed, step and team hashes), so per-entity and pair tallies and the admission ledger work unchanged at level 2.

**Interaction classes** (ADR-028 section 5 "Interactions (2)"; `config/differential/battle-interaction-classes.v1.json`, read by `readInteractionClasses`, hashed by `classesHash`). The reviewed data file holds every word that names game content; a class matches a step when each group of its `all` list has a signal the step shows: a draw of a method (the speed-tie class is the engine's `shuffle`), or an omniscient line of a type, optionally holding a text or a `[from]` tag that starts with a text (an empty one: any tag). v1's classes: `faint_replacement`, `item_consumption`, `mega_timing`, `protection_multi_target`, `redirection`, `residual_order`, `speed_control` (Trick Room, Tailwind, Quick-Claw-like effects starting or acting), `speed_order_tie`, `switch_in_trigger`, `weather_terrain_readers`. They tag the steps whose lines show the interaction, not every step a condition is active in (a state-based classifier is the spike's to add, with its own coverage). A class added later is a new file version.

**Fresh corpora** (`freshSpec`, `battleFreshSeed`). Battle `i` takes the mix `uniform-all`, `random-legal` or `pending-first` by `i mod 3` and its seed, teams and actor seeds from `leagueGameStreams(<fresh seed>/<mix>, 1, i)` (the reducer sweep's draw, `sweepActors`) on the loop's own pool function (`datasetTeamPool`: the dev and training splits of a verified dataset, never validation); the fresh seed is G1's for the Showdown battle backend's version (`freshSeed({backend_commit, backend_format: REPLAY_FORMAT})`). The size is a parameter (200,000 for admission is the spike's).

**Tests and gates.** Gate 1 (every committed battle: golden, the random-play corpus, `unavailable/`, the singles baton-pass, baton-pass-volatiles, fling, illusion, revival and side-guard, and the 200 battles of `search-fidelity/`; recorded and replayed on a second engine object, zero differences at every step of both seats): `packages/team-dataset/test/differential-battle.test.ts` and `differential-battle-targeted.test.ts`. `transform/battle.json` is not replayable (it was cut from a league game and holds no choices) and is left out. Gate 2 (broken backends, each caught with its kind, step and seat): a forced `random(16)` roll off by one and a flipped forced chance draw (`channel` at their step), two draw requests reported in the other order with the same answers and lines (`draws`), a `-damage` line dropped from one seat (`channel` for that seat), a skipped residual (`channel`), a changed request body with its hash recomputed and a request with a missing field (`request`), a pending candidate made legal (`mask`), a wrong winner (`outcome` at the last step), a dropped result (`count`). Gate 3 (a trace is the runner's own record: the concatenated omniscient lines and channels equal `runBattle`'s `omniscient_log` and channels, the same requests, choices, legal sets, hidden verdicts, winner and turns; recording twice gives the same bytes): `packages/showdown-bridge/test/battle-trace.test.ts`, which also holds the random sources against the engine's generator, the channel split and the backend's refusals. The core's own tests (`packages/differential/test/battle-*.test.ts`) drive an echo backend with hand-made traces through every difference kind. Isolation (ADR-030 rule 1): `packages/showdown-bridge/test/battle-trace-isolation.test.ts` requires that only the bridge's own battle files, the core and the composition root's `differential*` files name the recorder, the backend or the committed-battle list, and never an evaluation, progress, private-test, sealed or A2 path. The migration suite runs the three gate files as `battle-differential` (`make migrate-check`, docs/runbooks/migration.md).

**Size check** (gate 4; `node packages/team-dataset/scripts/differential-battle.ts --battles 2000`, one thread at nice 19 on a shared machine, pin `7244fe8e`, the committed `fixtures-v1` dev pool of 120 teams, 100-turn cap): 2,000 battles (110 teams: the 120 dev teams minus Illusion holders, the run configs' exclusion; 42,086 steps, every one compared, none unreached), **zero differences**. Wall time 16 min 5 s (record 290 ms and forced replay 193 ms a battle, about 0.48 s in all), trace 318 KB a battle as JSON on average and 885 KB at most, peak RSS 1.06 GB (the fresh tally's pair counts grow with the corpus; the traces are dropped chunk by chunk). For the spike's 200,000 battles that is about 27 hours on one thread, or 64 GB if the traces were kept. Every exercised entity was equal: species 323, moves 386, abilities 173, items 148, volatiles 58, side 8, field 8, status 6, weather 4. Interaction-class steps (tagged, all equal): faint_replacement 10,414, residual_order 10,034, speed_order_tie 5,473, switch_in_trigger 3,383, weather_terrain_readers 2,551, mega_timing 1,936, item_consumption 1,478, speed_control 704, redirection 142, protection_multi_target 75. At this size protection_multi_target and redirection are below ADR-028's 200 exercising turns per class; at the spike's 100 times the size they would clear it. These figures are from one shared machine and are not claimed to repeat.
