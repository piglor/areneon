# Progress evaluation and reports

The progress evaluation, head-to-head tools, diagnostics, the look log and the run dashboard.

Part of the architecture documentation split out of `CLAUDE.md` (index: [README](README.md)). Ticket references such as `#1179` point to Redmine (`redmine.piglor.com/projects/areneon`), where measured figures and verdicts are recorded.

**Evaluating a pair that reads candidate features** (ADR-022 §6, §7, #1181; the progress evaluation, its head to head and the private test). No contract changed and a pair without the option keeps every byte, id and record. The seats of a run whose config sets `candidate_features` build the rows with the builder `policyActor` uses in training: `pairFeatureSetup(engine, config)` (`progress-cli.ts`, `featureSetup` with a usage error) names the feature set from the run's config, fails closed when this checkout computes another hash, and gives the pair's `PolicyWorkerClient` its statement (`FrozenPairClientOptions.features`; the handshake checks the worker's `ready.feature_set` against it) and `ProgressOptions.features` / `PrivateTestOptions.features` the `FeatureConfigs`, which every seat of that run (the candidate, previous generation, anchors, the ablation's Previews) carries as `PolicySeat.features`. A build failure forfeits the game as `crash` like any policy failure (a latency overrun is a scored loss), nothing is invented. **Each run has its own statement:** for a head to head (`--versus-dir`) or the private test's `--opponent-run-dir` the Node side reads that directory's `run-config.json` itself (the progress command checks it against the `--versus` run config hash) and sets that pair up from ITS config, so a features pair against a no-features pair gives each seat its own worker, statement and rows (the DF2 control); the client option falls back to the evaluated run's setup only when no pair is passed, never for another run's pair (`null` means none). **Policy ids:** Python derives every id with `policy_id(..., features=features_hash(config))` from the config of the run the pair belongs to (candidate, previous, anchor, ablation, `_versus_pair`, the private test's pair and opponent), so they equal the training ids; `read_progress_record` (`_check_run`) recomputes the candidate's and the same run's previous and anchor ids, and leaves a `run` opponent's id to `_check_versus` at evaluation, against THAT run's config (the record does not carry it; a read-back root does not recompute it, which also lets a no-features candidate meet a features run and two different feature sets meet). Latency and the family label are unchanged (the dashboard names the pair). Tests: `packages/team-dataset/test/progress-features.python.test.ts` (real workers and probe: a features run and a plain run, baselines, anchor, previous, head to head, ids equal to `policyId`, no forfeit, byte-identical rerun), `tests/ml/progress/test_features.py`, `packages/showdown-bridge/test/private-test.test.ts`.

**Progress evaluation** (ADR-017 slices 4 and 5, `packages/showdown-bridge/src/progress-*.ts`, `packages/team-dataset/src/progress-pool.ts`, `packages/team-dataset/scripts/progress.ts`, `ml/areneon_ml/progress/`, `python -m areneon_ml.loop progress`; the docs section is `docs/training-run.md` section 4). A progress view of a committed generation, never the Training gate: the frozen pair plays `random-legal@v1` and `actor-rule@v1`, each in sample and argmax mode, on the VALIDATION split of the run's `team_dataset` (a run without one is refused), read through `readDataset` (`datasetValidationPool`; the bridge cannot import the team-dataset package, so `runProgressCli` takes the pool as a port, as `runGenerationCli` does). Design B-i (version 1 records; a version 2 record plays pair `k` twice, see below): game `k` of every match is the disjoint ordered validation pair `k` (`progress-pairing/1`: SHA-256 order of `{run_key, canonical_team_hash, purpose: "progress-pairing"}`, cut into consecutive pairs; more games than pairs is refused, never wrapped) with the seed of `progress-seed/1` (`progressGameStreams`: SHA-256 of the JCS of `{run_key, game, purpose: "progress-game"}`, bytes 0 to 15 the battle seed, bytes 16 to 19 the baseline stream; the ADR vector is pinned in TS and Python), the candidate on p1 for an even game and p2 for an odd one, no seat swap (v1). The same pairs and seeds serve every opponent, mode and generation. Refused before any game: a validation team whose played-form hash is in the newest generation's `team-set.json`, a progress seed equal to a seed of any committed `plan.json` (checked in TS and again in Python, at evaluation time against the plans committed then: a later generation's plan is not covered by an earlier record and generation 0 sees no plans yet; the practical risk is about 2^-128 because the purpose strings differ), more games than the pairs allow (v1: `--games` above half the dataset manifest's validation teams; v2: above the number of validation teams, two games per pair; Python checks before the worker starts, Node refuses exactly), a non-synthetic checkpoint record. A1 `policyGame` with `guardActor`, one worker query at a time (`n_parallel` 1), worker on CPU; a policy forfeit is a scored loss for the failing side with its cause, a harness incident fails the evaluation and commits nothing. The contracts are `ProgressEvaluationRecord` and `ProgressGameRecord` (`packages/schema/contracts/v1`, integers only, `data_class` the constant `synthetic`; the `previous` opponent variant carries the previous pair's checkpoint ids). The readers (`progress-records.ts`, `areneon_ml.progress.records`) add the rules the profile cannot say: counts equal the game rows, matches sorted and unique, rows complete with alternating seats, forfeits and turn-cap ties recounted, a stored game's choices among its candidates, team hashes, `omniscient_log_sha256` (SHA-256 of the JCS of the log's lines) and the seed recomputed; the Python reader also ties a record to its run config and checks each policy id from its checkpoints and mode (`policy_id(preview, battle, mode)`; sample and argmax are different policies). The Wilson interval (`progress/stats.py`, integer arithmetic only, parts per million) is derived on display, never stored, and always labelled "conditional on the fixed validation plan" (a deviation from protocol 6.2: an erratum candidate). For a schema-version-2 record (every pair from both seats) the games are not independent, so `summary_of`, the dashboard and the ablation use the pair-level percentile bootstrap instead (#948, ADR-017 E2 items 2 and 6; `stats.pair_interval`: 4,000 resamples of pairs, ranks 100 and 3,899 of the sorted integer sums, a SHA-256 counter stream seeded from the run key, generation and statistic label, parts per million rounded outward; labelled descriptive and conditional, no multiplicity control; `docs/training-run.md`); version 1 keeps Wilson unchanged. **Both seats, anchors, schema version 2 (ADR-017 erratum E2, #939 and #947).** A new evaluation writes a `ProgressEvaluationRecordV2` (`progress-evaluation-record-2.schema.json`, `schema_version` 2, beside the unchanged version 1; `readProgressEvaluationRecordV2` and `read_progress_record`, which dispatches on `schema_version`; a v1 root is verified and kept, never rewritten; what this paragraph's predecessors say about alternating seats, one game per pair or game index `k` describes v1). Every validation pair is played TWICE: game g is pair g>>1, the candidate on p1 for an even g and p2 for an odd g, the teams stay on their seats and both games share the pair's `progress-seed/1` seed (`ProgressGameRecord` gained the optional `pair`, its seed then being the pair's; the sampling `u` still differs because the seat is in its label), so `--games` is even and the pair is the unit of analysis. Anchors: `--anchors 0,10,20` (those earlier than the evaluated generation), `--anchor-games` (even, default 200), matches `anchor-g<A>-<mode>`, opponent `{kind: "anchor", generation, policy_id, checkpoints}`, one worker per anchor (`--anchor G,PREVIEW,BATTLE,POLICY_SAMPLE,POLICY_ARGMAX` and `--anchor-games` on the Node side; the fields are comma separated because a policy id holds a colon); `plan.anchor_games_per_match` is present exactly when anchor matches are, `teams.pairs_used` is half the largest games. The Python side verifies each anchor's checkpoint and policy ids from generation A's own records (`_check_anchors`, at evaluation and on verification). Not here, a separate ticket: the replay pages for v2 (#951); `summary_of` and the dashboard give the pair-level interval (#948, below). **Team Preview ablation (#940).** `python -m areneon_ml.loop progress --generation G --preview-ablation` (G >= 1, alone: no `--anchors`, no `--previous-matches`, not `--all`) plays G's Battle network, argmax, against `random-legal@v1` and `actor-rule@v1` with (i) its own Preview, (ii) a uniformly random Preview and (iii) generation 0's Preview, as six `preview-<learned|random|g0>-<baseline>-argmax` matches of a `ProgressEvaluationRecordV2` (optional match field `candidate_preview` `{kind: learned|random|generation(+generation, checkpoint)}`; same pairs, seeds and both seats). The random Preview is `policyActor`'s `preview_actor` (`PolicySeat.random_preview`): `randomLegalActor` over the engine-judged `request.legal` of the candidate's OWN Preview request, seeded by `randomPreviewSeed` (the first 8 hex digits of SHA-256 over the JCS of the policy stream label of seed, pair, seat and `random-preview@v1`); the worker is not asked, `assertOwnTeamStats` still runs. Generation 0's Preview runs in a third worker (`--ablation-preview GEN,PREVIEW,POLICY_ID_ARGMAX` and `--ablation-random-policy-id` on the Node side; the worker takes any Preview and Battle pair). A candidate's policy id is `policy_id(preview or 'random-preview@v1' or the earlier checkpoint, battle, mode)` (`candidate_preview_id`); the Python side checks the earlier Preview against that generation's own records (`_check_ablation`). `progress/ablation.py` derives, per baseline and variant, the mean pair score and, against the learned Preview, the mean paired difference and the better/equal/worse pair counts, in integers, each with its pair-level interval (#948). The Python command reads the run read-only (no run lock; the generation manifest is verified), builds `<run-dir>.progress/.g<N>.partial` (never inside the run), has Node write `progress.json` and `games/<match>-<k>.json` (the first `--record-games`, default 8), re-reads and cross-checks every file, then writes `manifest.json` last and commits with one `os.replace` under an `flock` on `.lock`; a committed directory is verified and skipped, never rewritten. `--all` evaluates the committed generations whose number is a multiple of 5, generation 0 included (`scheduled_generations`, `SCHEDULE_EVERY`; ADR-017 E2 item 3, #950); `--generation G` evaluates any one. **Previous-generation matches (slice 5, #924; opt-in since E2, #950).** With `--previous-matches` (`progress_generation(previous_matches=True)`; off by default, a no-op at generation 0) the pair from generation 1 also plays the previous generation's frozen pair `P_(G-1)`: `previous-sample` (sample against sample) and `previous-argmax` (argmax against argmax), 6 matches instead of 4. The plan, pairs, seats and seeds are the baselines' exactly (`progress-seed/1` has no match identity: the ADR reuses game index `k` across matches on purpose, and `previous-*` games hold a different pair of policy ids, so the sampling draws `u` (hashed over seat and policy id) differ); the match row names the opponent as `{kind: "previous", policy_id, checkpoints}` with the checkpoint ids of generation G-1, and the printed summary labels it "seen, same-lineage comparison: it can cycle". One worker session holds one frozen pair, so `runProgressCli` starts a second `PolicyWorkerClient` for `P_(G-1)` (flags `--previous-preview|battle|policy-id-sample|policy-id-argmax`, all or none; both clients `beginGame` before each previous game) and each seat queries its own client; a Python request carries `previous: PreviousPair` (None at generation 0 and whenever the flag is off; the status says `none: generation 0 has no previous generation` or `none: previous-generation matches are opt-in ...`). `_check_previous` refuses a record with `previous-*` matches that were not asked for, one asked for without both, and any whose opponent checkpoints or policy ids are not the verified generation G-1's. The runner records a choice when its actor answers, which with two workers can come in either seat order, so `buildProgressGameRecord` stores the decisions ordered by `request_seq` then seat (without it two reruns of a previous match differed in bytes). A root committed by slice 4 has no previous matches at generation 1 and up: it is verified and skipped, never rewritten (a committed generation without them is skipped whatever the flag says), and the output says `previous: none: ... evaluate into a new --progress-dir to add them` (a progress root is atomic per generation, so adding matches would mean a second record version; a new progress dir gives the same baseline bytes again). (Evaluation cost: see #940.) The game records hold the omniscient log of both sides: an evaluation artifact for the owner, refused by `readEpisode` and the training loader (a test passes one to the loader). The corpus samples avoid the `private` label (the guard refuses it anywhere), so the class tests flip it in code.

**Extra play modes and the play-mode gap** (ADR-023 section 1, section 2, #1044 and #1042; `packages/showdown-bridge/src/progress-modes.ts`, `ml/areneon_ml/progress/modes.py`, `gap.py`; the docs paragraph is `docs/training-run.md` section 4). `progress --modes sample:t<ppm>,sample:th<ppm>,sample:t<ppm>:th<ppm>` (a closed grammar, ppm 1 to 999999, an explicit 1,000,000 refused; `argmax` and `sample` are always played and may be listed) adds extra play modes, each a sample at a declared temperature and/or probability threshold, to the baseline matches (`random-legal@v1`, `actor-rule@v1`, `damage-aware@v1`/`v3`) and, with `--versus-run-dir`, to the head-to-head with BOTH sides in the mode (the other run's pair gets its own policy id in the mode, computed from its checkpoints and its own feature hash); anchors and previous-generation matches keep their two modes; not with `--preview-ablation`, `--search-mode` or `--preview-solve`. The matches are named `<opponent>-sample[-t<ppm>][-th<ppm>]` (one fixed rule) and the version 2 `Match` gained the optional `temperature_ppm` and `truncation` (`{kind: "threshold", min_ppm}`; a minor change within version 2: a reader older than the fields rejects such a record; absent keeps today's bytes and hash). Reader rules, both sides: the fields only on a `sample` match against a baseline or another run's pair, never a search or ablation match, the match id ends in `-sample` plus the settings' suffix (and a plain match is not named for settings), and the Python reader recomputes the candidate's `policy_id` from the pair, the mode and the settings (`policy_id(..., temperature_ppm, truncation)`); the TS reader has no policy-id constants, as before. `ProgressOptions.extra_modes` (TS) takes each mode with the policy ids the Python side computed (`--extra-mode <mode>,<candidate-policy-id>[,<versus-policy-id>]` on the Node command); the candidate seat gets `play` in its `PolicySeat`, so the query carries `temperature_ppm`/`truncation`, and the other run's seat gets the same. `_check_extra_modes` (Python) requires the extra matches to be exactly the modes asked for, each against every opponent that plays plain sample, with the sibling's opponent (the other run's pair: its id in the mode). The **play-mode gap** is derived on display and never stored (`progress/gap.py`, `play_mode_gap(record)`): for each baseline and the cross-run head-to-head of a version 2 record, per pair `d_k` = argmax pair score minus the mode's pair score (`paired_differences`), the mean and the pair-level bootstrap interval (`pair_interval`, stream label `gap:<opponent>:argmax:<mode>`, `sample` or `sample:t500000`...), the scores and the pairs argmax did better, equally and worse; labelled "diagnostic: play-mode gap, conditional on the fixed validation plan"; a version 1 record says "not available: version 1 record"; anchor and previous-generation rows carry "both sides play the same mode; the play-mode gap is not read from them"; a Preview ablation or search record has no gap. It is in the printed result (`play_mode_gap`; `summary_of` also gained `mode`, the label, for every match), the dashboard (a "Play-mode gap" section, a Mode column in the matches table, the mode in the generation table; the generation charts keep the plain modes only) and the replay pages (the mode label in the seat and context words). Over the local `public-main-003` progress roots the rows reproduce ADR-023 M1: g50 against `damage-aware@v1` +19.0 points [+10.5, +27.0] (the ticket's upper bound +27.5 came from the throwaway script's own resamples; this stream label gives 27.0). Tests: `tests/ml/progress/test_play_modes.py`, `packages/showdown-bridge/test/progress-modes.test.ts`, `packages/team-dataset/test/progress.test.ts` ("extra play modes"), `progress-modes.test.ts` (the command's flag), `progress.python.test.ts` (real workers, byte-identical rerun, today's bytes without the flag), the corpus samples `progress-evaluation-record-2/*/extra-mode-*` and the report cases in `tests/ml/report/test_report_v2.py`. Not here: extra modes for anchors, any gate use.

**Head-to-head between runs** (ADR-010 erratum A4 item 6, #1003; builds the `run` opponent kind that #969 describes: one implementation). `python -m areneon_ml.loop progress --run-dir A --generation G --versus-run-dir B --versus-generation H [--run-games 200] --progress-dir NEW` adds `run-sample` and `run-argmax` to the evaluation of run A's generation G: B's frozen pair, each pair from both seats on A's plan and `progress-seed/1` seeds, pair-level interval from `stats.py`, summary `diff_*` (pair score minus 1/2) and the label "cross-run comparison". Run B is read only (no lock, never written): `_versus_pair` (`progress/run.py`) refuses the same directory or run key, another format or `team_dataset.dataset_hash`, a run without a team dataset, an uncommitted generation, a non-synthetic record, and `versus_relation` compared pairs that share a checkpoint or one in the other's ancestry (runs with equal init seeds share the seeded generation-0 pair: labelled, not refused; it builds the C1/C6 graph from both runs' records, one node per shared checkpoint id, every generation verified, for the printed `head_to_head.lineage`: "independent lineage" or "related lineage: shared start"). TS: `ProgressOptions.versus` / `run_games` (a worker per run: `--versus`, `--versus-dir`, `--versus-encoder-version`, `--versus-team-set`, `--run-games` of `progress-cli.ts`; the other run's team set joins the training teams and its plans' seeds the league seeds). Record: opponent `{kind: "run", run_id, run_config_hash, generation, policy_id, checkpoints}` (minor change within v2), `plan.run_games_per_match` exactly when run matches are, matches named `run-<mode>`, never the record's own `run_id`. Dashboard section "Head to head against another run", replay wording, samples `run-*`. With `--eval-dataset-dir/--eval-dataset-hash` the two runs may name different team datasets (the evaluation dataset's validation split is the common one; #1244, EXP-M1), and that dataset must not be the other run's own training dataset nor hold any dev or training team of EITHER run (the Python side refuses the dataset; the Node command, which reads the datasets, also refuses it with a `UsageError` and takes `ports.run_teams` of the other run's config, from `--versus-dir`'s `run-config.json`, into `training_teams` beside the evaluated run's, so `progressPlan` refuses a validation team in either run's whole dev or training split); without it the same-dataset rule stays. Opt-in, not with the Preview ablation, not with `--all`; a committed directory is verified and kept (lenient without the flag). Tests: `tests/ml/progress/test_versus.py`, the `progress.python.test.ts` case with two real tiny runs. **Other engine-data table (#1306):** `--versus-engine-data FILE` (Python command and Node `progress-cli.ts`, evaluation path only; the private test's `--opponent-run-dir` does not take it yet) names the other run's engine-data table when its checkpoints were made for another one than `--engine-data` (EXP-A7: an `exact_volatiles` run needs the version 2 table, the control keeps version 1). The versus pair's worker loads that file and checks its hash in the handshake, and the other run's `--versus-encoder-version` is computed from it (`VersusSpec.engine_data`, `RunPair.engine_data`); every other worker (candidate, previous, anchors, ablation) keeps the evaluated run's table. Absent: the evaluated run's table is used and no argument is passed, so every byte, record and argument is as before; the record is unchanged (checkpoints and policy ids name the pairs). It needs `--versus-run-dir` (Python) / `--versus` (Node), and an unreadable or off-contract table is a usage error before any work. Run-to-run checks (format, team dataset) are unchanged. Test: `progress.python.test.ts` (a v2-table run against a v1-table run with real workers, refused without the option, byte-identical rerun, the refusals).

**Move-use diagnostic** (#1164; `ml/areneon_ml/report/move_use.py`, `packages/showdown-bridge/src/move-classes.ts`, `packages/schema/contracts/v1/move-class-table.schema.json`; part of the proof plan #1163, reported beside a proof and never an adoption measure). A read-only computation over the stored `ProgressGameRecord`s of a committed progress generation (head-to-head matches included, the `run-*` ones): per match and seat (the candidate and the opponent; a damage-aware opponent is marked as the reference), the slot actions in each move class and how often a move of a class was among a slot's candidates and not chosen. It is labelled "descriptive move-use diagnostic: not a strength measure" and ranks nothing. It is in the printed `progress` result (`move_use` per generation, integers) and in a dashboard section "Move-use diagnostic" (two tables: chosen count and share per class; not chosen of offered), with the class table's JCS hash and the engine-data hash on the page and both fixture files among the page's inputs. Only the stored games count (the first `--record-games` of each match), so a count is over those games, not the 200. The classes are a `MoveClassTable` (contract v1, sorted lists of move ids, closed; golden `fixtures/showdown/<format>/move-classes.json` and `.summary.json`, MIT-derived like the engine-data table and under its `NOTICE`; `node packages/showdown-bridge/scripts/export-move-classes.ts` rewrites them after a pin bump or a rule change, and `test/move-classes.test.ts` re-exports and compares byte for byte). Decision where the ticket left room: the fields the classes need (boosts, secondaries, side condition, weather, terrain, pseudo-weather, stalling move) are NOT added to the engine-data export, because that is a schema_version 2 and moves the engine-data hash that every checkpoint, encoder version and worker handshake is bound to; the table is a sibling export that names the engine-data table by hash (`engine_data_hash`), its ids resolve in it and its `status` list must equal the table's Status moves exactly (`readMoveClassTable`, `read_move_classes`, which also refuses a table of another engine-data table, format or mod). The rules are the exporter's (reviewed code over the engine's own fields, no move name): `status` is the Status category; `lowers_target_stat` a boosts table with a negative stage on a foe-target move or a secondary with chance 100 that lowers one; `raises_own_stat` a positive boosts table on a self or ally target, a `self`/`selfBoost` boost, or a chance-100 secondary self boost; `side_condition` a `sideCondition`; `field_condition` a weather, terrain or pseudo-weather; `protection` the engine's `stallingMove` (Protect, Detect, King's Shield, Spiky Shield, Baneful Bunker, Endure; Wide and Quick Guard are side conditions). A move may be in several classes. Not read: effects an engine callback produces (Parting Shot, Belly Drum, Haze at this pin) and secondaries with a chance below 100; every `move_targets` kind must be in the exporter's friendly, foe or no-Pokemon group, so a pin that adds one refuses the export. `switch` is the one class the Python side makes: a `switch N` slot action of a move request (a forced replacement after a faint is a forced switch request and is not counted); there is no separate speed-control class (Tailwind and Trick Room are side and field conditions, Icy Wind a stat-lowering move). How a candidate becomes a move: the record keeps no request, so `move N` is the N-th move of the Pokemon in that slot, rebuilt from the omniscient log's `|switch|`, `|drag|`, `|replace|`, `|faint|` and `|swap|` lines and the seat's own team (display name, the engine lists a set's moves in the set's order), at the frame `decision_points` places the decision. A slot action is `unresolved`, counted apart and never guessed, when its Pokemon cannot be named, the slot offers a move number past the set's moves or only `move 1` for a set of several (a lock, a charge turn, a recharge, Struggle), or the seat used in that game a move its set does not hold outside a `[from]` call (Transform's copied moves). Known limits: an Illusion user's slot may name the disguise; a refused choice and its retry count once (the retry); about 5 percent of slot actions are unresolved on the local progress records. Reading the games is the cost: `progress_move_use` runs every stored game through `read_game_record` (about 0.1 s each), so a dashboard over 200 stored games per match takes minutes. Memory (#1245): `stored_games` is a generator and `progress_diagnostics` (`dominated.py`) folds each game into both tallies (`MoveUseTally`, `DominatedTally`) in one pass, to the same bytes (a test compares it with the held-list result): one parsed game alive at a time (about 1.5 MB of heap per stored game, measured with tracemalloc on `public-main-011` g50); memory does not grow with the number of stored games. `verify_progress_dir` ties a match's stored games by the exact name `<match_id>-<k>.json` and the record's own `match_id`, not by prefix, and refuses a stored game that belongs to no match. The ticket allowed adding the statically dominated rate of #1025 (ADR-022 M2) to the same pass; it is not here, because it needs its own reviewed config record with a versioned hash, the type chart and the targeted species of each action, and the M2 definition. Tests: `tests/ml/report/test_move_use.py` (hand-built games with known counts, the pinned classes, the table refusals, the page with CSP, hostile strings and a negative control), `tests/ml/progress/test_main.py`, `packages/showdown-bridge/test/move-classes.test.ts` and the `move-class-table` corpus samples.

**Dominated-move rate** (#1025; `ml/areneon_ml/report/dominated.py`, `config/diagnostics/<format>/dominated-move.v1.json`; ADR-022 measurement M2 and slice M; a secondary diagnostic, never a gate, stop, reward, mask or adoption measure). Beside the move-use diagnostic, over the same stored `ProgressGameRecord`s (`move_use.stored_games` reads a generation once; `progress_move_use` and `progress_dominated` take its games, in `progress` and in the dashboard model; the head-to-head `run-*` matches are matches like any other). Labelled everywhere "approximate static proxy: not a mechanics claim, never a gate or adoption measure". For each slot action that uses a damaging move against the opposing actives it computes a static score in exact rationals: base power times the type-chart cell values of the target's shown types, times a same-type factor when the move's type is one of the user's shown types; a spread move is the sum over the alive foes times a spread factor, a random-target move the mean over them. The action is *dominated* when its score is below the threshold share of the best score among the same Pokemon's enabled damaging moves (the slot's `move N` candidates, each on its best target) and *immune* when its score is 0 while that best is positive (an immune action is also dominated). Counted apart and left out of the rates: status moves, moves aimed at the ally, damaging-category moves with no base power, actions the table cannot score (a species or move the engine-data lacks, a fainted target, no foe on the field), and unresolved slots (the move-use rules). The slot's Pokemon is resolved as for the move-use diagnostic; the shown species per slot follows `|switch|`, `|drag|`, `|replace|`, `|swap|`, `|faint|` and `|detailschange|` (a temporary type change is not tracked). A foe's location in `move N L` is the engine's (L is the foe in active slot L - 1, #1180). No rule in code (owner rule R7): move type, category, base power and target, species types and the chart cells come from the hashed engine-data export; the value of each `damage_taken` code (`effectiveness_ppm`: 0 normal, 1 super effective, 2 resisted, 3 immune), the same-type, spread and threshold factors (ppm) and which move targets are single, spread or random live in the reviewed, versioned record `config/diagnostics/<format>/dominated-move.v1.json` (closed keys; `read_dominated_table` refuses an unknown or missing key, a non-integer, a code the chart uses but the list lacks, a target kind the engine-data lacks or in two groups, and another engine-data table by its `engine_data_hash`; a new version is a new file). Its JCS hash (`config_hash`) and the engine-data hash are on the page and the file is among the page's inputs. Output per match and seat (candidate and opponent, a damage-aware opponent marked as the reference): scored, dominated, immune and the apart counts, in the printed `progress` result (`dominated` per generation, integers; the Wilson interval is derived, `progress/stats.py`) and a dashboard table "Statically dominated damaging moves" whose caption says the interval is binomial and not clustered by game. Only the stored games count (the first `--record-games` of each match). Tests: `tests/ml/report/test_dominated.py` (hand-built games with worked answers: a best move, a score exactly at the threshold, a dominated spread move, an immune target, a spread move summed over alive foes, a fainted target, status, ally target, a switch and an empty candidate list; the config refusals; the page, no table without games or config, a hostile canary) and `tests/ml/progress/test_main.py`.
