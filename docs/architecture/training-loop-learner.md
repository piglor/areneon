# Training loop and learner

TrainingRunConfig, the PPO and cloning learners, warm start, schedules, the generation loop, run metrics, teacher data and the GPU learner.

Part of the architecture documentation split out of `CLAUDE.md` (index: [README](README.md)). Ticket references such as `#1179` point to Redmine (`redmine.piglor.com/projects/areneon`), where measured figures and verdicts are recorded.

**TrainingRunConfig, PPO learner and learner state** (`packages/schema/contracts/v1/training-run-config.schema.json`, `packages/showdown-bridge/src/training-run-config.ts`, `ml/areneon_ml/learner/`, ADR-010 §1, §5, #840). `TrainingRunConfig` is the one record of a run's values: lineage and format, every seed (`run_key`, the two initialisation seeds, the learner's generator), the `model` section (encoder and network sizes), the `generation` plan (self-play games, games per scripted baseline, `max_turns`, `n_parallel`, latency budgets, handshake timeout, `max_line_bytes`), the `ppo` settings and the learner's `device` (`cpu` or `cuda`) and thread count. Contracts carry no floating-point numbers, so real values are integers in millionths (`learning_rate_micro`, `clip_micro`, ...) or billionths (`adam_eps_nano`); `areneon_ml.learner.config.read_run_config` is the one place that divides them. `ppo.target_kl_micro` (optional, ADR-010 erratum A1, a minor change within v1): after each complete epoch, if the mean of that epoch's per-minibatch `approx_kl` (minibatch order) is greater than it, the role's remaining epochs are skipped; the train report then carries per role `epochs_run` and `kl_stopped`, and both keys are omitted without the field so existing reports keep their bytes (the dashboard reader takes them as optional keys). `ppo.learning_rate_schedule` (optional, ADR-010 erratum A1, a `kind`-tagged `oneOf`: `constant` or `linear {final_micro, generations >= 1}`): update `t` (the learner generation counter, from 0) uses `L0 + trunc((Lf - L0) * min(t, generations) / generations)` millionths in exact integers (`LinearSchedule.rate_micro`), set on both optimisers before the epochs; the learner-state sidecar records `learning_rate_micro` (the newest update's rate) only for `linear`, so other runs keep their `learner_state_hash`, and a restore refuses a sidecar whose rate is not the schedule's. The reader rules the profile cannot say (heads divide `d_model`, `max_picks` ≤ `max_team`, a baseline listed once) are checked by `read_run_config` and by the TS `readTrainingRunConfig`, which also gives `runConfigHash` (SHA-256 of the JCS bytes, `CheckpointRecord.run_config_hash`). League mixture and freeze-interval values are not in v1: they come with the league scheduler (Wave 5). The learner is PPO with GAE over the TrainingExample stream: `learner/data.py` reads a stream only through `read_stream` with its manifest, refuses a set that is not `learner_ready` or was not played by the `behaviour_policy_id` it trains, and splits each Episode into one Preview step and one Battle trajectory (encoded from the example's observation and candidates alone). The reward is the game score at the last step of a trajectory (win 1, tie ½, loss 0, `ppo.GAME_SCORE`); every earlier step, a refused pending choice among them, has zero immediate reward. `learner/trainer.py` recomputes the behaviour policy's log-probability and the value of every decision from the frozen weights with no gradient (no probability is stored in an Episode), computes advantages with GAE, then runs the configured epochs over minibatches shuffled by the learner's own generator; the loss is the clipped surrogate over a softmax across the real candidates (`ppo.py`, checked against hand-computed values) plus the value error and the entropy bonus. Determinism claim: on CPU, with the config's thread count and deterministic algorithms, the same inputs on the same machine and software give bit-identical weights; nothing is claimed across machines or torch builds, and a CUDA learner is not bit-reproducible (its run config, with `device: cuda`, hashes differently). The learner state (`learner/state.py`) is `learner-<g>.safetensors` (both networks' weights, the Adam moment tensors, the generator's state tensor) plus `learner-<g>.json` (JCS: generation, run config hash, seeds, PPO settings, optimiser step counts); `learner_state_hash` is SHA-256 of `JCS({tensors_sha256, sidecar})`. `restore_state` loads only through safetensors and a JSON parser, recomputes the hash, refuses a state of another run config, a sidecar that contradicts the networks and tensors of another name, dtype or shape, and changes the learner only after every check. `checkpoint/files.py` gained `pack_safetensors` / `unpack_safetensors` (float32 and uint8) beside the checkpoint writer.

**Supervised cloning learner** (`packages/schema/contracts/v1/clone-run-config.schema.json`, `packages/showdown-bridge/src/clone-run-config.ts`, `ml/areneon_ml/learner/clone*.py`, ADR-019 track 1, ADR-010 erratum A2, #967). `python -m areneon_ml.learner clone --config C --stream-dir D --engine-data E --version-manifest V --out O` trains a Preview and a Battle network, separately, to imitate a scripted teacher (`damage-aware@v1`) from its learner-ready `TrainingSet` (`D/stream.jsonl` and `D/training-set.json`, read only through `trajectories` / `read_stream`), and writes the new directory `O` (never overwritten; built beside it and renamed): `checkpoints/<id>.safetensors`, `records/<id>.json` (a `CheckpointRecord` each, named by id so `python -m areneon_ml.checkpoint classify|independent --records O/records --sources O/sources.json` reads it as it is), `sources.json` (the teacher set hash mapped to `[]`, an outside behaviour-cloning source), `clone-state.safetensors` / `clone-state.json` (weights, Adam moments, generator state, a JCS sidecar of `kind: "clone"`; its `state_hash` is the records' `learner_state_hash`), `clone-report.json`, `clone-run-config.json` and `provenance.json`. `CloneRunConfig` v1 (integers only, closed; `cloneRunConfigHash` / `CloneConfig.hash` is SHA-256 of its JCS bytes and the records' `run_config_hash`) holds the lineage, format, seeds (`run_key`, the two initialisation seeds, the learner generator), the `model` section (the shape of `TrainingRunConfig.model`; heads divide `d_model`, `max_picks` ≤ `max_team` are reader rules on both sides), the `teacher` (`behaviour_policy_id` `<name>@<commit>`, never a learned `policy:<hash>` pair, and `training_set_hash`, the SHA-256 of the manifest's JCS bytes), the `clone` settings (`epochs`, `minibatch_size`, `learning_rate_micro`, Adam betas and epsilon, `max_grad_norm_micro`, `holdout {key, ppm}`) and the learner `device` / `threads`. `clone.check_teacher` fails closed: the manifest must be synthetic, `learner_ready`, played by the named teacher and hash to `teacher.training_set_hash`. The loss is `ppo.policy_terms`' softmax over the real candidates (padding masked), `-mean(log p[teacher choice])`, per minibatch of a seeded shuffle (`torch.randperm` on the learner generator, Preview first then Battle); the value head has no label and is untrained here (the PPO phase learns it). The held-back part is chosen per Episode by `held_back(key, episode_hash, ppm)`: HMAC-SHA256 over the 64 hex characters, first 8 bytes big endian as n, held back when `n * 10^6 < ppm * 2^64` (the rule shape of ADR-015; ppm at most 500,000; a role with nothing left to train on is refused). The report holds, per role, the loss of each epoch and the agreement on the training and the held-back parts (steps, mean cross-entropy, top-1 hits against the teacher's choice, and `chance`, the mean of 1/candidates), deterministic values only. The records carry `parent` absent, `training_set_hashes` the teacher set, no league opponents, `data_class` synthetic, a `team_set_manifest_hash` over the own teams the examples' observations carry, and the version manifest of the teacher games (the `--version-manifest` file: the teacher run must provide it). Determinism claim as for the PPO learner (CPU, one machine and software; `configure_learner` sets it up). `Trajectory.episode` (new, optional) lets the split find an Episode; `state.gather_tensors` is the shared tensor collection of `pack_state`. Not here: `TrainingRunConfig.warm_start`, the loop and the KL anchor (next slices), the teacher run (#965).

**Clone situation weights and `clone-eval`** (ADR-010 erratum A13, #1390; `ml/areneon_ml/learner/{clone,clone_config,clone_eval,data,situation,parallel}.py`, `packages/showdown-bridge/src/clone-run-config.ts`). Optional `clone.situation_weights {streak_ppm, threatened_ppm?}` in `CloneRunConfig` (integers 1 to 100,000,000, millionths; a minor change within v1, an older reader refuses it; absent keeps every clone byte, `clone_run_config_hash`, checkpoint id and report, pinned by `tests/ml/learner/test_clone_situation.py` against values computed at the previous main). Reader rules in both readers (`readCloneRunConfig`, `read_clone_config`): `streak_ppm` needs `model.encoder.options.recent_history`, `threatened_ppm` needs a `candidate_features` set with threat rows (`THREAT_ROW_FEATURE_SETS`, A11.2's rule); `threatened_ppm` alone is a schema error. **Groups** (one per Battle decision, exclusive, first match, a pure function of the example; `Step.group`, `None` without the block and on Preview steps; carried by the parallel load's piece transport): `streak` = some living own active slot of the move request has reducer `protect_streak >= 1` and a not-`disabled` stalling move of `Vocabulary.stall_moves` among that slot's request moves (`situation.streak_slots`); `threatened` = not streak and A11.2's `threatened_flag`, only when `threatened_ppm` is set (else `other`; the flag missing from an example is a `LearnerDataError`); `other` = the rest, forced switches included. A streak decision takes `streak_ppm` only (weights do not multiply). A streak step also carries `Step.stall`, per candidate whether it uses a stalling move in a streak slot (`stall_candidates`), for the report. **Loss:** only the Battle role is weighted; factor `w_i * |S| / sum_S w` per training step (`situation_factors`: one exact integer ratio, rounded once to float64 and cast to float32, mean exactly 1; the global normaliser, not a per-minibatch mean, so a decision's weight does not depend on the shuffle), minibatch loss `mean(factor * CE)`; shuffle, minibatch size, epochs, optimiser steps and the generator's state are unchanged (tested), and with all weights 1,000,000 the clone is bit-identical to one without the block. **Report** (Battle role, only with the block): `situation_weights`, `weight_mean_ppm` (floor of the mean weight), `train_groups` and `holdout_groups` (`streak`, `threatened`, `other`: `steps`, UNWEIGHTED `loss`, `top1_hits`, `chance`; `streak` also `stall_teacher` and `stall_clone`; `holdout_groups` only with a held-back part); `epoch_loss` is then the WEIGHTED objective while `train` and `holdout` stay the unweighted agreements, comparable with every earlier clone. The held-back Episodes are chosen by the keyed hash as before, never by group or weight. **`python -m areneon_ml.learner clone-eval --clone-dir O --stream-dir D --engine-data E [--out F]`** (read-only, CPU, refuses an `--out` inside `O` or one that exists): loads the clone's Battle checkpoint and `clone-run-config.json` (the report's config hash must match; the teacher set must be the one the config names), re-splits the stream with the clone's own holdout key and ppm and prints (and writes) `train`, `holdout`, `train_groups`, `holdout_groups` for ANY clone, with or without the block (`threatened_read` says whether the Threatened group was read, which needs a feature set with threat rows; nothing is weighted), so the P4b clone is measured on the footing of P4c's. Tests: `tests/ml/learner/test_clone_situation.py` (groups by hand: streak with and without a stall offered, disabled stall, fainted active, forced switch, threatened precedence; factors against a hand computation; the report keys; a rerun byte-identical; the workers equal one process; `clone-eval` equal to the clone's own report and changing no file), `packages/showdown-bridge/test/clone-run-config.test.ts` and the corpus samples `clone-run-config/*situation-weights*`. Follow-ups (#1390 reviews): `clone-eval --out` is created exclusively (`xb`: a dangling symlink or a race never overwrites); `situation_factors` falls back to 1,000,000 only for an unset weight (`is None`); a grouped Battle `Step` carries `unmatched` (`situation.streak_unmatched`: living request slots whose ident matches no roster entry, which `streak_slots` skips; it travels in the parallel piece as entry 9) and the `streak` group of the clone report gains `streak_unmatched` (the sum over grouped steps); the plain loss path is held by a test that an epoch of one minibatch reports the independently computed mean cross-entropy of the initial network (to 1e-5: a pinned literal would move with the torch build).

**Warm start** (`TrainingRunConfig.warm_start`, `ml/areneon_ml/loop/warm_start.py`, ADR-010 erratum A2, ADR-019 §4, §6, #966). An optional `warm_start: {preview, battle}` (two 64-hex checkpoint ids; a minor change within v1: absent keeps today's bytes and `run_config_hash`, an older reader refuses it; both readers also refuse one id for both roles) makes generation 0 a declared cloned pair instead of the seeded random pair. Nothing is fetched: `python -m areneon_ml.loop import-clone --clone-dir O --run-dir R` copies a `learner clone` output into the run directory (the checkpoints into `checkpoints/`, the records into `warm-start/records/<role>.json`; it checks each record is a clone record, each file hashes to its record's id and `sources.json` maps the teacher sets to `[]`; rerunning is a no-op and it never replaces a record with other bytes). At the start of generation 0 (and when a run is resumed at generation 0) `load_warm_start` loads both through `load_checkpoint` and refuses, as a `LoopError` (exit 3), a file missing from the store, one that does not hash to its id, another role, another engine-data table, encoder version or `model` section than the run's (the whole `ModelConfig` must be equal) or bytes that do not re-serialise as themselves, and a record that is not a clone record (empty `training_set_hashes`, a `parent`, an exploiter target or league opponents, not synthetic), made for another encoder version or format, or naming another checkpoint. Generation 0 freezes the pair with no learner step: its checkpoint ids are the cloned ids and its `records/<role>.json` are the clone records byte for byte (a checkpoint has one record and the provenance graph refuses a second), so `learner_state_hash` and `run_config_hash` inside them are the cloning run's; the generation's manifest and learner state (`learner-0`) are this run's. The learner's Adam moments and generator start fresh from the cloned weights (the supervised phase's optimiser state is not carried over); generation 1 is the first policy-gradient step and its records name the cloned ids as `parent`. `sources_registry` / `export_provenance` map every training set a generation-0 record names to `[]` (an outside behaviour-cloning source), so `classify` / `independent` see the teacher set in the ancestry: two warm runs on one teacher set are not independent (C6, ADR-019 §6), runs on different teacher sets or none are. Resume and the SIGKILL claims hold (tests kill at every stage of generations 0 to 2 of a tiny warm run and compare manifests and learner state bytes). **Battle-only (#1165):** `warm_start` may be `{battle}` alone (`preview` optional, a minor change within v1; `{preview, battle}` and an absent key keep every hash and byte; both readers refuse `preview` as the only key through the schema's `required: [battle]`, and one id for both roles). Only the named roles are imported (`import-clone --roles battle` copies the Battle checkpoint and record and neither reads nor copies the output's Preview; `import_clone(..., roles=("battle",))`), loaded and checked (`load_warm_start` iterates the named roles), and carry clone records; the other role starts from the seeded init of its `seeds.init_*` exactly as a scratch run's generation 0 (same checkpoint id) with an ordinary built record (no training sets, no parent, this run's state hash), and `Sealing.records` holds the clone records of the warm roles only. `ppo.value_warmup` and `ppo.anchor` act only on the warm-started roles (`Learner.warm_roles`): an unwarmed role trains as plain PPO from update 0, the anchor networks are given exactly for the warm roles (`LearnerError` otherwise), and `train-report.json` carries `value_warmup`, `anchor_kl` and `anchor_beta_micro` for the warm roles alone (the learner-state sidecar's `anchor_beta_micro` is the schedule's value for the warm role). Provenance: the Preview lineage starts at the seeded init (generation 0's Preview has no teacher set), the Battle lineage names the clone; from generation 1 both descend from the cloned Battle network through the games it played (the sources registry maps the set to the pair that played it). Why: damage-aware@v1 plays one fixed actor-rule Preview choice, so a cloned Preview would start near-deterministic and the anchor would hold it there. Tests: `tests/ml/loop/test_warm_start_battle_only.py`. Not here: the KL anchor, human-data warm starts, the experiment runs. **Binding a clone made before #853 (#1356):** `import-clone` refuses a clone directory without `provenance.json`. `python -m areneon_ml.learner bind --clone-dir D` (`learner/clone_bind.py`) is the migration: it checks exactly what `write_clone` and `import-clone` require (one clone record per role named by its checkpoint id, each checkpoint file hashing to its record's id, `sources.json` canonical and mapping every teacher set to `[]`, `clone-state.safetensors`/`.json` hashing to the records' `learner_state_hash` with a sidecar of kind `clone` naming their `run_config_hash`), writes `provenance.json` only then, refuses (exit 3, nothing written) on any mismatch, is a no-op when the identical binding exists and never overwrites a different one. It is a self-consistency check of the directory, as the binding is. Tests: `tests/ml/learner/test_clone_bind.py`.

**Value warm-up** (`ppo.value_warmup`, `ml/areneon_ml/learner/trainer.py`, ADR-019 §4, #1111; `docs/training-run.md` section 5). Optional `{generations: N}` in the `ppo` block (integer at least 1; a minor change within v1: absent keeps today's run config hash, learner-state hash and every generation file); a reader rule on both sides (`readTrainingRunConfig`, `read_run_config`) requires `warm_start`. The learner updates with index below N (`value_warmup_active`; generation 1 is update 0) train the value head only: every parameter outside `value.*`, the shared trunk included, has `requires_grad` off for the update (restored after), so the cloned policy's outputs stay byte-identical, the backward pass is the value error alone (`value_coef` is not applied and `target_kl` is skipped), and Adam, which skips a parameter without a gradient, holds moments for the value head only; the same optimiser serves PPO afterwards (the value head's moments carry on, the rest start at update N + 1). The learning-rate schedule's index counts the warm-up updates. `RoleReport.value_warmup` (`true`, in `train-report.json` only on a warm-up update; the dashboard reader's optional key set gained it) and the sidecar's `ppo` block record it only when set. Resume needs nothing new: the position is the restored generation counter. Tests: `tests/ml/learner/test_value_warmup.py` (frozen policy, value-only Adam state, byte-identical logits, resume at and inside the warm-up) and `tests/ml/loop/test_value_warmup.py` (a warm loop: only `value.*` tensors move through the warm-up, killed anywhere resumes to the same files).

**Teacher imitation mix** (`ppo.imitation`, `ml/areneon_ml/learner/{config,imitation,trainer,state}.py`, `loop/teacher.py`, `driver.py`, ADR-010 erratum A11.3, #1367; `docs/training-run.md` section 5). Optional `{training_set_hash, coef_micro, share_ppm, schedule}` in the `ppo` block (a minor change within v1: absent keeps every hash, report, sidecar and file; an older reader refuses it; both readers require `warm_start`; a population takes it since #1437, see below). `training_set_hash` is the SHA-256 of a scripted teacher's `TrainingSet` manifest JCS bytes; `coef_micro` is lambda_im (1 to 10^8), `share_ppm` 1 to 10^6, `schedule` an `AnchorSchedule` started from `coef_micro` (`ImitationSettings.coef_micro_at`, the anchor's integer rule; `steps(N, available)` is K = floor(share * N / 10^6) capped at the set size). **Stream:** nothing is fetched. `python -m areneon_ml.loop import-teacher --stream-dir D --run-dir R` (`loop/teacher.py`) checks `D/stream.jsonl` against `D/training-set.json` (`check_stream_file`), refuses a manifest that is not synthetic, not `learner_ready` or played by a learned `policy:` id (`learner/imitation.py` `check_teacher_manifest`, which also holds the manifest to the config's hash), refuses a hash other than `R/run-config.json`'s `ppo.imitation.training_set_hash` once that file exists and a config without the block, copies both files into `R/teacher/<hash>/` (temp file, fsync, rename; never other bytes over an existing file; a rerun is a no-op; under the run lock). The driver opens them once per process with `open_teacher` (`check_teacher_manifest`, `check_stream_file` by path, then every example, Previews included, encoded once and dropped so the encoder's refusals surface at the first update as `LearnerDataError`) and keeps only a `TeacherSet`: the byte offsets of the Battle examples in stream order. Each update draws its K indices over that order and `TeacherSet.fetch` reads and encodes just those (fresh view and encoder session per example, tensors equal to the whole-stream read, a test compares them), so memory is bounded by K, not the set size; the steps die with the update's table (a weakref test). A resumed run indexes again. **Loss:** the Battle minibatch loss gains `lambda_im(t) * mean(-log pi_theta(teacher choice))` over that minibatch's teacher steps, a second forward pass of the Battle network on the fixed states (`policy_terms` at `generation.play`'s temperature over the real candidates, padding masked; no clip, no value term). The update's K steps are drawn without replacement by `DrawStream` (a generator seeded from SHA-256 of the JCS of `{purpose: "imitation/1", seed: learner seed, update}`, also used for the per-epoch shuffles), spread over the Battle minibatches by `_spread` as the A10 labels are, in `_epochs` and in the `shared_trunk` joint step (the gradient reaches the shared trunk); the learner's main generator is never touched, so Preview's orders and a run without the block keep their bytes (a test compares generator states). Off during `ppo.value_warmup` (no draw, coefficient 0); `t` counts from the first policy update (`Learner.imitation_coef_micro`). **Report:** Battle role only, only with the block: `imitation_steps`, `imitation_coef_micro`, `imitation_ce_before` (frozen weights), `imitation_ce_after` and `imitation_top1_ppm` (after the epochs; a warm-up update reports 0, 0, 0.0, 0.0, 0); the dashboard's train-report reader takes the five keys together on the Battle role. **State:** the sidecar records `imitation_coef_micro` for a linear schedule only and `restore_state` refuses one that is not the schedule's (present or absent). **Provenance:** from generation 1 the teacher set's hash joins `label_set_hashes` (so each record's `training_set_hashes`, sorted and unique, and the manifest facts that a resume checks) and `sources_registry` maps every `R/teacher/*/training-set.json` hash to `[]`, an outside behaviour-cloning source like a warm start's teacher set: two runs that read one teacher set are not independent (C6), `L2` must use its own teacher run. Decisions where the erratum left room: the K draw and shuffles share one stream per update (the update's draw first, then one shuffle per epoch); the import refuses a hash other than the config's only when a config exists. Tests: `tests/ml/learner/test_imitation.py` (reader and schema rules, stream refusals, draw determinism and independence from the main generator, cross-entropy against hand values at tau 1 and 0.5, report keys, warm-up off, shared trunk, sidecar, resume, restore refusal), `tests/ml/loop/test_imitation.py` (`import-teacher`, a tiny warm loop: byte-identical rerun, kills at four stages, provenance export and `independent`), `tests/ml/report/test_report.py`, `training-run-config.test.ts` and the corpus samples `training-run-config/*imitation-*`. **Inside a population (#1437, ADR-010 erratum A11 clarification, ADR-021; `loop/population.py`):** both readers accept `ppo.imitation` with `population` (the former refusal "no per-member teacher stream" is gone; the sample `imitation-population` moved from `reader-invalid/` to `valid/`, its JCS digest unchanged). `python -m areneon_ml.loop import-teacher` is run once on the run directory; `PopulationLoop._teacher_set` opens and indexes that one stream once per process (`open_teacher`, refusals as for a single run, `LearnerDataError` with the `import-teacher` hint when it is missing) and every member's `learner.train(found, None, teacher)` draws from it with the member's OWN learner seed (`DrawStream(config.learner_seed, update)`: `member_config` gives each member its `population-seed/1` learner seed, and a copy's new seed from `selection.learner_seed` follows the learner), so draws are a function of seed and update index alone, never of scheduling, start slots or shards. A `DrawStream` seed of 2^53 or more (a population draw reaches 2^63, beyond what JCS holds) enters the preimage as its decimal string; a seed below it keeps the integer, so every single run's draws and bytes are unchanged. Each member's `train-report.json` carries the Battle role's `imitation_*` keys and its sidecar `imitation_coef_micro` (linear schedule) exactly as a single run's; the members share the warm start's value warm-up and schedule index. **Provenance:** every member's records for a trained generation list `sorted({own training set, teacher set})` in `training_set_hashes` (`PopulationLoop._set_hashes`, also what a resume checks); a quarantined or copied member whose update was dropped has no training set that generation and keeps the records it has; `population_sources` maps the teacher hash, which no generation's own sets cover, to `[]` (an outside behaviour-cloning source), so `export_provenance`/`classify`/`independent` see it in every member's ancestry. A population without the block keeps every byte (the teacher index is never opened). Tests: `tests/ml/loop/test_population_imitation.py` (a tiny two-member warm population: per-member report keys, records, registry and `ProvenanceGraph`, byte-identical rerun, kills at three stages, the missing import, absent-keeps-no-term), `tests/ml/learner/test_imitation.py` (big-seed draw), `training-run-config.test.ts`.

**Entropy schedule** (`ppo.entropy_schedule`, `ml/areneon_ml/learner/{config,trainer,state}.py`, ADR-023 §3 step 3, ADR-010 erratum A6 item 4, #1048). Optional in the `ppo` block, a `kind`-tagged `oneOf` (a minor change within v1; absent or `constant` keeps every `learner_state_hash`, train report and generation file, and the run config hash of a record that carries `constant` still differs from one without the key): `{kind: "constant"}` or `{kind: "linear", final_micro, generations}` (schema defs `EntropySchedule` / `EntropyLinearSchedule`: a final of 0 is allowed, which the learning-rate `LinearSchedule` forbids). Update `t` uses `E0 + trunc((Ef - E0) * min(t, generations) / generations)` millionths, `E0` = `entropy_coef_micro`, in exact integers (`LinearSchedule.rate_micro`, the one helper the learning-rate schedule and the anchor share; `Learner.entropy_coef_micro(update)`), set on the loss weights of both roles before the epochs; `read_run_config` divides by 10^6 in its one place. **Value warm-up interaction (decided):** `t` counts POLICY updates, as the anchor's does: with `ppo.value_warmup` of N updates the index is `max(0, u - N)`, so the decay is not spent while the policy is frozen; the warm-up updates report `E0` (the entropy term is not in the value-only loss). The index is one value per update for both roles, so a role that a battle-only warm start leaves unwarmed trains plain PPO through the warm-up with `E0`. The sidecar records `entropy_coef_micro` (the newest update's weight) and each role of `train-report.json` the same key, ONLY under a `linear` schedule; `restore_state` refuses a sidecar whose weight is not the schedule's (present or absent: "entropy weight"), and the dashboard reader's optional key set gained `entropy_coef_micro` (an integer). Tests: `tests/ml/learner/test_entropy_schedule.py` (hand values falling to 0, rising and past `generations`, the warm-up offset, flat schedule equals no schedule, resume, tampered sidecar), `tests/ml/loop/test_entropy_schedule.py` (a tiny loop: keys per generation, byte-identical rerun, kills at four stages resume to the same hashes), `packages/showdown-bridge/test/training-run-config.test.ts` and the corpus samples `training-run-config/*entropy-*`. Not here: a target-entropy controller, the schedule values of EXP-T2.

**Learner micro-batch** (operational, `python -m areneon_ml.loop run --learner-micro-batch N`, also `learner clone` and `learner bench`; `Learner(..., micro_batch=N)`, `clone(..., micro_batch=N)`; not a config field, so no run-config hash moves). On CUDA each query of a minibatch is padded to the minibatch's largest candidate count (about 45 MB of activations a query at width 256), so a step reached about 16 GB on a 16 GB card, WSL paged and train phases ran 8 to 9 times slower (463 s against 53 s). With N each minibatch index is cut into chunks of at most N (`_accumulate`): `_minibatch_loss` runs per chunk with `shares` (the chunk's share of the minibatch's decisions, label steps, teacher steps and move-reveal targets), each chunk is backpropagated at once (gradient accumulation, graph freed) and the reported loss terms and anchor KL are the share-weighted sums, so the report means are the minibatch means; `zero_grad` is once per optimiser step, clipping and `step` after the last chunk, and the shared-trunk joint step accumulates every role's chunks the same way. The no-gradient passes (`_score`, `_anchor_scores`, `_imitation_eval`, `_label_kl`) use `min(minibatch_size, N)`. Default `None` keeps the single pass and every byte; with N the gradients equal the single pass's to float32 rounding (reproducible per N only), and N at least the minibatch is the single pass exactly. Recommended N = 64 on a 16 GB card (memory and time figures on #1195). `metrics/g*.json` gains the optional `learner_micro_batch` (run-metrics contract, minor change within v1; written only when set). Tests: `tests/ml/learner/test_micro_batch.py` (gradients and report equal for plain, anchor, anchor with warm-up, shared trunk, aux moves, anchor.threatened, imitation, search distillation and shared trunk with imitation; N larger than the batch is exact; the default never enters the chunked path), `test_clone.py`, `test_bench.py`, `tests/ml/loop/test_metrics.py`.

**Generation loop** (`ml/areneon_ml/loop/`, `packages/showdown-bridge/src/league-generation.ts`, `generation-cli.ts`, ADR-010 §1, #840). `python -m areneon_ml.loop run --config <TrainingRunConfig.json> --run-dir R --engine-data <engine-data.json> --generations N [--node node] [--worker-python <python>]` continues the run in `R` until N generations are committed (resuming from the last one, a no-op if N are there); `provenance --run-dir R --out D` writes `D/records/` and `D/sources.json` (derived from the run's own manifests) for `python -m areneon_ml.checkpoint classify|independent`. Generation 0 is the seeded random pair (ADR-010 §4) unless the config declares `warm_start` (see Warm start); generation g plays the pair frozen at g-1 on A1 (`play-generation.ts`: the Python worker on CPU torch behind the TS client, `policyGame` for self-play and for each configured scripted baseline), writes an Episode for every played seat (`episodeFromRecord`, collection kind `league`, `run_id` = the config's `run_key`, the seed the battle ran with), loads only the pair's own seats through `loadTrainingSet` (`behaviour_policy_id` = `policy:` + SHA-256 of `JCS({preview, battle, mode, temperature, precision})`; a baseline's Episodes are kept but the loader would refuse them), trains (`learner/`), freezes the new pair and commits. The frozen pair always plays with temperature-1 sampling, never argmax (`playOne`; the policy id says `mode: sample`), and a baseline seat is never queried or loaded (tests fail on either). The match plan (battle seeds, team indices, baseline seats) is a pure function of the config, the generation and the team pool (`planGeneration`), so a killed generation is replayed from the same plan. Run directory: `run-config.json`, `checkpoints/<id>.safetensors` (the store the worker reads), `generations/g<NNNNNN>/` (Episodes, `stream.jsonl`, `training-set.json`, `plan.json`, `generation.json`, `train-report.json`, `learner-<g>.safetensors|json`, `records/{battle,preview}.json`, the cumulative `team-set.json`, `manifest.json` = SHA-256 of every other file plus the checkpoint ids and hashes). `run()` holds an exclusive `flock` on `<run dir>/.lock` for its whole run (a second driver on the directory fails fast; the operating system releases the lock when the holder dies; caveats: `fcntl` is POSIX only, NFS needs a working lock service, and a WSL2 `/mnt/c` directory (DrvFs/9p) may not honour `flock`, so keep run directories on a local Linux filesystem; `generations/`, `checkpoints/`, the run directory and its parent are fsynced when first created). A generation is built in `.g<NNNNNN>.partial`; every file and directory in it is fsynced (the Node side's own files too: `writeGeneration` fsyncs each file, then both directories, `generation.json` last), the manifest is hashed from the flushed bytes, and one `os.replace` of the directory commits it, followed by an fsync of `generations/` (`write_checkpoint` and `run-config.json` are written the same way, temp file, fsync, rename, fsync of the directory; stale `checkpoints/.*.partial` files of a killed run are deleted at start); the next start deletes partials, finds the newest committed generation, verifies its manifest (only the newest: the learner state, records and team set a resume needs live there, `latest_complete` checks that the numbers run 0..n without a gap, and `provenance` verifies every generation), restores the learner (`restore_state`, hash checked), and refuses unless the restored weights are the stored checkpoints (written again if the store lost them) and the records agree with the state and the manifest (checkpoint id, learner state hash, run config hash, training-set hashes). Each generation's two `CheckpointRecord`s carry the lineage, the parent (the previous generation's same-role checkpoint), the TrainingSet hash, the run config hash, the learner state hash, the encoder version, the cumulative team-set manifest hash and the format's version manifest (from `format-manifest.ts`). The team pool is the interim one (`trainingTeamPool`): the golden team, the legal paste fixtures and the random-play corpus teams, all committed CC0 synthetic and proven synthetic by that source; the ADR-013 team generator does not exist yet. `generation.excluded_abilities` of the config keeps out teams that hold an ability on its list; the tiny and the current configs list `Illusion`, a stop-gap for the reducer's former `|replace|` gap, which #851 closed. To drop it: remove `"Illusion"` from `generation.excluded_abilities` of a NEW run's config (a new `run_key`; the list is part of the run config hash, and the pool, hence every team index of `planGeneration`, changes with it, so never edit a run in progress), then sweep first: `node packages/team-dataset/scripts/reducer-sweep.ts --config <config> --mix uniform-all --battles 300 --only-ability Illusion --out OUT.jsonl` and `uv run python scripts/reducer_sweep.py OUT.jsonl` must report `unexplained: 0`. A new run restarts from generation 0 (ADR-010 §4); the committed `config/training/public-gpu16.json` still lists Illusion until a follow-up decides. The training self-play and the learner may batch; evaluation never does (§2). A forfeited game's `PlayedEntry` carries `stored: []` on the spilled path (#1184; without it `playGeneration` refused any generation with a forfeit as "not all kept the way this generation keeps its Episodes"), so a forfeit is kept like an in-memory one and a generation without forfeits writes the same bytes. **Feature rows by the game processes** (#1185, ADR-022 section 4): with a candidate feature set and `--game-processes` above 1, the stream's rows were recomputed serially by the parent after the games (a tail of about 330 s that did not shrink with the processes, #1179). League mixtures, a freeze interval and exploiters are Wave 5. **Throughput (#957).** `python -m areneon_ml.loop run --game-processes S --policy-workers K` (operational flags of `NodePlayer`, never config fields, so no run config hash moves; both default to 1 and are then not passed) shares a generation's games over `S` Node processes, each with `K` worker processes. `playEntries(options, {index, of})` plays the games `g mod of = index` (a game stays on one worker, chosen by its place in the wave; waves hold `n_parallel` games per worker) and returns `PlayedEntry`s (row and Episodes); `playGeneration` puts its own slice and `options.others` (the other slices) in plan order, refuses a game missing or played twice, and loads the training set once. `runGenerationCli` is the parent (shard 0): it starts `S-1` children of the same script (the `shardScript` argument, `process.argv[1]` of both scripts; `--shard INDEX/COUNT` is internal) before it loads its own pool, each child writes `shard.jsonl` in a scratch directory that the parent reads and removes with the directory (also on failure); a child ends if the parent dies (its stdin closes). (Throughput figures of the game processes: see #957.) Progress evaluation stays unbatched and unchanged. The operational flag `--batch-seam` (ADR-030 step 1, #1455) advances a game process's waves in lockstep without changing a byte: see "Batch seam" in `features.md`.

**Failing game processes** (#1100). A game process that exits non-zero fails the generation at once: `startShard` reports it on `exit` (not `close`, which waits for every holder of its stderr pipe) with its stderr tail, `playGeneration` aborts this process's own games (`GenerationOptions.signal`, checked before each wave and after each worker restart, so no wave and no worker restart follows) and rethrows, the CLI's `finally` kills the other children, closes the workers and removes the scratch directory, and the play scripts `process.exit` on a non-zero code so a game still running cannot keep the process alive (the cause of a 7.6-hour hang: `others` rejected, the parent returned 1, but its own games went on and restarted workers). An idle watchdog (`live_children`, `idle_grace_ms` default 60 s) fails a generation that still awaits the other processes' games with none alive and none of its own in flight. The driver's `--generation-timeout-minutes` (default 180, `NodePlayer.generation_timeout_s`) keeps the Node process in the driver's own process group (so a kill of the driver's group still ends it, as `training-loop.python.test.ts` requires) and past the limit kills it and every descendant found under `/proc` (`PlayError`, nothing committed). All operational: no output byte changes.

**Shared team pool and a single observation build in the merge** (ADR-028 F5, #1192, #980; operational only: no run-config field, plan, seed or hash moves, every generation file is byte-identical). (1) `pool-share.ts`, `parent-link.ts`: with `--game-processes` above 1 the starting process loads and normalises the pool once, writes it to `pool.json` (mode 0600, plain JSON so the sets keep their key order; written as `.partial` and renamed) in the shard scratch directory, and sends the SHA-256 of those bytes to each further game process as the line `pool <hex>` over the stdin pipe it already holds for them (`vouchTo`; the digest is not a secret). A further game process (started with the internal `--pool-file`) does not poll: it waits for that line while its policy workers start, and a worker that fails to start ends the wait; if the starter dies the closing pipe ends the process (`exitWhenParentDies`, registered before the pool and the workers start). `readPoolFile` reads the file once as one string (a pool is a few megabytes) and checks, in this order: the file is owned by the invoking user with mode 0600; its bytes hash to the digest the starter sent; its layout version; its request key (SHA-256 of the JCS of format, `team_dataset` and the excluded abilities as a sorted set, derived from the reader's own run config) is the reader's; the hash list is sorted and unique; every team `teamHash`es to its listed hash. `known_synthetic` is rebuilt from that hash list, which the starter vouched for: this is NOT a re-read of the dataset by the child, so the child trusts its starter's load (same user, same scratch directory made 0700), and a file the starter did not write is refused. (3) The parent's serial merge: `readEpisode` already rebuilds every decision's observation to check it, and the loader rebuilt each a second time for the examples. `readEpisodeObserved` / `readTrainingObserved` hand the checked observations to `examplesOf` (new optional last parameter `known`; `EpisodeFeed` may yield them as a third element), so each is built once (the in-memory path, `memoryFeed` of `loadTrainingSet`, keeps the observations alive with its Episodes; the spilled path holds one Episode's at a time); they are used only when the engine's commit equals the Episode manifest's (the regime `decisionObservations` reads), else rebuilt as before. Tests: `test/pool-share.test.ts`, the generation file-for-file equality of an own and a shared pool in `league-generation.test.ts`, the observation-reuse equality in `training-loader.test.ts` (examples and stream equal the ones built without them), the parent-death test (a real process, its worker ends too; the module is `parent-link.ts`), the killed-child signal name and the digest line in `generation-cli.test.ts`, the commit-mismatch case (observations `undefined`, the loader rebuilds them) in `training-loader.test.ts`, and `training-loop.python.test.ts` still requires the sharded run (now reading the shared pool) to equal the single-process one.

The teacher is a `guardActor` `scripted` role: an overrun or any failure is a `baseline_failure` incident that fails the run. `teacher.json` holds the baseline identity hash, the budget and the per-game and summed integer counts (fallbacks, unsupported queries, epsilon plays). The damage-aware actor counts a fractional-priority speed order (Quick Claw and the like) as `unsupported` like the Focus-Punch limit (it was an uncaught `MechanicsProbeError`). Any other `MechanicsProbeError` from a query it built is a `ProbeRefusal`: that request is answered by the `actor-rule` candidate and counted in `probe_refusals` (new `DamageAwareCounts` field; optional `BaselineCounts.probe_refusals` in the LeagueRunRecord, a minor change within v1, written only above 0 so existing records keep their bytes, never above `queries`). Root cause of public-main-004's crash (game 604, `baseline_failure: the engine does not take that status`): the assumed opponent ability (first in vocabulary order, Limber) blocked a paralysis the player had SEEN, so the declared state was refused; `assumedFor` now rules out an unrevealed ability the engine refuses with the public status and assumes the next. The probes (`mechanics-damage.ts`, `mechanics-speed.ts`) declare a status as an observed fact (`setStatus(..., ignoreImmunities)`), so a type immunity (Corrosion on a Steel type) no longer refuses a query; an ability or engine hook still does. The pool request (`PoolRequest`) is the part of a run config that names format, dataset and excluded abilities, so `datasetTeamPool` serves teacher runs without a `TrainingRunConfig`. `--teacher damage-aware@v1|damage-aware@v3` (#1182; default `v1`, so absent keeps every byte of today's runs; anything else is a usage error, exit 2) selects the committed record the teacher plays (`TeacherSettings.teacher_version`, `teacherContext` loads `loadDamageAwareConfig(version)`, the actor's `commit` is `v3` or `v3-eps<ppm>`); the Episodes', the TrainingSet's, `teacher.json`'s and the printed line's policy id then say `damage-aware@v3` and `teacher_identity_hash` is v3's baseline identity (the one the scripted head to head reports), while the opponent games stay `random-legal@v1` / `actor-rule@v1`; `loadTrainingSet` under `damage-aware@v1` refuses a v3 run's Episodes, and `learner clone` takes a config naming `damage-aware@v3` with no contract change. v2 is not a teacher (it needs the belief port).

**KL anchor** (`ppo.anchor`, `ml/areneon_ml/learner/{config,ppo,trainer,state}.py`, `loop/driver.py`, ADR-019 §4, ADR-010 erratum A2 item 3, #968; `docs/training-run.md` section 5). Optional `{kl_micro, schedule}` in the `ppo` block (`kl_micro` 1 to 10^8; `schedule` is `constant` or `linear {final_micro 0 to 10^8, generations >= 1}`, schema defs `AnchorSchedule` / `AnchorLinearSchedule`, since the learning-rate `LinearSchedule` forbids a final of 0; a minor change within v1: absent keeps every hash, report and file); both readers require `warm_start`. The loss adds `beta * KL(pi_theta || pi_anchor)` per decision (`ppo.anchor_kl`: softmax over the real candidates, padding masked), `pi_anchor` the warm-start pair loaded by the driver (`_new_learner` calls `load_warm_start` again, a separate frozen copy: `Learner(..., anchors)`, required exactly when the config has an anchor; evaluation mode, `requires_grad` off) and scored once per generation per role with no gradient (`_anchor_scores`, one log-probability vector per step over its real candidates). `AnchorSettings.beta_micro(t)` is the integer rule of `learning_rate_schedule` started from `kl_micro`; `Learner.anchor_beta_micro(update)` decides what `t` counts: with `value_warmup` N the updates below N have beta 0 (policy frozen; no anchor pass, KL reported as 0) and update `u` >= N uses `t = u - N` (the decay starts with the first policy update; the learning-rate schedule keeps counting the warm-up), without it `t` is the update index. `RoleReport.anchor_kl` (mean over the role's minibatches, measured before each step) and `anchor_beta_micro` are in `train-report.json` only when the anchor is set (the dashboard reader's optional keys, both or neither, KL not negative; it charts "Anchor KL" beside approximate KL); the learner-state sidecar records `anchor_beta_micro` (the newest update's beta) only when set and `restore_state` refuses a sidecar whose beta is not the schedule's. The ADR-023 amendment is applied (#1046): when the run declares `generation.play`, the KL is between the tempered policies (both the trained and the anchor policy at tau; see Training play temperature). Tests: `tests/ml/learner/test_anchor.py` (reader and schema refusals, beta at 0, mid and past `generations` including the warm-up offset, the KL against a hand computation on three candidates, once-per-generation scoring, report and sidecar keys, resume), `tests/ml/loop/test_anchor.py` (a warm-started tiny loop with and without a warm-up: report and sidecar beta per generation, rerun and kills at four stages reach identical bytes) and the dashboard cases in `tests/ml/report/test_report.py`.

**GPU learner** (`ml/gpu-env/`, ADR-010 §4, §5.2, #840). The learner runs on the local GPU from a separate uv project, `ml/gpu-env/` (its own `pyproject.toml` and `uv.lock`, `areneon-ml` and `areneon-contracts` by path, `torch` 2.14.1 from the PyTorch cu130 index through `override-dependencies`; the root `pyproject.toml` lists it under the workspace `exclude`, it is never a member or in `SHIPPED`, its venv is gitignored). `cd ml/gpu-env && uv sync`, then run `ml/gpu-env/.venv/bin/python -m areneon_ml.loop run ... --worker-python <root .venv python>`: the learner is CUDA torch, the A1 worker stays CPU torch from the shipped closure (C-4). A config with `learner.device: "cuda"` is refused where there is no CUDA device (`configure_learner`), never replaced by the CPU, and `configure_learner` sets `CUBLAS_WORKSPACE_CONFIG=:4096:8` (if unset) with deterministic algorithms on (warn-only on CUDA). `python -m areneon_ml.learner bench --config … --engine-data … --stream-dir <generation dir> --repeats N` times the learner on a recorded stream (one untimed warm-up pass, decisions and optimiser steps per second, peak CUDA memory); the figures are measurements and are not claimed to repeat. **Run inputs for a rented machine** (ADR-024 section 3.5, slice S-b, #1078; `packages/schema/contracts/v1/run-input-manifest.schema.json`, `packages/showdown-bridge/src/run-input-manifest.ts`, `packages/team-dataset/src/run-inputs.ts`, `run-inputs-cli.ts`, `scripts/run-inputs.ts`). The machine pulls first, then runs: every public input of a run (the run config and the synthetic team dataset directory; the training split is never committed, so it travels through the inputs bucket) is fetched from the private inputs bucket and checked by hash before the loop starts, and the loop then reads local hashed files with no network I/O. Everything in git (engine data, the Showdown pin, lockfiles, code) is not copied: it comes from the repository at the manifest's commit. **Contract** `RunInputManifest` (v1, integers only, closed, `data_class` the constant `synthetic`; generated TS and pydantic types, corpus samples `run-input-manifest/` valid, invalid and reader-invalid): `run_key`, `commit` (40 hex), `run_config_hash`, `dataset_hash`, `config_file`, `dataset_dir` and `files` (`path`, `size` at most 268435456 (the shared client's one-object ceiling), `sha256`; 2 to 4096 files). `readRunInputManifest` adds what the profile cannot say, with fixed words that quote no path: every path (files, `config_file`, `dataset_dir`) is a safe relative path (`isSafeRelativePath`: `/`-separated segments of letters, digits, `.`, `_`, `-`, none empty, `.` or `..`; so no absolute path, backslash or space), files sorted by path (code units) and unique, also ignoring case (a case-insensitive disk would merge two paths), no path both a file and a directory, the config file among the files and outside the dataset directory, and a file under the dataset directory. It is stored as its JCS bytes (`runInputManifestBytes`); its hash (`runInputManifestHash`) is the SHA-256 of those bytes and is the ONLY authenticity anchor: every other check is a hash the manifest itself lists, so whoever can write the bucket can write a manifest that agrees with doctored files. The owner passes the hash (printed by `publish`) to the machine out of band, and `fetch` requires `--manifest-hash HEX` or an explicit `--no-pin` (never both, never neither). There is no Python reader (the fetch runs in Node); the Python models are generated and the corpus is classified identically by Ajv and python-jsonschema. **Keys and layout:** `runs/<run_key>/inputs/manifest.json` and `runs/<run_key>/inputs/files/<path>`; `runInputLayout(runKey)` is the layout injected into the shared client (`@areneon/object-store`; `team-dataset` now depends on it): those keys, the one listing prefix `.../files/`, no overwrite (`overwriteKey: null`), so any other key, another run's keys and `..` paths are refused before a request. **Owner side:** `buildRunInputs({engine, configFile, datasetDir, commit})` reads the config with `readTrainingRunConfig`, requires a `team_dataset` and `verifiedDatasetHash` of the directory (the dataset through `readDataset`) to equal the config's `dataset_hash`, lists every plain file of the dataset directory under `dataset/` plus the config bytes as `run-config.json` (a symbolic link or special file is `input_unsupported`, a file over the object ceiling `input_too_large`), and returns the manifest; `uploadRunInputs(store, inputs)` re-checks each local file's size and SHA-256 against its manifest entry just before it is put (`size_mismatch` / `hash_mismatch`), then puts every file and the manifest LAST with `putIfAbsent`: an interrupted upload leaves no manifest, and a rerun resumes, because on `exists` the stored object is read back and accepted only when its size and SHA-256 equal the entry's (else `hash_mismatch`); nothing is overwritten. **Machine side:** `fetchRunInputs({store, engine, runKey, outDir, headCommit, expectedManifestHash?})` refuses an existing `outDir`, reads the manifest (UTF-8 JSON, `data_class` synthetic, schema and reader rules, the stored bytes equal its JCS form, the optional hash pin, `run_key` equal to the requested one, `commit` equal to `headCommit()`, which the command takes from `git rev-parse HEAD` of `--repo`), lists `files/` and requires exactly the manifest's objects (no missing, no extra), downloads each (size, then SHA-256) into a hidden temporary sibling of `outDir`, reads the written config (`readTrainingRunConfig`; its `runConfigHash` must equal the manifest's, its `seeds.run_key` the manifest's, its `team_dataset.dataset_hash` the manifest's), runs the dataset hash check (`verifiedDatasetHash`, i.e. `readDataset`) on the written directory against the same hash, requires the config's `team_dataset.path` to resolve (relative to `cwd`, default the process's working directory) to `<outDir>/<dataset_dir>` (`dataset_path_mismatch`), fsyncs every written file and directory, and only then renames the sibling to `outDir`; on any failure the sibling is removed and nothing exists at `outDir`. It returns the directory, the dataset directory (`<out>/dataset`), the config file and the hashes. Decisions where the ticket left room: files go one at a time (no concurrency), a file over 256 MiB cannot travel (the client's ceiling; a bigger dataset needs chunking, not built), the command refuses a repository with uncommitted changes to tracked files (`git status --porcelain --untracked-files=no`, code `tree_dirty`), and the run config's `team_dataset.path` is part of its hash, so the owner writes into the config BEFORE publishing the path the machine will use (for example a relative `inputs/dataset` with `fetch --out inputs`, run from the repository root); the fetch does not rewrite it and refuses a config whose path is elsewhere. The 256 MiB ceiling is per file: the largest file of the gpu16 run's dataset (`records.training.jsonl` of `train-v1`) is 34,616,259 bytes, about 13% of it. **Errors:** `RunInputError` with a code in `RUN_INPUT_REFUSALS` (`run_key_invalid`, `output_exists`, `manifest_missing`, `manifest_not_synthetic`, `manifest_invalid`, `manifest_not_canonical`, `manifest_other_run`, `manifest_hash_mismatch`, `commit_mismatch`, `object_missing`, `object_extra`, `size_mismatch`, `hash_mismatch`, `config_invalid`, `config_hash_mismatch`, `config_other_run`, `dataset_hash_mismatch`, `dataset_invalid`, `dataset_path_mismatch`, `tree_dirty`, `input_unsupported`, `input_too_large`, `write_failed`) and a fixed message with no path, hash, key or credential; a store failure keeps the shared client's own fixed `ObjectStoreError`. **Command** `node packages/team-dataset/scripts/run-inputs.ts publish --run-config F --dataset-dir D --commit SHA --bucket B` (owner, write credential) and `... fetch --run-key K --out DIR --bucket B (--manifest-hash H | --no-pin) [--repo DIR]` (machine, read-only credential): the credentials come from the environment only (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL`, `AWS_DEFAULT_REGION`, optional `AWS_SESSION_TOKEN`), a command line that carries one is `credentials_on_argv` (exit 2, also when the option is unknown to the parser), a usage error exits 2, a refusal prints `run-inputs: <code>: <message>` and exits 1, success prints one JSON line. The logic is `runInputsCli(argv, deps)` with the store, engine and `headCommit` injected, so no test opens a socket; the script wires `R2ObjectStore`. No real bucket, provider or credential was touched by this slice: uploading the inputs of a real run is the owner's. Tests: `showdown-bridge/test/run-input-manifest.test.ts` (every sample, every reader message, paths, the JCS bytes), `team-dataset/test/run-inputs.test.ts` (byte-for-byte fetch, the first-generation plan and dataset hash equal on the fetched directory and the source, each tamper with its code and no directory left, the owner builder's refusals, the layout), `run-inputs-cli.test.ts` and `run-inputs-canary.test.ts` (markers in the five variables and the bucket over publish and fetch with echoing, throwing and malformed fakes; negative controls).
