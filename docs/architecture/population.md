# Population loop and ladder

The ADR-021 population: config, plan, ladder, rating, driver, selection, health and frozen pool.

Part of the architecture documentation split out of `CLAUDE.md` (index: [README](README.md)). Ticket references such as `#1179` point to Redmine (`redmine.piglor.com/projects/areneon`), where measured figures and verdicts are recorded.

**Population config and `population-seed/1`** (ADR-021 sections 2, 3, 5, 6 and 8, ADR-010 erratum A3, slice 1, #982; contracts and readers only, no loop behaviour). `TrainingRunConfig.population` is an optional, closed object (a minor change within v1; absent keeps today's bytes, `run_config_hash` and every committed config): `members` (code bound 1 to 16), `exploiters` (0 to 2), `seats_per_member`, `shares` (`ladder_ppm`, `self_play_ppm`, `past_pool_ppm`), `past_pool`, `rating`, `selection`, `explore.bounds` (inclusive `{min, max}` per tunable: learning rate, entropy weight, epochs, clip, optional target KL, and the three shares), `health`, `exploiter.reset_every` and optional `member_ppo` starting overrides (sorted by member). Integers only; every value (4 members, 500,000 / 250,000 / 250,000, the copy-rule thresholds) is config data, the code holds only the outer bounds. Reader rules in both readers (`readTrainingRunConfig`, `read_run_config`), each with a `reader-invalid` sample and a refusal test on each side: the shares sum to 10^6, `selection.min_roots` is at most `members`, `past_pool.max_past_per_member` is at most `max_size`, every explore bound contains its starting value (per member: its override, else the `ppo` value; shares start from `population.shares`), `member_ppo` is sorted, unique and below `members`, and a target-KL bound or override needs `ppo.target_kl_micro`. `Loop.__init__` refuses a config with `population` (`LoopError`: a population is run by `PopulationLoop`, below). `population-seed/1` (`packages/showdown-bridge/src/population-seed.ts` `populationDraw`, Python twin `ml/areneon_ml/loop/population_seed.py` `population_draw`) is SHA-256 over the JCS of `{run_key, generation, member, purpose, index}` with purposes `member-init`, `member-learner`, `opponent-draw`, `explore`, `bootstrap`; the first 8 bytes big endian as an unsigned 64-bit integer (a `bigint` in TS), reduced as each use states. Decision where the ADR left room: `member` is the label `m<k>` (learning member) or `x<k>` (exploiter seat) as a string, so a member and an exploiter never share a draw; `generation` and `index` count from 0 (generation 0 holds the initialisation draws). Six vectors computed with Python hashlib are pinned on both sides (the computation is in the test comments). Battle seeds and team draws keep `league-seed/1`.

**LadderRecord v1** (ADR-021 sections 4, 6, 8, slice 3, #984; `packages/schema/contracts/v1/ladder-record.schema.json`, generated TS and pydantic types, samples in `fixtures/contracts/v1/ladder-record/`, readers `packages/showdown-bridge/src/ladder-record.ts` (`readLadderRecord(value, previous?)`, `ladderRecordHash`, `checkLadderRecord`) and `ml/areneon_ml/loop/ladder.py` (`read_ladder_record(raw, previous, config)`, same rules and words); integers only, closed, `data_class` the constant `synthetic`). One record per population generation: `window`, frozen `anchors` (scale 10^9, `actor-rule@v1` exactly 10^9), `members` (strength with bootstrap `lower`/`upper`, generation-0 `root`, effective `settings` and opponent `shares`), frozen `snapshots` (`<member>@g<generation>`), the pair-score `cells` (member, opponent of kind `member`/`snapshot`/`anchor`, `scores` = pairs at 0/250000/500000/750000/1000000 ppm, `pairs`, `score_sum_ppm`), `cyclic_triples` and `selections`. Decisions where the ADR left room: (1) `selections` is an array, the first the copy test's outcome (`kind` `copy` or `none` with the failed Figure 2 condition), the rest `health` replacements sorted by member, so "at most one copy" is a reader rule and several quarantines can share a generation; (2) the members listed are the state at the decision (before the copy), so `roots_before` counts their roots and `roots_after` replaces the loser's root by the donor's; (3) a copy carries `margin_ppm` and its `lower_bound_ppm` must exceed 500000 plus it; its `pairs` equals the donor-against-loser cell, its donor has the highest member strength, and its anchor minima are recomputed from the anchor cells as an integer `floor(score_sum_ppm / pairs)` (every member has exactly one cell per anchor; pair counts and score counts are at most 10^9 so the sums stay below 2^53); a snapshot is frozen in a generation before the record's; (4) `previous` (generation - 1, same run and config) requires the same members, equal anchor strengths and unchanged strength and bounds for snapshots present in both; (5) the config tie (`checkLadderRecord`, `read_ladder_record(config=...)`, values from `population`, Python reads `config.raw`) requires a population, `members` equal to `population.members` (exploiter seats are NOT rated: ADR-021 sections 3 and 6 have them play the top member and never be copy targets, so the table holds learning members only), `window.size == rating.window`, a copy's `margin_ppm`, `pairs >= n_min` and `roots_after >= min_roots`, and a `none` with `root_floor` only when the members hold at most `min_roots` distinct roots (a copy changes the count by at most one). Nothing computes a strength here (slice 6), writes the record (slice 7) or copies (slice 8). Tests: `test/ladder-record.test.ts`, `tests/ml/loop/test_ladder.py` (one refusal per reader-invalid sample, same words), the corpus.

**Population plan and play on the simulator side** (ADR-021 sections 2, 3, 5 and 8, slice 4, #985; `packages/showdown-bridge/src/population-plan.ts`, `population-generation.ts`, `population-cli.ts`, `LeagueRunFactsV2`/`buildLeagueRunRecordV2` in `league-run-record.ts`; the Node half of the scheduler, the Python driver (slice 5) runs it). `planPopulation(config, generation, poolSize)` is pure and sits beside `planGeneration`, which is untouched (a config without `population` plans and plays byte-identically). Per member `m<k>` it schedules `seats_per_member` team PAIRS split by the three shares (`seatCounts`: floors, then the largest remainders, ties ladder, self, past; with one member the ladder share goes to self-play): ladder pairs against another member drawn uniformly by `population-seed/1` (`opponent-draw`, index = the member's i-th ladder pair), self-play pairs, then for each baseline of `generation.baseline_games` `games / 2` anchor pairs (an odd count is refused). A "seat" of `seats_per_member` is one scheduled pair the member initiated (it plays both of its games); an opposing member also holds a seat in, and gets Episodes from, the pairs others drew against it. Each pair has one global index (`league-seed/1`: battle seed, both team draws, baseline stream), its two games are `2 * pair + half` (the sampler's `game`), share the seed and, for ladder and anchor pairs, the teams, with the policies' seats swapped in half 1. A self-play pair swaps the two (kept distinct) teams' seats instead, since swapping one policy with itself would repeat the game. Teams are indices into the pool the caller passes, which is the run's dev and training teams (`datasetTeamPool`); a validation team cannot be named. Refused with fixed words (`PopulationPlanError`, a `GenerationError`): a non-zero `past_pool_ppm` without its committed pool (`PAST_POOL_MISSING`; the past pool is slice 10, below), exploiter seats, odd baseline counts. `playPopulationGeneration` starts nothing itself: it takes one started client per member (`PopulationMember`: pair policy id, checkpoint ids, client; distinct policy ids are required, since an Episode belongs to its member by `behaviour_policy_id`), plays waves in which no client serves more than `n_parallel` games (`populationWaves`; `beginGame` on every client a wave uses; a result never depends on the wave), each seat queries its own member's client and a baseline seat is a fresh guarded actor per game (`baselineActor`, `baselineRecords` shared with `playEntries`). Episodes go to disk at once under `members/m<k>/episodes/` (a member's seat under that member; a baseline seat's Episode under the member the pair was scheduled for, kept and not loaded, as in a single-lineage run), then each member gets `stream.jsonl` and `training-set.json` through the unchanged loader (`writeStoredTrainingStream` for its own policy id: it accepts a member's Episodes for that member and refuses them for another). A member with no Episode of its own fails the generation. `writePopulationGeneration` writes `plan.json`, `league-run.json` (`schema_version` 2) and `generation.json` last (`schema_version` 2: game rows carry `pair`, `half`, `kind`, `member`, `opponent`, `seats`; per-member `training_set_hash`, `examples`, `episode_hashes`). `buildLeagueRunRecordV2` follows the schema's counting rule (a member's entry holds every game it has a seat in; a game between two members is in both; self-play is one entry with the member as opponent and two Episodes; root totals are distinct games; `copy_decision_hash` null). `play-generation` takes `--member m<k>,PREVIEW,BATTLE,POLICY_ID` once per member for a population config (and refuses `--member` for any other, `--shard`, `--game-processes` and `--policy-workers` with a population: one process, one worker per member). `checkPopulationConfig` (the plan's refusals, the member checks, features and sheet) runs before the CLI creates any worker client, since each real-size session is about 445 MB peak RSS (measured, CPU). The single-lineage readers (`readers.read_plan`, `read_generation`, `read_run_dir_config`) refuse a population config, a schema 2 `generation.json` with members or a plan with seats in fixed words (`POPULATION_REFUSAL`, `tests/ml/inspector/test_population_refusal.py` over `fixtures/loop/population-play/`, which the TS test requires equal to a fresh run); the dashboard reads a population run since slice 11 and the inspector since slice 12b, each through its own population readers. Not here: an opponent sheet in a population run (refused; candidate features and game processes, #1333, see the paragraph after the driver's), training, freezing, copying, the ladder record and rating, the past pool, exploiters, the inspector and dashboard. `population-plan.test.ts` pins a small plan's SHA-256; `population-generation.test.ts` plays a tiny M = 2 generation on the stand-in worker (byte-identical rerun of every file, per-member loader acceptance and refusal, the v2 record through its reader, a forfeit, the CLI port); `team-dataset/test/population-pool.test.ts` checks no validation team is drawn.

**Integer Bradley-Terry rating** (ADR-021 section 4, slice 6, #987; `ml/areneon_ml/loop/rating.py`, pure: no I/O, torch or floats). Inputs are `ResultCell(player, opponent, scores)` (the record's `Cell.scores`; the reverse direction is implied, both directions add; `cell_totals` gives `pairs` and `score_sum_ppm`); outputs are the record's integers (`Strength` strength/lower/upper at scale 10^9, `cyclic_triples`). `fit_strengths(cells, rated, anchors)`: Ford/Hunter MM in Jacobi form, `T_i = sum floor(n_ij 10^18 / (P_i + P_j))`, `P_i' = floor(W_i 10^12 / T_i)` clamped to 1..10^15, exactly 64 iterations from 10^9, anchors fixed and absent from the output, one virtual 500000 ppm pair per rated player against `actor-rule@v1` (which must be an anchor at exactly 10^9); a rated player with no chain of real results to an anchor, an exploiter seat (`x<k>`) and an unknown id are refused (`RatingError`). The 64 fixed iterations compress the top (all-win pairs 10/100/400/1000 give 1.998e10/5.5e10/6.2e10/6.4e10 against exact 2.1e10/2.0e11/8.0e11/2.0e12; monotone, under-rated never over-rated, ordering kept): a player scoring above about 0.97 over 100 pairs is under-estimated; the copy gate uses `head_to_head_lower`, which does not go through the fit. Percentile bounds need not bracket the point estimate (`lower <= strength <= upper` is not guaranteed). `bootstrap_strengths(..., BootstrapPlan(seed, resamples, alpha_ppm))`: percentile bootstrap that redraws the pairs within each cell and refits, drawing `population_draw(run_key, generation, member, "bootstrap", lane << 32 | counter)` (lane 0 for the fit); a draw is two 32-bit pieces, `below(n)` rejects pieces at or above `floor(2^32/n) n` (nothing read for n = 1), the index picks the first score bucket whose running total exceeds it; bounds are `sorted[alpha B // 10^6]` and `sorted[B - 1 - alpha B // 10^6]`. `head_to_head_bounds` / `head_to_head_lower` (lane `LANE_COPY` = 2^20; a lane must be below 2^21 so the index stays under 2^53) give the one-sided bounds of a mean pair score for the copy test; `cyclic_triples` bootstraps each member pair `i < j` once on lane `1 + 64 i + j` (i over j when the lower bound exceeds 500000, j over i when the upper bound is below it) and counts triples with a directed 3-cycle. Callers pick distinct `member` labels or lanes per use. Tests: `tests/ml/loop/test_rating.py` (closed forms within 4 of x = w/(n - w), anchors, all-wins, refusals, pinned bootstrap digests, rock-paper-scissors, 100% line and branch coverage).

**Population loop driver** (ADR-021 sections 2, 7, 8 and 12, slice 5, #986; `ml/areneon_ml/loop/population.py`, `PopulationLoop`; `play.py` `PopulationPlayer` / `NodePlayer.play_population`; `league.py` `check_population_plan`). `python -m areneon_ml.loop run` on a config with `population` runs `PopulationLoop` (`__main__._run` picks it; `--policy-workers` and `--game-processes` reach the play side, #1333). `Loop` still refuses such a config and `PopulationLoop` refuses one without it, so a config without `population` behaves and writes exactly as before (the single-lineage determinism, resume and SIGKILL tests keep their bytes). Exploiter seats (a non-zero `past_pool_ppm` is played since slice 10) and an opponent sheet are refused as the play side refuses them (candidate features since #1333); the shares, `member_ppo` and the explore bounds are the config's, nothing is scheduled by them yet (ratings, `ladder.json`, copies, quarantine and the past pool are slices 6 to 10). **Per generation:** `play_population` runs the slice 4 script with `--member m<k>,PREVIEW,BATTLE,POLICY_ID` for every member, in member order, into the partial directory; the driver then checks the files (`generation.json` schema 2 of this generation; the `league-run.json` v2 through `read_league_run_record_v2`, naming exactly the pairs asked for, its forfeits and causes equal to `generation.json`'s and its games to the rows'; `plan.json` through `check_population_plan`: sha256 equal to `plan_hash`, one entry per game, each carrying the `league-seed/1` seed of its PAIR `game // 2`, not of its game index), and for each member in index order loads only that member's stream (`members/m<k>/stream.jsonl` and `training-set.json`, whose hash must be the one `generation.json` lists, with its own `behaviour_policy_id`), trains it with its own learner and writes its train report; one learner on the device at a time (the stream is dropped and, on CUDA, the cache emptied between members). Stage hooks fire `played`, `trained:m<k>` after each member, `trained`, `written`, `committed`. **Layout** of a committed `generations/g<NNNNNN>/`: `plan.json`, `league-run.json`, `generation.json` and `episodes` of the simulator side, `team-set.json` (the run's cumulative team set, one for all members), and per member `members/m<k>/` with `episodes/`, `stream.jsonl`, `training-set.json`, `train-report.json`, `learner-<g>.safetensors|json` and `records/{battle,preview}.json`; the manifest (`manifest.json`, written last, then one `os.replace`) holds `members: {m<k>: {checkpoints, learner_state_hash, training_set_hash}}`, `team_set_manifest_hash` and `run_config_hash` and the SHA-256 of every file; the committed checkpoints sit in the shared `checkpoints/` store. Partials are discarded at start; resume restores every member's learner (`restore_state`, hash checked), requires the manifest to hold exactly `m0..m<M-1>` and checks each member's weights against its stored checkpoint ids and its records against the state, training set and run config hash (a lineage other than `<lineage>.m<k>` is refused) before it continues. **Seeds (decided here; the draws are `population-seed/1` generation 0, reduced `& (2^63 - 1)` to the networks' seed range):** member `m<k>`'s Preview network is `member-init` index 0, its Battle network `member-init` index 1 and its learner generator `member-learner` index 0 (`member_config`; only seeds and the `member_ppo` starting values differ from the run's `RunConfig`, `raw` and `hash` stay the run's, so records and sidecars name the run config hash). **Generation-0 pairs (ticket decision):** a population run takes no warm start, or a Battle-only one (`warm_start: {battle}`): every member loads its own copy of the cloned Battle network (a separate `load_warm_start` each, the shared checkpoint id) and its Preview is seeded from its own `member-init` draw, so the pair ids differ (the play side refuses two members with one pair); a two-role warm start with `population` is refused by both config readers (`training-run-config.ts`, `learner/config.py`; corpus samples `valid/population-warm-start-battle-only`, `reader-invalid/population-warm-start-both`). At generation 0 the shared Battle checkpoint keeps the clone record, byte for byte, under every member (a checkpoint has one record; its `lineage_id` is the clone run's), and a resume of generation 0 checks it. `ppo.anchor` and `value_warmup` act on the warm Battle role of every member as in a single lineage. **Records:** the ordinary `CheckpointRecord` (`RecordFacts` gained the optional `lineage_id` and `league_opponents`, absent for a single lineage): `lineage_id` is `<lineage>.m<k>`, `parent` the member's previous checkpoint of the same role, `training_set_hashes` its own set, and `league_opponents` the Preview and Battle checkpoints, from the generation just played (the previous generation's frozen pairs), of every OTHER member it met in a game that was played (`opponents` entries of the member's v2 record with a `member` other than itself and `played > 0`), sorted; self-play, baselines and unplayed games name none. The provenance export of a population run is slice 12 (the paragraph after this one); the inspector and dashboard readers keep refusing a population run (the driver reads none of their readers). **Device residency:** every member's learner (networks, frozen anchors, Adam moments) is built and kept on the CPU; `_train_member` brings one to the device (`bring_up`, `move_learner`), trains it and parks it again (`park`, in a `finally`, then `empty_cache`), so one learner at a time is on the GPU; moving tensors changes no value, so learner-state hashes and checkpoints are identical (a test replaces `bring_up` and `park` and asserts one learner at a time and equal bytes). `_initial` asserts that the members' generation-0 pair ids are distinct (the seeds make that overwhelmingly likely; fixed message `population: two members start from the same frozen pair`). `league_opponents` uses the v2 record's per-opponent `played`, which counts games actually played (a forfeited game is in `games` and the forfeits, not in `played`), and `check_population_plan` also checks `half == game % 2`. `inspect` and `replay` read a population run since slice 12b and `report` since slice 11; only `inspect --resimulate` and `replay --progress-dir` refuse one by name (`refuse_population`, `__main__._refuse_population_dir`, `_SINGLE_LINEAGE_ONLY` is empty). **A member whose games all forfeited** has no Episode of its own, and the play side then fails the whole generation (`no Episode of m<k>'s frozen pair`, exit 1 from the script, a `PlayError` here, nothing committed): the driver keeps that fail-closed and adds nothing. **Run metrics:** one `RunMetrics` file per generation as before, with the phases summed over the members and the counts summed (games from the record, decisions and optimiser steps over members); the per-member counts are `metrics/members/g<NNNNNN>.json` (`{generation, members: {m<k>: {games, decisions, optimiser_steps}}}`, JCS, outside every manifest and hash, not under any contract: the `RunMetrics` contract is closed and has no member keys). **Seed fixes (#982 nits):** Python `population_draw` refuses a bool or a non-integer generation or index; the member regex stays the looser `[mx](0|[1-9][0-9]?)` of both twins (the config bounds members at 16 and exploiters at 2; a draw for an out-of-range member is the caller's error). Not here: throughput by game processes (#985's follow-up: shard by pair index over S processes each holding M workers), exploiters, the past pool, copies, quarantine, ratings. Tests: `tests/ml/loop/test_population.py` (a fake simulator side that writes slice 4's files from a tiny M = 2 plan: seeds, `member_ppo`, the layout, distinct pairs, record lineage/parent/league opponents, the team set, run metrics, byte-identical independent rerun, in-process kills at `played`, `trained:m0`, `trained:m1`, `trained`, `written`, `committed` and the next generation's `played`, each resuming to the same bytes, tampered resume refusals, every refusal of the simulator side's files, a single member, a Battle-only warm start and its resume), `test_play.py` (`--member` flags), `test_main.py`, `test_population_seed.py`, `tests/ml/learner/test_config.py`, and `packages/showdown-bridge/test/training-loop-population.python.test.ts` (the real Node script and workers: three generations of two members, an independent rerun, SIGKILLs of the process group at play, write and seal of generation 3, each resumed to the same manifests and learner-state hashes).

**Population loop: candidate features, shared trunk, game processes** (ADR-021, ADR-022, #1333; builds on #957, #1185 and #1271; every byte, hash and test of the single-lineage loop and of a population run without them is unchanged). The control config of EXP-A3 (probe-damage/1 `candidate_features`, `candidate_matchup`, `shared_trunk`, a Battle-only `warm_start` with `value_warmup` and the anchor) now runs as a population. **Candidate features:** `featureSetup` (the single-lineage builder, same refusal of a hash this checkout does not compute) is built in the population branch of `generation-cli.ts` and handed to `runPopulationCli`; every `PolicyWorkerClient` of the run (members' and snapshots') states the set at the handshake, and every seat that reads a worker (a member's and a past-pool snapshot's) gets `features: {configs, memo}` so it attaches the rows (a worker that stated a set refuses a query without rows), one memo per seat per game as in `playOne` of `league-generation.ts`; a builder refusal stays a `crash` forfeit. The seats of a snapshot are the same run's pair (one config), so each pair is set up from its own config by construction: the past pool, the ladder opponents and the self-play seats all read the run's set. The member's own seats leave the play-time sidecar (`writePlayRows`) as the single lineage does, and a post-game pass (`writeFeatureRows`) fills any gap; the loader (`writeStoredTrainingStream`) gets `features: {engine, configs, precomputed: readFeatureRows(...)}` per member, so the stream is the recomputed bytes either way (`test/population-features.test.ts`: one process with no rows directory against two game processes with one equals, every own Episode has its rows file equal to `episodeFeatureRows`, with the post-game pass turned off). The rows directory exists only with game processes (as in the single lineage); `population-generation.ts` `PopulationOptions.features` / `features_dir`. **Policy ids:** Python `PopulationFrozen.features` (the run's `features_hash`) is in every member's policy id (`PopulationFrozen.policy_id`, the generation-0 pair ids, the play request's `--member` ids, each past-pool snapshot's `policy_id`), absent for a run without the option (ids unchanged; `tests/ml/loop/test_population_features.py`). The progress evaluation of a member already derived its ids with `features_hash`. Each process starts workers only for the members that hold a seat in its slice (`membersPlaying`; the others get an unused client), K workers per member (`PopulationMember.peers`; `populationWaves(plan, n_parallel, workers)` gives a label n_parallel games per worker), and one worker per snapshot session, opened at the wave that first needs it as before. The team pool is loaded by the starting process and shared through the scratch directory (`obtainPool`, `--pool-file`), as in a single lineage. Not here: the per-process resource usage line (a population run prints none), `--profile` (still refused), a members' memory cap, the league smoke run of the control config at real size (the ticket's done-when, an operator run). **Driver flags `--max-concurrent-starts` and the memory guard (#1394):** the Python driver now passes `--max-concurrent-starts N` to the play script (single lineage and population; only when given, so the default command line and Node's default of 2 are unchanged; `NodePlayer.max_concurrent_starts`). `ml/areneon_ml/loop/memory_guard.py`: before each play phase `NodePlayer` (`memory_guard`, default on, `--no-memory-guard` off, `meminfo` a test seam) compares `MemAvailable` (swap not counted) less a 4 GB driver reserve with `S` x an estimate per game process (the largest game process and policy worker peaks of the newest `metrics/g*.json` that has both, a worker term of `K` x `min(members, 1 + ceil(members / S))`; else 0.6 GB + 0.43 GB per worker with every member counted); the population play script now prints the `resource_usage` line and a further game process writes `usage.json`, so population metrics carry `peak_rss_bytes` game_process and policy_worker (`population-cli.ts`) and refuses with a fixed `PlayError` message naming the largest `S` that fits; it never lowers `S`, does nothing where `/proc/meminfo` is unreadable, and moves no hash or file (docs/training-run.md, sizing). **Frozen past pool with integer PFSP and frozen-rated snapshots** (ADR-021 sections 3 and 4, slice 10, #991; `ml/areneon_ml/loop/past_pool.py` (pure) and `packages/showdown-bridge/src/past-pool.ts` (its twin, which the plan calls), `population-plan.ts`, `population-generation.ts`, `population-cli.ts`, `generation-cli.ts`, `ladder_write.py`, `population.py`; a config with `past_pool_ppm` 0 is byte-identical to before: no `past-pool.json`, no new manifest key, no `past` games). **Membership:** a snapshot `m<k>@g<G>` is member k's frozen pair at the end of generation G; every `past_pool.snapshot_every` generations (generation 0 included: the seeded or cloned start pairs) each member's pair joins, the pool is capped at `max_size` with the oldest evicted first and generation-0 pairs never evicted (so the pool passes the cap by exactly those); eviction is a function of the committed generation alone (`pool_keys` / `poolKeys`, both sides held to the same cases). **The committed file:** every committed generation of such a run holds `past-pool.json` (JCS, in the manifest, named by the manifest's `past_pool_hash`): the pool the NEXT generation plays (each snapshot's id, member, generation, `policy_id` and checkpoint ids) and each member's pair-score counts against each pool snapshot over the rating window ending at that generation. The plan of generation g reads only g-1's file (`--past-pool` of `play-generation.ts`, required exactly when the config has a past-pool share, refused otherwise), so it stays a pure function of committed bytes and a killed generation replays the same plan (`readPastPool` / `read_file` check the run, the sort order, that the snapshots are exactly the pool the config gives at that generation, and the cells). **Decision (the ticket reads the weights from `ladder.json`):** the weights come from `past-pool.json` instead, because the LadderRecord's `Snapshot` requires a frozen strength and so can list only a snapshot that already has `n_min` pairs, while PFSP needs the counts of young snapshots too (a young one would otherwise keep the largest weight until rated); the file is built from the same window rows as the ladder. **PFSP `f_hard`:** `w = max(floor_ppm, (10^6 - s)^p // 10^(6 (p - 1)))`, `s = score_sum_ppm // pairs` of the member against the snapshot (BigInt on the TS side: p goes to 16); a snapshot with no games gets 10^6, the largest weight the rule gives. **Draw (`drawPast` / `draw_past`, `opponent-draw` indices `PAST_SELECT_BASE` 1,000,000 + j and `PAST_ASSIGN_BASE` 2,000,000 + i, clear of the ladder's `0..`):** the candidates are the pool minus the snapshots whose policy id is the member's own current pair (one policy on both seats); at most `min(max_past_per_member, candidates, past pairs)` distinct snapshots are drawn one by one without replacement, weighted; each past pair then takes one of those, weighted again; the 64-bit draw is reduced modulo the weight total (bias below 2^-40; all-zero weights count as equal). A member with no candidate gives its past pairs to self-play. `planPopulation(config, generation, poolSize, {pool, current})`; the order within a member is ladder, self-play, past, anchors; a past game is kind `past`, its snapshot seat `{snapshot, policy_id}`. Vectors for the draws are computed with the Python twin and pinned in `past-pool.test.ts` and `test_past_pool.py`, and the driver re-draws every member's past pairs from the committed file and refuses a `plan.json` that differs (`_check_past_plan`). **Play:** a snapshot has its own frozen worker session (`PastOptions.open`, one `PolicyWorkerClient` on the snapshot's checkpoints), opened by the wave that first needs it and closed after the last wave that uses it, so only the snapshots in use are resident (at most `members * max_past_per_member` over a generation); its Episodes are kept under the member the pair was scheduled for and never loaded (the loader takes an Episode only for the policy that played it, as for a scripted baseline). In `league-run.json` a snapshot is an opponent named by its pair's policy id, like a baseline without a report (no schema change); `generation.json` rows have `kind: "past"` and `opponent` the snapshot id; the sealed checkpoint records add the snapshots met in played games to `league_opponents`. **Frozen-rated snapshots:** `build_ladder_record(..., pool)`; a pool snapshot listed in the previous record keeps its strength and bounds untouched (the `previous` check enforces it) and is a fixed reference of this record's fit (`rating.bootstrap_strengths` takes it in `anchors`); a pool snapshot with `selection.n_min` pairs in the window and no strength is rated once, against the anchors, the frozen snapshots and the members' fitted strengths held fixed (bootstrap lane `LANE_SNAPSHOT + 16 * generation + member index`, new `lane` argument of `bootstrap_strengths`, default unchanged), listed in the record and in the fit from the next record on. Cells against snapshots without a strength are not in the record; an evicted snapshot leaves the record and its old results are dropped. Tests: `test_past_pool.py` (eviction order, the generation-0 rule, hand-computed weights, the floor, the no-games maximum, the cap, the file readers, rating at entry, freezing, eviction, a tiny loop with `snapshot_every` 1: rerun byte-identical, kills at three stages resume to the same bytes and the same plan, a swapped plan refused), `past-pool.test.ts` (the same vectors, the pinned plan hash from a fixture pool), `population-past.test.ts` (real engine, stand-in workers: lazy sessions, the record, Episodes, byte-identical rerun, the CLI port) and `generation-cli.test.ts`. **With the copy step (slice 8):** snapshots are immutable frozen pairs, so a copied slot's earlier `m<k>@g...` snapshots keep the old lineage under the same label; the counts of `past-pool.json` use the copy cut of the NEXT record (`snapshot_cells`: a slot copied in c meets the snapshots afresh from the pair frozen at the end of c + 1), a copy decided in the generation being sealed does not cut (the old pair still plays the next generation); the pool is sealed from the generation's final frozen pairs, after training and the copy step. **Checks:** `_check_past_plan` also requires each member's past pair count to equal the configured count (`past_pairs`, the twin of `seatCounts`) when it has a candidate snapshot and 0 otherwise; `read_file` raises `PastPoolError` for every malformed input (keys, types, bools, member names, `policy:<64hex>` and 64-hex pair ids, as the TS reader); a run refuses to start when `LANE_SNAPSHOT + 16 * generations + 15` would reach the copy test's lane.
