# Damage kernel (ADR-030 step 3)

A clean-room integer implementation of the Champions damage computation behind the mechanics probe's interface, the CPU reference of ADR-030 step 3. It answers `damage` mechanics queries (the `rows` and `threats` arrays of the feature builders) with the probe's exact bytes, for **training games only** and only for content admitted by byte-equality with the pinned probe through the differential harness ([differential.md](differential.md)). The probe stays the definition and the evaluation path (ADR-016 as amended by ADR-030). Ticket figures and verdicts are on Redmine #1457.

Part of the architecture documentation split out of `CLAUDE.md` (index: [README](README.md)).

**Not wired.** No training run, loader or evaluation path uses the kernel in this step: `generation.backends`, routing in the batch seam, per-entity fallback counts in run metrics and the per-generation shadow check (ADR-030 common rules 4 and 5) are the next part of #1457. A source scan (`packages/team-dataset/test/differential-kernel.test.ts`) requires that only the kernel's own modules, the bridge index, the differential composition root and its script name it: a module specifier of a kernel module, a named import or a destructured dynamic import or require of a kernel name from the package index, a namespace binding of the index (`import * as`, a dynamic import or require bound to a name) that reads a kernel name off it, or an `export *` of the index (negative controls show each form is flagged and a namespace import that reads no kernel name is not).

**Modules** (`packages/showdown-bridge/src/`):

- `damage-kernel.ts`: `prepareQuery` decodes one `damage` query (the probe envelope's validated sets) into the numbers `getDamage` reads, or a finished outcome (`unsupported` `query_kind` for a status, multi-hit, fixed-damage or OHKO move, or a move the record marks as failing; all-zero vectors for an immunity), or throws `KernelAbstain` naming the entity it does not implement (`<kind>:<id>`, a fixed `why`). `computeBatch` runs the roll loop of a batch over struct-of-arrays `Int32Array` columns (base damage, final-modifier chain, flags, weather, same-type and type modifiers): 16 no-crit and 16 crit rolls per query. Integers only: every division is exact integer division, every modifier the engine's 4096-based integer (`modify`, `chain` = `chainModify`). `KERNEL_FORMAT` (4) is bumped when it computes anything differently or covers more.
- `damage-kernel-data.ts`: the pinned engine's DATA for the format's mod, read once per engine and format (`kernelData`): species base stats and types, natures, the type chart, moves' damage fields, Mega Stones, hook ordering siblings, `breakable`. **Inertness by reflection:** an ability, item or move is inert when none of its data keys is a hook the probe's damage path can reach; a hook is any key starting `on` or ending `Callback` (constants such as Battle Armor's `onCriticalHit: false` included; ordering siblings such as `onModifyAtkPriority` excluded), also inside `condition`, `secondary`, `secondaries` and `self`. `INERT_HOOKS` is the reviewed list of hook names that cannot change a `damage` answer in the probe's flow (after-hit, residual, switching, speed, accuracy, PP, healing, item-taking, trapping, boost-application and volatile-adding hooks, a switch-in's `onStart`, whose stages, item and field the declared state overwrites); `STATUS_HOOKS` are inert only without a declared status on the holder. `simLiterals` scans the pinned simulator sources for ids the code tests by name (`hasItem('ironball')`, `hasAbility('levitate')`, `move.id === 'facade'`, volatiles by name, `.includes` lists): such an id is non-inert whatever its hooks.
- `damage-kernel-effects.ts` and `config/backends/<format>.damage-kernel.effects.json`: the reviewed effects record (abilities, items, moves and, since format 3, `conditions`: weather damage modifiers by type and their excepted moves, a weather's direct stat modify, terrain boosts, weakened moves, halved types and the priority block, screens and what a two-category screen yields to; code holds only the mechanism, owner rule R7). `checkKernelEffects` holds every entry to the engine's data: its kind must explain each damage-path hook of its entity (a `no_damage_effect` entry names exactly the hooks it `hides`), else `KernelRecordError` (the backend throws, never routes). The kernel holds effect KINDS (how each step of `getDamage` applies one: `pinch`, `base_power_flag`, `stab`, `no_crit`, `guts`, `attack_multiplier`, `source_type_attack`, `technician`, `super_effective_taken`, `full_hp_taken`, `crit_damage`, `defense_multiplier`, `ground_immunity`, `suppress_weather`, `mold_breaker`, `absorb`, `flag_immunity`, `infiltrator`, `priority_block`, `ate`, `sheer_force`, `unnerve`, `type_boost`, `resist_berry`, `final_modifier`, `super_effective_dealt`, `category_power`, `crit_ratio`, `status_power`, `constant_power`, `boost_power`, `needs_sleep`, `fails`, `no_damage_effect`); which ability, item or move has which kind, and its type, flag, 4096-based modifier or threshold, is data, never code (since format 4 also the pinch abilities' modifier and HP threshold, a `{numerator, denominator}` fraction of the maximum HP, Guts' modifier and each resist berry's modifier). What stays in code are the damage FORMULA's own constants (`getDamage` and `modifyDamage`: the spread reduction, the same-type bonus, the burn halving, the critical-hit multiplier and the crit-ratio table), which belong to no ability, item, move or condition. The record is bound to the pin (`showdown_commit`); another pin's record makes the kernel abstain on every query (`state:effects_record`).
- `damage-kernel-backend.ts`: `kernelBackend(engine, {config, snapshot?, backend_commit})` is the kernel behind the probe interface, a level-1 `Backend` of the harness: a batch of parsed queries in, outcomes in order. The result envelope (identity, set check, scope check, scenario check) is the probe's own (`probeEnvelope` in `mechanics-probe.ts`, factored out unchanged), so a result differs only in what the kernel computed. A query of another kind and every abstention is a `KernelAbstain` outcome; `counts` holds answers and abstentions by entity (the per-entity fallbacks run metrics will report).

**What KERNEL_FORMAT 4 covers:** the set's species forme (a Mega or battle-only forme as a set's own species abstains) or the Mega forme its stone makes; Champions Stat Point stats; absolute stages; declared HP and status; Physical and Special moves with a fixed base power and single or spread targets, with `willCrit`, `critRatio`, the stat overrides, `ignoreDefensive` and `ignoreImmunity` from data; type, absorbing and flag immunities and Psychic Terrain's priority block (all-zero vectors); rain, sun, sand and snow, the four terrains, Reflect, Light Screen and Aurora Veil, Trick Room and Tailwind, burn; the effects record's entries; a declared history with no volatile and no pending slot condition whose facts the engine would accept (used moves of the set, engine moves and items, no attacker list or stall counter: the probe refuses or checks those against its own state). **Event order:** the handlers an event finds are ordered as the engine orders them (order, priority, speed, sub-order, from the data's ordering siblings); two Pokemon's handlers tying on order and priority (their speeds decide, or the engine draws) or two conditions tying on equal sub-orders, the same side's included (the engine draws their order: two screens on one side), make the kernel abstain (`state:handler_tie`).

**Admission** (`packages/team-dataset/src/differential-kernel.ts`, the composition root; `scripts/differential-kernel-admission.ts`). An abstained query routes to the engine and is no evidence either way, so only COVERED queries are compared and tallied (the harness would read an abstention as a difference); coverage is counted beside the tally. Queries are the ones the feature builders issue (`collectQueries`, `probe-damage/2` and `probe-outcome/1`). Regression corpora: the committed random, search-fidelity and unavailable corpora (debugging evidence, never admission). The fresh corpus: seeded random-legal battles on the generator pool (the `fixtures-v1` dev split, Illusion excluded as the run configs do), battle `i` drawn from `fresh-<freshSeed(kernel)>` (`freshBattle`), so it cannot exist before the kernel's commit is frozen; the first 200,000 distinct covered damage queries in battle order. `differential-kernel-admission.ts fresh --commit SHA --shard K/S` plays shards in parallel (it refuses unless every file of `KERNEL_INPUTS` equals the frozen commit's: the kernel's four modules, its effects record and the mechanics inventory, and the whole probe envelope it shares, `mechanics-probe.ts`, `mechanics-ko.ts`, `mechanics-scenario.ts`, `mechanics-query.ts`, `mechanics-result.ts`, `canonical-json.ts` and the mechanics config `config/mechanics/<format>.json`), `ledger` merges them in battle order (only battles every shard finished), compares the kernel with the recorded probe answers, adds the committed, targeted and interaction-sweep corpora as regression corpora (a difference in the last two refuses to write), and writes the `BackendAdmission` ledger in its lines form (`config/backends/<format>.damage-kernel.admission.jsonl`) and a counts report; `regression` prints coverage, differences and abstentions per committed corpus; `bench` times the kernel and the probe on the same queries.

**Tests:** `packages/showdown-bridge/test/damage-kernel.test.ts` (ADR-016's hand-worked damage fixtures covered and equal; targeted queries for every entry of the effects record, as attacker and defender, across six field states, statuses, HP and stages; data rules; history; batch order; every abstention rule; the stat formula, stages, the record's reader, reflection and the simulator scan); `packages/team-dataset/test/differential-kernel.test.ts` (zero differences on the first battles of each committed corpus with a coverage floor; negative controls: a perturbed roll is caught at `$.answer.no_crit[3]` naming the move, and a kernel that answered in place of an abstention is caught; a small fresh corpus's ledger is read by the reader and admits nothing below 200,000 items; the committed ledger is this pin's; the isolation scan). Both were run first against a stub kernel (every roll 0) and failed (commit `238b0c04`), then against the kernel and passed.

**Speed** (format 4; `differential-kernel-admission.ts bench`, 10,000 damage queries of the committed random corpus, one thread, nice 19, a shared machine at load 2 to 3): kernel per covered query median 0.116 ms, p99 0.541 ms; the probe on the same queries median 1.96 ms, p99 9.10 ms (18.6x on the mean); 45% of the probe's time on those queries is on queries the kernel covers (41.5% on a 13,334-query sample of search-fidelity). Projection (ADR-030's shares: rows and threats 53% of the builder, the builder 45 to 65% of play, play 75% of a generation): builder time to about 0.78 (1.28x), a generation to about 0.90 to 0.93. **ADR-030's speed gate (builder 1.5x, `T'/T` at most 0.85) is not met**; it needs about 75% of the probe's damage time covered. The kernel's per-query time is mostly the probe's shared envelope (query hash, validated-set memo), not the roll loop. Format 3 measured the same within noise (0.115 ms against 2.07 ms, 24x, at load 7).

**Format 3 (review of PR #415).** Body Press (`overrideOffensiveStat`) attacks with the user's Defense, but the pinned engine sets the stat event from the category right before it runs it (`sim/battle-actions.ts`: `attackStat = (category === 'Physical' ? 'atk' : 'spa')`, then `runEvent('Modify' + statTable[attackStat], source, ...)`), so the user's ModifyAtk hooks run and snow's Defense hook does not; the kernel already did this (a probe-against-kernel test of Abomasnow's Body Press in snow passed before any change). Psyshock's defending stat, Foul Play's attacking Pokemon and stages, Shell Side Arm's hook (abstained) and the direct weather stat modify are tested per class the roster reaches; Body Press with Fur Coat, Huge Power or Guts, a snow or sand defender with another defence modifier, and Photon Geyser are not reachable at this pin (the arithmetic is tested on `applyStatHandlers`). `onUpdate` is no longer inert. Inert hooks that are inert only because the probe declares the state absolutely (a switch-in's `onStart`, boost-application, item-taking) are named as such in `INERT_HOOKS`' comment.

**Regression corpora that must be fully equal or abstained** (the ledger script refuses to write a ledger otherwise):
- the **targeted corpus** `fixtures/backends/<format>/damage-kernel-targeted.json`: one reviewed query spec per case a review, a fresh admission corpus or a per-generation shadow check found, each with its `reason` and `source`. **Every future difference found by any of those gets an entry here**, so it can never come back. It holds Body Press in snow (both sides), Psyshock and Foul Play cases, snow and sand defenders, Shell Side Arm, and format 1's Magician draw and Electric Surge status refusal;
- the **interaction sweep** (`interactionSweep`): one query for every reachable combination of a move with an unusual stat or event rule (a stat override, Foul Play's target, ignored defence, a set or raised crit, a spread target, priority, ignored immunity) or one ordinary damaging move per type, with every ability, item and condition of the effects record on the side it acts from; and, since format 4, the condition x entity crossings: every weather, terrain and screen of the record with every stat- or damage-modifying ability and item (as attacker and as defender) on up to two of those moves the condition changes (a type it boosts or weakens, the stat or category it modifies; a weather's stat rule takes a defender of its type), where the roster holds such a Pokemon; derived from the record and the engine's data, never by hand: 16,038 queries at this pin with the crossings (13,981 answered, 2,057 abstained; format 3's sweep without them had 13,766). CI runs every 20th; the admission flow runs all of it.

**The committed ledger** is a lines form (`admissionLines` / `readAdmissionLines` in `@areneon/differential`, `backend_admission_lines` / `read_backend_admission_lines` in `areneon_contracts.backend_admission`): a header line, then one canonical (RFC 8785) line per entity, pair and revocation in the ledger's order. It reads back to the very ledger, so `admission_hash` (over the JCS of the whole ledger) is unchanged; it diffs line by line, so a format bump is a reviewable diff, not a new single-line blob. Both readers refuse a missing header, a line out of order, a non-canonical line, a line of another kind and a missing final newline. `KERNEL_INPUTS` names every file whose bytes can change a kernel answer (the kernel's modules, the effects record, the shared probe envelope `mechanics-probe.ts`, `mechanics-ko.ts`, the mechanics inventory fixture); the script refuses a fresh run or a ledger unless they equal the frozen commit's, and a test requires the committed ledger's frozen commit to hold the same inputs (`git diff`, the CI job has the full history), its fresh seed to be `freshSeed(backend)` and its `admission_hash` to equal `KERNEL_ADMISSION_HASH`.

**Conservative abstentions (deliberate over-refusal, each costs coverage, never correctness):** any declared volatile and any pending slot condition; a declared attacker list or stall counter; two Pokemon's handlers on equal order and priority, and two conditions on equal keys (two screens on one side: the probe answers `random_effect`, the kernel abstains); a declared status beside an ability that starts a condition with a status hook; any `onUpdate` holder; a Mega or battle-only forme as a set's own species; a format whose level is not the set's; a single target other than `normal`, `any`, `adjacentFoe` and `randomNormal`; a powder move; a move with a base power of 0; a weather or terrain the record does not list.
