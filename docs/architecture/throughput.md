# Throughput harness

Decisions per host-core-hour of an arm of the throughput comparison, measured the same way for every arm: the current Showdown path, a native engine or a GPU engine. Part of the architecture documentation split out of `CLAUDE.md` (index: [README](README.md)). Ticket references such as `#1507` point to Redmine (`redmine.piglor.com/projects/areneon`), where measured figures and verdicts are recorded.

**Where it lives.** `packages/team-dataset/scripts/throughput-bench.ts` (thin) over `packages/team-dataset/src/throughput/` (`cli.ts`, `runner.ts`, `guard.ts`, `monitor.ts`, `procfs.ts`, `arms.ts`, `showdown-arm.ts`, `system.ts`, `summary.ts`); the contract `packages/schema/contracts/v1/throughput-record.schema.json` (generated TS and pydantic types, samples in `fixtures/contracts/v1/throughput-record/`) with its reader `packages/showdown-bridge/src/throughput-record.ts`; and `ml/areneon_ml/loop/play_ids.py`. Tests are `packages/team-dataset/test/throughput/` (a fake arm and a stand-in for the play script run as real process trees), `packages/showdown-bridge/test/throughput-record.test.ts` and `tests/ml/loop/test_play_ids.py`. Linux only (it reads `/proc`). It is an ordinary tool: no arm is changed to be measured, and nothing a run writes is read by a run, a hash or a gate.

## The unit of comparison

**decisions per host-core-hour = decisions x 3,600,000 / host CPU ms of the arm's whole process tree, launch to exit** (truncated to an integer; 0 when no CPU was counted, and such a run is void).

- **Host CPU** is the user plus system time of every process the arm started and every thread of each, summed over the run from launch to exit. It is read exactly: the kernel adds a process's CPU time, and that of the descendants it waited for, to its parent's `cutime` and `cstime` when the parent reaps it. The harness starts the arm as its child in a process group of its own, so the change of its own `cutime + cstime` between starting the arm and the arm's exit is the CPU of the whole tree, to the clock tick (10 ms). That covers game processes, policy workers, launchers, record writers and the Python host of a GPU arm. The GPU's own time is not host CPU; a GPU arm's host driver thread is.
- A **decision** is full: one policy query answered for the learned pair (Team Preview, move or forced switch), with the engine step to reach it, the legal mask, the features, the encoding, the policy forward and the sampling its request kind has. Decisions of scripted baseline seats are not counted (they have no policy forward) but their CPU is, because the arm spends it; the report states them apart (`scripted_decisions`) so an arm that plays no baseline games is visibly doing less. For the Showdown arm a decision is a training example of the play script's loaded stream (the pair's seats of every played game), so a forfeited game's decisions are not counted.
- **Games** are games run to their end, forfeits included; `games_on_showdown` is how many of them the pinned Showdown engine played (all of them for the Showdown arm, 0 for an arm that plays the sub-pool natively).
- Also stated per run: decisions per wall-hour (over the run's wall clock), decisions per GPU-hour (over the wall clock the GPU was allocated, only for an arm that uses it) and, only when the arm states the CPU of each warm-up and tear-down phase, `decisions_per_core_hour_steady` (the same with those phases' CPU taken out). Start-up (pool load, worker start, kernel compile) and tear-down are INCLUDED in the headline; a short plan therefore understates every arm. Use plans of at least 2,000 games. The Showdown arm states its phases from the play script's profile with no CPU per phase (the profile times wall clock), so its steady rate is null; two plan sizes of one arm give the marginal rate by difference when it matters.

## Measuring the arm

The harness (`runner.ts`) starts the arm with `detached: true` (so the arm leads its own process group), stdout and stderr in files, and:

1. walks `/proc` every second (`--proc-interval-ms`), follows the descendants of the arm's root by parent pid, and keeps per process (told apart from a later process that reuses its pid by its start time) the last CPU reading, the peak resident set and the role (decided again at every walk: a forked child shows its parent's command line until it execs). `by_role` in the record is that split; `sampled_ms` is its sum and `unsampled_ms` the part of the exact total the walks did not see (processes that ended between two walks). A walk that sees more than the kernel credited, beyond one tick a process, makes the run void (`accounting_mismatch`);
2. reads `/proc/loadavg`, `/proc/meminfo`, `/proc/stat` and `nvidia-smi` every minute (`--condition-interval-ms`; ADR-028 section 1: "sampled every minute and journaled", `conditions.jsonl`), reads `MemAvailable` at every walk as well, so a memory floor that breaks is seen within a second (and the minute sample is brought forward), and runs one long-lived `nvidia-smi -lms 1000` for the GPU's utilisation and memory (its own CPU is `helper_ms`, read before it ends and never part of the arm; the harness's own CPU is `harness_ms`);
3. after the arm exits, reads the CPU figure and the wall clock first, then looks for processes left in the arm's process group or session (any live one is ended and the run is void: its CPU was never credited), stops the GPU monitor, takes the end sample and reads the arm's report.

Helpers that spawn and reap a process (git, `nvidia-smi`, the Python ids helper) run before the arm starts or after its CPU is read; the harness reaps no other child in between. A harness SIGINT or SIGTERM ends the arm's process group and voids the run.

## Idle-machine conditions (ADR-028 section 1)

`--mode idle` (the default) enforces the ADR before the start, and refuses to start (exit 3, nothing written) unless every one holds: 1-minute load average at most 1.00; system-wide CPU at most 7% busy over 5 s (`--start-window-ms`); no other run, training, evaluation or benchmark process (commands matching `BUSY_PATTERNS` in `guard.ts`, which includes the policy worker, the play script, `vitest` and `pytest`; add the owner's queue scripts with `--busy-pattern`); `MemAvailable` at least 8 GiB (`--min-mem-gib`); an idle GPU (at most 5% and 2000 MiB, where there is a card). During the run it records, per minute sample, a breach of: `MemAvailable` below 4 GiB, swap in use above its start value, or another run appearing; the first breach of each kind is in `conditions.breaches` and makes the run void. A memory breach also ends the arm (`--no-abort` turns that off), so a run beside other work cannot take the machine down. Load is not a run condition: the arm loads the machine itself.

`--mode non-idle` is the labelled way to measure beside other work (a training queue): it enforces only the memory floors, records everything else, and every summary says "a relative measurement, never a gate figure". `--wait-idle-minutes N` retries the start every 15 s for N minutes before giving up. `guard` prints the same check without starting anything.

A run is void (`valid: false`, `void_reasons`, recomputed by the reader) for exactly: `arm_failed` (exit code not 0), `aborted`, `survivors`, `no_decisions`, `memory_run`, `other_run`, `swap_growth`, `accounting_mismatch`. A void run is kept and listed, and left out of the medians of `summarise`.

## The record and the arm report

`ThroughputRecord` (contract v1, integers only, closed) is the arm-independent result; the harness is its only writer. Its `report` is an `ArmReport`, the one thing an arm writes: `{schema_version: 1, arm: {id, label, parameters[{name, value}]}, plan: {pool_id, pool_hash, plan_hash, config_hash}, counts: {games, games_forfeited, games_on_showdown, decisions, scripted_decisions}, phases[{name, kind: warmup|play|teardown, wall_ms, cpu_ms|null}], stages[{name, ms}], gpu_used}`. It states nothing about CPU, wall clock or the machine. `stages` are process-milliseconds of the pipeline stages (the Showdown arm: `engine_step`, `legal_mask`, `features`, `observation`, `policy_encode`, `policy_forward`), sorted by name. A Python arm validates its file with the generated model, `areneon_contracts.models.v1.throughput_record.ArmReport`; the schema also validates it as `#/$defs/ArmReport`, and the TS reader is `readArmReport`. `readThroughputRecord` recomputes every derived field (rates, sums, void reasons, the valid flag), so a record with a changed number is refused; it states a rule and never repeats a value.

A record also holds the machine (logical CPUs, memory, CPU model), the code (commit, engine pin, `tree_clean`: whether tracked files had uncommitted changes, in which case the commit does not name the code), the conditions (mode, thresholds, start and end samples, extremes, breaches), the window (start, wall clock, exit code, whether the harness ended the arm), the host CPU and the GPU figures. Two records are comparable only when `plan` (pool, plan hash, config hash), the code and the mode agree; `summarise` says "not comparable" where runs of one arm differ.

## Arms

- **`--arm showdown`** runs `packages/team-dataset/scripts/play-generation.ts` as the generation loop runs it (`--config`, `--generation`, `--policy-id`, `--preview`, `--battle`, `--run-dir`, `--engine-data`, `--encoder-version`, `--worker-python`, `--out`, `--policy-workers`, `--game-processes`, plus `--profile`, whose timers only read clocks) from the repository root. The run directory is read only (checkpoints and `run-config.json`). The policy id and the encoder version come from `--policy-id` and `--encoder-version`, or from `python -m areneon_ml.loop.play_ids` (`--ids-python PATH`: the driver's own `Frozen.policy_id` and `encoder_version`, so temperature, batched inference and candidate features enter the id as in a run). `--game-processes 4,6` plays both settings, interleaved: round r plays every setting before round r+1 (`--repeats N`), each as `<run-id>-gp<S>-r<r>`. The report is built from the script's summary line (`examples` = decisions), the `league-run.json` it leaves (`games`, `forfeits`, the plan hash, the run config hash, the pair policy id, which must be the one given) and its `profile` line (stages, phases, scripted decisions = profile decisions less examples). The play's own output (Episodes, stream, run record) is removed after the record is written unless `--keep-arm-output`. Worker processes the play script starts get an empty environment, so `--worker-python` must be a program that sets `PYTHONPATH` itself when the code under test is not the installed one.
- **`--arm command`** is any command: `-- COMMAND ARGS...` after the options, `--arm-report FILE` (the file the command writes its ArmReport to), `--arm-id`, `--arm-label`, repeated `--arm-param name=integer`, `--pool-id`, `--pool-hash`, `--gpu` (the arm computes on the GPU). A GPU or native-engine launcher is measured this way, with the same guard, accounting and record.

## Protocol for the baseline number

The baseline's denominator is measured, not estimated (the figure of about 140 host-core-ms a decision comes from one contended run of the loop, not from this harness). On an idle machine, with training queues paused and the GPU idle: pick the plan (a run config naming the team pool, the generation, a frozen LR1 checkpoint pair), run `guard`, then `run --arm showdown --game-processes 4,6 --repeats 3 --wait-idle-minutes 10 --ids-python ... --worker-python ...` with a plan of at least 2,000 games, journal `summary.md` and `conditions.jsonl` of each run, and `summarise OUT` for the medians and ranges. The same command line with `--arm command` measures every other arm, so the three-arm comparison uses one definition.

## Limits

- Linux `/proc` only. A process that moves itself out of the arm's group and session and whose parent exits is not found (its CPU is lost and nothing marks the run).
- The clock tick is 10 ms: a run of a few CPU-seconds has that much relative error; plans of minutes do not.
- The harness's own CPU (`harness_ms`, a few tens of ms a minute) and the GPU monitor's are outside the arm's total.
- Memory is the sum of resident sets over one walk (shared pages are counted per process).
- The Showdown arm's `pool_load` and `merge` phases are the play script's wall-clock timers; worker start-up is inside `play`.
- Nothing in the repository runs the harness at full size: a real baseline needs an idle machine and belongs to the measurement tickets.
