# Runbook: the dev rules store (ADR-007)

This runbook is for the project owner. It sets up the **dev** rules store: a private PostgreSQL 18 database on Coolify that holds the published rules snapshots and the channel history, append-only (ADR-007, #704). The owner performs every step; no agent and no CI job connects to this database.

Labels used in sections 4 and 5: **Owner: verify on Coolify** marks a statement that could not be checked without the Coolify instance (a setting name, a behaviour); do not rely on it before you have seen it. **Owner: verify on GitHub** marks the same for a GitHub setting (a token scope, an Actions run). **Owner: verify** alone marks a behaviour of a tool that needs a real token or the live service to see. **Owner: decide** marks a choice that is the owner's, to be recorded on the ticket. **Spike** marks a step the owner runs to settle an open question; its evidence goes on #771.

| Section | Covers | Status |
|---|---|---|
| 1 | Create the private database resource on Coolify | this runbook (#769) |
| 2 | Bootstrap the roles from Coolify secrets (`db/bootstrap.sql`) | this runbook (#769) |
| 3 | Run the migrations with the pinned dbmate and verify the schema | this runbook (#769) |
| 4 | Deploy the rules importer: image, secrets, first run, summary line and exit codes, verification, failure modes | this runbook (#770) |
| 5 | Schedule the importer: the scheduled-execution spike | this runbook (#770); the owner runs the spike (#771) |

Ground rules for every step:

- **No secret leaves Coolify.** Each password is generated by the owner and stored only as a Coolify secret. It never goes into the repository, a shell history, a command line, a ticket, a chat or a screenshot. The examples below use placeholders such as `<from Coolify secret RULES_IMPORTER_PASSWORD>`; never replace a placeholder in a file you save.
- **No public port.** Every connection runs on the Coolify server, over Coolify's internal Docker network. The database never gets a published port, not even for a moment.
- **Local development is different.** `make db-up` / `make db-test` run a throwaway local container on `127.0.0.1:55432` (`db/compose.yaml`) with fixed local passwords. Never point them, or anything in this runbook, the other way round.

## 1. Create the private database resource on Coolify

The Coolify UI changes between versions; the field names below are the ones to look for, not exact click paths.

1. In Coolify, open the Areneon project and its **dev** environment, then add a new resource of type **PostgreSQL**. Pick version **18** (the image `postgres:18` or a newer 18.x tag; the local container in `db/compose.yaml` pins `postgres:18.6`).
   *Expected result:* a new PostgreSQL resource exists in the dev environment, not yet started.
2. For **server / destination**, choose the same Coolify server the rules importer will run on (section 4). Both must share one Docker network, because the importer will reach the database only by its internal hostname.
   *Expected result:* the resource's server and destination match the ones planned for the importer.
3. In the resource's general settings:
   - **Initial database:** `areneon` (the name the local setup and the examples below use).
   - **Username / password:** keep the generated superuser name (usually `postgres`) and the generated password. This is the bootstrap superuser; Coolify already stores it. Do not copy it anywhere else.
   - **Make it publicly available** (`is_public`): **off**. Leave **public port** empty.
   - **Ports mappings:** empty. No `host:container` mapping.
   *Expected result:* after saving, the resource shows no public URL and no published port; only the internal connection URL is shown.
4. Start the resource.
   *Expected result:* the status turns to running (healthy).
5. Open the resource's **Backups** tab and add a **scheduled backup**:
   - enable **S3** and pick the S3 storage configured under Coolify's S3 storages (configure one first if none exists);
   - set a frequency (for example daily) and a retention you are comfortable with;
   - make sure the database list includes `areneon`.
   Then run the backup once by hand.
   *Expected result:* the first backup run succeeds and the dump appears in the S3 bucket. A dump holds one database, not the cluster roles: after a restore into a fresh resource, re-run section 2 first, then restore the dump.
6. Write down these values (in your password manager or private notes, not in a ticket):

   | Value | Where to find it | Used as |
   |---|---|---|
   | Resource UUID | the resource's URL or settings page | the **internal hostname** (`<db-uuid>` below); the container is named after it too |
   | Internal port | the internal connection URL | `5432` |
   | Database name | general settings | `areneon` |
   | Docker network | the destination's network (default `coolify`) | `<coolify-network>` below |

   *Expected result:* you can fill every `<db-uuid>` and `<coolify-network>` placeholder below.

Optional check, on the Coolify server's shell (SSH, or Coolify's terminal on the server itself):

```bash
docker inspect <db-uuid> --format '{{json .NetworkSettings.Ports}} {{range $k, $v := .NetworkSettings.Networks}}{{$k}} {{end}}'
```

*Expected result:* the port map shows `5432/tcp` with no host binding (`null` or empty), followed by the network name(s), which include `<coolify-network>`.

## 2. Bootstrap the roles from Coolify secrets

`db/bootstrap.sql` runs once per database, as the superuser, before the first migration. It creates:

| Role | Login | Purpose |
|---|---|---|
| `rules_owner` | no (`NOLOGIN`) | owns the schema `rules` and its tables |
| `rules_migrator` | yes | runs dbmate; gets the owner's rights only through `SET ROLE rules_owner` (`INHERIT FALSE, SET TRUE`) |
| `importer` | yes | inserts published artifacts; never updates or deletes |
| `areneon_reader` | yes | reads the active snapshot |

It also creates the schema `rules`, and revokes `CONNECT` on the database from `PUBLIC`. It reads the three login passwords from environment variables with psql's `\getenv`: `RULES_MIGRATOR_PASSWORD`, `RULES_IMPORTER_PASSWORD`, `RULES_READER_PASSWORD`. A missing or blank one (empty or ASCII whitespace only) raises an error and stops the script before anything is created. psql checks for a blank one on the client, through a POSIX `sh` (dash, bash or busybox, where `printf` is a builtin), so no password is sent to the server, or into a process's arguments, except inside its own `CREATE ROLE`. Its role and schema work runs in one transaction, so a failure there leaves nothing half-made.

### 2.1 Create the secrets

1. Generate three passwords in your password manager: at least 32 characters, **letters and digits only** (no `@ : / ? # % &`), so they can go into a connection URL in section 3 without escaping.
   *Expected result:* three new passwords, seen only in the password manager.
2. Store each one in Coolify as a secret (a locked environment variable that the UI hides), in the dev environment, named exactly:
   - `RULES_MIGRATOR_PASSWORD`
   - `RULES_IMPORTER_PASSWORD`
   - `RULES_READER_PASSWORD`

   The importer (section 4) will receive `RULES_IMPORTER_PASSWORD` from here; nothing else needs a copy.
   *Expected result:* the three secrets exist in Coolify and their values are hidden in the UI.

### 2.2 Prepare a psql session on the internal network

All commands from here on run in a shell **on the Coolify server** (SSH, or Coolify's terminal on the server host). They use a one-off container on `<coolify-network>`, so the connection never leaves the server. Do not use Coolify's public-port feature for this.

Do not run them on a shared server account. While a one-off container runs, anyone with Docker access can see its environment (and so the passwords) with `docker inspect`, and the same user or root can read the exported variables of your shell. Use an admin account only you use, at a time when nobody else is working on the server.

1. Get `db/` from a reviewed commit on `main` (the files hold no secrets):

   ```bash
   git clone https://github.com/piglor/areneon.git areneon-db
   cd areneon-db
   git checkout <main commit SHA you reviewed>
   ls db/bootstrap.sql db/migrations/
   ```

   *Expected result:* `db/bootstrap.sql` and `db/migrations/20261019000000_rules_store.sql` are listed. If the repository cannot be read without credentials, use a read-only deploy key, or copy only the `db/` directory to the server; never paste a token into a command.
2. The commands below need bash. If the terminal is `sh` (Coolify's terminal often is), run `bash` first. Then keep the session out of the shell history:

   ```bash
   unset HISTFILE
   ```

   *Expected result:* no output. The commands below read secrets with `read -rsp`, so the values never appear on screen or in a command line.
3. Read the superuser password (from the database resource's settings in Coolify) without echoing it:

   ```bash
   read -rsp 'PGPASSWORD: ' PGPASSWORD; echo; export PGPASSWORD
   ```

   Paste `<from Coolify: the database resource's superuser password>` and press Enter.
   *Expected result:* only the prompt and a line break are printed, never the value.
4. Define the psql shortcut for this session. `-e PGPASSWORD` passes the variable by name, so the value is not on the `docker` command line:

   ```bash
   PSQL_IMAGE='postgres:18.6@sha256:74935e72241653ca55e0414067e6d8763aceb8a810eb51b452253ec3dcfc4336'
   psql_su() { docker run --rm -i --network <coolify-network> -e PGPASSWORD "$PSQL_IMAGE" \
     psql -h <db-uuid> -p 5432 -U postgres -d areneon -v ON_ERROR_STOP=1 "$@"; }
   psql_su -c 'SELECT version();'
   ```

   *Expected result:* one row starting with `PostgreSQL 18.`. If the connection is refused, check `<db-uuid>`, `<coolify-network>` and that the resource is running. (The image is the one `db/compose.yaml` pins; any psql 18 client works. The server's image flavour on Coolify, for example Alpine, may differ from this Debian-based client image; that is fine.)

### 2.3 Make sure passwords will not be logged

`CREATE ROLE … PASSWORD '…'` would be written to the server log in plain text if statement logging is on, or kept by a preloaded library that records statements. Each password reaches the server only inside its own `CREATE ROLE` (psql checks for missing and blank ones on the client), so a logged statement exposes one password, not all three.

On Coolify the server log is the database container's output: the resource's **Logs** view in Coolify, which is the container's Docker log (`docker logs <db-uuid>`). If a log drain is configured for the server, the log is copied there too.

1. Check the logging settings and the preloaded libraries:

   ```bash
   psql_su -c 'SHOW log_statement;' -c 'SHOW log_min_duration_statement;' -c 'SHOW log_min_error_statement;' \
     -c 'SHOW shared_preload_libraries;' -c 'SHOW session_preload_libraries;' -c '\drds'
   ```

   *Expected result:* `log_statement` is `none`, `log_min_duration_statement` is `-1`, both preload lists are empty or at least name none of `pgaudit`, `auto_explain` or `pg_stat_statements`, and `\drds` prints `Did not find any settings.` **If one of those libraries is loaded, stop here**: remove it in the resource's custom PostgreSQL configuration and restart the resource first, then start 2.3 again.

   The `SHOW` runs as `postgres` on `areneon`, the same user and database as the bootstrap, so it already includes any per-role or per-database override (`ALTER ROLE … SET` / `ALTER DATABASE … SET`); `\drds` shows where such an override comes from.
2. Only if a value in step 1 differs: fix it, reload, and check again. Remove per-role and per-database overrides first, then set the server value:

   ```bash
   psql_su -c 'ALTER ROLE postgres IN DATABASE areneon RESET log_statement;' \
     -c 'ALTER ROLE postgres RESET log_statement;' \
     -c 'ALTER DATABASE areneon RESET log_statement;'
   psql_su -c "ALTER SYSTEM SET log_statement = 'none';" \
     -c 'ALTER SYSTEM SET log_min_duration_statement = -1;' \
     -c 'SELECT pg_reload_conf();'
   psql_su -c 'SHOW log_statement;' -c 'SHOW log_min_duration_statement;' -c '\drds'
   ```

   Use the same three `RESET` lines for `log_min_duration_statement` if `\drds` lists it.
   *Expected result:* the `RESET`s print `ALTER ROLE` / `ALTER DATABASE`, `pg_reload_conf` returns `t`, and the re-check shows `none`, `-1` and `Did not find any settings.` Do not continue until it does.

   `pg_reload_conf()` only signals the server; the reload is asynchronous. If a check shows the old value, wait a second and repeat the check before looking for another source.

   If the re-check still shows the old value, Coolify passes it as a `-c` flag or in a mounted configuration file, which `ALTER SYSTEM` cannot override. Find the source:

   ```bash
   psql_su -c "SELECT name, setting, source, sourcefile FROM pg_settings
     WHERE name IN ('log_statement', 'log_min_duration_statement', 'log_min_error_statement');"
   ```

   Then set the value in the resource's custom PostgreSQL configuration in Coolify, restart the resource, and start 2.3 again.
3. Keep **failing** statements out of the log during the bootstrap. By default (`log_min_error_statement = error`) PostgreSQL logs the text of any statement that fails:

   ```bash
   psql_su -c "ALTER SYSTEM SET log_min_error_statement = 'panic';" -c 'SELECT pg_reload_conf();'
   psql_su -c 'SHOW log_min_error_statement;'
   ```

   *Expected result:* `pg_reload_conf` returns `t` and the check shows `panic` (if it shows `error`, wait a second and repeat the check: the reload is asynchronous). If it still does not, find the source as in step 2. Section 2.4 step 4 resets it. Note what this check showed: section 2.4 needs it if the bootstrap fails.

### 2.4 Run the bootstrap

1. Read the three role passwords from the Coolify secrets, without echoing them:

   ```bash
   read -rsp 'RULES_MIGRATOR_PASSWORD: ' RULES_MIGRATOR_PASSWORD; echo; export RULES_MIGRATOR_PASSWORD
   read -rsp 'RULES_IMPORTER_PASSWORD: ' RULES_IMPORTER_PASSWORD; echo; export RULES_IMPORTER_PASSWORD
   read -rsp 'RULES_READER_PASSWORD: ' RULES_READER_PASSWORD; echo; export RULES_READER_PASSWORD
   ```

   At each prompt paste, in order, `<from Coolify secret RULES_MIGRATOR_PASSWORD>`, `<from Coolify secret RULES_IMPORTER_PASSWORD>`, `<from Coolify secret RULES_READER_PASSWORD>`.
   *Expected result:* only the three prompts are printed, never a value.
2. Run `db/bootstrap.sql` (the same file and flags `make db-up` uses locally), passing the variables by name:

   ```bash
   docker run --rm -i --network <coolify-network> -e PGPASSWORD \
     -e RULES_MIGRATOR_PASSWORD -e RULES_IMPORTER_PASSWORD -e RULES_READER_PASSWORD \
     "$PSQL_IMAGE" psql -h <db-uuid> -p 5432 -U postgres -d areneon -v ON_ERROR_STOP=1 -f - < db/bootstrap.sql
   ```

   *Expected result:* psql prints `BEGIN`, `CREATE ROLE`, `CREATE ROLE`, `GRANT ROLE`, `CREATE ROLE`, `CREATE ROLE`, `CREATE SCHEMA`, `GRANT`, `GRANT`, `REVOKE`, `GRANT`, `COMMIT`, and exits 0. A message such as `RULES_IMPORTER_PASSWORD is not set` or `… is empty` means a variable was missing or blank; nothing was created. `role "rules_owner" already exists` means the bootstrap already ran: do not run it again.

   **If this step failed in any way, or you abandoned it**, handle it now, while the three variables are still exported, before step 3 clears them:

   1. Check whether a password reached the server log. `grep -cF` prints only a count, never the matched line or the password (the shell expands the variable, so the value stays out of your history; it is in `grep`'s arguments for the instant it runs, visible in `ps`, which is one more reason not to use a shared account):

      ```bash
      docker logs <db-uuid> 2>&1 | grep -cF -- "$RULES_MIGRATOR_PASSWORD"
      docker logs <db-uuid> 2>&1 | grep -cF -- "$RULES_IMPORTER_PASSWORD"
      docker logs <db-uuid> 2>&1 | grep -cF -- "$RULES_READER_PASSWORD"
      ```

      *Expected result:* each prints `0`. Optional coarse view: `docker logs <db-uuid> 2>&1 | grep -c -i -E 'password|rules_migrator|importer|areneon_reader'` also counts ordinary lines such as `password authentication failed`, so a count above 0 there is not proof of a leak.
   2. Decide whether to keep the passwords:
      - If the 2.3 step 3 check showed `panic` for this run, or the run stopped at a missing- or blank-variable message, **and** every count in step 1 is `0`, nothing was logged: you may keep the passwords.
      - Otherwise purge the log (step 3 below) and decide which passwords are exposed. If psql printed `BEGIN`, the run got past the checks and may have sent any `CREATE ROLE`: treat **all three** as exposed. If it stopped before `BEGIN`, no password left the client (no statement but its own `CREATE ROLE` carries one): treat as exposed only those whose count in step 1 is above `0`. Generate a new password for each exposed one to replace its Coolify secret (2.1).
   3. Purge the log, only if step 2 says so. First check the container's log driver:

      ```bash
      docker inspect --format '{{.HostConfig.LogConfig.Type}}' <db-uuid>
      ```

      If it prints `json-file`, truncate the current log file and any rotated ones. The glob must be expanded by root, because a normal user cannot list Docker's log directory; hence `sh -c` under `sudo` (`-c` creates no file when there is nothing rotated):

      ```bash
      LOG="$(docker inspect --format '{{.LogPath}}' <db-uuid>)"
      sudo sh -c 'truncate -c -s 0 "$1" "$1".*' _ "$LOG"
      docker logs <db-uuid> 2>&1 | grep -cF -- "$RULES_MIGRATOR_PASSWORD"
      ```

      *Expected result:* the count is `0` (repeat it for the other two variables). Coolify's **Logs** view reads the same Docker log, so nothing more is needed there. For any other driver (`local`, `journald`, …) do not guess: `local` keeps compressed files that must not be edited, and `journald` can only drop whole journal files, which deletes every log on the host. Stop and decide with whoever runs the server. Remove any log drain copy too.
   4. Do steps 3 and 4 below, fix the cause, then run 2.3 step 3 and this section again.
3. Clear the role passwords from the shell:

   ```bash
   unset RULES_MIGRATOR_PASSWORD RULES_IMPORTER_PASSWORD RULES_READER_PASSWORD
   ```

   *Expected result:* no output. Keep `PGPASSWORD` until the end of section 3.
4. Restore the default for failing statements (set in 2.3 step 3). Do this after every run of step 2: after a success, a failure, an abandoned run, and the missing- or blank-variable case alike.

   ```bash
   psql_su -c 'ALTER SYSTEM RESET log_min_error_statement;' -c 'SELECT pg_reload_conf();'
   psql_su -c 'SHOW log_min_error_statement;'
   ```

   *Expected result:* `pg_reload_conf` returns `t` and the check shows `error` (if it still shows `panic`, wait a second and repeat the check: the reload is asynchronous).

### 2.5 Verify the roles

1. List the roles and their attributes:

   ```bash
   psql_su -c "SELECT rolname, rolcanlogin, rolsuper, rolinherit, rolcreaterole, rolcreatedb, rolbypassrls
     FROM pg_roles WHERE rolname IN ('rules_owner', 'rules_migrator', 'importer', 'areneon_reader') ORDER BY rolname;"
   ```

   *Expected result:* four rows. `rules_owner` has `rolcanlogin = f`; `rules_migrator`, `importer` and `areneon_reader` have `rolcanlogin = t`. All four have `rolsuper`, `rolcreaterole`, `rolcreatedb` and `rolbypassrls` = `f`.
2. Check the one membership and the schema owner:

   ```bash
   psql_su -c "SELECT g.rolname AS granted_role, m.rolname AS member, a.inherit_option, a.set_option, a.admin_option
     FROM pg_auth_members a JOIN pg_roles g ON g.oid = a.roleid JOIN pg_roles m ON m.oid = a.member
     WHERE g.rolname IN ('rules_owner', 'rules_migrator', 'importer', 'areneon_reader')
        OR m.rolname IN ('rules_owner', 'rules_migrator', 'importer', 'areneon_reader');" \
     -c '\dn+ rules' -c '\l areneon'
   ```

   *Expected result:* exactly one membership row: `rules_owner | rules_migrator | f | t | f` (no inherit, set allowed, no admin). Schema `rules` is owned by `rules_owner`, with `USAGE` for `importer` and `areneon_reader` and `USAGE, CREATE` for `rules_migrator`. The database's access privileges list `CONNECT` for `rules_migrator`, `importer` and `areneon_reader` and no `=Tc/` (PUBLIC) entry.

## 3. Run the migrations with dbmate

The migrations in `db/migrations/` run as `rules_migrator`, with the same pinned dbmate image and flags as `make db-up` (see the `DBMATE` variable in the `Makefile`):

```
ghcr.io/amacneil/dbmate:2.36.0@sha256:520c740c6e0ad73fde2cd1ea7e2b779aaf789d22aca8858f87a478e7094535fb
--no-dump-schema --migrations-dir /db/migrations
```

Each migration switches to `rules_owner` with `SET LOCAL ROLE`, so every table belongs to the owner, and dbmate keeps its version table `rules.schema_migrations` because the URL sets `search_path=rules`.

**`sslmode`:** the connection stays on `<coolify-network>`, a Docker network on this one server, so the examples use `sslmode=disable`, as the local setup does. If you enabled SSL on the Coolify resource, use `sslmode=require` instead.

1. Build the dbmate URL from the migrator secret, without echoing it. dbmate reads it from `DATABASE_URL`, which `docker run -e DATABASE_URL` passes by name:

   ```bash
   read -rsp 'RULES_MIGRATOR_PASSWORD: ' RULES_MIGRATOR_PASSWORD; echo
   export DATABASE_URL="postgres://rules_migrator:${RULES_MIGRATOR_PASSWORD}@<db-uuid>:5432/areneon?sslmode=disable&search_path=rules"
   unset RULES_MIGRATOR_PASSWORD
   DBMATE_IMAGE='ghcr.io/amacneil/dbmate:2.36.0@sha256:520c740c6e0ad73fde2cd1ea7e2b779aaf789d22aca8858f87a478e7094535fb'
   dbmate() { docker run --rm --network <coolify-network> -v "$PWD/db:/db:ro" -e DATABASE_URL "$DBMATE_IMAGE" \
     --no-dump-schema --migrations-dir /db/migrations "$@"; }
   ```

   Paste `<from Coolify secret RULES_MIGRATOR_PASSWORD>` at the prompt.
   *Expected result:* only the prompt is printed, never the value. Run these from the `areneon-db` checkout, so `$PWD/db` is the repository's `db/`.
2. Show what will run:

   ```bash
   dbmate status
   ```

   *Expected result:* `[ ] 20261019000000_rules_store.sql` and `Pending: 1`.
3. Apply the migrations:

   ```bash
   dbmate migrate
   ```

   *Expected result:* `Applying: 20261019000000_rules_store.sql`, then `Applied: …` and exit 0. Running it again applies nothing.
4. Confirm:

   ```bash
   dbmate status
   ```

   *Expected result:* `[X] 20261019000000_rules_store.sql`, `Applied: 1`, `Pending: 0`.
5. Clear the URL:

   ```bash
   unset DATABASE_URL
   ```

   *Expected result:* no output.

### 3.1 Verify the schema

1. Tables and their owners:

   ```bash
   psql_su -c '\dt rules.*'
   ```

   *Expected result:* `rules_release` and `rules_snapshot` owned by `rules_owner`, and dbmate's `schema_migrations` owned by `rules_migrator`.
2. Triggers:

   ```bash
   psql_su -c "SELECT tgrelid::regclass AS table_name, tgname FROM pg_trigger
     WHERE NOT tgisinternal AND tgrelid::regclass::text LIKE 'rules.%' ORDER BY 1, 2;"
   ```

   *Expected result:* four rows, in any order: `rules_release_append_only`, `rules_release_no_truncate` on `rules.rules_release`; `rules_snapshot_append_only`, `rules_snapshot_no_truncate` on `rules.rules_snapshot`.
3. Constraints:

   ```bash
   psql_su -c "SELECT conrelid::regclass AS table_name, conname, contype FROM pg_constraint
     WHERE connamespace = 'rules'::regnamespace AND contype <> 'n' ORDER BY 1, 2;"
   ```

   *Expected result:* on `rules.rules_release`: `release_channel_in_enum`, `release_seq_positive`, `release_snapshot_exists` (`f`), `release_seq_unique_per_channel` and `release_source_commit_unique_per_channel` (`u`), `release_source_commit_is_sha1`, and the primary key `rules_release_pkey` (`p`). On `rules.rules_snapshot`: `snapshot_hash_is_sha256_of_body`, `snapshot_payload_is_body`, `snapshot_schema_version_from_payload`, `snapshot_showdown_commit_from_payload`, `snapshot_source_commit_is_sha1` and `rules_snapshot_pkey` (`p`). dbmate's `schema_migrations_pkey` may also appear.
4. Table privileges, without writing a row:

   ```bash
   psql_su -c "SELECT r AS role, t AS table_name,
       has_table_privilege(r, t, 'SELECT') AS sel, has_table_privilege(r, t, 'INSERT') AS ins,
       has_table_privilege(r, t, 'UPDATE') AS upd, has_table_privilege(r, t, 'DELETE') AS del,
       has_table_privilege(r, t, 'TRUNCATE') AS trunc
     FROM unnest(ARRAY['importer', 'areneon_reader']::name[]) AS r,
          unnest(ARRAY['rules.rules_snapshot', 'rules.rules_release']) AS t ORDER BY 1, 2;"
   ```

   *Expected result:* `importer` has `sel = t`, `ins = t` and `upd`, `del`, `trunc` = `f` on both tables; `areneon_reader` has only `sel = t`.
5. Prove that `importer` cannot update or delete. Each statement runs in a transaction that is rolled back and matches no row, so nothing changes:

   ```bash
   psql_su -c 'BEGIN; SET LOCAL ROLE importer; UPDATE rules.rules_release SET seq = seq WHERE false; ROLLBACK;'
   psql_su -c 'BEGIN; SET LOCAL ROLE importer; DELETE FROM rules.rules_snapshot WHERE false; ROLLBACK;'
   ```

   *Expected result:* each fails with `ERROR:  permission denied for table rules_release` / `… rules_snapshot`. Do **not** test INSERT with a real row: the store is append-only, so a test row could never be removed. The privilege check in step 4 covers INSERT, and the importer's first real run (section 4) exercises it.
6. End the session:

   ```bash
   unset PGPASSWORD
   cd .. && rm -rf areneon-db
   ```

   *Expected result:* no output. No password remains in the shell, and none was ever on a command line or in the history.

### 3.2 The GitHub environment `rules-dev`

The repository already has the GitHub environment **`rules-dev`**, used by `.github/workflows/rules-publish.yml`: it publishes each merged rules change as a Release with a build-provenance attestation. Only its `publish` job uses the environment, and only when its read-only `plan` job found an artifact not yet released, so a push with nothing new to publish asks for no approval. The plan job's workflow artifact is kept 90 days, longer than the 30-day approval timeout, and re-running only the `publish` job reuses that original plan artifact; once it has expired the download fails closed, so re-run the whole workflow. If release fails with '… is not in the release set', another run released it meanwhile; re-run the publish job. The environment has a required reviewer (the owner) and its deployment branches are limited to `main`, so a publish runs only from `main` and only after the owner approves it (verified via the GitHub API on 2026-10-19: required reviewer `arceushui`, deployment branch policy `main`). It holds no database credentials: GitHub never connects to this database. The importer that pulls those Releases into the store is section 4.

1. Check it in GitHub under the repository's **Settings → Environments → rules-dev**.
   *Expected result:* **Required reviewers** lists the owner, **Deployment branches and tags** allows only `main`, and there are no environment secrets for this database.

## 4. Deploy the rules importer

The importer is a one-shot command, not a service: it lists the published, attested rules Releases of `piglor/areneon`, verifies each with `gh attestation verify`, and writes what is new into the rules store in one transaction (ADR-007 §6, `packages/rules-importer`). It then prints one JSON line and exits. It listens on no port, keeps no state outside the database and needs only outbound HTTPS to GitHub plus the database over the internal network.

| Fact | Value |
|---|---|
| Image | built from the repository root: `docker build -f packages/rules-importer/Dockerfile -t areneon-rules-importer .` (`make importer-image` also builds the test image; the default, last stage `runtime`, is the production image). No registry image is published; Coolify or you build it from the repository. |
| Entrypoint | `node packages/rules-importer/src/cli.ts` (working directory `/app`, user `1000:1000`). Arguments are not read; configuration is environment only. |
| Contents | `node`, the pinned `gh` (checked against a SHA-256 at build time), the CA bundle and `/app`. No shell tooling beyond Debian slim's base, no `curl`, `npm`, `pnpm`, no test files, no fixtures. |
| Reaches | `api.github.com` and `github.com` (HTTPS, through `gh`), and the database by its internal hostname. **Owner: verify:** `gh release download` is also redirected to GitHub's asset storage (`*.githubusercontent.com`), and `gh attestation verify` fetches the Sigstore trusted root over TUF (Sigstore's public TUF repository host). If the server filters outbound traffic, these hosts must be allowed too. |

Environment variables (nothing secret is baked into the image; the Dockerfile has no build arguments for them):

| Variable | Required | Secret | Meaning |
|---|---|---|---|
| `DATABASE_URL` | yes | **yes** (it contains the `importer` password) | `postgres://importer:<from Coolify secret RULES_IMPORTER_PASSWORD>@<db-uuid>:5432/areneon?sslmode=<mode>`. Must log in as `importer`; any other role exits 2. A URL that sets `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout` or `options` is refused (exit 2). |
| `GH_TOKEN` | yes | **yes** | A read-only fine-grained GitHub token (4.2). `gh` reads it to list Releases, download assets and verify attestations. |
| `RULES_IMPORT_STATEMENT_TIMEOUT_MS` | no | no | Statement timeout of the session, 1 to 999999999 ms. Default 300000. |
| `RULES_IMPORT_LOCK_TIMEOUT_MS` | no | no | Lock wait timeout, same range. Default 300000. |
| `RULES_IMPORT_IDLE_IN_TRANSACTION_TIMEOUT_MS` | no | no | Idle-in-transaction timeout, same range. Default 60000. |

A timeout that is exceeded fails the statement and rolls the whole import back (exit 1). A value that is not a whole number in range exits 2. Leave all three unset unless a run times out. ### 4.1 The ADR-007 §6 flow, end to end

```text
 PR with rules/ changes merged to main
   1. rules-publish.yml, job "plan" (read-only, no environment): re-checks rules and channels on the
      merged commit, builds the artifacts not yet released with a sha256 manifest.
      Nothing new -> the workflow ends here and asks for nothing.
   2. job "publish" waits for the owner's approval of the GitHub environment rules-dev.     <- OWNER
      Approved -> verifies the plan's files against the manifest, attests them (build provenance),
      and creates the Releases: rules-snapshot-<hash> first, then rules-channel-<channel>-<commit>.
   3. The importer runs (scheduled, section 5, or by hand). It:
        a. connects as `importer`; reads which snapshot hashes the store has;
        b. lists the non-draft rules-* Releases; a snapshot already stored is not downloaded (it is
           checked by reference); every other asset is downloaded and checked with
           `gh attestation verify` (repo piglor/areneon, workflow rules-publish.yml, ref
           refs/heads/main, GitHub-hosted runner, and the file's own sha256);
        c. plans: each artifact must be canonical JSON, match its schema and its own name, and a
           channel artifact must name a snapshot that is released or already stored;
        d. applies the plan in ONE transaction: snapshots, then channel steps with a seq above the
           channel's current maximum. Anything refused rolls the whole plan back (a
           `stale` channel step is not a refusal; see 4.6).
   4. Readers (areneon_reader) see the new rows; a runtime pins the snapshot hash at battle start.
```

The dev environment is `rules-dev` (3.2); ADR-007's text says `rules-prod`, which is the later production environment (#715). The approval in step 2 can wait up to the environment's timeout (30 days); the importer simply finds nothing new until the Releases exist, and imports them on the first run after.

`source_commit` is read from the Release's Git tag, which is mutable. It is deliberately not compared with the commit the attestation names (the #765 design): what the importer trusts is the attested bytes, whose channel artifact carries its own `source_commit`, and it refuses an artifact whose own commit disagrees with its tag's.

### 4.6 The summary line and exit codes

The importer prints exactly one line to stdout and exits.

Success or stale channel: `{"ok":<bool>,"steps":[ … ]}`, steps in plan order (snapshots by hash, then channel steps by channel and seq). Failure: `{"ok":false,"error":"<ErrorName>: <message>"}` (the database URL and password are removed from the message).

| Step | Status | Meaning |
|---|---|---|
| snapshot | `inserted` | New snapshot row written. |
| snapshot | `already-present` | The snapshot was downloaded and found stored already (another import stored it first). Rare. No change. |
| snapshot | `referenced` | The snapshot was already stored, so it was **not downloaded or attested again**; a channel step names it, and the stored row was checked to hash to its own body. No change. This is the normal status of every stored snapshot on a re-run. |
| channel | `inserted` | New `rules_release` row (its `seq` is above the channel's maximum). |
| channel | `already-present` | The same channel, `seq`, hash and `source_commit` are stored. No change; the normal status of every old channel artifact on a re-run. |
| channel | `stale` | The artifact's `seq` is at or below the channel's maximum, but the stored row at that `seq` differs or does not exist. Nothing is written for it, `ok` is `false` and the exit is 1. The other steps of the same run are **not** rolled back: they commit (a partial commit). Since the stale artifact is a permanent Release listed on every run, every later run exits 1 too, until that Release is removed. |

| Exit | Meaning | Examples (all checked locally) |
|---|---|---|
| 0 | Every step was `inserted`, `already-present` or `referenced`. | `{"ok":true,"steps":[ … ]}` |
| 1 | Refused or stale: the plan, the Release listing, the attestation, the database, a timeout, or a `stale` step. A refused run that is not `stale` writes nothing; a `stale` run commits its other steps (see the `stale` row). | `ImportPlanError: could not list the released rules artifacts: … gh attestation verify exited 1 …`; `ImportPlanError: channel … names snapshot …, which is neither released nor imported`; a wrong database password (`error: password authentication failed for user "importer"`) or an unreachable database (`Error: connect ECONNREFUSED …`) are exit **1**, not 2. |
| 2 | Configuration: the importer cannot start the import. | `ConfigError: DATABASE_URL is not set`; `ConfigError: RULES_IMPORT_LOCK_TIMEOUT_MS must be a whole number of milliseconds …`; `SessionConfigError: the database URL must not set statement_timeout …`; `SessionConfigError: the database URL is not a connection string`; `SessionConfigError: <setting> is … ms, not the requested … ms` (checked in the code, not run); `ConfigError: the rules import runs as importer, not session areneon_reader …` |

What to do for each non-zero exit:

| Exit and message | Action |
|---|---|
| 2, `DATABASE_URL is not set` | The variable is missing from the application or the `docker run`. Set it (4.3). |
| 2, a timeout variable | Fix or remove the `RULES_IMPORT_*_TIMEOUT_MS` value (whole milliseconds, 1 to 999999999). |
| 2, URL sets a timeout or `options` | Remove that query parameter from `DATABASE_URL`. |
| 2, `SessionConfigError: the database URL is not a connection string` | `DATABASE_URL` is malformed (a password with a reserved character, a missing scheme). Fix the secret. |
| 2, `SessionConfigError: <setting> is … ms, not the requested … ms` | The server session did not take the requested timeouts (a connection pooler that drops startup parameters). Connect to the database directly, not through a pooler. |
| 2, runs as importer, not … | The URL logs in as another role. Use the `importer` user. |
| 1, `password authentication failed` or a connection error | Wrong or rotated `importer` password in `DATABASE_URL`, wrong `<db-uuid>`, wrong network, or the database is down. Check with `psql` as in 4.7 and the resource's status. Nothing was written. |
| 1, `ImportPlanError: could not list …` | Read the rest of the message; see 4.8 (attestation, token, GitHub). |
| 1, `names snapshot …, which is neither released nor imported` | See 4.8 (unreleased snapshot). |
| 1, a timeout (`canceling statement due to …`) | Raise the matching `RULES_IMPORT_*_TIMEOUT_MS`; look for another long session on the database. The import rolled back. |
| 1, `"status":"stale"` | See 4.8 (stale channel): the other steps committed, and the exit repeats on every run until the Release is removed (an owner decision; ticket #811 will change this). |

### 4.8 Failure modes and fixes

Every failure below leaves the database unchanged, except a `stale` step: the run commits its other steps and exits 1 (partial commit), and every later run exits 1 again until the stale Release is removed. The importer never retries inside a run; the next run is the retry.

**A snapshot that was never released** (`channel <channel> seq <n> names snapshot <hash>, which is neither released nor imported`; exit 1).
A channel artifact was released, or its Release exists, but the snapshot it names has no Release and is not stored. Causes: a cancelled or never approved `publish` run, a channel change that predates the publish workflow, or a Release that is still a draft.
1. In GitHub, open the Actions run of `rules-publish` for the commit that last changed the snapshot's records (`source_commit` of the artifact, or the commit the channel names). If `publish` is waiting, approve `rules-dev` (3.2). If it was cancelled or failed, re-run it: re-run only the `publish` job while the plan artifact is still kept (90 days); after that, re-run the whole workflow.
2. A snapshot older than the workflow was never released. Re-run that commit's workflow, or revert the records in a PR so a new snapshot is published (CLAUDE.md, rules store).
3. Run the importer again.
   *Expected result:* `inserted` for the snapshot, then the channel.

**An attestation or listing failure** (`ImportPlanError: could not list the released rules artifacts: <file>: gh attestation verify exited 1: …`, or `ReleaseSourceError` text inside it; exit 1).
`gh` could not verify an asset against repo `piglor/areneon`, workflow `rules-publish.yml`, ref `refs/heads/main`, a GitHub-hosted runner, and the asset's own sha256; or a Release is a pre-release, has no asset, or an asset is incomplete; or `gh` itself failed.
1. Read the stderr text after `exited 1:`. `HTTP 401`, `HTTP 403`, `rate limit`, `bad credentials` or `authentication`: the token expired, lost its repository selection or hit a rate limit. Create a new token (4.2), replace the Coolify secret, run again.
2. `no attestations found` for an asset: its Release was made without the `attest` step, or the attestation was deleted. The `publish` job attests before it releases, so look at that run in Actions.
3. `no statement subject has sha256 …`, a signer or ref mismatch, `is not in canonical form`, or `sha256 of its bytes is not …`: the asset differs from what `publish` attested, or came from another workflow or ref. Treat it as a possible tampering: **do not import around it**. Verify the asset yourself from your own machine (`gh attestation verify <downloaded file> --repo piglor/areneon --signer-workflow piglor/areneon/.github/workflows/rules-publish.yml --source-ref refs/heads/main`), and record the finding on the ticket. **Owner: decide** whether to delete that Release and re-run `publish` so it is created again; the database is not edited either way.
4. A network failure, `timed out after …`, or `exceeded … bytes`: run again; if it persists, check the server's outbound HTTPS.
The same message, exit 1, appears in the local check where one asset is tampered (`make importer-e2e`): nothing is written, not even the snapshot that verified before it.

**A stale channel** (`"status":"stale"` in the summary, `ok` false, exit 1).
A channel artifact has a `seq` at or below the stored maximum and is not identical to the stored row at that `seq`. Normal changes cannot do this (CI makes `seq` rise by one per change). The usual cause is a `publish` approved late for an older commit after a newer one was already imported, or a Release edited by hand.
1. List what the database holds: the query of 4.7 step 2, and `SELECT channel, seq, hash, source_commit FROM rules.rules_release ORDER BY channel, seq;`.
2. List the channel Releases on GitHub and find the one whose `seq`, hash or commit differs from the row at that `seq`.
3. The database is authoritative and append-only; do not edit it. **Owner: decide**: a superseded older Release (a late approval) can be deleted on GitHub so the importer stops listing it; a Release that disagrees with `rules/channels/<channel>.json` on `main` is a bug to record on the ticket first.
   Until the offending Release is removed, **every** run exits 1 with the same `stale` step (partial commit, perpetual exit 1 until the Release is removed), while its other steps still commit. Deleting the Release is an **Owner: decide** choice, recorded on the ticket. This is the current behaviour: ticket #811 will change the importer so that a stale artifact is skipped and logged with exit 0 (as ADR-007 §6 says); this section will then be updated.

**Other** (see 4.6): a changed `importer` password (exit 1), a missing variable (exit 2), a timeout (exit 1).

## 5. Schedule the importer

The importer must run on a schedule, because nothing pushes to it (ADR-007 §6: a pull model; the database is never exposed). ADR-007 lists Coolify's scheduled execution as unverified and names the fallback: a long-running container that polls. This section is the **spike** that settles it (#770 documents it, #771 is where the owner records the result). Everything about Coolify's scheduling below is **Owner: verify on Coolify**; this runbook could not check it.

Frequency: rules changes are rare, and a publish waits for a human approval first, so hourly is plenty. The import is idempotent and each channel is locked with a PostgreSQL advisory lock for the transaction, so an accidental overlap of two runs is safe, but it is still wasteful. Each run lists the Releases and downloads and attests every channel artifact (the history grows with each channel change), and each `gh` call is limited to 60 seconds (the database connection to 10 seconds); if a run ever takes minutes in total, that is a finding to record.

### 5.1 The options

| | **A. Scheduled task on the application** | **B. A cron container (polling loop)** |
|---|---|---|
| What runs | Coolify runs a command at a cron time inside the application's container. | A container that stays up and runs the importer every N seconds, restarting on failure. |
| Fit with the image | The image's entrypoint runs one import and exits, so there is no running container to run a command in. The container must be kept alive (for example a different entrypoint such as `sleep infinity`; a start-command override alone only adds arguments to `node …/cli.ts`, because the Dockerfile sets an `ENTRYPOINT`), and the task's command is `node packages/rules-importer/src/cli.ts`. | The same image with an entrypoint override that loops: `sh -c 'while true; do node packages/rules-importer/src/cli.ts; sleep 3600; done'` (the image has `sh` and `sleep` from the Debian base, and no cron). |
| Secrets | Application environment variables (4.3). | Same, through a compose file that references them. |
| Run history, exit code | Coolify's execution log per run, with a status. **Owner: verify** that a non-zero exit is shown as failed. | Only the container's log; the loop must record the exit code in the log line it prints, and one run's failure must not stop the loop. |
| Failure alerting | Coolify notification settings, if they cover scheduled tasks. **Owner: verify.** | Container restart policy only; no per-run status. |
| Moving parts | Coolify's scheduler, the kept-alive container. | A compose resource, a long-lived container, no dependency on the scheduler. |
| Cost | One idle container. | One container, mostly sleeping. |

How to choose: take **A** if all of its acceptance checks in 5.2 pass, because it gives a per-run history and exit status in Coolify. Take **B** if the entrypoint override or the command execution does not work, if a failed run is not visible, or if the scheduler drifts or skips runs. B is the ADR's fallback and needs nothing from Coolify's scheduler. A third option, a cron entry on the server's host running `docker run`, would put the secrets on the host and in a crontab, which this runbook forbids; do not use it.

### 5.2 The spike (the owner runs this)

**Spike.** Do 4.1 to 4.7 first; the manual import must work and be verified before any schedule is added. Use the dev environment only.

1. **Try A.**
   1. In the application of 4.4 A, set a custom entrypoint that keeps the container alive (look in the application's advanced or custom Docker options for an entrypoint or container option; **Owner: verify on Coolify** that one exists and that the Dockerfile's `ENTRYPOINT` is replaced, not extended). Deploy; the container should stay running.
   2. Add a scheduled task: the command `node packages/rules-importer/src/cli.ts`, the container being the application's, the schedule a cron expression (for example `17 * * * *`, hourly at minute 17), with a timeout of a few minutes if the form has one.
   3. Use the task's option to run it now, or wait for the time.
   *Acceptance checks:* the run happens at the scheduled time (note the clock time, and how Coolify shows it); the log of the run is exactly the importer's JSON line; a run with nothing new shows `referenced` and `already-present`; the container's environment, and so `DATABASE_URL` and `GH_TOKEN`, is the one of 4.3 (the import connects as `importer`).
2. **Failure drill (A).** Temporarily set `RULES_IMPORT_LOCK_TIMEOUT_MS` to `abc`, run the task, then remove the variable. *Acceptance check:* the run is shown as failed and the log shows `ConfigError: … must be a whole number of milliseconds …` (exit 2). Note what Coolify does on a failure (a notification, a retry, nothing). Do not use a wrong `DATABASE_URL` for the drill: that risks writing a bad secret.
3. **Two consecutive scheduled runs.** Let at least two scheduled executions pass unattended, and look at the history: both ran at their time, both `exit 0`.
4. **Leak check.** Do the log checks of 4.3 against the container, and look at the scheduled task's execution log in Coolify. *Acceptance check:* every count is `0` and no value is visible.
5. **Redeploy.** Redeploy the application (or restart the server's Docker). *Acceptance check:* the container comes back, the schedule is still there, and the next run happens.
6. **If any acceptance check above fails, try B** (**Owner: verify on Coolify** every compose detail): add a Docker Compose resource from the same repository, in the same environment and network, with a service like this one (no `ports`, no `volumes`; the variable names are the secrets of 4.3, set in the resource's environment variables):

   ```yaml
   services:
     importer:
       build:
         context: .
         dockerfile: packages/rules-importer/Dockerfile
       restart: unless-stopped
       entrypoint: ["sh", "-c", "while true; do node packages/rules-importer/src/cli.ts; echo \"importer exit=$$?\"; sleep 3600; done"]
       environment:
         DATABASE_URL: ${DATABASE_URL}
         GH_TOKEN: ${GH_TOKEN}
   ```

   This is a compose file: `$$` is the escaped `$`, so the container sees `$?`, and `${DATABASE_URL}` is replaced by the resource's variable. **Owner: verify on Coolify** that Coolify does not rewrite the `$$`. The service must join the database's network (`<coolify-network>`); how a compose resource is attached to an existing destination network is **Owner: verify on Coolify**. Repeat checks 3 to 5 (the failure drill needs a temporary `RULES_IMPORT_LOCK_TIMEOUT_MS=abc` and a redeploy) and note that run history exists only in the container log.
7. **Outside check** (also #771's "done when"): from a machine outside the server, the database port must not answer, for example `nc -vz -w 5 <server public address> 5432` must fail or time out; and the importer's application has no published port.
8. Record the decision (A or B) and clean up: remove the temporary variable, and any test schedule that you will not keep.
