# Runbook: the dev rules store (ADR-007)

This runbook is for the project owner. It sets up the **dev** rules store: a private PostgreSQL 18 database on Coolify that holds the published rules snapshots and the channel history, append-only (ADR-007, #704). The owner performs every step; no agent and no CI job connects to this database.

| Section | Covers | Status |
|---|---|---|
| 1 | Create the private database resource on Coolify | this runbook (#769) |
| 2 | Bootstrap the roles from Coolify secrets (`db/bootstrap.sql`) | this runbook (#769) |
| 3 | Run the migrations with the pinned dbmate and verify the schema | this runbook (#769) |
| 4 | Deploy the rules importer | later (#770) |
| 5 | Schedule the importer | later (#770) |

Ground rules for every step:

- **No secret leaves Coolify.** Each password is generated by the owner and stored only as a Coolify secret. It never goes into the repository, a shell history, a command line, a ticket, a chat or a screenshot. The examples below use placeholders such as `<from Coolify secret RULES_IMPORTER_PASSWORD>`; never replace a placeholder in a file you save.
- **No public port.** Every connection runs on the Coolify server, over Coolify's internal Docker network. The database never gets a published port, not even for a moment.
- **Local development is different.** `make db-up` / `make db-test` run a throwaway local container on `127.0.0.1:55432` (`db/compose.yaml`) with fixed local passwords. Never point them, or anything in this runbook, the other way round.

## 1. Create the private database resource on Coolify

The Coolify UI changes between versions; the field names below are the ones to look for, not exact click paths.

1. In Coolify, open the Areneon project and its **dev** environment, then add a new resource of type **PostgreSQL**. Pick version **18** (the image `postgres:18` or a newer 18.x tag; the local container in `db/compose.yaml` pins `postgres:18.6`).
   *Expected result:* a new PostgreSQL resource exists in the dev environment, not yet started.
2. For **server / destination**, choose the same Coolify server the rules importer will run on (section 4). Both must share one Docker network, because the importer will reach the database only by its internal hostname.
   *Expected result:* the resource's server and destination match the ones planned for the importer.
3. In the resource's general settings:
   - **Initial database:** `areneon` (the name the local setup and the examples below use).
   - **Username / password:** keep the generated superuser name (usually `postgres`) and the generated password. This is the bootstrap superuser; Coolify already stores it. Do not copy it anywhere else.
   - **Make it publicly available** (`is_public`): **off**. Leave **public port** empty.
   - **Ports mappings:** empty. No `host:container` mapping.
   *Expected result:* after saving, the resource shows no public URL and no published port; only the internal connection URL is shown.
4. Start the resource.
   *Expected result:* the status turns to running (healthy).
5. Open the resource's **Backups** tab and add a **scheduled backup**:
   - enable **S3** and pick the S3 storage configured under Coolify's S3 storages (configure one first if none exists);
   - set a frequency (for example daily) and a retention you are comfortable with;
   - make sure the database list includes `areneon`.
   Then run the backup once by hand.
   *Expected result:* the first backup run succeeds and the dump appears in the S3 bucket. A dump holds one database, not the cluster roles: after a restore into a fresh resource, re-run section 2 first, then restore the dump.
6. Write down these values (in your password manager or private notes, not in a ticket):

   | Value | Where to find it | Used as |
   |---|---|---|
   | Resource UUID | the resource's URL or settings page | the **internal hostname** (`<db-uuid>` below); the container is named after it too |
   | Internal port | the internal connection URL | `5432` |
   | Database name | general settings | `areneon` |
   | Docker network | the destination's network (default `coolify`) | `<coolify-network>` below |

   *Expected result:* you can fill every `<db-uuid>` and `<coolify-network>` placeholder below.

Optional check, on the Coolify server's shell (SSH, or Coolify's terminal on the server itself):

```bash
docker inspect <db-uuid> --format '{{json .NetworkSettings.Ports}} {{range $k, $v := .NetworkSettings.Networks}}{{$k}} {{end}}'
```

*Expected result:* the port map shows `5432/tcp` with no host binding (`null` or empty), followed by the network name(s), which include `<coolify-network>`.

## 2. Bootstrap the roles from Coolify secrets

`db/bootstrap.sql` runs once per database, as the superuser, before the first migration. It creates:

| Role | Login | Purpose |
|---|---|---|
| `rules_owner` | no (`NOLOGIN`) | owns the schema `rules` and its tables |
| `rules_migrator` | yes | runs dbmate; gets the owner's rights only through `SET ROLE rules_owner` (`INHERIT FALSE, SET TRUE`) |
| `importer` | yes | inserts published artifacts; never updates or deletes |
| `areneon_reader` | yes | reads the active snapshot |

It also creates the schema `rules`, and revokes `CONNECT` on the database from `PUBLIC`. It reads the three login passwords from environment variables with psql's `\getenv`: `RULES_MIGRATOR_PASSWORD`, `RULES_IMPORTER_PASSWORD`, `RULES_READER_PASSWORD`. A missing or blank one (empty or whitespace only) raises an error and stops the script before anything is created. psql checks for a blank one on the client, so no password is sent to the server except inside its own `CREATE ROLE`. Its role and schema work runs in one transaction, so a failure there leaves nothing half-made.

### 2.1 Create the secrets

1. Generate three passwords in your password manager: at least 32 characters, **letters and digits only** (no `@ : / ? # % &`), so they can go into a connection URL in section 3 without escaping.
   *Expected result:* three new passwords, seen only in the password manager.
2. Store each one in Coolify as a secret (a locked environment variable that the UI hides), in the dev environment, named exactly:
   - `RULES_MIGRATOR_PASSWORD`
   - `RULES_IMPORTER_PASSWORD`
   - `RULES_READER_PASSWORD`

   The importer (section 4) will receive `RULES_IMPORTER_PASSWORD` from here; nothing else needs a copy.
   *Expected result:* the three secrets exist in Coolify and their values are hidden in the UI.

### 2.2 Prepare a psql session on the internal network

All commands from here on run in a shell **on the Coolify server** (SSH, or Coolify's terminal on the server host). They use a one-off container on `<coolify-network>`, so the connection never leaves the server. Do not use Coolify's public-port feature for this.

Do not run them on a shared server account. While a one-off container runs, anyone with Docker access can see its environment (and so the passwords) with `docker inspect`, and the same user or root can read the exported variables of your shell. Use an admin account only you use, at a time when nobody else is working on the server.

1. Get `db/` from a reviewed commit on `main` (the files hold no secrets):

   ```bash
   git clone https://github.com/piglor/areneon.git areneon-db
   cd areneon-db
   git checkout <main commit SHA you reviewed>
   ls db/bootstrap.sql db/migrations/
   ```

   *Expected result:* `db/bootstrap.sql` and `db/migrations/20261019000000_rules_store.sql` are listed. If the repository cannot be read without credentials, use a read-only deploy key, or copy only the `db/` directory to the server; never paste a token into a command.
2. The commands below need bash. If the terminal is `sh` (Coolify's terminal often is), run `bash` first. Then keep the session out of the shell history:

   ```bash
   unset HISTFILE
   ```

   *Expected result:* no output. The commands below read secrets with `read -rsp`, so the values never appear on screen or in a command line.
3. Read the superuser password (from the database resource's settings in Coolify) without echoing it:

   ```bash
   read -rsp 'PGPASSWORD: ' PGPASSWORD; echo; export PGPASSWORD
   ```

   Paste `<from Coolify: the database resource's superuser password>` and press Enter.
   *Expected result:* only the prompt and a line break are printed, never the value.
4. Define the psql shortcut for this session. `-e PGPASSWORD` passes the variable by name, so the value is not on the `docker` command line:

   ```bash
   PSQL_IMAGE='postgres:18.6@sha256:74935e72241653ca55e0414067e6d8763aceb8a810eb51b452253ec3dcfc4336'
   psql_su() { docker run --rm -i --network <coolify-network> -e PGPASSWORD "$PSQL_IMAGE" \
     psql -h <db-uuid> -p 5432 -U postgres -d areneon -v ON_ERROR_STOP=1 "$@"; }
   psql_su -c 'SELECT version();'
   ```

   *Expected result:* one row starting with `PostgreSQL 18.`. If the connection is refused, check `<db-uuid>`, `<coolify-network>` and that the resource is running. (The image is the one `db/compose.yaml` pins; any psql 18 client works. The server's image flavour on Coolify, for example Alpine, may differ from this Debian-based client image; that is fine.)

### 2.3 Make sure passwords will not be logged

`CREATE ROLE … PASSWORD '…'` would be written to the server log in plain text if statement logging is on, or kept by a preloaded library that records statements. Each password reaches the server only inside its own `CREATE ROLE` (psql checks for missing and blank ones on the client), so a logged statement exposes one password, not all three.

On Coolify the server log is the database container's output: the resource's **Logs** view in Coolify, which is the container's Docker log (`docker logs <db-uuid>`). If a log drain is configured for the server, the log is copied there too.

1. Check the logging settings and the preloaded libraries:

   ```bash
   psql_su -c 'SHOW log_statement;' -c 'SHOW log_min_duration_statement;' -c 'SHOW log_min_error_statement;' \
     -c 'SHOW shared_preload_libraries;' -c 'SHOW session_preload_libraries;' -c '\drds'
   ```

   *Expected result:* `log_statement` is `none`, `log_min_duration_statement` is `-1`, both preload lists are empty or at least name none of `pgaudit`, `auto_explain` or `pg_stat_statements`, and `\drds` prints `Did not find any settings.` **If one of those libraries is loaded, stop here**: remove it in the resource's custom PostgreSQL configuration and restart the resource first, then start 2.3 again.

   The `SHOW` runs as `postgres` on `areneon`, the same user and database as the bootstrap, so it already includes any per-role or per-database override (`ALTER ROLE … SET` / `ALTER DATABASE … SET`); `\drds` shows where such an override comes from.
2. Only if a value in step 1 differs: fix it, reload, and check again. Remove per-role and per-database overrides first, then set the server value:

   ```bash
   psql_su -c 'ALTER ROLE postgres IN DATABASE areneon RESET log_statement;' \
     -c 'ALTER ROLE postgres RESET log_statement;' \
     -c 'ALTER DATABASE areneon RESET log_statement;'
   psql_su -c "ALTER SYSTEM SET log_statement = 'none';" \
     -c 'ALTER SYSTEM SET log_min_duration_statement = -1;' \
     -c 'SELECT pg_reload_conf();'
   psql_su -c 'SHOW log_statement;' -c 'SHOW log_min_duration_statement;' -c '\drds'
   ```

   Use the same three `RESET` lines for `log_min_duration_statement` if `\drds` lists it.
   *Expected result:* the `RESET`s print `ALTER ROLE` / `ALTER DATABASE`, `pg_reload_conf` returns `t`, and the re-check shows `none`, `-1` and `Did not find any settings.` Do not continue until it does.

   `pg_reload_conf()` only signals the server; the reload is asynchronous. If a check shows the old value, wait a second and repeat the check before looking for another source.

   If the re-check still shows the old value, Coolify passes it as a `-c` flag or in a mounted configuration file, which `ALTER SYSTEM` cannot override. Find the source:

   ```bash
   psql_su -c "SELECT name, setting, source, sourcefile FROM pg_settings
     WHERE name IN ('log_statement', 'log_min_duration_statement', 'log_min_error_statement');"
   ```

   Then set the value in the resource's custom PostgreSQL configuration in Coolify, restart the resource, and start 2.3 again.
3. Keep **failing** statements out of the log during the bootstrap. By default (`log_min_error_statement = error`) PostgreSQL logs the text of any statement that fails:

   ```bash
   psql_su -c "ALTER SYSTEM SET log_min_error_statement = 'panic';" -c 'SELECT pg_reload_conf();'
   psql_su -c 'SHOW log_min_error_statement;'
   ```

   *Expected result:* `pg_reload_conf` returns `t` and the check shows `panic` (if it shows `error`, wait a second and repeat the check: the reload is asynchronous). If it still does not, find the source as in step 2. Section 2.4 step 4 resets it. Note what this check showed: section 2.4 needs it if the bootstrap fails.

### 2.4 Run the bootstrap

1. Read the three role passwords from the Coolify secrets, without echoing them:

   ```bash
   read -rsp 'RULES_MIGRATOR_PASSWORD: ' RULES_MIGRATOR_PASSWORD; echo; export RULES_MIGRATOR_PASSWORD
   read -rsp 'RULES_IMPORTER_PASSWORD: ' RULES_IMPORTER_PASSWORD; echo; export RULES_IMPORTER_PASSWORD
   read -rsp 'RULES_READER_PASSWORD: ' RULES_READER_PASSWORD; echo; export RULES_READER_PASSWORD
   ```

   At each prompt paste, in order, `<from Coolify secret RULES_MIGRATOR_PASSWORD>`, `<from Coolify secret RULES_IMPORTER_PASSWORD>`, `<from Coolify secret RULES_READER_PASSWORD>`.
   *Expected result:* only the three prompts are printed, never a value.
2. Run `db/bootstrap.sql` (the same file and flags `make db-up` uses locally), passing the variables by name:

   ```bash
   docker run --rm -i --network <coolify-network> -e PGPASSWORD \
     -e RULES_MIGRATOR_PASSWORD -e RULES_IMPORTER_PASSWORD -e RULES_READER_PASSWORD \
     "$PSQL_IMAGE" psql -h <db-uuid> -p 5432 -U postgres -d areneon -v ON_ERROR_STOP=1 -f - < db/bootstrap.sql
   ```

   *Expected result:* psql prints `BEGIN`, `CREATE ROLE`, `CREATE ROLE`, `GRANT ROLE`, `CREATE ROLE`, `CREATE ROLE`, `CREATE SCHEMA`, `GRANT`, `GRANT`, `REVOKE`, `GRANT`, `COMMIT`, and exits 0. A message such as `RULES_IMPORTER_PASSWORD is not set` or `… is empty` means a variable was missing or blank; nothing was created. `role "rules_owner" already exists` means the bootstrap already ran: do not run it again.

   **If this step failed in any way, or you abandoned it**, handle it now, while the three variables are still exported, before step 3 clears them:

   1. Check whether a password reached the server log. `grep -cF` prints only a count, never the matched line or the password (the shell expands the variable, so the value stays out of your history; it is in `grep`'s arguments for the instant it runs, visible in `ps`, which is one more reason not to use a shared account):

      ```bash
      docker logs <db-uuid> 2>&1 | grep -cF -- "$RULES_MIGRATOR_PASSWORD"
      docker logs <db-uuid> 2>&1 | grep -cF -- "$RULES_IMPORTER_PASSWORD"
      docker logs <db-uuid> 2>&1 | grep -cF -- "$RULES_READER_PASSWORD"
      ```

      *Expected result:* each prints `0`. Optional coarse view: `docker logs <db-uuid> 2>&1 | grep -c -i -E 'password|rules_migrator|importer|areneon_reader'` also counts ordinary lines such as `password authentication failed`, so a count above 0 there is not proof of a leak.
   2. Decide whether to keep the passwords:
      - If the 2.3 step 3 check showed `panic` for this run, or the run stopped at a missing- or blank-variable message, **and** every count in step 1 is `0`, nothing was logged: you may keep the passwords.
      - Otherwise purge the log (step 3 below) and decide which passwords are exposed. If psql printed `BEGIN`, the run got past the checks and may have sent any `CREATE ROLE`: treat **all three** as exposed. If it stopped before `BEGIN`, no password left the client (no statement but its own `CREATE ROLE` carries one): treat as exposed only those whose count in step 1 is above `0`. Generate a new password for each exposed one to replace its Coolify secret (2.1).
   3. Purge the log, only if step 2 says so. First check the container's log driver:

      ```bash
      docker inspect --format '{{.HostConfig.LogConfig.Type}}' <db-uuid>
      ```

      If it prints `json-file`, truncate the current log file and any rotated ones. The glob must be expanded by root, because a normal user cannot list Docker's log directory; hence `sh -c` under `sudo` (`-c` creates no file when there is nothing rotated):

      ```bash
      LOG="$(docker inspect --format '{{.LogPath}}' <db-uuid>)"
      sudo sh -c 'truncate -c -s 0 "$1" "$1".*' _ "$LOG"
      docker logs <db-uuid> 2>&1 | grep -cF -- "$RULES_MIGRATOR_PASSWORD"
      ```

      *Expected result:* the count is `0` (repeat it for the other two variables). Coolify's **Logs** view reads the same Docker log, so nothing more is needed there. For any other driver (`local`, `journald`, …) do not guess: `local` keeps compressed files that must not be edited, and `journald` can only drop whole journal files, which deletes every log on the host. Stop and decide with whoever runs the server. Remove any log drain copy too.
   4. Do steps 3 and 4 below, fix the cause, then run 2.3 step 3 and this section again.
3. Clear the role passwords from the shell:

   ```bash
   unset RULES_MIGRATOR_PASSWORD RULES_IMPORTER_PASSWORD RULES_READER_PASSWORD
   ```

   *Expected result:* no output. Keep `PGPASSWORD` until the end of section 3.
4. Restore the default for failing statements (set in 2.3 step 3). Do this after every run of step 2: after a success, a failure, an abandoned run, and the missing- or blank-variable case alike.

   ```bash
   psql_su -c 'ALTER SYSTEM RESET log_min_error_statement;' -c 'SELECT pg_reload_conf();'
   psql_su -c 'SHOW log_min_error_statement;'
   ```

   *Expected result:* `pg_reload_conf` returns `t` and the check shows `error` (if it still shows `panic`, wait a second and repeat the check: the reload is asynchronous).

### 2.5 Verify the roles

1. List the roles and their attributes:

   ```bash
   psql_su -c "SELECT rolname, rolcanlogin, rolsuper, rolinherit, rolcreaterole, rolcreatedb, rolbypassrls
     FROM pg_roles WHERE rolname IN ('rules_owner', 'rules_migrator', 'importer', 'areneon_reader') ORDER BY rolname;"
   ```

   *Expected result:* four rows. `rules_owner` has `rolcanlogin = f`; `rules_migrator`, `importer` and `areneon_reader` have `rolcanlogin = t`. All four have `rolsuper`, `rolcreaterole`, `rolcreatedb` and `rolbypassrls` = `f`.
2. Check the one membership and the schema owner:

   ```bash
   psql_su -c "SELECT g.rolname AS granted_role, m.rolname AS member, a.inherit_option, a.set_option, a.admin_option
     FROM pg_auth_members a JOIN pg_roles g ON g.oid = a.roleid JOIN pg_roles m ON m.oid = a.member
     WHERE g.rolname IN ('rules_owner', 'rules_migrator', 'importer', 'areneon_reader')
        OR m.rolname IN ('rules_owner', 'rules_migrator', 'importer', 'areneon_reader');" \
     -c '\dn+ rules' -c '\l areneon'
   ```

   *Expected result:* exactly one membership row: `rules_owner | rules_migrator | f | t | f` (no inherit, set allowed, no admin). Schema `rules` is owned by `rules_owner`, with `USAGE` for `importer` and `areneon_reader` and `USAGE, CREATE` for `rules_migrator`. The database's access privileges list `CONNECT` for `rules_migrator`, `importer` and `areneon_reader` and no `=Tc/` (PUBLIC) entry.

## 3. Run the migrations with dbmate

The migrations in `db/migrations/` run as `rules_migrator`, with the same pinned dbmate image and flags as `make db-up` (see the `DBMATE` variable in the `Makefile`):

```
ghcr.io/amacneil/dbmate:2.36.0@sha256:520c740c6e0ad73fde2cd1ea7e2b779aaf789d22aca8858f87a478e7094535fb
--no-dump-schema --migrations-dir /db/migrations
```

Each migration switches to `rules_owner` with `SET LOCAL ROLE`, so every table belongs to the owner, and dbmate keeps its version table `rules.schema_migrations` because the URL sets `search_path=rules`.

**`sslmode`:** the connection stays on `<coolify-network>`, a Docker network on this one server, so the examples use `sslmode=disable`, as the local setup does. If you enabled SSL on the Coolify resource, use `sslmode=require` instead.

1. Build the dbmate URL from the migrator secret, without echoing it. dbmate reads it from `DATABASE_URL`, which `docker run -e DATABASE_URL` passes by name:

   ```bash
   read -rsp 'RULES_MIGRATOR_PASSWORD: ' RULES_MIGRATOR_PASSWORD; echo
   export DATABASE_URL="postgres://rules_migrator:${RULES_MIGRATOR_PASSWORD}@<db-uuid>:5432/areneon?sslmode=disable&search_path=rules"
   unset RULES_MIGRATOR_PASSWORD
   DBMATE_IMAGE='ghcr.io/amacneil/dbmate:2.36.0@sha256:520c740c6e0ad73fde2cd1ea7e2b779aaf789d22aca8858f87a478e7094535fb'
   dbmate() { docker run --rm --network <coolify-network> -v "$PWD/db:/db:ro" -e DATABASE_URL "$DBMATE_IMAGE" \
     --no-dump-schema --migrations-dir /db/migrations "$@"; }
   ```

   Paste `<from Coolify secret RULES_MIGRATOR_PASSWORD>` at the prompt.
   *Expected result:* only the prompt is printed, never the value. Run these from the `areneon-db` checkout, so `$PWD/db` is the repository's `db/`.
2. Show what will run:

   ```bash
   dbmate status
   ```

   *Expected result:* `[ ] 20261019000000_rules_store.sql` and `Pending: 1`.
3. Apply the migrations:

   ```bash
   dbmate migrate
   ```

   *Expected result:* `Applying: 20261019000000_rules_store.sql`, then `Applied: …` and exit 0. Running it again applies nothing.
4. Confirm:

   ```bash
   dbmate status
   ```

   *Expected result:* `[X] 20261019000000_rules_store.sql`, `Applied: 1`, `Pending: 0`.
5. Clear the URL:

   ```bash
   unset DATABASE_URL
   ```

   *Expected result:* no output.

### 3.1 Verify the schema

1. Tables and their owners:

   ```bash
   psql_su -c '\dt rules.*'
   ```

   *Expected result:* `rules_release` and `rules_snapshot` owned by `rules_owner`, and dbmate's `schema_migrations` owned by `rules_migrator`.
2. Triggers:

   ```bash
   psql_su -c "SELECT tgrelid::regclass AS table_name, tgname FROM pg_trigger
     WHERE NOT tgisinternal AND tgrelid::regclass::text LIKE 'rules.%' ORDER BY 1, 2;"
   ```

   *Expected result:* four rows, in any order: `rules_release_append_only`, `rules_release_no_truncate` on `rules.rules_release`; `rules_snapshot_append_only`, `rules_snapshot_no_truncate` on `rules.rules_snapshot`.
3. Constraints:

   ```bash
   psql_su -c "SELECT conrelid::regclass AS table_name, conname, contype FROM pg_constraint
     WHERE connamespace = 'rules'::regnamespace AND contype <> 'n' ORDER BY 1, 2;"
   ```

   *Expected result:* on `rules.rules_release`: `release_channel_in_enum`, `release_seq_positive`, `release_snapshot_exists` (`f`), `release_seq_unique_per_channel` and `release_source_commit_unique_per_channel` (`u`), `release_source_commit_is_sha1`, and the primary key `rules_release_pkey` (`p`). On `rules.rules_snapshot`: `snapshot_hash_is_sha256_of_body`, `snapshot_payload_is_body`, `snapshot_schema_version_from_payload`, `snapshot_showdown_commit_from_payload`, `snapshot_source_commit_is_sha1` and `rules_snapshot_pkey` (`p`). dbmate's `schema_migrations_pkey` may also appear.
4. Table privileges, without writing a row:

   ```bash
   psql_su -c "SELECT r AS role, t AS table_name,
       has_table_privilege(r, t, 'SELECT') AS sel, has_table_privilege(r, t, 'INSERT') AS ins,
       has_table_privilege(r, t, 'UPDATE') AS upd, has_table_privilege(r, t, 'DELETE') AS del,
       has_table_privilege(r, t, 'TRUNCATE') AS trunc
     FROM unnest(ARRAY['importer', 'areneon_reader']::name[]) AS r,
          unnest(ARRAY['rules.rules_snapshot', 'rules.rules_release']) AS t ORDER BY 1, 2;"
   ```

   *Expected result:* `importer` has `sel = t`, `ins = t` and `upd`, `del`, `trunc` = `f` on both tables; `areneon_reader` has only `sel = t`.
5. Prove that `importer` cannot update or delete. Each statement runs in a transaction that is rolled back and matches no row, so nothing changes:

   ```bash
   psql_su -c 'BEGIN; SET LOCAL ROLE importer; UPDATE rules.rules_release SET seq = seq WHERE false; ROLLBACK;'
   psql_su -c 'BEGIN; SET LOCAL ROLE importer; DELETE FROM rules.rules_snapshot WHERE false; ROLLBACK;'
   ```

   *Expected result:* each fails with `ERROR:  permission denied for table rules_release` / `… rules_snapshot`. Do **not** test INSERT with a real row: the store is append-only, so a test row could never be removed. The privilege check in step 4 covers INSERT, and the importer's first real run (section 4) exercises it.
6. End the session:

   ```bash
   unset PGPASSWORD
   cd .. && rm -rf areneon-db
   ```

   *Expected result:* no output. No password remains in the shell, and none was ever on a command line or in the history.

### 3.2 The GitHub environment `rules-dev`

The repository already has the GitHub environment **`rules-dev`**, used by `.github/workflows/rules-publish.yml`: it publishes each merged rules change as a Release with a build-provenance attestation. The environment has a required reviewer (the owner) and its deployment branches are limited to `main`, so a publish runs only from `main` and only after the owner approves it (verified via the GitHub API on 2026-10-19: required reviewer `arceushui`, deployment branch policy `main`). It holds no database credentials: GitHub never connects to this database. The importer that pulls those Releases into the store is section 4.

1. Check it in GitHub under the repository's **Settings → Environments → rules-dev**.
   *Expected result:* **Required reviewers** lists the owner, **Deployment branches and tags** allows only `main`, and there are no environment secrets for this database.
